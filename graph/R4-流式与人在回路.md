## 5.1 流式：离散超步让它变简单

### 是什么？

**流式（Streaming）** 是指在Agent执行过程中，**实时地**把中间进展吐出来，而不是等到最后才返回结果。

在我们的引擎里，流式有两种模式：

| 模式 | 关心什么 | 典型用途 | 产出内容 |
|------|---------|---------|---------|
| **`updates`** | 这一步发生了什么变化 | 显示进度日志 | `{"__step__": 1, "nodes": ["agent"], "state": {...}}` |
| **`values`** | 现在的完整状态是什么 | 实时刷新UI | `{"messages": [...], "count": 2}` |

**使用示例：**

```python
# stream_mode="updates"：每个超步吐出"跑了哪些节点 + 当时状态"
for event in app.stream(input, stream_mode="updates"):
    print(f"超步{event['__step__']}: 跑了 {event['nodes']}, count={event['state']['count']}")

# stream_mode="values"：每个超步吐出完整状态快照
for state_snapshot in app.stream(input, stream_mode="values"):
    print(f"当前状态: {state_snapshot}")
```

### 为什么？

**问题：第1章的循环为什么做不到流式？**

```python
# 第1章的循环
def run_agent(user_input):
    state = {"messages": [user_input]}
    while should_continue(state):
        state = call_model(state)      # 这里在干什么？外部看不到
        state = call_tools(state)      # 这里在干什么？外部也看不到
    return state  # 只有一个 return，中间过程完全黑盒
```

外部调用者只能：
```python
result = run_agent("天气如何?")  # 等待...等待...等待... 才得到结果
# 中间发生了什么？调了几次工具？模型思考了什么？完全不知道
```

**图运行时从根上改变了这点**：执行被切成了**离散的超步**，每个超步之后都有一个 `yield`（R2章那道缝隙）。

```python
# R2章的引擎主循环
while active:
    # 执行一个超步
    writes = self._run_superstep(tasks, channels)
    self._commit(channels, writes)
    
    yield state_snapshot  # ← 这道缝隙！每个超步后都吐一次
    
    active = self._next_active(...)
```

有了离散步骤，流式就是一件很直接的事：**在每个 `yield` 处把当前进展吐出去**。

### 怎么用？

#### 1. `updates` 模式：看变化

#### 1. `updates` 模式：看变化

适合显示进度日志，让用户知道"Agent正在做什么"。

**运行示例：**

```python
# 一个简单的计数图：每步 count+1，走3步
for event in app.stream({"count": 0}, stream_mode="updates"):
    print(f"超步{event['__step__']}: nodes={event['nodes']}, count={event['state']['count']}")

# 输出:
# 超步1: nodes=['step'], count=1
# 超步2: nodes=['step'], count=2
# 超步3: nodes=['step'], count=3
```

**event 的结构：**

```python
{
    "__step__": 1,              # 超步编号（从1开始）
    "nodes": ["step"],          # 这个超步跑了哪些节点
    "state": {"count": 1}       # 执行后的状态快照
}
```

**典型应用场景：**

```python
# UI 上显示进度
for event in app.stream(input, stream_mode="updates"):
    if "agent" in event["nodes"]:
        show_spinner("AI 正在思考...")
    elif "tools" in event["nodes"]:
        show_spinner("正在调用工具...")
```

#### 2. `values` 模式：看完整状态

适合实时刷新整个UI，比如聊天界面需要显示完整的消息列表。

**运行示例：**

```python
# 同一个计数图
for state in app.stream({"count": 0}, stream_mode="values"):
    print(f"count={state['count']}, log={state['log']}")

# 输出:
# count=1, log=['step->1']
# count=2, log=['step->1', 'step->2']
# count=3, log=['step->1', 'step->2', 'step->3']
```

注意每次都是**完整状态**，不是增量。这样UI可以直接用最新的state替换整个显示，无需自己维护状态。

**典型应用场景：**

```python
# 聊天UI：每次更新都重新渲染整个消息列表
for state in app.stream(input, stream_mode="values"):
    render_messages(state["messages"])  # 直接渲染完整列表
```

#### 对比总结

| 特性 | `updates` | `values` |
|------|-----------|----------|
| 关心 | 这一步的变化 | 当前的完整状态 |
| 产出 | `{__step__, nodes, state}` | 状态快照 `dict` |
| 适合 | 进度日志、加载提示 | 实时刷新UI |
| 信息量 | 知道"做了什么" | 知道"现在是什么" |

### 为什么两种模式都能存在？

根本原因是同一个：**执行是离散步骤，每步之间都是天然的汇报点**。

```python
# pregel.py 主循环
while active:
    # ... 执行超步 ...
    
    # ← 这里是缝隙：超步刚结束，下一步还没开始
    #   状态是稳定的、确定的
    #   此时吐出数据，外部能看到完整的中间状态
    if stream_mode == "updates":
        yield {"__step__": steps, "nodes": active_nodes, "state": snapshot}
    elif stream_mode == "values":
        yield snapshot
    
    # 继续下一个超步
```

这道缝隙是**统一的插入点**：
- 流式输出在这里吐数据
- 检查点在这里存档（R3章）
- 中断在这里停下（5.2节）

### 对照真实框架

真实 LangGraph 提供 **6 种** streaming 模式：

| 模式 | 产出内容 | 粒度 |
|------|---------|------|
| `values` | 完整状态快照 | 超步级 |
| `updates` | 节点产出的增量 | 超步级 |
| `messages` | 逐 token 文本 | token 级（超步内） |
| `tasks` | 待执行的任务列表 | 超步级 |
| `checkpoints` | 检查点元数据 | 超步级 |
| `custom` | 节点内主动发的事件 | 任意 |

我们实现了最核心的 `values` 和 `updates`。它们之所以都能存在，根本原因是同一个：**执行是离散步骤**。

### 逐 token 输出：粒度差了一层

`messages` 模式要逐 token 吐字（"你|好|，|今|天|天|气|..."），这里有个**层次错位**值得先讲清，否则容易和 `values`/`updates` 搞混：

> **`values`/`updates` 流的是"超步级"事件** —— 一个节点跑完了。  
> **`messages` 流的是"超步内部、节点还没跑完时"的 token**。  
> 粒度差了一层：前者在 `yield` 那道缝隙里产出，后者必须在节点**执行过程中**就往外漏。

**为什么逐 token 不能靠主循环的 `yield` 实现？**

```python
# 主循环的 yield 是在节点跑完后
while active:
    result = call_model(state)  # ← 模型在这里跑，内部生成了很多 token
                                #   但这个函数要等模型全部返回才结束
    self._commit(channels, result)
    yield state  # ← 这时才 yield，token 早就生成完了
```

所以逐 token 不能靠主循环，得在节点**内部**开一条旁路把 token 推出去。

**最小实现思路（机制示意）：**

```python
# ① 模型层支持流式调用
class BaseChatModel:
    def stream(self, messages):
        """逐块 yield token，而非一次性 return"""
        raise NotImplementedError

# 真实 provider:
# - Anthropic: client.messages.stream(...)
# - OpenAI: create(..., stream=True)
# 它们边收边 yield 文本增量（delta）

# ② 进程内的 stream writer（和R3章 _RESUME_BOX 同样的思路）
_STREAM_WRITER = {"fn": None}

def get_stream_writer():
    """节点内调用，拿到一个函数，可以往外推事件"""
    return _STREAM_WRITER["fn"] or (lambda _chunk: None)  # 没人接就丢弃

# ③ call_model 节点边收 token 边推，最后仍返回完整 AIMessage
def call_model(state):
    writer = get_stream_writer()  # 拿到推送函数
    text = ""
    
    # 逐块接收 token
    for delta in model.stream(state["messages"]):
        text += delta
        writer({"type": "token", "delta": delta})  # ← token 实时漏出去（旁路）
    
    # 节点契约不变：仍然返回完整的 AIMessage
    return {"messages": [AIMessage(content=text)]}
```

**关键的"两不影响"：**

1. **逐 token 漏出去的是旁路事件**（给UI看的，用户体验好）
2. **节点最终返回的仍是完整 AIMessage**（给状态和检查点用的，保证正确性）

所以 token 流和我们前四章建立的那套机制——"节点只返回增量、引擎确定性合并、检查点存完整状态"——是**正交**的：

- **token** 是"执行途中的观察"，不是"状态的一部分"
- 检查点里不存 token 流，只存完整的 AIMessage
- token 流中断了（比如网络抖动），不影响检查点的完整性

这也是为什么真实 LangGraph 能把多种流式模式**叠加**着用：
```python
for chunk in app.stream(input, stream_mode=["messages", "updates", "values"]):
    # messages: 看 token（用户体验）
    # updates: 看节点产出（进度跟踪）
    # values: 看完整快照（状态同步）
    # 它们处在不同层次，互不干扰
```

剩下的纯是工程量（每个 provider 的流式 API 格式不同，要各写一份增量解析），核心机制我们已经具备。

## 5.2 中断不是"挂起进程"，而是"存档 + 退出 + 重跑"

### 是什么？

**中断（Interrupt）** 是Agent在执行过程中**主动暂停**，等待外部输入（比如人工审批），然后**从暂停处恢复继续**的能力。

典型场景：
```python
def execute_action(state):
    action = state["planned_action"]
    
    # 如果是危险操作，等人批准
    if is_dangerous(action):
        approval = interrupt(f"是否批准: {action}?")  # ← 在这里暂停
        if approval != "approve":
            return {"status": "cancelled"}
    
    # 批准后才执行
    result = do_action(action)
    return {"result": result}
```

**关键特性：**
- 第一次执行到 `interrupt()` → 暂停，进程退出
- 几天后，人点了批准 → 恢复执行，`interrupt()` 返回 `"approve"`
- Agent 带着这个值继续往下走

### 为什么？

**问题：如果用"挂起进程"的方式等待，会怎样？**

最直观的想法是让进程等待：

```python
def execute_action(state):
    action = state["planned_action"]
    
    if is_dangerous(action):
        # 阻塞等待用户输入
        approval = input("是否批准？(yes/no): ")  # ← 进程卡在这里
        if approval != "yes":
            return {"status": "cancelled"}
    
    result = do_action(action)
    return {"result": result}
```

**灾难性的后果：**

```
时间线    进程状态                                成本
────────────────────────────────────────────────────────
09:00   Agent 跑到 execute，卡在 input()         内存: 200MB
09:01   等待...                                  连接: 3个数据库连接
09:02   等待...                                  线程: 1个
...     ...                                      ...
12:00   等待...（3小时了）                       成本累积中
...     ...                                      ...
第2天   等待...（24小时了）                      成本继续累积
...     ...                                      ...
第7天   服务器重启 → 进程消失 → 前功尽弃         💥 全丢了！
```

问题：
1. **资源占用**：进程、内存、数据库连接，几天都不释放
2. **不可扩展**：1000个等待审批的任务 = 1000个进程挂着
3. **不可靠**：服务器重启 → 所有等待中的任务全部丢失
4. **不灵活**：审批人可能在另一个时区、另一台设备，进程不能跨机器

### LangGraph 的反直觉思路

> **中断 = "在这个点提前存个检查点，然后让进程正常退出"**  
> **恢复 = "从检查点重建状态，重新跑被中断的那个节点——但这次 `interrupt()` 不再暂停，而是返回外部注入的值"**

换句话说，"暂停几天"期间**根本没有进程在等**：
- 状态躺在数据库里（检查点）
- 进程早就退出了，零资源占用
- 几天后人点了批准，我们才重新拉起执行、从检查点恢复

**对比两种思路：**

```
【挂起进程等审批】
  进程 ████████████████████████████████████████████  ← 整整几天都在跑
       plan  execute: input() 阻塞…………………………………人点批准  继续
       ▲
       └─ 占着内存、连接、线程，几天不放
          服务器一重启 → 全部蒸发，从头再来

【interrupt: 存档 + 退出 + 重跑】
  进程① ███╳                                          ← 跑到 execute 存档就退出
       plan  存检查点(next=[execute])  进程结束
            └─ 状态躺在数据库里 ─┐
                                ╎  ← 这几天【没有任何进程】，零成本
       (几天后，人点了批准)      ╎
  进程② ████                    ┘  ← 另起进程，从检查点恢复，只重跑 execute
       从 cp 重建状态 → interrupt() 这次返回 "approve" → 真正执行删库
       ▲
       └─ 可以是另一台机器、另一个时区、隔了几个月
```

上面那条"整根填满"的进程线是成本（几天的资源占用，加上重启即丢）；下面 interrupt 的方案里，等待期那段是**空的**——没有进程、没有占用，状态只是数据库里一条记录。

**这就是为什么官方敢说能等 "several days (or months!)"** —— 因为等待是零成本的，等于没等。

### 和"崩溃恢复"的区别

| 特性 | 崩溃恢复（R3章） | 中断恢复（本章） |
|------|-----------------|----------------|
| **触发方式** | 被动（进程意外死了） | 主动（节点里调 `interrupt()`） |
| **存档时机** | 每个超步后自动存 | 中断时提前存 |
| **next_nodes** | 指向下一个要跑的节点 | 指向被中断的节点本身 |
| **恢复时** | 直接从 next_nodes 继续 | 重跑被中断的节点，但 `interrupt()` 返回值 |
| **典型场景** | 服务器崩溃、网络断线 | 人工审批、外部输入 |

**共同点：两者复用同一套机制**
- 都是"从检查点重建 + 从 `next_nodes` 续跑"
- 都依赖R3章的检查点系统
- 都能跨进程、跨机器、跨时间

中断只多做了一件事：在喊停的地方提前存档，并在恢复时给被中断的节点喂一个 resume 值。

## 5.3 实现 interrupt()：三个零件

### 是什么？

整个中断机制只需要：
1. 一个不到 50 行的新文件 `tinygraph/interrupt.py`
2. 在引擎主循环里加一段 `try/except`
3. 在引擎入口加一段 `if isinstance(input, Command)`

### 为什么这么简单？

因为中断**复用了R3章的检查点系统**：
- 暂停 = 提前存个检查点 + 退出
- 恢复 = R3章的 `input=None` 恢复路径

我们只需要解决一个新问题：**如何让 `interrupt()` 在首次抛异常、恢复时返回值？**

答案是：用一个"传递通道"（`_RESUME_BOX`）在引擎和节点之间传递 resume 值。

### 怎么用？

#### 零件一：`interrupt()` 函数与 `GraphInterrupt` 异常

这是 `tinygraph/interrupt.py` 的完整代码（可以直接抄）：

```python
# tinygraph/interrupt.py —— 完整文件
from typing import Any, Dict, Optional


class GraphInterrupt(Exception):
    """节点内调用 interrupt() 时抛出，被引擎捕获 → 存档并停下
    
    参数:
        value: 抛给外部的内容（如待审批的操作描述）
    """
    def __init__(self, value: Any) -> None:
        super().__init__("graph interrupted")
        self.value = value  # 比如 "是否批准删除生产库?"


# ========== resume 值的传递通道 ==========
# 调用方用 Command(resume=...) 注入，引擎放进这里，
# 节点重跑时 interrupt() 从这里取。
# 教学用最简方案：一个模块级字典（真实框架用更稳健的方式）
_RESUME_BOX: Dict[str, Any] = {}


def set_resume(value: Any) -> None:
    """引擎调用：把外部注入的 resume 值放进通道
    
    参数:
        value: 恢复值（比如 "approve" / "reject"）
    """
    _RESUME_BOX["value"] = value
    _RESUME_BOX["consumed"] = False  # 标记为"未消费"


def interrupt(value: Any) -> Any:
    """节点内调用：主动暂停或获取恢复值
    
    双重身份:
        首次执行: 抛 GraphInterrupt(value)，触发暂停
        恢复执行: 返回 _RESUME_BOX 里的 resume 值
    
    参数:
        value: 抛给外部的内容（待审批的操作描述）
    
    返回:
        恢复时: 外部注入的值（比如 "approve"）
        首次: 不返回，直接抛异常
    
    示例:
        # 节点代码
        def execute(state):
            action = state["action"]
            
            # 第一次执行: 抛异常，暂停
            # 恢复执行: 返回 "approve" 或 "reject"
            approval = interrupt(f"是否批准: {action}?")
            
            if approval == "approve":
                return {"result": do_action(action)}
            else:
                return {"status": "cancelled"}
    """
    # 检查 _RESUME_BOX 里有没有外部注入的 resume 值
    if _RESUME_BOX.get("value") is not None and not _RESUME_BOX.get("consumed", True):
        # 有值 且 未消费 → 返回它（恢复路径）
        _RESUME_BOX["consumed"] = True  # 标记为"已消费"，防止重复取
        return _RESUME_BOX["value"]
    
    # 否则 → 抛异常，触发暂停（首次执行路径）
    raise GraphInterrupt(value)


class Command:
    """恢复指令
    
    Command(resume=x) 表示 "带着值 x 从中断处继续"
    
    参数:
        resume: 要注入给 interrupt() 的值
    
    示例:
        # 用户批准后，恢复执行
        app.invoke(Command(resume="approve"), config)
    """
    def __init__(self, resume: Optional[Any] = None) -> None:
        self.resume = resume
```

**关键理解：`interrupt()` 的双重身份**

同一行代码 `approval = interrupt("是否批准?")`，在不同时刻有不同行为：

| 时刻 | `_RESUME_BOX` 状态 | `interrupt()` 行为 | 效果 |
|------|-------------------|-------------------|------|
| 首次执行 | 空（无 resume 值） | 抛 `GraphInterrupt` 异常 | 节点中止，引擎存档退出 |
| 恢复执行 | 有值（比如 `"approve"`） | 返回该值 | 节点带着这个值继续往下 |

**为什么需要 `consumed` 标志？**

防止一个 resume 值被多次取走：

```python
def node(state):
    # 如果这个节点里有多个 interrupt()
    x = interrupt("问题1")  # ← 第一个取走 resume 值
    y = interrupt("问题2")  # ← 第二个不应该再取到同一个值，应该抛异常
```

`consumed` 确保一个 resume 值只被第一个 `interrupt()` 消费一次。

#### 零件二：引擎捕获中断 → 存档 → 停下

`interrupt.py` 三个零件齐了，但它们要靠引擎接住才有用。在 `pregel.py` 的主循环里，执行节点那一步要包一层 `try/except GraphInterrupt`：

```python
# tinygraph/pregel.py 主循环（在执行节点那一步）

while active:
    steps += 1
    
    # 准备任务
    tasks = []
    for node_name in active:
        node = self.nodes[node_name]
        task = node(self._state_snapshot(channels))
        tasks.append((node_name, task))
    
    # ========== 关键：用 try/except 包住执行步骤 ==========
    try:
        # 收集写入
        writes = {}
        for node_name, result in tasks:
            self._collect_writes(result, writes, node_name)
        
        # 提交到 channel
        self._commit(channels, writes)
        
    except GraphInterrupt as gi:
        # ========== 节点喊停了！==========
        # 1. 存检查点，且 next_nodes 仍指向【被中断的节点】
        if self.checkpointer is not None:
            # 注意: active 现在指向被中断的节点（比如 ["execute"]）
            # 恢复时会重跑这个节点
            cp = self._make_checkpoint(
                thread_id=thread_id,
                channels=channels,      # 当前状态（中断前的）
                active=active,          # 被中断的节点（恢复时要重跑）
                parent_id=parent_id,
                steps=steps
            )
            self.checkpointer.put(cp)
        
        # 2. 把待审批内容透传给调用方
        yield {"__interrupt__": gi.value}
        
        # 3. 引擎停下，函数返回（进程可退出）
        return
    
    # 如果没有异常，继续正常流程
    state_now = self._state_snapshot(channels)
    yield state_now  # 流式输出
    
    # 存检查点（正常超步）
    if self.checkpointer is not None:
        active = self._next_active(tasks, state_now)
        cp = self._make_checkpoint(thread_id, channels, active, parent_id, steps)
        self.checkpointer.put(cp)
        parent_id = cp.checkpoint_id
    
    # 计算下一批节点
    active = self._next_active(tasks, state_now)
```

**关键点1：`next_nodes` 指向被中断的节点本身**

```python
# 中断时的存档
cp = self._make_checkpoint(..., active=active, ...)
# 此时 active = ["execute"]（被中断的节点）

# 存进检查点：
cp.next_nodes = ["execute"]  # ← 恢复时要重跑 execute
```

对比正常的检查点：
```python
# 正常超步结束后的存档
active = self._next_active(...)  # 计算"下一批"节点
cp = self._make_checkpoint(..., active=active, ...)
# active = ["tools"]（下一个要跑的）

cp.next_nodes = ["tools"]  # ← 恢复时跑 tools（不是重跑当前节点）
```

这个区别很重要：
- **正常检查点**：`next_nodes` 指向"下一个"节点（因为当前节点已经跑完了）
- **中断检查点**：`next_nodes` 指向"当前"节点（因为它被中断了，还没跑完）

**关键点2：`yield {"__interrupt__": gi.value}` 把待审批内容交给外部**

```python
# 外部调用
for event in app.stream(input, config):
    if "__interrupt__" in event:
        # 遇到中断！
        print(f"等待审批: {event['__interrupt__']}")
        # 可以把这个信息展示给用户，等他点按钮
```

**关键点3：`return` 让引擎停下，进程可以退出**

```python
yield {"__interrupt__": gi.value}
return  # ← 函数返回，循环结束
# 进程可以正常退出，不占资源
```

#### 零件三：`Command(resume=x)` 注入恢复值

`Command` 类已经在 `interrupt.py` 里定义了（就是个装着 `resume` 值的小盒子）。它怎么被引擎用上？

在 `pregel.py` 的 `stream()` 一进来就判断：

```python
# tinygraph/pregel.py stream() 开头
def stream(self, input, config=None, stream_mode="updates"):
    thread_id = self._thread_id(config)
    
    # ========== 处理 Command 输入 ==========
    if isinstance(input, Command):
        # 1. 把 resume 值放进 _RESUME_BOX
        from tinygraph.interrupt import set_resume
        set_resume(input.resume)
        
        # 2. 然后按 "从检查点恢复" 处理（input=None）
        input = None
    
    # 后面就是R3章的恢复逻辑：
    # if input is None and self.checkpointer is not None:
    #     resume_cp = self.checkpointer.get(thread_id)
    #     channels = self._channels_from_checkpoint(resume_cp)
    #     active = list(resume_cp.next_nodes)  # ← 重跑被中断的节点
    #     ...
```

**完整的恢复流程：**

```
1. 用户调用: app.invoke(Command(resume="approve"), config)
   ↓
2. 引擎识别出 Command，执行:
   set_resume("approve")  # ← "approve" 放进 _RESUME_BOX
   input = None
   ↓
3. 走R3章的恢复路径:
   resume_cp = checkpointer.get(thread_id)
   # resume_cp.next_nodes = ["execute"]
   channels = _channels_from_checkpoint(resume_cp)
   active = ["execute"]
   ↓
4. 重跑 execute 节点:
   def execute(state):
       approval = interrupt("是否批准?")  # ← 这次不抛异常
       # interrupt() 发现 _RESUME_BOX["value"] = "approve"
       # 返回 "approve"
       ↓
       if approval == "approve":  # ← True
           return do_action()
```

**为什么要把 `input` 改成 `None`？**

因为我们想复用R3章的恢复逻辑：
- `input=None` → 引擎走"从检查点恢复"分支
- `input=Command(...)` → 先注入 resume 值，然后变成 `input=None`

这样 `Command` 就无缝接入了现有的恢复系统，不需要写新的分支。

### 整个机制有多省？

- `interrupt.py`：不到 50 行
- 引擎改动：
  - 主循环加一段 `except GraphInterrupt`：约 10 行
  - 入口加一段 `if isinstance(input, Command)`：约 5 行

剩下的**全是复用**R3章已有的检查点存取和恢复路径。

这正是 5.5 节要讲的"缝隙是统一插入点"：
- 流式输出在缝隙里吐数据
- 检查点在缝隙里存档
- 中断在缝隙里停下

都是同一个地方，同一套机制。

### 对照真实框架

真实 LangGraph 的 API 和我们完全一样：
- `interrupt(value)` —— 节点内调用，暂停或返回值
- `Command(resume=x)` —— 恢复时传入
- `GraphInterrupt` —— 异常类型

区别在于：
- **真实框架**：resume 值存在检查点的 `pending_writes` 里（更稳健，支持持久化）
- **我们的实现**：用模块级的 `_RESUME_BOX`（教学用最简方案）

真实框架还支持：
- 一个节点多次 `interrupt()`
- 异步版本 `ainterrupt()`
- 更丰富的 Command 语法（比如 `Command(goto="other_node")`）

但核心机制完全一样："存档 + 退出 + 重跑 + 返回值"。

## 5.4 跑起来:一个完整的审批流

示例 B 是一个"Agent 想删生产库,必须人工批准"的完整流程:

```python
def plan(state):
    return {"action": "DELETE prod database"}      # Agent 决定危险操作

def execute(state):
    decision = interrupt({"approve_action": state["action"]})   # 执行前喊停
    if decision == "approve":
        return {"result": f"已执行: {state['action']}"}
    return {"result": f"已拒绝: {state['action']}"}

app = g.compile(checkpointer=InMemorySaver())      # 中断必须配 checkpointer
config = {"configurable": {"thread_id": "approval-1"}}
```

第一次运行,跑到 `execute` 就暂停:

```python
for ev in app.stream({"action": "", "result": ""}, config):
    if "__interrupt__" in ev:
        print("暂停,等待审批:", ev["__interrupt__"])
# 暂停,等待审批:{'approve_action': 'DELETE prod database'}
```

此刻检查点里 `next_nodes=['execute']`——execute **还没执行**,删库操作没发生。进程现在可以安全退出。几天后人点了批准:

```python
final = app.invoke(Command(resume="approve"), config)
# 恢复执行,结果:已执行: DELETE prod database
```

完整输出:

```
启动 Agent...
  图已暂停,等待人工审批:{'approve_action': 'DELETE prod database'}
  检查点显示 next_nodes=['execute'](execute 还没执行)
人工决定:approve
  恢复执行,结果:已执行: DELETE prod database
```

回味这个流程的安全性:危险操作 `DELETE prod database` 在人点"批准"之前,**一行都没执行**。它被卡在 `interrupt()` 这道闸门后面,状态安全地躺在检查点里。这正是第 1 章那条边界——"模型只发出请求,框架决定执不执行"——的具体兑现:我们在边界上插了一道人工闸门。如果人点"拒绝"(`Command(resume="reject")`),execute 会走另一个分支,删库永不发生。

### 跟着引擎走完整个中断-恢复循环

把上面这段流程在引擎内部摊开,你会看到"中断"真的只是"存档 + 退出"加"恢复 + 注值"的组合。图是 `START → plan → execute → END`,`_RESUME_BOX` 初始为空。

**第一次 `app.stream({...}, config)`(首次执行,会被中断):**

```
超步1: active=["plan"]
        plan 跑完 → writes={action:"DELETE prod database"} → commit
        _next_active → ["execute"]
        存检查点 cp1:{values:{action:...}, next_nodes:["execute"]}
超步2: active=["execute"]
        _run_superstep 调用 execute(state)
          → execute 内部调 interrupt({approve_action: "DELETE..."})
          → _RESUME_BOX 为空 → interrupt 抛 GraphInterrupt(value=...)
        引擎 except GraphInterrupt 捕获:
          → 存检查点 cp2:{values 不变, next_nodes=["execute"]}  ← 注意仍指向 execute
          → yield {"__interrupt__": {approve_action:...}}
          → return  ← 引擎停下,stream() 生成器结束,进程可安全退出
```

此刻磁盘或内存里 cp2 的 `next_nodes=["execute"]`,而 `execute` 的写入(result)**从未提交**——删库没发生。进程退出,等几天,零成本。

**之后 `app.invoke(Command(resume="approve"), config)`(恢复):**

```
0. input 是 Command → set_resume("approve")
     → _RESUME_BOX = {value:"approve", consumed:False}
   → input 改成 None,走 "从检查点恢复" 分支
1. checkpointer.get(thread) → cp2
2. _channels_from_checkpoint(cp2) → 状态回到 "plan 跑完、execute 没跑" 那一刻
3. active = cp2.next_nodes = ["execute"]   ← 只重跑 execute,plan 不再跑
   steps  = cp2.step
4. while active: 超步 → 调用 execute(state)
     → execute 内部再次调 interrupt({approve_action:...})
     → 这次 _RESUME_BOX 有值且 consumed=False
       → 标记 consumed=True,返回 "approve"  ← 不抛异常
     → decision=="approve" → return {result:"已执行: DELETE..."}
   commit → _next_active → END → active=[] → 退出
5. 返回最终状态 {result:"已执行: DELETE prod database"}
```

三个细节值得停下来看:

- **`plan` 没有重跑。** 恢复是从 `cp2.next_nodes=["execute"]` 起步的,`plan` 属于更早的超步、其写入已在 cp2 里,所以恢复只重跑 `execute` 这一个节点。这正是 `next_nodes` 记录"执行进度"的价值——精确到"下一个超步跑谁"。
- **同一行 `interrupt()`,两次行为相反。** 首次 `_RESUME_BOX` 空,抛异常;恢复时有值,返回值。节点代码一个字没改,"暂停点"自动变成了"继续点"。这就是 5.3 节说的双重身份。
- **`consumed` 标志防止重复消费。** 如果一次恢复里 `execute` 因某种原因被多次进入,`consumed=True` 保证 resume 值只被第一个 `interrupt()` 取走,不会让后续 `interrupt()` 误拿到旧值。

这里有一个会咬人的正确性约束:恢复时 `execute` 是**从头重跑**的。如果你在 `interrupt()` **之前**写了有副作用的代码(比如先记一条日志、先扣一次款,再 `interrupt()` 等审批),那段副作用会执行**两次**(首次执行一次、恢复重跑一次)。

这不是吓唬人,跑一下就看得见。把副作用(扣款)故意放在 `interrupt()` 之前,用一个进程内计数器记录它被调了几次:

```python
charge_calls = {"n": 0}        # 模拟扣款的副作用计数器

def plan(state):
    return {"action": "买一杯咖啡"}

def execute(state):
    charge_calls["n"] += 1                       # ← 副作用:放在 interrupt 之前(错误示范)
    print(f"  [副作用] charge_money() 第 {charge_calls['n']} 次执行")
    decision = interrupt({"approve": state["action"]})
    if decision == "approve":
        return {"result": f"已下单: {state['action']}"}
    return {"result": "已取消"}

app = g.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "bug-demo"}}

for ev in app.stream({"action": "", "result": ""}, config):   # 第一次:停在 interrupt
    if "__interrupt__" in ev:
        print("  暂停,等待审批")
final = app.invoke(Command(resume="approve"), config)         # 恢复
print(f"charge_money 总共被调用了 {charge_calls['n']} 次")
```

输出:

```
  [副作用] charge_money() 第 1 次执行     ← 首次执行,停在 interrupt
  暂停,等待审批
  [副作用] charge_money() 第 2 次执行     ← 恢复时 execute 从头重跑,又扣一次
charge_money 总共被调用了 2 次
```

用户只下了一单,却被扣了两次款。修复办法很简单:**把 `interrupt()` 放在节点最前面**,所有副作用都放在它拿到审批结果**之后**:

```python
def execute(state):
    decision = interrupt({"approve": state["action"]})   # ← interrupt 放最前
    if decision == "approve":
        charge_calls["n"] += 1                           # ← 副作用在拿到 resume 之后
        return {"result": f"已下单: {state['action']}"}
    return {"result": "已取消"}
```

这样首次执行时,`interrupt()` 第一行就抛异常退出了,`charge_calls` 根本没碰;恢复重跑时 `interrupt()` 直接返回 `"approve"`,才往下走到扣款——只扣一次。真实 LangGraph 也有同样的约束,官方文档专门提醒"code before interrupt will re-run"。理解了我们这个"恢复 = 重跑整个节点"的实现,你就知道这条约束从哪来:它不是框架的随意规定,而是"重跑"这个实现选择的直接后果。

## 5.5 这一章在架构上的意义

注意 `interrupt()` 几乎没写新机制——它**完全复用**了R3 章的检查点:暂停 = 提前存档 + 退出,恢复 = 从检查点续跑 + 注入 resume 值。这印证了R1 章那个论断:

> 一旦把控制流变成"外部引擎一步步驱动图",那么"步骤之间的缝隙"就成了统一的插入点。

我们在同一个 `yield` 位置,R2 章挂了流式,R3 章挂了存档,R4 章挂了中断。三个看似不同的能力,底层是同一个机制。一个正确的底层抽象,让上层能力一个接一个地长出来,而不必每次都重新发明地基。

## 5.6 阶段性回顾:`tinygraph` 完工了

到这里,底层运行时 `tinygraph`(对应 LangGraph)的核心功能全部完成。R1 章六个局限全部解决:

| 局限 | 解决于 | 机制 |
|---|---|---|
| 存不到磁盘 | R3 章 | Checkpoint(channel 值 + 版本 + next_nodes) |
| 无法暂停恢复 | R4 章 | interrupt() = 存档 + 退出 + 重跑 |
| 不能并行 | R2 章 | BSP 超步内并行 + 确定性合并 |
| 中间过程不可见 | 第 3/5 章 | 离散超步 + 每步 yield |
| 不能回到历史 | R3 章 | 不可变检查点链 |
| 出错只能整体重来 | R3 章 | 恢复不重做已完成超步 |

我们手里现在有一个**通用的有状态执行运行时**:它能确定性并发地执行带环的图,能存档恢复,能中断续跑,能流式观察。**它完全不知道"Agent"是什么**——它只管可靠地跑图。

接下来三章(6、7、8)换一层视角,在这个运行时**之上**建造好用的 Agent 抽象 `tinyagent`(对应 LangChain),让用户一行 `create_agent(model, tools)` 就能得到一个具备上面所有能力的 Agent。

## 5.7 自测:你真的吃透中断了吗

**Q1. 为什么 `interrupt()` 必须配 `checkpointer` 才能工作?不配会怎样?**

<details><summary>想清楚再展开</summary>

因为中断的本质是"存档 + 退出"。引擎捕获 `GraphInterrupt` 后要把"停在哪、状态是什么"存进检查点(`next_nodes` 指向被中断的节点),恢复时才能从这里续跑。没有 checkpointer,引擎抛出中断后无处存档,恢复时也无从读回——"暂停几天再恢复"就无从谈起。所以中断和检查点是同一套机制的两面。
</details>

**Q2. 引擎捕获中断时存的检查点,`next_nodes` 设成了 `tasks`(被中断的节点自己),而不是"它的下一个节点"。为什么?**

<details><summary>想清楚再展开</summary>

因为被中断的节点**还没成功跑完**(它在 `interrupt()` 处抛了异常,写入没提交)。恢复时必须**重跑这个节点**,让它这次拿到 resume 值走完。如果 `next_nodes` 指向"下一个节点",就等于跳过了被中断的节点,审批结果永远不会被用上、危险操作也永远不会真正执行。"指向自己"才能实现"带着审批结果重来一次"。
</details>

**Q3. "暂停几天"期间,服务器内存里有没有一个进程在等?这和 `time.sleep(几天)` 有什么本质区别?**

<details><summary>想清楚再展开</summary>

没有任何进程在等。`interrupt()` 让引擎存档后**正常返回**,生成器结束,进程可以彻底退出,内存、连接全部释放。状态只躺在数据库里。`time.sleep` 则是真的占着一个进程干等,服务器重启就全丢、还浪费资源。本质区别:中断把"等待"从"进程的运行时状态"变成了"数据库里的一条记录"——等待因此变成零成本,也因此能跨进程、跨机器、跨任意长时间。
</details>

**Q4(进阶). 如果在 `execute` 节点里把一行 `charge_money()`(扣款,有副作用)放在 `interrupt()` 之前,恢复后会发生什么?该怎么改?**

<details><summary>想清楚再展开</summary>

会扣两次款。因为恢复时 `execute` 是从头重跑的:首次执行跑到 `interrupt()` 前已经扣了一次,恢复重跑又会再跑一次 `charge_money()`。修复办法:把 `interrupt()` 放在节点**最前面**,所有副作用都放在 `interrupt()` 拿到审批结果**之后**。这条"interrupt 之前不放副作用"的约束,真实 LangGraph 同样存在——根源就是"恢复 = 重跑整个节点"这个实现选择。
</details>

## 5.8 本章小结

- **流式**因"执行是离散超步"而简单:每个超步的 `yield` 处吐出进展。`updates`(变化)与 `values`(完整快照)是两种视角;真实 LangGraph 有 6 种模式,核心机制是同一个。
- **`interrupt()` 不挂起进程**,而是"存档 + 退出";恢复是"从检查点重跑被中断的节点,这次 `interrupt()` 返回注入的 resume 值"。所以能"等几天"而零成本。
- 三个零件:`interrupt()`/`GraphInterrupt`(双重身份)、引擎捕获后存档(`next_nodes` 指向被中断节点)、`Command(resume=x)` 注入恢复值。
- 危险操作在审批通过前**一行都不执行**——这是"模型请求 / 框架执行"边界上的人工闸门。
- 中断完全复用检查点机制,印证"缝隙是统一插入点":流式、存档、中断同挂一处。
- **`tinygraph` 核心完工**,六个局限全解。下一阶段在它之上建 Agent 抽象。
