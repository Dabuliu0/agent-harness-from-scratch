# R1 · 为什么这个循环撑不起真实应用

> 📍 **深入篇 · 路线 B(图运行时)** —— 本章原为两层教程的第 2 章,现编号 R1;章内小节号(2.x)保持原状。文中「第 0 章」「第 1 章」指主线章节;本篇代码使用 `code/tinygraph` + `code/tinyagent`(与主线 `tinycore` 概念同构,仅 usage 等生产字段有出入)。从主线来的读者建议先读 [[10-第二条路线-图运行时|第 10 章·桥]] 与 [[R0-深入篇导读]]。


> 第 1 章那个 `run_agent` 函数能跑,逻辑也对。但把它放进真实产品里,你会接连遇到六件它做不到的事。本章不写新代码,只做一件事:把这六件事逐个讲清楚,然后指出它们其实是同一个结构问题的六种表现。看懂这个结构问题,R2 章那套"图运行时"的设计你就会觉得是顺理成章推出来的,而不是凭空发明的。

## 2.1 先看清这个循环的两个结构事实

再看一眼第 1 章循环的骨架,这次我们不关心它做对了什么,只关心它的两个结构特征:

```python
def run_agent(model, tools, user_input):
    messages = [HumanMessage(user_input)]      # ← 事实一:状态是个局部变量
    for _ in range(max_iters):
        ai_msg = model.invoke(messages)
        messages.append(ai_msg)
        if not ai_msg.tool_calls:
            return ai_msg.content
        for call in ai_msg.tool_calls:          # ← 事实二:执行进度在循环计数里
            messages.append(run_tool(call))
```

**事实一:状态是一个局部变量。** `messages` 是 `run_agent` 函数里的局部变量,它的生命周期就是这次函数调用的生命周期。函数一返回,或者进程一退出,这个变量就被回收了。你没有任何办法把"函数执行到一半时的 `messages`"拿到函数外面去。

**事实二:执行进度藏在 Python 的运行位置里。** "现在执行到第几轮循环"、"`for call in ...` 执行到第几个工具",这些信息不在任何一个你能访问的变量里——它们藏在 Python 解释器的指令指针(就是 CPU 当前执行到哪一行)里。你同样没办法把"执行到哪一步了"这个信息读出来。

这两个事实单独看都很正常,几乎所有普通函数都这样。问题在于,Agent 不是普通函数——它要长时间运行、要能中途暂停、要能崩溃后恢复。下面六个局限,全部是这两个事实在不同场景下撞出来的结果。

## 2.2 局限一:状态停在内存里,存不到磁盘

**场景**:用户和 Agent 聊了 20 轮,服务器需要重启(发版、扩容、或者就是崩了)。重启之后,这 20 轮的对话上下文在哪?

答案是:没了。这 20 轮的 `messages` 活在那次 `run_agent` 调用的栈帧里,函数早就返回了,栈帧早就被回收了。

你可能会想:"那我每轮结束都把 `messages` 写进数据库不就行了?"这能存下**对话内容**,但存不下**执行进度**。这两者的差别,是本章最关键的一个区分,值得用一个具体例子讲透。

假设 Agent 正在处理"对比北京、上海、广州的天气",模型一次发起了三个工具调用,框架执行完前两个,正准备执行第三个时进程崩溃了。崩溃前一刻,`messages` 是这样的:

```
[System,
 Human("对比北京/上海/广州天气"),
 AI(tool_calls=[get_weather(北京), get_weather(上海), get_weather(广州)]),
 Tool("北京 5°C",  tool_call_id=北京那次),    ← 已执行
 Tool("上海 12°C", tool_call_id=上海那次)]    ← 已执行
                                            ← 广州还没执行,进程就崩了
```

重启后,你把这串 `messages` 从数据库读回来。现在的问题是:**你怎么知道"广州那次调用还没做"?**

你得写一段代码:遍历最后那条 `AIMessage` 的三个 `tool_calls`,再去 `messages` 里找有没有对应 `tool_call_id` 的 `ToolMessage`,发现北京、上海都有,广州没有,于是反推出"还差广州一次调用"。

这段反推代码能写,但它很脆弱。如果模型一轮发起十个调用、其中有的成功有的抛异常、有的还触发了嵌套的子任务,你这套"对比 tool_calls 和 ToolMessage 反推进度"的逻辑会迅速变得没法维护。而它的本质,是在**手工重建那个已经丢失的执行进度**——也就是事实二里说的、藏在指令指针里、没法读出来的东西。

真正的问题不是"数据没存进数据库",而是**执行进度这个东西,在这个循环里压根没有一个能被存下来的形态**。它不是一个变量,而是 Python 当前执行到了 `for` 循环的第几次迭代。这种东西无法序列化、无法写盘。

## 2.3 局限二:执行无法暂停,更无法在别处恢复

**场景**:Agent 决定调用 `delete_database(name="prod")`。在真正执行这个危险操作前,你想插入一道人工审批:弹一个确认框,人点"批准"才执行,点"拒绝"就跳过。而且现实中,这个人可能几小时、甚至几天后才来点这个按钮。

在第 1 章的循环里,执行工具就是这一行:

```python
for call in ai_msg.tool_calls:
    messages.append(run_tool(call))    # ← 怎么在这里"暂停几天等人审批"?
```

你能想到的几种办法都有硬伤:

- **用 `input()` 阻塞等待**:那这个 Python 进程就得挂在这里几天不动,一直占着内存、数据库连接、文件句柄。这几天里服务器一旦重启,前面做的一切又全没了(回到局限一)。
- **用全局变量加轮询**:状态还是在内存里,服务器重启照样丢;而且代码会变成一团互相纠缠的标志位,难以维护。

真正想要的效果是:在执行工具**之前**,把整个 Agent 的当前状态**冻结成一份可以存盘的快照**,然后让进程正常退出——不占任何资源。几天后人点了"批准",我们从那份快照**恢复**,接着往下执行。理想情况下,恢复甚至可以发生在另一台机器上(原来那台可能已经因为扩容被回收了)。

这个效果在第 1 章的循环里做不到。因为"冻结当前执行点"本质上就是要把指令指针(执行到 `for` 循环第几个工具)序列化保存下来,而这正是事实二说的、做不到的事。

## 2.4 局限三:独立的工具调用只能一个个串行执行

**场景**:用户问"对比北京、上海、广州今天的天气"。模型会一次性发起三个工具调用:

```python
ai_msg.tool_calls = [
    ToolCall("get_weather", {"city": "北京"}),
    ToolCall("get_weather", {"city": "上海"}),
    ToolCall("get_weather", {"city": "广州"}),
]
```

这三个调用互不依赖,本应同时发出去。但第 1 章的循环是这样执行的:

```python
for call in ai_msg.tool_calls:
    messages.append(run_tool(call))    # ← 必须等一个查完,才查下一个
```

如果每次天气查询要 2 秒(调外部 API 很正常),串行就是 6 秒,而并行只需要 2 秒。当工具调用涉及网络请求时,串行执行浪费的时间会非常可观。

更进一步,如果你想让两个子 Agent 分别研究两个子问题、最后汇总结果,这种"分叉出去、各自执行、再合并回来"的结构,单线程的 `for` 循环根本表达不了。

这里的难点不只是"并行执行"——用线程池就能并行。真正的难点是**并行写入之后如何确定性地合并**。三个城市的天气结果回来了,该按什么顺序追加进 `messages`?如果今天北京先返回、明天上海先返回,最终 `messages` 的顺序就不一样,那么喂给模型的历史就不一样,模型的回答也可能不一样——同样的输入产生不同的结果,这种不确定性在生产环境里是调试噩梦。第 1 章的 `for` 循环既没有并行能力,也完全没有"合并"这个概念。这个"并行写入如何确定性合并"的问题,会在R2 章变成一个专门的抽象,叫 **Reducer**。

## 2.5 局限四:中间过程对外完全不可见

**场景**:Agent 要跑 10 秒。用户盯着屏幕,你想实时显示进度:"正在思考……" → "正在查天气……" → 然后让最终回答像打字机一样逐字蹦出来。这就是 ChatGPT 那种边生成边显示的体验。

第 1 章的 `run_agent` 只有一个 `return`,它在**最后一刻**才把结果一次性吐出来。在那之前的 10 秒里,模型在生成、工具在执行、又开始下一轮——这些过程对函数外部完全不可见。调用方只能看到两个状态:函数还没返回,函数返回了。中间是一个黑盒。

你可能会想用回调函数打补丁:给每个环节塞一个 callback。这能凑合,但很快会失控,因为"看中间过程"其实有好几种不同粒度的需求:

- 想看**每个步骤执行完后,状态发生了什么增量更新**;
- 想看**每个步骤之后的完整状态快照**;
- 想看**模型正在逐 token 输出的文本**(打字机效果);
- 想看**工具内部自己上报的进度**(比如"已下载 30%")。

每种粒度都塞一套 callback,代码会变成回调地狱。而根本原因是:第 1 章的循环里没有"步骤"这个概念。它就是一个连续运行的函数,没有任何明确的"一步执行完了"的时刻,自然也就没有地方去汇报"这一步发生了什么"。

## 2.6 局限五:状态被覆盖,无法回到历史上的某一步

**场景**:Agent 聊到第 8 轮时走偏了,给了一个错误方向的回答。你想"倒带"回第 5 轮那个状态,换一种问法重新往下走;同时还想保留原来第 5 到第 8 轮那条分支,方便对比两种走法。

第 1 章的循环做不到,因为第 5 轮时的那份 `messages`,早就被后面的 `append` 一路覆盖掉了。`messages` 只有一个,它始终是"当前最新"的状态,中间任何一个历史版本都没有被保留。你手里没有任何一个"第 5 轮的快照"可以回去。

要支持这种"回到历史某一步、并从那里分叉"的能力,需要每一步都留下一份**不可变的状态快照**,并且这些快照能串成一条可以回溯的链。这又回到了局限一的核心要求:状态必须是显式的、可序列化的、有版本的——而不是一个被反复覆盖的局部变量。

## 2.7 局限六:出错只能整体重来

**场景**:Agent 已经成功执行了 4 个有副作用的操作(比如发了 4 封邮件),第 5 个操作因为网络抖动超时失败了。你想只重试第 5 个,但第 1 章的循环里,任何一步抛异常都会让整个 `run_agent` 函数栈崩掉,之前做的 4 步全部丢失。如果直接从头重跑整个 Agent,那 4 封邮件会被重新发一遍——副作用被重复执行了。

可靠的重试需要框架"记得哪些步骤已经成功完成过",成功的就不再重做。而第 1 章的循环没有"步骤"这个单元,也没有任何地方记录"哪些步骤已完成",所以它只能整体成功或整体失败。

顺带一提,这个局限和**可观测性**是同一个根源。线上 Agent 行为诡异时,你想知道"它到底走了哪几步、每一步的输入输出分别是什么"。但第 1 章的循环是个黑盒,除非你手动到处加 `print`,否则看不到任何执行轨迹。可靠重试需要"记住哪些步骤完成了",可观测需要"每一步都是一个有名字、有边界的单元"——两者都要求把执行切分成可记录的步骤,而这正是第 1 章的循环所缺的。

## 2.8 六个局限的共同根因

把六个局限排在一起,会发现它们指向同一个东西:

| 局限 | 真正缺的能力 |
|---|---|
| 存不到磁盘 | 执行进度无法序列化(它藏在指令指针里) |
| 无法暂停恢复 | 无法把执行点冻结成快照 |
| 不能并行 | 无法表达"独立任务",也没有合并结果的机制 |
| 中间过程不可见 | 没有"离散步骤"这个汇报时机 |
| 不能回到历史 | 没有逐步保留的、带版本的状态快照 |
| 出错只能整体重来 | 没有"有边界、可记录"的执行单元 |

最右一列说的其实是同一件事的不同侧面。用一句话概括这个共同根因:

> 第 1 章的循环把**状态**和**控制流**都关进了一个正在运行的 Python 函数内部——状态是函数里的局部变量,控制流是 `for`/`while` 当前执行到的位置。而这两样东西都**无法被序列化、无法被暂停、无法被外部检查、无法被外部介入**。

只要状态和控制流还焊在一个运行中的函数里,这六件事就一件都做不成。反过来,如果能把这两样东西从函数里"取出来",变成函数外部可以访问、可以保存、可以一步步驱动的数据结构,这六件事就同时有了着手的地方。R2 章做的就是这件事。

## 2.9 为什么不直接用 Celery / Airflow / Temporal

在自己造运行时之前,有个合理的反问:持久化、重试、可观测这些能力,现成的任务调度和工作流引擎不是早就有了吗?直接拿来用不行吗?

这个反问值得正面回答,因为这些引擎确实各自解决了上面的一部分问题。但它们都不是为 Agent 这种形态设计的,卡点各不相同:

- **Celery 这类任务队列**:擅长"把一个任务异步丢出去执行,失败了自动重试"。但它的重试粒度是"整个任务"。Agent 跑到第 8 轮崩了,Celery 只能从头重跑整个 Agent,把前 7 轮的副作用全部重做一遍。它解决的是"任务调度",不是"有状态的多步执行"——它没有"执行到一半的状态"这个概念。

- **Airflow 这类 DAG 编排引擎**:擅长"固定的多步流水线,每步可观测"。但它的核心假设是 **DAG(有向无环图)**,而 Agent 的控制流**带环**:model → tools → model → tools → … 转几圈由模型在运行时决定。你没法用 Airflow 表达"反复在 model 和 tools 之间循环,直到模型说停为止"这种动态的环。

- **Temporal 这类持久化工作流引擎**:最接近我们要的东西,它确实能做"持久化执行 + 中断恢复",理念和我们要造的运行时相通。但它是一个**通用工作流引擎**,没有 Agent 的领域概念(消息、工具调用、ReAct 循环、中间件),你得在它之上自己搭一整层这些抽象。而且它的编程模型(workflow / activity 的划分、确定性重放的约束)是为传统业务流程设计的,套到"由大模型驱动的、每一步都不确定的动态控制流"上并不贴合。

把这三者放在一起看:Celery 重试粒度太粗,Airflow 假设无环,Temporal 缺 Agent 领域抽象。我们要造的运行时,恰好落在"支持环 + 细粒度状态 + 为 Agent 而生"这个它们都没占住的位置上。这也解释了 LangGraph 为什么不直接用现成的引擎——它需要的这个组合,市面上没有。

## 2.10 解决方向:把状态和控制流从函数里取出来

既然根因是"状态和控制流被关在运行中的函数里",方向就清楚了:把这两样东西都取出来,做成函数外部可以访问的、显式的数据结构。

**第一步,把状态取出来。** 不再用局部变量 `messages`,而是定义一个**显式的状态对象**(本质上就是一个 dict)。它独立于任何一次函数调用而存在,因此可以被序列化、写盘、做快照、保留多个版本。这一步直接解决局限一(持久化)和局限五(回到历史)。

**第二步,把控制流取出来。** 不再用 `for`/`while`,而是把每一步逻辑写成一个**独立的函数(称为节点 node)**,再用**边(edge)**描述"这一步之后该走哪一步"。这样整个 Agent 就从"一个大循环"变成了"一张由节点和边组成的图"。然后,由一个**外部的引擎(runtime)** 来驱动这张图:引擎每次只推进一步,在推进每一步的前后,它都有机会存盘、暂停、汇报进度、并行调度、记录轨迹。这一步解决剩下四个局限。

两种形态的对比可以浓缩成一句话:

```
第 1 章的循环:  Agent = 一个你写死、然后一口气跑完的函数
图运行时:       Agent = 一张"节点 + 状态"的图 + 一个一步步驱动它的外部引擎
```

把这两种形态画出来,就能看清"外部介入的机会"是从哪里冒出来的:

```
【第 1 章的循环】状态和控制流都焊在一次函数调用里:

   run_agent() ┌─────────────────────────────────────┐
               │  messages = [...]   ← 状态是局部变量   │
               │  for ...:           ← 进度在循环计数里 │
               │      invoke → append → run_tool       │  ← 一口气跑完,
               │      ...                              │     中途无法介入
               │  return                               │
               └─────────────────────────────────────┘
        外部能看到的只有:函数还没返回 / 函数返回了。中间是黑盒。

【图运行时】外部引擎一步步推进,每两步之间都留有一道空隙:

   引擎     ┌─步骤1─┐  空隙  ┌─步骤2─┐  空隙  ┌─步骤3─┐  空隙
   ────────▶│ model │──┃───▶│ tools │──┃───▶│ model │──┃──▶ ...
            └───────┘  ↑    └───────┘  ↑    └───────┘  ↑
                    在每道空隙处,引擎手里都攥着完整且一致的状态,
                    于是可以:存盘 / 暂停 / 汇报 / 并行调度 / 记录
            状态不再是局部变量,而存在引擎管理的、可序列化的容器里。
```

左边那个"一口气跑完的黑盒"和右边那个"被引擎一步步推进、每步留空隙"的图,区别不在于能不能算出正确答案(两者都能),而在于**外部能不能在执行途中介入**。本章前面六个局限,本质上全是"我想在执行途中做点什么"——存盘、暂停、并行、观察、回退。这些事在左边全都无解,在右边全都有了下手的地方。

这个转变的关键在于:**一旦控制流变成"外部引擎一步步推进节点",那么"每两步之间"就成了一个万能的插入点**。在这个插入点上,引擎可以存盘(检查点)、可以暂停(中断)、可以汇报(流式)、可以并行调度、可以记录(观测)。本章所有局限,都是在这个"步骤之间的空隙"里被解决的。

这就是 LangGraph 的核心思想,也是R2 章要亲手造的东西。

## 2.11 一个预告:为什么是"图"而不是"DAG"

2.9 节提到 Airflow 假设无环,这里把这个点单独拎出来,因为它是R2 章一个核心技术决策的由来。

传统工作流引擎用 DAG(有向无环图)加拓扑排序来调度任务。拓扑排序的前提是图里**没有环**——正因为无环,才能算出一个"先做谁后做谁"的线性顺序。但 Agent 的控制流天生带环:model → tools → model → tools → … 要转几圈,写代码时根本不知道,得由模型在运行时决定。带环的图没有拓扑排序,传统 DAG 调度器处理不了。

所以R2 章会用一个既**支持环**、又能**保证确定性并发**的执行模型,叫 **Pregel / BSP(整体同步并行)**。它把执行切成一个个"超步(super-step)":每个超步内部,所有该执行的节点并行执行;超步与超步之间,设一道同步屏障,把这一超步产生的所有状态更新确定性地合并进状态,再开始下一超步。这个模型最早来自 Google 处理大规模图计算的 Pregel 系统,LangGraph 把它借来跑 Agent。名字听起来抽象,但你在R2 章会看到,它的核心逻辑只有几十行,简单得出乎意料。

## 2.12 本章小结

- 第 1 章的循环有两个结构事实:状态是局部变量,执行进度藏在指令指针里。这两样东西都无法被外部访问、保存或介入。
- 由此派生出六个局限:**存不到磁盘、无法暂停恢复、不能并行、中间过程不可见、不能回到历史、出错只能整体重来**。
- 它们的共同根因是:状态和控制流都被关在一个正在运行的函数内部。
- 现成的引擎都不合适:Celery 重试粒度太粗,Airflow 假设无环,Temporal 缺 Agent 领域抽象。
- 解决方向是把两样东西取出来:状态变成**显式可序列化的对象**,控制流变成**节点 + 边的图**,由一个**外部引擎**一步步驱动。一旦如此,"步骤之间的空隙"就成了解决所有局限的统一插入点。
- Agent 的控制流带环,所以不能用 DAG 调度,要用支持环的 **Pregel / BSP** 模型——这是下一章的主角。
