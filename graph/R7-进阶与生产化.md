## 8.1 多智能体:子图即节点

单个 Agent 能力有限。复杂任务常需要**多个专精 Agent 协作**——一个查天气、一个写代码、一个做数学,再有个"主管(supervisor)"负责分派。

实现多智能体,**不需要任何新机制**。关键只有一句:

> 一个 Agent 本身就是一张图;把它当作另一张图的一个节点,就得到了多智能体。

因为节点函数的契约是"接收 state、返回更新",而一个编译好的 Agent 的 `invoke` 也正好是"接收 state、返回更新"——所以 Agent 可以**无缝嵌套**进更大的图。这就是"图可组合"带来的结果。

示例 A 是一个 supervisor 模式:主管节点根据问题路由到对应专家:

```python
def supervisor(state):
    route = "weather" if "天气" in state["query"] else "math"
    return {"route": route}

g.add_node("supervisor", supervisor)
g.add_node("weather", weather_agent)    # 真实场景:create_agent(...).invoke
g.add_node("math", math_agent)
g.add_edge(START, "supervisor")
g.add_conditional_edges("supervisor", lambda s: s["route"],
                        {"weather": "weather", "math": "math"})
```

运行:

```
问:北京今天天气怎么样?  →  [天气专家] 今天晴,25°C。
问:帮我算个数          →  [数学专家] 答案是 42。
```

这里 `weather` / `math` 节点为了简洁直接处理了,但**它们完全可以是 `create_agent(...)` 出来的完整子 Agent**(各带自己的工具和中间件)。supervisor 通过条件边决定调用谁。

这里有个隐蔽的设计问题:**子 Agent 的 state 是共享还是隔离?** 当你把一个子 Agent 当节点嵌进父图,绕不开的问题是:子 Agent 跑出来的 `messages` 要不要并进父图的 `messages`?如果**直接共享同一个 `messages` channel**,三个专家 Agent 的内部独白(它们各自的工具调用、中间结果)会全部涌进父图历史,很快把上下文撑爆、还互相干扰("数学专家"看到"天气专家"的一堆 tool 消息会困惑)。生产里的常见做法是**隔离**:子 Agent 在自己的"私有 messages"上跑,只把**最终结论**(一条干净的消息)返回给父图。这正好用得上R5 章的 state 契约——父图的节点函数调用 `weather_agent.invoke(...)` 后,**自己决定**从子 Agent 的返回里摘出什么、以什么形式并回父 state(比如只取 `result["messages"][-1]`)。"子图即节点"给了你组合的自由,但"边界上传什么数据"是你要主动设计的——这恰恰是多智能体里最影响效果的决策,比拓扑选 Supervisor 还是 Swarm 更关键。

常见的多智能体拓扑有几种,都用同样的"图 + 节点"表达:

- **Supervisor(主管)**:一个中心节点分派给多个专家(示例 A)。
- **Handoff(交接)**:Agent A 干完把控制权"交接"给 Agent B(用一个特殊的"交接工具"触发,本质是改条件边的走向)。
- **Swarm(群体)**:多个 Agent 平等协作,谁该接手由当前上下文决定。

把三种拓扑画出来,差异就一目了然——它们的区别只在"边怎么连",节点都是"一个 Agent 子图":

```
  Supervisor(星型,中心分派)        Handoff(链式,接力交接)
                                    
        ┌──────────┐                 ┌─────┐  交接   ┌─────┐  交接   ┌─────┐
        │supervisor│                 │ A   │────────▶│ B   │────────▶│ C   │
        └────┬─────┘                 └─────┘         └─────┘         └─────┘
       ┌─────┼─────┐                 控制权单向传递,A 决定交给谁、何时交
       ▼     ▼     ▼                 (本质:A 的条件边指向 B)
   ┌──────┐┌────┐┌────┐
   │天气   ││数学││代码│              Swarm(网状,平等协作)
   └──┬───┘└─┬──┘└─┬──┘                 ┌─────┐◀───────▶┌─────┐
      │      │     │                     │ A   │         │ B   │
      └──────┼─────┘                     └──┬──┘         └──┬──┘
             ▼  专家干完回到 supervisor       │   ╲       ╱   │
        (再决定下一步/收尾)                   │    ╲     ╱    │
                                            ▼     ╲   ╱     ▼
   中心化:谁干活由 supervisor 定          ┌─────┐  ╳   ┌─────┐
                                          │ C   │◀────▶│ D   │
                                          └─────┘      └─────┘
                                       去中心化:谁接手由当前上下文定
```

三者本质都是"Agent 子图当节点 + 不同的边拓扑":Supervisor 是**星型**(控制权始终回到中心),Handoff 是**链式**(控制权单向接力),Swarm 是**网状**(任意 Agent 间可流转)。没有任何新机制——换的只是 `add_edge` / `add_conditional_edges` 怎么连。这也是为什么 LangGraph 不需要为多智能体造新东西:图本来就可组合。

(对照真实框架:LangGraph 的多智能体正是这么做的——子图作为节点,supervisor / handoff 都有官方封装(`langgraph-supervisor`、`langgraph-swarm`)。交接靠 `Command(goto=...)` 实现节点间跳转,我们R4 章的 `Command` 只做了 `resume`,加 `goto` 是个好练习。)

## 8.2 记忆的两个层次:thread 内 vs 跨 thread

"记忆"在 Agent 里其实是两个不同的东西,容易混淆,这里讲清。

### 短期记忆 = 检查点(thread 内)

第 4、6 章讲的检查点,是**单条对话(thread)内**的记忆。同一个 `thread_id` 下,`messages` 历史持续累积,这让 Agent 在一次对话里记得前文。但**换个 `thread_id`,记忆就清零了**——这是设计使然,不同用户和会话本就该隔离。

### 长期记忆 = Store(跨 thread)

但有些信息需要**跨对话**持久:用户的语言偏好、历史画像、知识库。这就需要第二个层次——**Store**。它用 `(namespace, key)` 寻址,独立于任何 thread:

```python
# 示例 B
store = InMemoryStore()
ns = ("user", "alice")            # 命名空间:用户 alice

# 会话1 写入
store.put(ns, "language", "中文")

# 会话2(完全不同的 thread)仍能读到
store.get(ns, "language")          # → "中文",跨 thread 共享
```

两层记忆的分工:

| | 检查点(Checkpointer) | 长期记忆(Store) |
|---|---|---|
| 寻址 | `thread_id` | `(namespace, key)` |
| 范围 | 单条对话内 | 跨所有对话 |
| 存什么 | 完整执行状态(messages、进度) | 提炼出的事实/偏好 |
| 类比 | 工作记忆 | 长期记忆 |

怎么用?典型是配合中间件:`before_agent` 钩子从 Store 读出用户画像注入到上下文,`after_agent` 钩子把本次对话里学到的新事实写回 Store。这样长期记忆就和 Agent 循环解耦了。

(对照真实框架:对应 LangGraph 的 `BaseStore` / `InMemoryStore`,`compile(checkpointer=..., store=...)` 同时挂两者。真实 Store 还支持向量检索(`search` 可按语义找记忆)。LangChain 也有专门的 memory 中间件封装"读画像→注入→存新事实"这套。)

## 8.3 容错:重试、超时、错误处理

生产 Agent 必须扛得住外部故障(API 超时、工具抛异常、模型限流)。

R3 章我们已经拿到容错的**地基**:检查点让"恢复时不重做已完成的超步"成为可能——重试不会重复有副作用的操作。在此之上,生产框架还会加:

- **节点级重试**:某节点失败,只重试**这一个节点**(用 `pending writes` 记住同超步里已成功的其他节点的结果,不重做它们)。这正是 LangGraph `put_writes` 那个方法的用途。
- **超时**:给节点设执行时限,超时按失败处理。
- **错误处理策略**:工具抛异常时,是把错误信息作为 `ToolMessage` 喂回模型让它自己想办法(常见且有效),还是直接中止。

在我们的框架里落地这些并不难:`_run_superstep` 里给节点调用包一层 try/except + 重试循环即可;超时用 `concurrent.futures` 的 `future.result(timeout=...)`。这是把 `tinygraph` 推向生产的明确下一步。

这里有一个绕不开的前提:**节点最好是幂等的。** "失败就重试"听着简单,但它埋着一个和R4 章"interrupt 前别放副作用"同源的陷阱:**如果节点在抛异常之前已经产生了副作用(发了一半的邮件、扣了款、写了外部数据库),重试会让那个副作用发生两次。** 检查点能保证"已成功提交的超步不重做",但保不了"一个超步内部、节点跑到一半挂掉"这种情况——那个节点会被整个重跑。所以生产里有两条配套做法值得记住:

1. **让有副作用的操作幂等**(比如带一个去重 key,服务端见过就不重复执行),这样重跑安全。
2. **把"决定做什么"和"真正做"拆进不同节点**,让带副作用的那个节点尽量小、尽量靠后,缩小重跑的爆炸半径。

这不是 `tinygraph` 特有的约束,是所有"可重试的有状态执行"系统(包括 Temporal、Airflow)都要面对的——重试的前提是操作可安全重放。

(对照真实框架:LangGraph 把节点建模成"discrete steps",所以能做细粒度重试和超时(官方博客《Retries, Timeouts and Error Handlers》)。`create_agent` 的 `ToolStrategy(handle_errors=...)` 控制工具错误处理。)

## 8.4 可观测性:Agent 不该是黑盒

线上 Agent 行为诡异时,你需要看清"它走了哪些步、每步输入输出是什么、花了多少 token"。R1 章说过,第 1 章那个循环是黑盒;而图运行时天然可观测——因为**每个超步、每个节点都是有名字、有边界的单元**。

我们的 `stream(stream_mode="updates")` 已经能产出每步轨迹,这就是可观测性的雏形。生产级再加:每个节点的耗时、token 用量、输入输出快照,汇总成一条可追溯的 trace。

(对照真实框架:这是 LangSmith(LangChain 的可观测平台)做的事——自动把每次运行的完整图执行轨迹记录成可视化 trace。因为执行是离散步骤,埋点天然清晰。)

## 8.5 性能:为什么长对话不会越来越慢

最后一个值得想清的点。你可能担心:对话越长,检查点越大,会不会越来越慢?

LangGraph 的设计保证了**不会**——关键在于R2 章的 channel 版本机制。官方博客指出,几乎所有操作都是 **"Constant on the length of history"(对历史长度是常数级)**:恢复时只加载**最新一个**检查点(它已经聚合了之前所有写入),而不是回放整个历史。所以 200 轮的 Agent 和 2 轮的 Agent,单步开销一样。多个 thread 之间也完全独立(线程数 O(1))。

不过有个真实的工程挑战:**长跑 Agent 的检查点本身可能很大**。官方一个数据:一个跑 200 轮的编码 Agent,传统方式要序列化 **5.3GB** 到检查点存储。LangChain 为此引入了 **delta channels(增量通道)**——只存 channel 的**变化量**而非每次全量快照,把 5.3GB 压到 **129MB(40 倍缩减)**,性能几乎无损。

我们的框架每步存了全量快照(教学清晰优先),正好撞上这个问题——如果你拿它跑长任务,会看到检查点膨胀。这恰恰是理解 delta channels 价值的最好时机:把 `_make_checkpoint` 改成"只记录本超步变化的 channel + 指向父检查点",恢复时沿链聚合——这就是 delta channels 的核心思路,也是个有挑战的进阶练习。

(对照真实框架:对应官方博客《How We're Evolving our Runtime for Long-Running Agents》里的 delta channels。"Constant on history length"是 LangGraph 性能模型的核心承诺。)

## 8.6 本章小结

- **多智能体 = 子图即节点**:一个 Agent 是一张图,嵌进更大的图就是多智能体。Supervisor/Handoff/Swarm 都用"图 + 节点 + 条件边"表达,无需新机制。边界上传什么数据(共享还是隔离 state)是最关键的设计决策。
- **记忆分两层**:检查点是 thread 内短期记忆(工作记忆),Store 是跨 thread 长期记忆(用 `(namespace,key)` 寻址),常配合中间件"读画像→注入→存新事实"。
- **容错**建立在检查点之上:节点级重试(不重做已成功的)、超时、工具错误喂回模型。我们框架里加 try/except + timeout 即可落地;前提是有副作用的节点要幂等。
- **可观测性**因"执行是离散有名节点"而天然清晰;`stream(updates)` 是 trace 的雏形。
- **性能**:channel 版本机制让操作对历史长度是常数级(只加载最新检查点);长跑 Agent 的检查点膨胀由 **delta channels**(只存增量,40x 缩减)解决。
- 多处指出了把 `tinygraph`/`tinyagent` 推向生产的明确练习:`Command(goto)`、节点重试、Store 集成、delta channels。
