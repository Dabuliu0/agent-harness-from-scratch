> 前面的循环、图、检查点,很多框架都有;而**中间件系统是 LangChain 1.0 真正的定义性特性**。它让你在不改 Agent 内核的前提下,在生命周期的 6 个时机插入逻辑——压缩历史、脱敏、审批、换模型、加护栏。理解它,你就理解了现代 Agent 工程的核心:**上下文工程(context engineering)**。本章示例对接真实模型,需配好 `TINYAGENT_MODEL` 与 key。

## 7.1 为什么需要中间件:上下文工程

先讲动机,不然中间件只是一堆抽象钩子。

R5 章那个 Agent 循环,默认行为是"把全部历史原样发给模型,模型说调啥工具就调啥"。但真实生产里,你几乎总要在这个默认行为上动手脚:

- 对话太长了,超出模型上下文窗口 → 得**压缩**早期历史。
- 用户消息里有手机号、邮箱 → 发给模型前得**脱敏**。
- 模型想调"删库"这种危险工具 → 执行前得**人工审批**。
- 简单问题用便宜模型、复杂问题用强模型 → 得**动态换模型**。
- 模型输出可能有害内容 → 返回给用户前得**过护栏校验**。
- 每次运行前要加载用户的长期记忆 → 得在开始时**注入上下文**。

这些需求有个统称:**上下文工程**——"在正确的时机,把正确的信息给到模型"。它们的共同点是:**都不该写进 Agent 内核**(否则内核会变成一坨 if-else 大杂烩),而应该是**可插拔、可组合**的。

中间件就是这个"可插拔层"。它的设计思路是:**Agent 内核只管最纯粹的循环,所有"在某时机做某事"的逻辑都外置成中间件**。这是 Web 框架(Django/Express 的 middleware)验证了二十年的成熟模式,LangChain 1.0 把它引入了 Agent。

(对照真实框架:官方文档原话,中间件是"the defining feature of create_agent",存在的目的就是支持上下文工程——"getting the right information to the model at the right time"。)

## 7.2 六个生命周期钩子

中间件在 Agent 运行的 6 个时机被调用。基类 `AgentMiddleware` 把它们都定义成"默认什么都不做",子类按需重写。这就是 `tinyagent/middleware.py` 里那个基类的全部:

```python
# tinyagent/middleware.py —— 基类完整定义,可直接抄下来
class AgentMiddleware:
    # —— 生命周期两端(整个运行各一次)——
    def before_agent(self, state): return None        # Agent 开始前
    def after_agent(self, state): return None          # Agent 结束后

    # —— 模型调用前后(每轮模型调用)——
    def before_model(self, messages): return None      # 每次调模型前
    def after_model(self, message): return None         # 每次模型响应后

    # —— 包裹型钩子(handler-passing)——
    def wrap_model_call(self, messages, handler):       # 包裹模型调用
        return handler(messages)
    def wrap_tool_call(self, call, handler):            # 包裹工具调用
        return handler()
```

每个钩子默认 `return None`(对 before/after 而言意为"不改"),`wrap_*` 默认直接调 `handler`(意为"原样放行")。所以一个中间件只重写它关心的那几个钩子,其余继承这个"无操作"的默认行为。按触发时机和用途分三类:

| 钩子 | 时机 | 典型用途 |
|---|---|---|
| `before_agent` | Agent 启动前(整个运行一次) | 加载长期记忆、校验输入 |
| `before_model` | **每次**调模型前 | 裁剪/摘要历史、注入提示 |
| `wrap_model_call` | **包裹**每次模型调用 | 改写请求/响应、换模型、重试 |
| `after_model` | **每次**模型响应后 | 校验输出、加护栏 |
| `wrap_tool_call` | **包裹**每次工具调用 | 审批、改参数、脱敏结果 |
| `after_agent` | Agent 结束后(整个运行一次) | 保存结果、清理 |

注意"before/after"型和"wrap"型的区别——这是理解中间件的关键:

- **before/after** 是**观察/改写点**:你拿到数据,可以返回一个修改版(返回 `None` 表示不改)。它们不能"阻止"下一步。
- **wrap** 是**包裹点**:你拿到数据**和一个 `handler`(代表"下一步")**。你可以改输入、决定**调不调** handler、改 handler 的返回值,甚至完全不调它直接返回别的。这给了你对这一层的**完全控制权**。

(对照真实框架:这 6 个钩子名与 LangChain 1.0 的 `AgentMiddleware` 完全一致:`before_agent` / `before_model` / `wrap_model_call` / `wrap_tool_call` / `after_model` / `after_agent`。)

## 7.3 handler-passing 模式:洋葱式包裹

`wrap_*` 钩子用的是 **handler-passing(传递处理器)** 模式——这是整个中间件系统最关键的设计,务必理解。

核心思想:每个 `wrap` 中间件拿到一个 `handler`(代表"剩下的所有步骤"),它可以在调用 `handler` **前后**做事,形成一层"包裹"。多个中间件叠起来,就像**洋葱**:

```
请求 →  MW1 外层  →  MW2 外层  →  [真正的模型调用]  →  MW2 内层  →  MW1 内层  → 响应
```

我们在 `create_agent` 里这样把中间件串成洋葱:

```python
# tinyagent/agent.py(节选)
def base_call(msgs):                    # 最内层:真正调模型
    return model.invoke(msgs)

handler = base_call
for mw in reversed(mws):                # 反向包裹:最先注册的在最外层
    handler = _wrap_model(mw, handler)
ai = handler(messages)                   # 从最外层开始执行,层层深入再层层返回
```

`_wrap_model` 就是把一个中间件的 `wrap_model_call` 接到 handler 链上:

```python
def _wrap_model(mw, handler):
    def wrapped(messages):
        return mw.wrap_model_call(messages, handler)   # 把 handler 交给中间件
    return wrapped
```

跑示例(`07_middleware.py` 的示例 D,用桩模型、无需 key),你能**亲眼看到**洋葱结构:

```
[MW1] wrap_model_call → 进入       ← 最外层先进入
[MW2] wrap_model_call → 进入       ←   次外层进入
[MW2] wrap_model_call ← 返回       ←   次外层先返回
[MW1] wrap_model_call ← 返回       ← 最外层后返回
```

MW1 包着 MW2,MW2 包着真正的模型调用。进入顺序 MW1→MW2,返回顺序 MW2→MW1——栈式嵌套。这种结构的用处在于:**一个中间件能完整掌控它包裹的那一层**——比如重试中间件可以在 `handler` 抛异常时反复调用它;缓存中间件可以在调 `handler` 前先查缓存、命中就直接返回不调 handler。

而 before/after 型钩子是**线性**的,同一个示例也能看出来:

```
[MW1] before_model     ← 按注册顺序
[MW2] before_model
...
[MW1] after_model      ← after 也按注册顺序(我们的实现)
[MW2] after_model
...
[MW2] after_agent      ← after_agent 反向(对称包裹整个运行)
[MW1] after_agent
```

(对照真实框架:官方文档把这叫"handler-passing pattern":钩子"receive the request plus a `handler` callable, and can mutate the request via `request.override(...)` before delegating"。我们用"传 messages + handler"简化了 `request.override` 的形式,机制一致。)

### 六个钩子在一次完整运行里的触发全景

前面分别讲了"线性的 before/after"和"洋葱的 wrap"。但实战中 6 个钩子是**交织**触发的。把一次"模型先调一个工具、再给出回答"的完整运行摊平成时间轴,你能一眼看清谁在外、谁在内、谁触发几次:

```
agent.invoke({messages:[Human]})
│
├─ before_agent ────────────────────────────── 整个运行【一次】(加载记忆/校验输入)
│
│   ┌─ 超步: model 节点 ───────────────────────┐
│   │ before_model         ← 每次调模型前        │
│   │   wrap_model_call ▼ 进入(洋葱外层)        │  第 1 次调模型
│   │     [真正 model.invoke] → AI(tool_calls)  │  → 模型决定调工具
│   │   wrap_model_call ▲ 返回(洋葱内层)        │
│   │ after_model          ← 每次模型响应后        │
│   └────────────────────────────────────────┘
│        should_continue:有 tool_calls → 去 tools
│   ┌─ 超步: tools 节点 ───────────────────────┐
│   │   wrap_tool_call ▼ 进入(可在此审批/改参)  │  执行被请求的工具
│   │     [真正 tool.invoke] → ToolMessage      │  (审批拒绝则不调 handler)
│   │   wrap_tool_call ▲ 返回                    │
│   └────────────────────────────────────────┘
│        边 tools→model:回到 model 再来一轮
│   ┌─ 超步: model 节点 ───────────────────────┐
│   │ before_model                              │  第 2 次调模型
│   │   wrap_model_call ▼▲                       │  → 无 tool_calls,纯文本回答
│   │ after_model                               │
│   └────────────────────────────────────────┘
│        should_continue:无 tool_calls → END
│
└─ after_agent ─────────────────────────────── 整个运行【一次】(保存结果/清理)
```

抓住三个"次数"的差异,就抓住了 6 个钩子的全部分工:

- **`before_agent` / `after_agent` 各只触发一次**——它们包住整个运行,适合"开场加载记忆、收场保存结果"这类一次性的事。
- **`before_model` / `wrap_model_call` / `after_model` 每轮模型调用都触发**——上例模型调了 2 次,它们就触发 2 次。摘要、脱敏、换模型这类"每次问模型前后都要做"的事挂这里。
- **`wrap_tool_call` 每次工具调用都触发**——模型一轮请求 3 个工具,它就触发 3 次。审批、改参、脱敏工具结果挂这里。

这也解释了为什么"压缩历史"用 `before_model`(每轮都可能超长,需每轮检查)而"加载长期记忆"用 `before_agent`(整个会话开头加载一次就够)——**钩子选哪个,取决于这件事该"每轮做"还是"每次运行做一次"**。

## 7.4 三个实战中间件

光有框架不够,看三个真正干活的中间件(都在 `tinyagent/middleware.py`)。它们对应 LangChain 1.0 内置的三个中间件。

### 摘要压缩:用 before_model 控制上下文长度

```python
class SummarizationMiddleware(AgentMiddleware):
    def __init__(self, max_messages=6, keep_recent=2):
        self.max_messages = max_messages
        self.keep_recent = keep_recent

    def before_model(self, messages):
        if len(messages) <= self.max_messages:
            return None                          # 没超阈值,不动
        head = messages[:-self.keep_recent]      # 早期消息
        recent = messages[-self.keep_recent:]    # 保留最近几条
        summary = "；".join(f"{m.role}:{m.content[:20]}" for m in head if m.content)
        return [SystemMessage(content=f"[早前对话摘要] {summary}")] + recent
```

它在**每次调模型前**检查历史长度,超阈值就把早期消息压成一条摘要 + 保留最近几条。这样无论对话多长,发给模型的消息数都受控。(真实实现会用 LLM 生成高质量摘要、按 token 数触发,我们用拼接模拟,机制一样。对应 LangChain 的 `SummarizationMiddleware`——"Condense conversation history when it gets too long"。)

### PII 脱敏:用 before_model 保护敏感信息

```python
class PIIRedactionMiddleware(AgentMiddleware):
    PHONE = re.compile(r"\b1[3-9]\d{9}\b")
    EMAIL = re.compile(r"\b[\w.+-]+@[\w-]+\.[\w.-]+\b")

    def before_model(self, messages):
        redacted = []
        for m in messages:
            text = self.PHONE.sub("[手机号]", m.content or "")
            text = self.EMAIL.sub("[邮箱]", text)
            redacted.append(dataclasses.replace(m, content=text)
                            if text != m.content else m)
        return redacted
```

它在消息发给模型**前**,把手机号、邮箱替换成占位符——敏感信息永远不离开你的系统进到模型 provider。(对应 LangChain 的 `PIIMiddleware`——"Redact sensitive information before sending to the model"。)

### 工具审批:用 wrap_tool_call 拦截危险操作

这个最能体现 `wrap` 的"控制权":

```python
class HumanApprovalMiddleware(AgentMiddleware):
    def __init__(self, sensitive_tools, approver):
        self.sensitive_tools = set(sensitive_tools)
        self.approver = approver

    def wrap_tool_call(self, call, handler):
        if call.name in self.sensitive_tools:
            if not self.approver(call):
                return f"[已拒绝] 工具 {call.name} 未获批准,跳过执行。"  # 不调 handler!
        return handler()                                                  # 批准才执行
```

注意**审批被拒时,它直接 `return` 而不调用 `handler()`**——工具根本不会执行。这就是 `wrap` 比 before/after 强的地方:它能**阻断**下一步。这正是第 1 章那条"模型请求 / 框架执行"边界的中间件化实现——闸门现在是一个可插拔的中间件了。(对应 LangChain 的 `HumanInTheLoopMiddleware`——"Require approval for sensitive tool calls",支持 approve/edit/reject。生产中它会配合R4 章的 `interrupt()` 真正暂停等人工输入;我们用 `approver` 回调模拟决策,聚焦中间件机制本身。)

### 组合起来用

示例 B 把三个中间件**叠在一起**:

```python
agent = create_agent(
    model=model, tools=[delete_file],
    middleware=[
        PIIRedactionMiddleware(),
        SummarizationMiddleware(max_messages=6, keep_recent=2),
        HumanApprovalMiddleware(sensitive_tools=["delete_file"], approver=approver),
    ],
)
result = agent.invoke({"messages": [
    HumanMessage("我的手机号是 13812345678,请删掉 important.db")
]})
```

一次典型输出(模型决定调 `delete_file`,被审批中间件拦下):

```
[审批] delete_file({'path': 'important.db'}) → 拒绝
工具结果: [已拒绝] 工具 delete_file 未获批准,跳过执行。
最终回答: 操作完成。
```

手机号被脱敏后才进模型,删库请求被审批拦下。**三个关注点(脱敏、压缩、审批)各自独立、互不知道对方存在,却能无缝协作**——这就是中间件"可组合"的价值。想加个新能力?写个新中间件塞进列表,不动任何现有代码。

### 顺序不是无所谓的:中间件的排列会改变行为

"可组合"容易让人误以为"中间件随便怎么排都一样",其实**顺序经常是有语义的**,排错会出微妙的 bug。回看 7.3 的洋葱图——`before_model` 按注册顺序执行,而它们处理的是**同一份 messages 的流水线**,前一个的输出是后一个的输入。

拿"脱敏 + 摘要"这对来说,顺序错了真的会把手机号漏给模型。下面用一个桩模型把"模型实际收到了什么"打印出来,直接看两种顺序的差别。关键设计:让摘要的截断点正好切在手机号中间——`SummarizationMiddleware` 拼摘要时每条只取 `content[:20]`:

```python
class SpyModel(BaseChatModel):              # 把"模型实际看到的消息"原样回显
    def bind_tools(self, tools): self._tools = list(tools); return self
    def invoke(self, messages):
        return AIMessage(content="模型看到:" + " | ".join(m.content or "" for m in messages))

history = [                                  # 手机号在第 14 个字符,content[:20] 会把它截断
    HumanMessage("请记录联系方式如下手机号 13812345678 谢谢"),
    HumanMessage("帮我记一下"), HumanMessage("第三句"), HumanMessage("第四句"),
    HumanMessage("第五句话现在问你"),
]

# 顺序①:脱敏在前,摘要在后(正确)
a1 = create_agent(model=SpyModel(), middleware=[
    PIIRedactionMiddleware(),
    SummarizationMiddleware(max_messages=4, keep_recent=2)])
# 顺序②:摘要在前,脱敏在后(危险)
a2 = create_agent(model=SpyModel(), middleware=[
    SummarizationMiddleware(max_messages=4, keep_recent=2),
    PIIRedactionMiddleware()])
```

两种顺序跑出来:

```
顺序①脱敏在前: 模型看到:[早前对话摘要] user:请记录联系方式如下手机号 [手机号] 谢；... | 第四句 | 第五句话现在问你
  → 手机号泄漏:无

顺序②摘要在前: 模型看到:[早前对话摘要] user:请记录联系方式如下手机号 1381234；... | 第四句 | 第五句话现在问你
  → 手机号泄漏:1381234
```

差别一目了然。**顺序②**里,摘要先跑,把 `13812345678` 截成了 `1381234`(`content[:20]` 砍掉了后 4 位);轮到脱敏时,`1381234` 已经不是 11 位手机号了,正则匹配不上,**残缺的号码就这么进了模型**。**顺序①**里,脱敏先在原始消息上把完整号码替成 `[手机号]`,摘要再怎么截都是在已脱敏的文本上操作,一位数字都漏不出去。

这就是"顺序有语义"的硬证据:同样三个中间件、同样的输入,只是列表顺序不同,一个安全、一个漏数据。正确原则是**脱敏在前、摘要在后**——先把原始消息里的 PII 抹掉,后续任何处理都是在干净数据上进行。

`wrap_*` 型中间件的顺序同样有语义。比如你有个"改写工具参数"的中间件和一个"审批"中间件都挂 `wrap_tool_call`,洋葱外层先进入,所以排列决定了**人审批的是改写前还是改写后的参数**——这是个产品决策,不是技术细节。

一个判断顺序的简单原则:`before_model` 这类"净化/裁剪输入"的中间件,谁的产出是另一个的前提,谁就该排在前面(数据沿列表顺序流过)。`wrap_*` 这类"包裹"的中间件,想要"最外层先看到、最后处理"的排在列表前面(它在洋葱最外层)。拿不准时,跑一遍上面那种"打印模型实际看到什么"的探针,把行为**看出来**再定。真实 LangChain 文档也专门提醒中间件顺序影响执行结果——它不是实现细节,是你设计 Agent 时要主动决策的一环。

## 7.5 typed context:让中间件拿到运行时上下文

最后提一个进阶点。中间件常常需要"运行时信息"来决策——比如"当前用户是 VIP 吗?用哪个模型?"。LangChain 1.0 用 `context_schema` 定义一个**类型化的运行时上下文**,在 invoke 时传入,流进每个钩子:

```python
# 真实 LangChain 的用法示意
agent = create_agent(model, tools, context_schema=MyContext)
agent.invoke({"messages": [...]}, context=MyContext(user_expertise="expert"))

# 中间件里:
def wrap_model_call(self, request, handler):
    if request.runtime.context.user_expertise == "expert":
        request = request.override(model=strong_model)   # 专家用强模型
    return handler(request)
```

我们的简化框架没实现 typed context(它需要把一个 context 对象贯穿传进所有节点和钩子),但你已理解机制——它就是给钩子多传一个携带运行时信息的参数。这是个不错的扩展练习。

(对照真实框架:对应 `context_schema` 参数和钩子里的 `request.runtime.context`。官方示例正是"swaps models and tool sets based on `request.runtime.context.user_expertise`"。)

- state/messages 契约、多轮记忆、结构化输出思路(R5 章)。
- **中间件系统**(本章):6 个钩子 + handler-passing 洋葱模式 + 三个实战中间件。

加上前五章的 `tinygraph`,我们现在有了一套**完整的、两层架构的、可运行的现代 Agent 框架**。它的概念结构和真实的 LangGraph + LangChain 1.0 是 1:1 对应的——你已经把现代 Agent 的底层原理从头到尾走了一遍。

下一章站在更高处,看几个生产化议题(多智能体、记忆、容错、性能);第 11 章对照真实框架,告诉你接下来去读什么源码。

## 7.7 本章小结

- **中间件是 LangChain 1.0 的定义性特性**,服务于"上下文工程"——在正确时机给模型正确信息。它把"在某时机做某事"的逻辑从 Agent 内核**外置**成可插拔、可组合的层。
- **6 个钩子**:`before_agent` / `before_model` / `wrap_model_call` / `wrap_tool_call` / `after_model` / `after_agent`。
- **before/after = 观察/改写点**(线性);**wrap = 包裹点**(洋葱式嵌套,能阻断下一步)。
- **handler-passing 模式**:`wrap` 钩子拿到 `handler`(代表后续步骤),可在其前后做事、决定调不调、改其返回值——完全掌控这一层。
- 三个实战中间件:**摘要**(before_model 控长度)、**PII 脱敏**(before_model 保护隐私)、**工具审批**(wrap_tool_call 阻断危险操作)。多个中间件各自独立却能无缝组合,但排列顺序有语义。
- `tinyagent` 完工。我们已拥有一套完整的两层架构现代 Agent 框架。
