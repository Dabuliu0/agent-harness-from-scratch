## 3.1 把R1 章的方向落成四个概念

R1 章定下的方向是:状态显式化、控制流图化、外部引擎驱动。现在落成四个具体概念,它们是这套运行时的全部词汇:

### 1. State(状态) —— 把状态从隐藏变成显式

**是什么？**
一个显式的 Python dict，用来存储 Agent 运行过程中的所有数据。

**为什么需要？**
第 1 章的循环里，状态藏在函数局部变量里：
```python
def agent_loop():
    messages = []  # 状态藏在这里，函数外看不到，程序退出就没了
    while True:
        ai = model.invoke(messages)
        messages.append(ai)
        ...
```

现在我们要把它变成显式的、可序列化的 dict：
```python
state = {
    "messages": [...],  # 消息历史
    "count": 3          # 其他状态字段
}
# 好处：
# 1. 可以保存到磁盘（R3 章的检查点）
# 2. 可以在节点之间传递
# 3. 可以随时查看和修改
```

### 2. Channel(通道) + Reducer(归并器) —— 给状态加上版本管理和合并规则

**Channel 是什么？**
State 里每个 key 的升级版，不仅存储值，还带版本号和合并规则。

**为什么需要 Channel？**
普通 dict 无法解决并发写入的问题：
```python
# 问题场景：三个节点同时写 messages
# 节点 A: messages.append("北京天气")
# 节点 B: messages.append("上海天气")
# 节点 C: messages.append("广州天气")
# 问题：谁先谁后？怎么合并？
```

Channel 的解决方案：
```python
Channel = {
    value: [...],           # 实际的值
    version: 5,             # 版本号，记录被修改了几次
    reducer: add_reducer    # 合并规则，告诉引擎怎么合并并发写入
}
```

**Reducer 是什么？**
一个函数 `(旧值, 新值) -> 合并后的值`，定义并发写入如何合并。

常见的 Reducer：
- `last_value`: 新值覆盖旧值（用于 count、status 等字段）
- `add_reducer`: 追加到列表（用于 messages 等历史记录）

**类比理解：**
- Channel 像 Git 仓库
- value 是当前文件内容
- version 是 commit 次数
- reducer 是 merge 策略

### 3. Node(节点) + Edge(边) —— 把控制流变成数据

**Node 是什么？**
一个执行具体逻辑的函数，代表 Agent 的一个步骤。

```python
def call_model(state):
    """节点函数：调用模型"""
    ai = model.invoke(state["messages"])
    return {"messages": [ai]}  # 返回要更新的部分

def call_tools(state):
    """节点函数：执行工具"""
    result = execute_tool(...)
    return {"messages": [result]}
```

**Edge 是什么？**
边描述"这个节点跑完后，下一步去哪"。

两种边：
```python
# 固定边：无条件跳转
graph.add_edge("tools", "model")  # tools 跑完后必然去 model

# 条件边：根据状态动态决定
def should_continue(state):
    if state["messages"][-1].tool_calls:
        return "tools"  # 有工具调用，去执行工具
    else:
        return END      # 没有，结束

graph.add_conditional_edges("model", should_continue)
```

**为什么需要 Node + Edge？**
第 1 章的控制流写死在代码里：
```python
while True:  # ← 循环写死
    ai = model.invoke(...)
    if ai.tool_calls:  # ← 条件写死
        result = call_tools(...)
    else:
        break  # ← 退出写死
```

现在变成数据化的图：
```
START → model →(条件边)→ tools → model → END
              └────────────────────→ END
```

好处：
1. 可以动态修改流程（不用改代码）
2. 可以在步骤之间暂停、恢复
3. 可以可视化展示流程

**用 StateGraph 声明图：**
```python
graph = StateGraph(schema)
graph.add_node("model", call_model)    # 添加节点
graph.add_node("tools", call_tools)
graph.add_edge(START, "model")         # 添加边
graph.add_conditional_edges("model", should_continue)
graph.add_edge("tools", "model")
```

### 4. Pregel / BSP 引擎 —— 那台驱动图运行的机器

**是什么？**
一个执行引擎，负责按照图的定义，一步步运行节点。

**为什么叫 Pregel / BSP？**
- **Pregel**: Google 的图计算框架，LangGraph 借鉴了它的思想
- **BSP**: Bulk Synchronous Parallel（整体同步并行），一种并行计算模型

**它做什么？**
```python
engine = graph.compile()  # 编译图，得到引擎
result = engine.invoke({"messages": [Human("你好")]})  # 执行

# 引擎内部做的事：
while 还有节点要跑:
    ① 规划：决定本轮跑哪些节点
    ② 执行：并行运行这些节点
    ③ 提交：合并所有节点的写入
    ④ 计算：下一轮跑哪些节点
```

**为什么需要外部引擎？**
如果在节点函数里写"调用下一个节点"：
```python
def model(state):
    ai = invoke_model(...)
    if ai.tool_calls:
        return call_tools(state)  # ✗ 节点互相调用，耦合严重
```

问题：
- 无法暂停（节点在调用栈里）
- 无法并行（同步调用）
- 无法存档（状态分散）

外部引擎的好处：
- 节点只管自己的逻辑
- 引擎负责调度、并行、存档
- 节点之间解耦

---

**四个概念的关系：**

```
State 定义了"存什么数据"
  ↓
Channel + Reducer 定义了"数据怎么管理"
  ↓
Node + Edge 定义了"流程怎么走"
  ↓
BSP 引擎 负责"真正把流程跑起来"
```

**类比：**
- State = 仓库里的货物
- Channel = 货架（带编号、有管理规则）
- Node = 工人（每人负责一道工序）
- Edge = 传送带（货物流转路线）
- BSP 引擎 = 厂长（协调所有工人按流程干活）

---

四个概念里,前三个是"声明"(描述图长什么样),只有第四个是"执行"(真正把图跑起来)。本章大头在第四个。建议边读边开着 `code/tinygraph/` 的 `channels.py`、`graph.py`、`pregel.py` 对照——这一章讲的每一行,那里都有。

## 3.2 State 与 Channel:给状态加上版本号

### 从裸 dict 到 Channel：为什么需要版本号？

第 1 章的循环里,状态就是一个普通的局部变量:

```python
messages = []  # 这就是状态，存在内存里，程序一退就没了
```

现在我们要把它变成显式的 dict:

```python
state = {
    "messages": [...],  # 消息历史
    "count": 3          # 某个计数器
}
```

但这个裸 dict 还不够。我们需要解决三个问题：

**问题 1：怎么知道状态改过没有？**

假设你要做"存档恢复"功能（R3 章会讲）：
```python
# 存档时：
save_to_disk(state)  # {"messages": [...], "count": 3}

# 恢复时：
state = load_from_disk()  # 拿到 {"messages": [...], "count": 3}

# 问题来了：这个 count = 3 是初始值 3，还是经过 10 次修改后的 3？
# 无法区分！
```

**问题 2：并发写入怎么合并？**

假设三个节点同时要修改 `messages`:
```python
# 节点 A: messages.append("北京天气")
# 节点 B: messages.append("上海天气")  
# 节点 C: messages.append("广州天气")

# 最终 messages 应该是什么顺序？谁说了算？
```

**问题 3：怎么知道"哪些节点该运行了"？**

真实的 LangGraph 需要知道："哪个 channel 的值更新了，依赖它的节点就该运行"。没有标记，引擎无法判断。

### Channel 的解决方案：值 + 版本号 + 合并规则

LangGraph 引入 **Channel** 概念，把每个状态字段包装成一个容器：

```
普通 dict:
    "messages" → [消息1, 消息2, ...]
    
Channel:
    "messages" → {
        value: [消息1, 消息2, ...],     # 实际的值
        version: 5,                      # 版本号：表示被成功修改过 5 次
        reducer: add_reducer             # 合并规则：告诉引擎怎么合并并发写入
    }
```

### Channel 的完整代码实现

```python
# tinygraph/channels.py
class Channel:
    """
    Channel 是状态中每个字段的容器
    
    核心设计：值 + 版本号 + 合并规则
    
    为什么要这样设计？
    1. value: 存储实际数据（就像普通 dict 的值）
    2. version: 版本号，单调递增，解决"改过几次"的问题
    3. reducer: 合并函数，解决"并发写入怎么合并"的问题
    
    类比：
    想象 Channel 是一个 Git 仓库：
    - value 是当前文件内容
    - version 是 commit 次数
    - reducer 是合并冲突的策略（比如 git merge 的策略）
    """
    
    def __init__(self, reducer=last_value, value=None):
        """
        初始化一个 Channel
        
        参数详解:
            reducer: 函数，签名为 (当前值, 新写入) -> 合并后的值
                    这是一个"合并策略"函数，决定当多个节点同时写这个 channel 时如何处理
                    
                    常见的 reducer:
                    - last_value: 新值直接覆盖旧值 (用于普通字段，如 count、status)
                    - add_reducer: 追加到列表 (用于消息历史、结果收集)
                    
            value: 初始值
                  默认为 None，表示"这个 channel 还没有任何写入"
        
        内部状态:
            self.value: 当前存储的值
            self.version: 版本号，从 0 开始
                         每次成功 update() 后 +1
                         就像 Git 的 commit 计数
        """
        self.reducer = reducer    # 合并策略
        self.value = value        # 当前值
        self.version = 0          # 版本号，初始为 0

    def update(self, writes):
        """
        将一批写入合并到当前值，并递增版本号
        
        参数详解:
            writes: list，一批写入的列表
                   例如: [新消息1, 新消息2, 新消息3]
                   
                   为什么是列表？
                   因为在并行场景下，可能有多个节点同时写这个 channel
                   引擎会收集所有写入，统一调用 update()
        
        工作流程（重要！）:
            假设 writes = [A, B, C]，当前 value = V0
            
            第1步: v = V0
            第2步: v = reducer(v, A)  → v 变成 V1
            第3步: v = reducer(V1, B) → v 变成 V2  
            第4步: v = reducer(V2, C) → v 变成 V3
            第5步: self.value = V3
            第6步: self.version += 1
            
            关键点：
            1. reducer 被调用多次（writes 有几个元素就调几次）
            2. 每次调用都是 (上次结果, 新元素) 的模式
            3. 这就是函数式编程里的 reduce/fold 操作
        
        为什么要按顺序合并？
            确保确定性！如果 writes 的顺序是固定的（由引擎保证），
            那么无论并行执行多少次，最终结果都一样。
            
        具体例子:
            当前 messages channel: value = [msg0], version = 1
            writes = [msg1, msg2]
            reducer = add_reducer (追加策略)
            
            执行过程:
            v = [msg0]                      # 从当前值开始
            v = add_reducer(v, msg1)        # [msg0] + [msg1] = [msg0, msg1]
            v = add_reducer(v, msg2)        # [msg0, msg1] + [msg2] = [msg0, msg1, msg2]
            self.value = [msg0, msg1, msg2] # 更新值
            self.version = 2                # 版本 +1 (从 1 变成 2)
        """
        if not writes:
            return  # 没有写入，什么都不做（保持 value 和 version 不变）
        
        v = self.value  # 从当前值开始
        
        # 关键循环：逐个应用 reducer
        for w in writes:
            # 每次调用 reducer，用上一次的结果和新写入合并
            # 这就是 reduce 操作的本质：
            # reduce([A,B,C], fn, init) = fn(fn(fn(init, A), B), C)
            v = self.reducer(v, w)
        
        self.value = v         # 更新为最终合并结果
        self.version += 1      # 版本号递增（标记"发生了一次提交"）
```

### 版本号的两个用途

现在只需记住一句话：**版本号记录这个 channel 被成功提交过几次**。

它有**浅、深**两个用途：

#### 浅用途（本章和R3 章）：存档恢复

```python
# 存档时：
checkpoint = {
    "messages": {
        "value": [msg1, msg2, msg3],
        "version": 5  # 记录：这是第 5 次提交后的状态
    }
}
save_to_disk(checkpoint)

# 恢复时：
checkpoint = load_from_disk()
# 不仅恢复值，还恢复版本号
# 这样恢复后的状态和存盘那一刻逐位相同

# 好处：
# 1. 可以判断"这个值是初始值还是修改过的"
# 2. 可以判断"恢复后是否有新的修改"
# 3. 可以实现"时间旅行"：回到版本 3 的状态
```

#### 深用途（真实 LangGraph 的核心）：版本订阅触发

```python
# 真实 LangGraph 的触发机制（我们简化版不用，但你要理解）：

# 节点 B 订阅了 messages channel
# B 记住：我上次运行时，messages 的版本是 3

# 每个超步结束后，引擎检查：
if messages.version > B上次见过的版本:
    # messages 有新内容了（version 从 3 变成了 4）
    # 触发 B 节点运行
    active.append(B)

# 这就是"版本订阅"机制：
# 谁订阅的 channel 版本涨了，谁就该运行
```

**我们的简化版不走这条路**，改用更直观的**边**来决定"下一批跑谁"。这是我们和真实 LangGraph 最大的分叉点。

等 3.5 节把引擎跑通后，我会**把两种触发模型放在同一个例子上算给你看**，你会看到它们产出同样的执行序列。

## 3.3 Reducer:并行写入凭什么能确定性合并

### 什么是 Reducer？

R1 章局限三留了个问题:三个节点并行查天气,结果怎么合并进一个列表?谁先谁后?

**Reducer 就是答案**。它是一个简单的二元函数：

```
reducer(旧值, 新写入) → 合并后的值
```

就这么简单！但它能解决并行合并的大问题。

### 两种最常用的 Reducer

```python
# tinygraph/channels.py

def last_value(current, update):
    """
    策略1: 覆盖策略 - 新值直接覆盖旧值
    
    参数:
        current: 当前值 (可能是 None，可能是之前的值)
        update: 新写入的值
    
    返回:
        update (直接返回新值，完全忽略旧值)
    
    使用场景:
        普通字段，例如 count、status、temperature 等
        
    例子:
        current = 3
        update = 5
        result = last_value(3, 5)  # 返回 5
        
        新值直接覆盖旧值，简单粗暴！
        
    为什么叫 last_value？
        因为最后写入的值（last value）胜出
    """
    return update


def add_reducer(current, update):
    """
    策略2: 追加策略 - 将新值追加到列表末尾
    
    参数:
        current: 当前列表 (可能是 None，可能是已有的列表)
        update: 新写入的值 (可以是单个元素或列表)
    
    返回:
        合并后的列表
    
    使用场景:
        需要保留历史的字段，例如:
        - messages: 消息历史，越来越长
        - results: 收集多个查询结果
        - logs: 日志记录
        
    例子1 (追加单个元素):
        current = ["北京"]
        update = "上海"
        result = add_reducer(current, "上海")
        # 返回 ["北京", "上海"]
        
    例子2 (追加列表):
        current = ["北京"]
        update = ["上海", "广州"]
        result = add_reducer(current, ["上海", "广州"])
        # 返回 ["北京", "上海", "广州"]
        
    例子3 (从空开始):
        current = None
        update = "北京"
        result = add_reducer(None, "北京")
        # 返回 ["北京"]
    
    为什么要检查 isinstance？
        允许节点既可以返回单个元素，也可以返回列表
        这样更灵活：
        - return {"messages": new_msg}           ← 单个
        - return {"messages": [msg1, msg2]}      ← 列表
        都能正确处理
    """
    # 初始化：如果当前值是 None，创建空列表
    if current is None:
        current = []
    
    # 如果新写入本身就是列表，直接拼接
    if isinstance(update, list):
        return current + update  # [1,2] + [3,4] = [1,2,3,4]
    
    # 否则将单个元素包装成列表再拼接
    return current + [update]    # [1,2] + [3] = [1,2,3]
```

### Reducer 的本质：二元函数 + 反复调用

**关键理解：Reducer 不是被调用一次，而是被反复调用！**

假设三个节点并行写入 messages channel，引擎收集到：
```python
writes = [消息A, 消息B, 消息C]
```

`Channel.update(writes)` 内部会这样调用 reducer：

```python
# 从当前值开始
v = current_value  # 假设是 []

# 第1次调用 reducer
v = add_reducer(v, 消息A)
# v 现在是 [消息A]

# 第2次调用 reducer  
v = add_reducer(v, 消息B)
# v 现在是 [消息A, 消息B]

# 第3次调用 reducer
v = add_reducer(v, 消息C)
# v 现在是 [消息A, 消息B, 消息C]

# 最终结果
return v  # [消息A, 消息B, 消息C]
```

**这就是函数式编程里的 `reduce` 操作**：用一个二元函数把列表"折叠"成单个值。

用 Python 的 `functools.reduce` 来理解：
```python
from functools import reduce

# 这两种写法等价：
result1 = Channel.update([A, B, C])  # 我们的实现

result2 = reduce(add_reducer, [A, B, C], current_value)  # Python 标准库
```

### 图解：Reducer 的工作过程

```
输入: writes = [A, B, C], current = []

┌─────────┐
│ current │ = []
│   []    │
└────┬────┘
     │
     │ add_reducer([], A)
     ▼
┌─────────┐
│  [A]    │
└────┬────┘
     │
     │ add_reducer([A], B)  
     ▼
┌─────────┐
│ [A, B]  │
└────┬────┘
     │
     │ add_reducer([A,B], C)
     ▼
┌──────────┐
│[A, B, C] │ ← 最终结果
└──────────┘
```

### 为什么 add_messages 比 add_reducer 复杂？

真实 LangGraph 的 `add_messages` reducer 比我们的 `add_reducer` 复杂，因为要处理一个实际需求：

**流式输出时，同一条消息会被更新！**

```python
# 场景：模型流式输出

# 第1次写入：先放一个空消息占位
messages = [AIMessage(id="msg_1", content="")]

# 第2次写入：token 来了，更新内容
messages = [AIMessage(id="msg_1", content="北京")]

# 第3次写入：更多 token
messages = [AIMessage(id="msg_1", content="北京今天")]

# 第4次写入：完整内容
messages = [AIMessage(id="msg_1", content="北京今天5度")]

# 如果用纯追加策略 add_reducer：
# 结果会是 [空消息, "北京", "北京今天", "北京今天5度"]
# 错了！应该是原地更新同一条消息！

# add_messages 的做法：
# 给每条消息配 id，新写入的 id 已存在就【替换】，id 是新的才追加
```

`add_messages` 的逻辑：
```python
def add_messages(current, update):
    """真实 LangGraph 的 messages reducer（简化版）"""
    if current is None:
        current = []
    
    result = list(current)  # 复制当前列表
    
    for new_msg in update:
        # 查找是否有相同 id 的消息
        found = False
        for i, old_msg in enumerate(result):
            if old_msg.id == new_msg.id:
                # 找到了，替换它
                result[i] = new_msg
                found = True
                break
        
        if not found:
            # 没找到，追加
            result.append(new_msg)
    
    return result
```

我们的 `add_reducer` 只做纯追加，够讲清机制；但你现在明白了真实版本那点"额外的聪明"是被实际需求倒逼出来的，不是为复杂而复杂。

### 先制造一次 bug:不做隔离的"直接版"引擎

假设我们偷懒,写一个最直接的并行引擎:所有节点共享**同一个** state dict,谁想改就直接改。把它跑在"三个节点各给计数器加一"上:

```python
import time, random
from concurrent.futures import ThreadPoolExecutor

# 共享状态：所有节点都能直接访问和修改
state = {"count": 0}

def make_worker(name):
    """创建一个工作函数，执行"读-计算-写"三步操作"""
    def worker():
        # ① 读取当前值
        cur = state["count"]
        print(f"[{name}] 读到 count = {cur}")
        
        # ② 模拟计算耗时 (真实场景中可能是网络IO、模型调用等)
        time.sleep(random.random()*0.01)
        
        # ③ 写回新值
        state["count"] = cur + 1
        print(f"[{name}] 写入 count = {cur + 1}")
    
    return worker

# 并行执行三个工作节点
with ThreadPoolExecutor(max_workers=3) as pool:
    # 提交三个任务到线程池
    futures = [pool.submit(make_worker(n)) for n in ("a", "b", "c")]
    # 等待所有任务完成
    for f in futures:
        f.result()

print(f"最终结果: {state['count']}")  # 期望是 3，但实际可能是 1、2 或 3
```

**问题出在哪？**

三个节点各加一,你以为输出一定是 `3`。**实际跑几次,你会看到 `3`、`2`、有时甚至 `1`**——这就是**丢失更新(Lost Update)**:

```
可能的执行时序:
时刻1: [a] 读到 count = 0
时刻2: [b] 读到 count = 0  ← b 还没看到 a 的写入
时刻3: [a] 写入 count = 1
时刻4: [c] 读到 count = 1  ← c 看到了 a 的写入
时刻5: [b] 写入 count = 1  ← b 把 a 的更新覆盖掉了！
时刻6: [c] 写入 count = 2
最终: count = 2 (丢失了 a 的 +1 操作)
```

这是**漏洞一**:**并行节点直接读写同一份状态,结果取决于线程调度,每次可能都不一样**。

再看漏洞二。把节点改成往同一个列表追加(列表 append 是原子的,不会丢,但**顺序**会乱):

```python
state = {"results": []}

def make_fetcher(city, delay):
    """创建一个查询天气的函数"""
    def fetch():
        print(f"开始查询 {city}...")
        
        # 模拟网络延迟 (不同城市响应速度不同)
        time.sleep(delay)
        
        # 直接追加到共享列表
        state["results"].append(city)
        print(f"{city} 查询完成")
    
    return fetch

with ThreadPoolExecutor(max_workers=3) as pool:
    # 按 北京、上海、广州 的顺序提交任务
    pool.submit(make_fetcher("北京", 0.03))  # 最慢
    pool.submit(make_fetcher("上海", 0.01))  # 最快
    pool.submit(make_fetcher("广州", 0.02))  # 中等

# 等待所有任务完成
pool.shutdown(wait=True)

print(state["results"])   
# 输出: ['上海', '广州', '北京']  ← 不是声明顺序，而是谁快谁先！
```

**问题出在哪？**

输出是 `['上海','广州','北京']`——**顺序由网络快慢决定**,不是你声明节点的顺序。换个网络状况,顺序又变了。这是**漏洞二**:**合并顺序不可复现**。

```
期望的行为 (确定性):
    无论网络快慢如何，结果永远是 ['北京', '上海', '广州']
    
实际的行为 (不确定性):
    运行1: ['上海', '广州', '北京']  ← 上海网快
    运行2: ['北京', '上海', '广州']  ← 碰巧北京网快了
    运行3: ['广州', '上海', '北京']  ← 广州突然变快
```

**为什么这两个 bug 很严重？**

1. **调试困难**：同样的输入，有时对有时错，无法复现问题
2. **测试失败**：测试用例有时通过有时失败，CI/CD 不稳定
3. **存档恢复失败**：R3 章要实现的检查点恢复依赖确定性——如果结果不可复现，恢复后的状态可能和之前不一致

这两个 bug 不是假想,是你随手写并行 Agent 一定会撞上的。**BSP 就是用来同时堵死这两个漏洞的。**

### Reducer 该满足的两个性质

回头看,这两个 bug 告诉我们 reducer 和它的调用方式必须满足两条:

**第一,写入必须按引擎能固定的顺序喂进来。** `add_reducer` 是 `current + [update]`,顺序敏感(`[a,b] ≠ [b,a]`)。这本身没问题——只要引擎**不按完成快慢、而按一个声明时就定好的顺序**收集写入(下一节的 `for name in tasks`)。如果像上面 demo 那样让"谁先到谁先进",确定性就崩了。

**第二,reducer 是"当前值 + 一个新写入"的二元函数,会被反复调用。** 看 `Channel.update` 里 `for w in writes: v = reducer(v, w)`——它吃掉一个写入、产出新值,再吃下一个。所以 `reducer(reducer(v, a), b)` 必须有意义。这就是函数式里 `reduce` 的那个二元算子。

那 `add_messages`(真实 LangGraph 的 messages reducer)为什么比我们的 `add_reducer` 复杂?因为 Agent 有个纯追加搞不定的需求:**同一条消息会被更新**。流式输出时,模型先放一条空的 AI 消息占位,token 到达后要**原地更新这一条**而非追加新的。`add_messages` 给每条消息配 id:新写入的 id 已存在就**替换**,id 是新的才追加。我们的 `add_reducer` 只做纯追加,够讲清机制;但你现在明白了它那点"额外的聪明"是被真实需求倒逼出来的,不是为复杂而复杂。

## 3.4 StateGraph:声明这张图

有了 Channel 和 Reducer,声明图的结构。`StateGraph` 是个纯**构建器**——只记录有哪些节点、哪些边、schema 长什么样,不负责执行:

```python
# tinygraph/graph.py

# 特殊的节点标识符
START = "__start__"    # 虚拟入口节点（图的起点）
END = "__end__"        # 虚拟终止节点（图的终点）

class StateGraph:
    """
    状态图的构建器，用于声明图的结构
    
    这是一个纯声明式的 API，只负责记录图的结构（节点、边、状态 schema），
    不负责执行。真正的执行引擎是 compile() 返回的 CompiledGraph。
    """
    
    def __init__(self, schema):
        """
        初始化状态图
        
        参数:
            schema: dict，定义状态的结构和每个字段的 reducer
                   例如: {"messages": add_reducer, "count": last_value}
                   
        schema 的作用:
            1. 定义状态中有哪些字段
            2. 定义每个字段如何合并并行写入（通过 reducer）
        """
        self.schema = dict(schema)  # 状态 schema
        self.nodes = {}             # 节点映射: 节点名 -> 节点函数
        self.edges = {}             # 固定边: 起点 -> [终点列表]
        self.branches = {}          # 条件边: 起点 -> (路由函数, 映射表)
    
    def add_node(self, name, fn):
        """
        添加一个节点
        
        参数:
            name: str，节点名称（唯一标识符）
            fn: 函数，节点函数，签名为 fn(state) -> updates
                - state: 完整的当前状态（dict）
                - updates: 部分更新（dict），只包含要修改的字段
        
        节点函数的契约:
            1. 接收完整 state（但不应该修改它！）
            2. 返回部分更新（增量），不是整个新状态
            3. 例如: {"messages": [新消息]} 而不是整个 state
        """
        if name in (START, END):
            raise ValueError(f"节点名不能是保留字 {START} 或 {END}")
        self.nodes[name] = fn
        return self  # 支持链式调用
    
    def add_edge(self, start, end):
        """
        添加一条固定边：start 节点跑完后无条件激活 end 节点
        
        参数:
            start: str，起点节点名（或 START）
            end: str，终点节点名（或 END）
        
        使用场景:
            确定的流程，例如:
            - add_edge(START, "model")  # 从入口进入 model 节点
            - add_edge("tools", "model")  # tools 跑完后必然回到 model
        """
        if start not in self.edges:
            self.edges[start] = []
        self.edges[start].append(end)
        return self
    
    def add_conditional_edges(self, start, router, mapping=None):
        """
        添加条件边：start 节点跑完后，根据 router 的返回值决定去哪
        
        参数:
            start: str，起点节点名
            router: 函数，签名为 router(state) -> next_node_name(s)
                   - 输入当前状态
                   - 返回字符串（单个下一节点）或列表（多个下一节点）
            mapping: dict 或 None，将 router 返回值映射到实际节点名
                    例如: {"continue": "tools", "end": END}
                    如果为 None，router 必须直接返回节点名
        
        使用场景:
            需要动态决定流程的地方，例如:
            - Agent 判断是否需要调用工具
            - 多路分支（如不同类型的错误走不同处理流程）
        
        示例:
            def should_continue(state):
                last_msg = state["messages"][-1]
                # 如果最后一条消息有工具调用，返回 "tools"
                # 否则返回 END
                return "tools" if last_msg.tool_calls else END
            
            graph.add_conditional_edges(
                "model", 
                should_continue,
                {"tools": "tools", END: END}
            )
        """
        self.branches[start] = (router, mapping or {})
        return self
    
    def compile(self, checkpointer=None):
        """
        编译图，返回可执行的 CompiledGraph
        
        参数:
            checkpointer: 检查点存储器（R3 章会讲），用于持久化
        
        返回:
            CompiledGraph 实例，可以调用 .invoke() 或 .stream() 执行图
        
        编译做什么？
            将声明式的图结构（节点、边、schema）转换为可执行的引擎
        """
        from .pregel import CompiledGraph
        return CompiledGraph(self, checkpointer=checkpointer)
```

**三种连接方式总结:**

1. **固定边** (`add_edge`)：无条件跳转
   ```python
   graph.add_edge("A", "B")  # A 跑完后必然进入 B
   ```

2. **条件边** (`add_conditional_edges`)：动态决定下一步
   ```python
   graph.add_conditional_edges("A", router, mapping)
   # A 跑完后调用 router(state)，根据返回值决定去哪
   ```

3. **入口** (`add_edge(START, ...)")：指定图的起点
   ```python
   graph.add_edge(START, "first_node")  # 从 START 虚拟节点连到第一个真实节点
   ```

**节点函数的契约极简**

```python
def call_model(state):
    """
    节点函数示例
    
    参数:
        state: dict，完整的当前状态
               例如: {"messages": [...], "count": 3}
    
    返回:
        dict，只包含要更新的字段（增量更新）
        例如: {"messages": [ai_message]}
        不需要返回整个 state，引擎会自动用 reducer 合并
    """
    # 读取需要的状态
    messages = state["messages"]
    
    # 执行逻辑
    ai = model.invoke(messages)
    
    # 只返回增量更新，不返回整个 state
    return {"messages": [ai]}
```

**为什么节点只返回增量？**

1. **关注点分离**：节点只管"我产出了什么"，不管"怎么合并到全局状态"
2. **支持并行**：多个节点各返回各的增量，引擎按固定顺序用 reducer 合并
3. **避免互相覆盖**：如果返回整个 state，并行节点会互相覆盖对方没改的字段

注意节点**只返回增量**,不返回整个新状态。怎么把增量并进全局状态?交给 Channel 的 reducer。节点不操心合并——这是关注点分离,也是下一节并行能成立的前提:回看 3.3 那个 bug,根源正是节点直接改了共享状态;只要节点严守"读 state、返回新增量、绝不原地改",漏洞一就从源头消失了。

## 3.5 Pregel / BSP 引擎:一步步驱动这张图

到了本章的核心。零件齐了:Channel(带版本的值)、Reducer(怎么合并)、StateGraph(图的声明)。现在造那台**把图跑起来的机器**。

我会用一个特殊的方式讲解：**先写最简单能跑的版本（有bug），再一步步修复**。这样你能看到每个设计决策背后的真实原因。

### 第 0 版:最朴素的想法（12行代码）

忘掉"BSP""超步"这些词。如果让你从零写一个"执行图"的引擎，你会怎么想？

**最朴素的想法：**
1. 从入口开始跑第一批节点
2. 跑完后看边连到哪，把下一批节点记下来
3. 再跑下一批...
4. 直到没有下一批了

把这个想法写成代码，真的只要 12 行：

```python
def run_v0(graph, channels, input):
    """
    最朴素的图执行引擎
    
    参数:
        graph: StateGraph，包含节点和边的定义
        channels: dict，{channel名: Channel实例}，存储状态
        input: dict，初始输入，例如 {"messages": [Human("你好")]}
    """
    # 步骤1: 把初始输入写进 channels
    for k, v in input.items():
        channels[k].update([v])  # 注意：update 接收列表
    
    # 步骤2: 从 START 的边找到第一批节点
    active = graph.edges[START][:]  # 例如 ["model"]
    
    # 步骤3: 主循环 - 只要还有节点要跑就继续
    while active:
        next_active = []  # 用于收集下一批
        
        # 步骤4: 运行这一批的每个节点
        for node in active:
            # 4.1 构造当前状态（从所有 channel 读值）
            state = {k: c.value for k, c in channels.items()}
            
            # 4.2 调用节点函数
            updates = graph.nodes[node](state)
            
            # 4.3 ⚠️ 立刻提交写入（问题就在这！）
            for k, v in (updates or {}).items():
                channels[k].update([v])
            
            # 4.4 根据边找下一批节点
            next_targets = resolve_next(graph, node, state)
            next_active += [t for t in next_targets if t != END]
        
        # 步骤5: 进入下一轮
        active = next_active
```

**这 12 行就是引擎的骨架！** 后面所有优化都在这个基础上改。

**先注意两个亮点：**

1. **循环不在代码里，在图的边里**
   ```python
   # 没有 while True 写死循环
   # 循环靠边实现：
   # add_edge("tools", "model")  ← 这条边让 tools 跑完后又激活 model
   # model 又进 active，while 下一圈又跑它
   # 直到条件边返回 END，active 变空，while 退出
   ```

2. **它能正确跑单链和带环图**
   ```python
   # 单链: START → A → B → END
   # 带环: START → model ⟲ tools → model → END
   # 都没问题！
   ```

### 第 1 版:v0 的致命缺陷 - 一旦并行就出 bug

v0 有个要命的隐患，就藏在这一行：

```python
for k, v in (updates or {}).items():
    channels[k].update([v])  # ← 立刻提交！
```

**当 `active` 里只有一个节点时**（单链、带环），没问题。

**当 `active` 里有多个节点时**（并行），灾难来了！

#### 问题场景：三个节点并行查天气

```python
# 图定义：
# START → [北京, 上海, 广州] → END
# 三个节点同时从 START 激活，应该并行运行

active = ["北京", "上海", "广州"]
```

如果天真地改成线程池并行：

```python
with ThreadPoolExecutor() as pool:
    for node in active:
        pool.submit(run_node, node)  # 三个线程同时跑
```

**会触发 3.3 的两个 bug！**

让我们用**慢动作回放**看看到底发生了什么：

#### Bug 重现：丢失更新（漏洞一）

假设改成给计数器加一：

```python
# 共享状态
channels = {"count": Channel(last_value, 0)}

# 三个节点，各给 count +1
def node_a(state):
    return {"count": state["count"] + 1}

def node_b(state):
    return {"count": state["count"] + 1}

def node_c(state):
    return {"count": state["count"] + 1}

# 期望：count 最终是 3
# 实际：可能是 1、2 或 3！
```

**时序分析：**

```
时间线         线程A              线程B              线程C           channels["count"]
──────────────────────────────────────────────────────────────────────────
t1         读 state              
           count = 0                                                  value=0
           
t2                           读 state
                             count = 0                               value=0
                             
t3         计算 0+1=1                                                value=0

t4                                             读 state
                                               count = 0             value=0
                                               
t5         update([1])                                               value=1 ✓
           
t6                           计算 0+1=1                               value=1

t7                                             计算 0+1=1             value=1
           
t8                           update([1])                             value=1 ✗ (A的更新被覆盖了！)

t9                                             update([1])           value=1 ✗ (A和B都被覆盖了！)

最终: count = 1，丢失了 2 次更新！
```

**为什么会这样？**

因为 B 和 C 在"A 读取"之后、"A 写回"之前也读到了旧值 0。三个线程基于同一个旧值计算，写回时互相覆盖。

这就是经典的**丢失更新（Lost Update）**问题。

#### Bug 重现：乱序合并（漏洞二）

假设改成追加列表：

```python
channels = {"results": Channel(add_reducer, [])}

# 三个节点查天气
def fetch_beijing(state):
    time.sleep(0.03)  # 慢
    return {"results": ["北京:5度"]}

def fetch_shanghai(state):  
    time.sleep(0.01)  # 快
    return {"results": ["上海:12度"]}

def fetch_guangzhou(state):
    time.sleep(0.02)  # 中
    return {"results": ["广州:22度"]}

# 期望：results = ["北京:5度", "上海:12度", "广州:22度"]
#      (按声明顺序)
# 实际：results = ["上海:12度", "广州:22度", "北京:5度"]  
#      (按网速快慢)
```

**时序分析：**

```
时间线    北京(0.03s)        上海(0.01s)        广州(0.02s)       results
───────────────────────────────────────────────────────────────────────
t=0      开始查询          开始查询            开始查询           []

t=0.01                    查询完成！                             []
                          update(["上海"])                        ["上海"] ✓

t=0.02                                       查询完成！          ["上海"]
                                             update(["广州"])     ["上海","广州"] ✓

t=0.03   查询完成！                                              ["上海","广州"]  
         update(["北京"])                                        ["上海","广州","北京"] ✓

最终: ["上海", "广州", "北京"]  ← 顺序由网速决定！
```

**为什么会这样？**

因为谁先跑完谁先调 `update()`，合并顺序由线程完成速度决定，而不是声明顺序。

换个网络环境，顺序又变了：
```
运行1: ["上海", "广州", "北京"]
运行2: ["北京", "上海", "广州"]  ← 碰巧北京网快了
运行3: ["广州", "上海", "北京"]  ← 又变了
```

**不可复现！**

### 问题的本质：执行和提交混在一起

v0 的根本问题是：**"执行节点" 和 "提交写入" 搅在一起**。

```python
# v0 的做法：
for node in active:
    updates = run_node(node)       # 执行
    channels.update(updates)       # 立刻提交 ← 问题！
```

当并行时：
- **执行阶段**：三个节点读写同一组 channels，互相干扰（漏洞一）
- **提交阶段**：谁先完成谁先提交，顺序不确定（漏洞二）

**解决方法：把它俩拆开！**

### 第 2 版:BSP 的核心思想 - 三段式 + 同步屏障

LangGraph 借鉴了 Google Pregel 的 **BSP(Bulk Synchronous Parallel, 整体同步并行)** 模型。

**核心思想：把"执行+提交"拆成严格分开的三段，中间隔一道屏障。**

```
一个超步 (Super-Step) 的三段式：

  ┌─────────────────────────────────────────────────────────┐
  │  ① 规划阶段 (Plan)                                        │
  │     从 active 中挑出真实节点 → tasks                       │
  └─────────────────────────────────────────────────────────┘
                           ↓
  ┌─────────────────────────────────────────────────────────┐
  │  ② 执行阶段 (Execute)                                     │
  │     • 所有节点【并行】执行                                 │
  │     • 每个节点拿到【独立副本】dict(snapshot)               │
  │     • 写入【先攒着】不提交                                 │
  └─────────────────────────────────────────────────────────┘
                           ↓
             ═════════════════════════════
             ║   同步屏障 (Barrier)      ║
             ║   等所有节点都跑完         ║
             ═════════════════════════════
                           ↓
  ┌─────────────────────────────────────────────────────────┐
  │  ③ 提交阶段 (Commit)                                      │
  │     • 按【tasks 固定顺序】收集写入                         │
  │     • 用 reducer 合并进 channels                          │
  │     • 版本号 +1                                           │
  └─────────────────────────────────────────────────────────┘
                           ↓
              计算下一批 active，进入下一个超步
              如果 active 为空，循环结束
```

### BSP 如何堵死两个漏洞？

让我们逐个击破：

#### 堵漏洞一：丢失更新

**v0 的问题：** 节点直接读写共享的 channels，B 可能读到 A 写之前的旧值。

**BSP 的解决：**

```python
# ② 执行阶段：

# 第1步：创建状态快照
snapshot = {k: c.value for k, c in channels.items()}
# 此时 snapshot = {"count": 0}

# 第2步：每个节点拿独立副本
state_a = dict(snapshot)  # 节点A的副本
state_b = dict(snapshot)  # 节点B的副本  
state_c = dict(snapshot)  # 节点C的副本

# 第3步：并行执行
# A: state_a["count"] = 0, 返回 {"count": 1}
# B: state_b["count"] = 0, 返回 {"count": 1}  ← B看到的还是0，但没关系！
# C: state_c["count"] = 0, 返回 {"count": 1}

# 第4步：写入先攒着，不立刻提交
writes = {"count": [1, 1, 1]}  # 收集了三个写入
```

**关键点：**
- B 确实读到了 A 写之前的旧值 0，**但这是对的**！
- 因为在 BSP 模型里，**本超步所有节点就该看同一份快照**
- A 的结果要等到下一个超步才对别人可见

**竞态被"定义掉"了** —— 不是修复 bug，而是重新定义了正确行为。

#### 堵漏洞二：乱序合并

**v0 的问题：** 谁先跑完谁先 update，合并顺序由网速决定。

**BSP 的解决：**

```python
# ② 执行阶段：节点可以乱序完成

# t=0.01s: 上海完成 → 先放进 futures 结果
# t=0.02s: 广州完成 → 再放进 futures 结果  
# t=0.03s: 北京完成 → 最后放进 futures 结果

results = {
    "上海": {"results": ["上海:12度"]},
    "广州": {"results": ["广州:22度"]},
    "北京": {"results": ["北京:5度"]}
}

# ③ 提交阶段：不管谁先完成，按 tasks 固定顺序收集

tasks = ["北京", "上海", "广州"]  # 声明时的顺序

writes = {"results": []}
for name in tasks:  # ← 关键：按 tasks 顺序，不是完成顺序
    writes["results"].append(results[name]["results"])

# writes = {"results": [["北京:5度"], ["上海:12度"], ["广州:22度"]]}
# 顺序固定！与完成快慢无关
```

**关键点：**
- 上海虽然最快完成，但合并时还是按声明顺序排在第二
- **同步屏障**把"并行的乱"和"合并的定"隔开

### 图解：BSP 的时序

用三城查天气的例子画个时序图：

```
超步流程：     ①规划         ②执行(并行)              ③提交(屏障后)
            选出tasks     各拿独立快照副本          按固定顺序合并
──────────────────────────────────────────────────────────────
            tasks=
            [北京,       ┌─北京─■ 0.03s完成─┐
            上海,        │ 看snapshot       │
            广州]  ─────▶├─上海───■ 0.01s完成┤─屏障─▶ for name in tasks:
                        │ 看同一份         │          reduce(北京)
                        ├─广州──■ 0.02s完成│          reduce(上海)
                        │ 互相看不见       │          reduce(广州)
                        └──────────────────┘
                               ▲                      results channel
                        所有节点跑完才能                version +1
                        越过同步屏障 ║                    ↓
                                              ["北京:5度",
                                               "上海:12度",  
                                               "广州:22度"]
                                                顺序固定！
```

**两个"无关"：**
- **执行阶段**：节点互相看不见（各拿副本，无数据竞争）
- **提交阶段**：合并顺序与完成快慢无关（广州最快，合并照样排第三）

**屏障的作用：**
```
屏障左边：可以乱序狂奔（并行加速）
   ║
   ║  ← 这道墙把"乱"和"定"隔开
   ║
屏障右边：一律按固定顺序结算（确定性）
```

### BSP 给出的核心能力：确定性并发

**确定性并发 = 可以并行加速，但结果和串行跑一样可复现**

```python
# 串行跑：
result_serial = run_serial([北京, 上海, 广州])
# → ["北京:5度", "上海:12度", "广州:22度"]

# BSP 并行跑：
result_bsp = run_bsp_parallel([北京, 上海, 广州])  
# → ["北京:5度", "上海:12度", "广州:22度"]

# 结果完全一样！
assert result_serial == result_bsp
```

这就是 LangGraph 比"随手开几个线程跑节点"硬核的地方。

> **真实历史：** LangGraph 的前身曾因并发节点行为不确定而出过生产事故。你在 3.3 亲手跑出的那个输出 `2` 和 `['上海','广州','北京']` 的 bug，就是它当年踩的坑。正是这个问题促使团队选择 BSP —— 从根本上消除数据竞争。

### 第 3 版：把三段式落成代码

现在把 BSP 的三段式翻译成可执行的代码。我会逐段讲解，让你看清每行代码是怎么堵住 bug 的。

#### 阶段②：执行（Execute）—— `_run_superstep` 函数

这是 BSP 的核心，负责并行执行节点，但不提交写入。

```python
# tinygraph/pregel.py
def _run_superstep(self, tasks, channels):
    """
    执行一个超步的第②阶段：并行执行节点，攒写入不提交
    
    参数:
        tasks: list[str]，本超步要执行的节点名列表
              例如: ["北京", "上海", "广州"]
        channels: dict，{channel名: Channel实例}
    
    返回:
        writes: dict，收集到的所有写入
               格式: {channel名: [写入1, 写入2, ...]}
               例如: {"results": ["北京:5度", "上海:12度", "广州:22度"]}
    
    这个函数做三件事（对应堵住两个漏洞）：
        1. 创建状态快照 → 所有节点看同一份输入
        2. 并行执行，各拿副本 → 堵漏洞一（丢失更新）
        3. 按 tasks 固定顺序收集 → 堵漏洞二（乱序合并）
    """
    
    # ═══════════════════════════════════════════
    # 第1步：创建状态快照
    # ═══════════════════════════════════════════
    # 从所有 channel 读取当前值，构造一个 dict
    snapshot = self._state_snapshot(channels)
    # 例如: {"messages": [msg1, msg2], "count": 3}
    
    # 这个 snapshot 是本超步所有节点的"共同输入"
    # 就像给每个节点拍了张照片：你们都看这张照片，不要看实时画面
    
    writes = {}  # 用于收集所有节点的写入
    
    # ═══════════════════════════════════════════
    # 第2步：执行节点（单节点优化 vs 并行执行）
    # ═══════════════════════════════════════════
    
    if len(tasks) == 1:
        # ─────────────────────────────────────
        # 优化：只有一个节点时不开线程池
        # ─────────────────────────────────────
        # 为什么？线程池有开销（创建线程、调度等）
        # 单节点时直接调用更快
        
        node_fn = self.graph.nodes[tasks[0]]
        updates = node_fn(dict(snapshot))  # ← dict(snapshot) 创建副本
        self._collect_writes(updates, writes)
        
    else:
        # ─────────────────────────────────────
        # 并行：多个节点用线程池
        # ─────────────────────────────────────
        
        with ThreadPoolExecutor(max_workers=len(tasks)) as pool:
            
            # 为每个节点提交一个任务
            futures = {}
            for name in tasks:
                node_fn = self.graph.nodes[name]
                
                # 关键：每个节点拿 dict(snapshot) —— 独立副本
                # dict() 创建浅拷贝，外层 dict 是新的
                future = pool.submit(node_fn, dict(snapshot))
                futures[future] = name
            
            # 等待所有任务完成，收集结果
            results = {}
            for future in futures:
                name = futures[future]
                results[name] = future.result()  # 阻塞等待
            
            # ═══════════════════════════════════════════
            # 第3步：按 tasks 固定顺序收集结果
            # ═══════════════════════════════════════════
            # ⚠️ 这是堵漏洞二的关键代码！
            
            # 错误做法（会导致乱序）：
            # for future in as_completed(futures):  ← 谁先完成先收谁
            #     ...
            
            # 正确做法（确定性）：
            for name in tasks:  # ← 按 tasks 顺序，不是完成顺序
                self._collect_writes(results[name], writes)
    
    return writes


def _collect_writes(self, updates, writes):
    """
    辅助函数：将节点返回的 updates 收集到 writes 字典中
    
    参数:
        updates: dict 或 None，节点返回的部分更新
                例如: {"messages": [新消息]}
        writes: dict，用于累积所有写入
               格式: {channel名: [写入列表]}
    
    作用:
        将 updates 按 channel 分类累积到 writes 中
        
    例子:
        updates = {"messages": [msgA]}
        writes = {"messages": [msg0]}  # 之前已有一个写入
        
        调用后:
        writes = {"messages": [msg0, msgA]}  # 追加新写入
    """
    if not updates:
        return
    
    for key, value in updates.items():
        if key not in writes:
            writes[key] = []
        writes[key].append(value)
```

**代码里堵漏洞的具体位置：**

```python
# 堵漏洞一（丢失更新）的代码：
snapshot = self._state_snapshot(channels)  # 所有节点看同一份快照
updates = node_fn(dict(snapshot))          # 每个节点拿独立副本

# 堵漏洞二（乱序合并）的代码：
for name in tasks:                         # 按声明顺序
    self._collect_writes(results[name], writes)  # 不是按完成顺序
```

#### 关于 `dict(snapshot)` 的深入理解

```python
# dict(snapshot) 是浅拷贝
snapshot = {"messages": [msg1, msg2], "count": 3}

# 三个节点各自的副本
state_a = dict(snapshot)
state_b = dict(snapshot)  
state_c = dict(snapshot)

# 外层 dict 是独立的：
state_a["count"] = 999  # 只改 state_a，不影响 state_b 和 state_c

# 但内层对象是共享的：
state_a["messages"].append(new_msg)  # ⚠️ 危险！
# state_b 和 state_c 的 messages 也会变（因为引用同一个列表对象）
```

**为什么我们的引擎不出事？**

因为节点严守契约：**只读 state，返回新对象，从不原地修改**。

```python
# ✅ 正确的节点写法：
def my_node(state):
    messages = state["messages"]  # 读取引用
    new_msg = create_message()    # 创建新消息
    return {"messages": [new_msg]}  # 返回新列表，不修改 state["messages"]

# ❌ 错误的节点写法：
def bad_node(state):
    state["messages"].append(new_msg)  # 原地修改！会影响其他节点
    return {"messages": state["messages"]}
```

所以"节点必须纯净"不是风格建议，是**确定性的前提**。

#### 阶段③：提交（Commit）—— `_commit` 函数

屏障之后，统一提交所有写入。

```python
# tinygraph/pregel.py
@staticmethod
def _commit(channels, writes):
    """
    执行一个超步的第③阶段：提交写入到 channels
    
    参数:
        channels: dict，{channel名: Channel实例}
        writes: dict，本超步收集的所有写入
               格式: {channel名: [写入列表]}
               例如: {"messages": [msgA, msgB], "count": [5]}
    
    作用:
        将 writes 中的写入按固定顺序合并到 channels 中
        
    确定性保证（两层顺序）:
        1. 外层：channel 按名字排序 (sorted)
        2. 内层：Channel.update 按 writes[key] 的顺序调用 reducer
        
    为什么要两层排序？
        外层排序：确保不同 channel 的处理顺序固定
        内层顺序：由 _run_superstep 的 tasks 顺序保证
    
    示例:
        writes = {
            "messages": [msgA, msgB],  # 按 tasks 顺序收集的
            "count": [5]
        }
        
        执行后:
        - messages channel: 
            reducer(current, msgA) → reducer(result, msgB) → version+1
        - count channel:
            reducer(current, 5) → version+1
    """
    # 外层：按 channel 名排序
    # 为什么要排序？确保处理顺序确定
    # 否则 dict 的迭代顺序在 Python 3.7 前是不确定的
    for key in sorted(writes.keys()):
        if key in channels:
            # 调用 Channel.update
            # 它会按 writes[key] 的顺序调用 reducer
            channels[key].update(writes[key])
            
            # Channel.update 内部：
            # v = channel.value
            # for w in writes[key]:  # ← 按列表顺序
            #     v = reducer(v, w)
            # channel.value = v
            # channel.version += 1
```

**两层顺序都被钉死：**

```python
# 外层：按 channel 名排序
for key in sorted(writes.keys()):  # ["count", "messages", "results"]

# 内层：按写入顺序（由 tasks 顺序保证）
channels[key].update(writes[key])
# writes[key] = [写入1, 写入2, 写入3]
# 这个顺序是 _run_superstep 中 for name in tasks 保证的
```

**整个提交过程零随机性！**

这就是为什么 v0 那个会输出 `2`、`['上海','广州','北京']` 的程序，换成 BSP 后永远输出 `3`、`['北京','上海','广州']`。

### 第 3 版:主循环——v0 骨架 + 三段式 + 配件

现在把执行、提交串回 v0 的骨架。下面这段就是 v0 的真身,只多了三样东西:防死循环的安全阀、`yield`(流式)、把"算下一批"写细:

```python
# tinygraph/pregel.py
# 这是本章范围内的完整主循环（去掉了第4/5章的检查点与中断分支）
def stream(self, input, stream_mode="updates"):
    """
    执行图并流式产出中间状态
    
    参数:
        input: dict，初始输入
              例如: {"messages": [HumanMessage("北京天气?")]}
        stream_mode: str，流式模式
                    - "values": 每个超步产出完整状态快照
                    - "updates": 产出每个超步的元信息（步骤号、运行的节点等）
    
    产出 (yield):
        每个超步执行完后 yield 一次，外部可以逐步观察执行过程
        
    工作流程:
        1. 初始化 channels
        2. 写入初始输入
        3. 主循环：while active 不为空
           - 规划：选出本步要跑的节点
           - 执行：并行跑节点（_run_superstep）
           - 提交：合并写入（_commit）
           - 流式产出当前状态
           - 计算下一批 active
        4. 循环结束
    """
    # ====== 步骤 1: 初始化 channels ======
    # 根据 schema 创建所有 channel 实例
    channels = self._fresh_channels()
    
    # ====== 步骤 2: 写入初始输入 ======
    # 将 input 当作 START 节点的输出，写入 channels
    init = {}
    self._collect_writes(input, init)  # 转换为 {channel: [value]} 格式
    self._commit(channels, init)       # 提交到 channels
    
    # ====== 步骤 3: 计算入口的下一批节点 ======
    # 从 START 虚拟节点的出边获取第一批要运行的节点
    active = self._resolve_next(START, self._state_snapshot(channels))
    
    # ====== 步骤 4: 主循环 ======
    steps = 0  # 超步计数器
    while active:  # ← 就是 v0 的 while active，只要还有节点要跑就继续
        steps += 1
        
        # 安全阀：防止死循环
        if steps > self.recursion_limit:
            raise RecursionError(
                f"达到递归限制 {self.recursion_limit}。"
                f"这通常表示图中有死循环，或者需要增大 recursion_limit。"
            )
        
        # ① 规划 Plan：从 active 中挑出真实节点（排除 START/END）
        tasks = self._plan(active)
        if not tasks:
            break  # 没有真实节点了，结束
        
        # ② 执行 Execute：并行跑节点，攒写入
        writes = self._run_superstep(tasks, channels)
        
        # ③ 提交 Commit：屏障后，确定性合并
        self._commit(channels, writes)
        
        # ====== 流式产出 ======
        state_now = self._state_snapshot(channels)  # 获取当前状态快照
        
        # ④ 计算下一批 active：看这批节点的边连到谁
        active = self._next_active(tasks, state_now)
        
        # 产出当前状态（每个超步一次）
        if stream_mode == "values":
            yield state_now  # 只产出状态
        else:
            # 产出更多元信息：步骤号、运行的节点、当前状态
            yield {"__step__": steps, "nodes": tasks, "state": state_now}


def _fresh_channels(self):
    """
    根据 schema 创建新的 channels
    
    返回:
        dict，{channel名: Channel实例}
        
    示例:
        schema = {"messages": add_reducer, "count": last_value}
        → channels = {
            "messages": Channel(reducer=add_reducer, value=None, version=0),
            "count": Channel(reducer=last_value, value=None, version=0)
          }
    """
    return {
        name: Channel(reducer=reducer, value=None)
        for name, reducer in self.graph.schema.items()
    }


def _state_snapshot(self, channels):
    """
    从所有 channels 读取当前值，构造状态快照
    
    参数:
        channels: dict，{channel名: Channel实例}
    
    返回:
        dict，当前状态，例如: {"messages": [...], "count": 3}
    """
    return {name: ch.value for name, ch in channels.items()}


def _plan(self, active):
    """
    规划阶段：从 active 中筛选出真实节点
    
    参数:
        active: list，下一批要激活的节点名
               可能包含 START、END 等虚拟节点
    
    返回:
        list，真实节点名列表（排除虚拟节点）
        
    为什么要筛选？
        START 和 END 是虚拟节点，不对应实际的节点函数
        只有真实节点才能被执行
    """
    return [name for name in active if name not in (START, END)]
```

**和 v0 逐行对比:**
- `while active` 没变 —— 这就是引擎的心脏
- v0 里"跑这一批 + 立刻提交"那一坨，拆成了：
  ```python
  # v0 (有bug):
  for node in active:
      updates = graph.nodes[node](state)
      for k, v in updates.items():
          channels[k].update([v])  # 立刻提交
  
  # v2 (正确):
  tasks = self._plan(active)           # ① 规划
  writes = self._run_superstep(tasks)  # ② 执行（攒着）

  ```
- v0 里 `next_active += resolve_next(...)` 变成了 `_next_active()`
- 多出来的 `yield`、`recursion_limit` 是挂在骨架上的配件

**关键理解：循环不在代码里，在图的边里**

这段代码里没有任何 `while True` 写死的 Agent 循环。那个"反复调模型"的环是怎么来的?

```python
# 假设图结构：
# model ─(条件边)→ tools ─(固定边)→ model
#       └─(条件边)→ END

# 超步 1: active = ["model"]

tasks = ["model"]
writes = _run_superstep(["model"])   # model 返回最终答案

```

**环靠边连回来转起来，引擎本身不知道有环。**

**`_resolve_next` 和 `_next_active`：算下一批的核心**

```python
def _resolve_next(self, node, state):
    """
    解析单个节点的下一批节点（同时处理固定边和条件边）
    
    参数:
        node: str，当前节点名
        state: dict，当前状态
    
    返回:
        list，该节点指向的下一批节点名
        
    工作原理:
        1. 检查固定边：如果有 add_edge(node, target)，直接加入
        2. 检查条件边：如果有 add_conditional_edges(node, router, mapping)
           调用 router(state)，根据返回值和 mapping 决定下一批
    """
    nxt = []
    
    # 处理固定边
    for target in self.graph.edges.get(node, []):
        nxt.append(target)
    
    # 处理条件边
    if node in self.graph.branches:
        router, mapping = self.graph.branches[node]
        
        # 调用路由函数，获取返回值
        result = router(state)
        
        # router 可能返回字符串（单个）或列表（多个）
        choices = result if isinstance(result, list) else [result]
        
        # 根据 mapping 映射到实际节点名
        for c in choices:
            # 如果 mapping 中有映射，使用映射值；否则直接用原值
            nxt.append(mapping.get(c, c) if mapping else c)
    
    return nxt


def _next_active(self, tasks, state):
    """
    计算下一批要激活的节点（本超步所有节点的下一批，去重去 END）
    
    参数:
        tasks: list，本超步运行的节点名列表
        state: dict，当前状态
    
    返回:
        list，下一批要激活的节点名（去重，去除 END）
        
    工作原理:
        对本超步的每个节点，调用 _resolve_next 获取它的下一批
        合并所有结果，去重，去除 END
    """
    out = []
    for name in tasks:
        # 获取这个节点的下一批
        for target in self._resolve_next(name, state):
            # 过滤 END 和已存在的（去重）
            if target != END and target not in out:
                out.append(target)
    return out
```

**示例：跟踪条件边的工作过程**

```python

    "model",
```

**`invoke` 只是 `stream` 的封装**

```python
def invoke(self, input):
    """
    执行图并返回最终状态（非流式）
    
    参数:
        input: dict，初始输入
    
    返回:
        dict，最终状态
        
    实现:
        调用 stream() 拿到所有快照，返回最后一个
    """
    last = {}
    for snap in self.stream(input, stream_mode="values"):
        last = snap  # 不断更新，保留最后一个
    return last
```

### recursion_limit 到底在数什么

```python
# 在主循环中：
steps = 0
while active:
    steps += 1
    if steps > self.recursion_limit:  # 默认 25
        raise RecursionError("达到递归限制")
```

**它数的是超步数**,不是"模型调用次数",也不是"工具调用次数"。

**示例分析：**

```python
# 示例 B 的执行轨迹：
超步1: model 节点（第1次调模型，返回 tool_calls）
超步2: tools 节点（执行工具）
超步3: model 节点（第2次调模型，返回最终答案）
# 总共 3 个超步，调了 2 次模型，1 次工具

# 如果模型连查 5 轮天气：
超步1: model → 超步2: tools → 超步3: model →
超步4: tools → 超步5: model → 超步6: tools →
超步7: model → 超步8: tools → 超步9: model →
超步10: tools → 超步11: model (最终答案)
# 总共 11 个超步，调了 6 次模型，5 次工具
```

所以 LangGraph 默认的 `recursion_limit=25` 不等于"最多调 25 次模型",而是"最多推进 25 个超步"——一个反复调工具的 Agent,实际能调模型约一半次数（因为 model 和 tools 交替，每次各占一个超步）。

**为什么会碰到 `GraphRecursionError`？**

```python
# 场景1：真的死循环
def bad_router(state):
    return "model"  # 永远返回 model，形成 model→model→model 的死循环

# 场景2：任务确实需要很多步
# 例如：复杂的代码调试任务，模型需要尝试 20+ 次才能修好 bug
# 这种情况可以增大 recursion_limit
graph.compile(recursion_limit=50)

# 场景3：重复调用检测失败
# 模型一直调用同一个工具，但没有被及时识别出来
```

**调大 recursion_limit 要谨慎:**

```python
# ❌ 不好的做法：
graph.compile(recursion_limit=1000)  # 太大，出问题可能烧很多钱

# ✅ 更好的做法：
# 1. 先保持默认值 25
# 2. 配合第 1 章的"重复调用检测"提前识别真死循环
# 3. 如果确实需要更多步骤，小幅增加（如 50、100）
# 4. 监控实际使用的超步数，了解任务的真实需求

def repeat_detector(state):
    """检测是否在重复调用同一个工具"""
    messages = state["messages"]
    tool_calls = [m.tool_calls for m in messages if hasattr(m, "tool_calls")]
    # 如果最近3次都调用同一个工具，可能是死循环
    if len(tool_calls) >= 3:
        recent = tool_calls[-3:]
        if all(tc == recent[0] for tc in recent):
            return END  # 提前终止
    return "tools"
```

**recursion_limit 是兜底防线:**

它的作用是防止**失控成本**——如果真的进入死循环，至少在 25 步后停下来，而不是无限烧钱。调大它等于把"失控成本上限"一起放大。

生产中更稳的策略是：
1. **保持较低的 recursion_limit**（如 25-50）
2. **在业务逻辑里提前检测循环**（如上面的 repeat_detector）
3. **记录实际使用的超步数**，了解任务特征
4. **对确实需要多步的任务，单独提高限制**

### 跟着引擎跑一遍(示例 B 的逐超步追踪)

读代码停在"字面理解"。真正吃透引擎的方法是**亲手在纸上当一次引擎**。拿示例 B 那张带环图,把每个超步里引擎内部发生的事逐格摊开。

**图结构:**
```
START → model →(should_continue)→ tools → model → ... → END
                       └────────────────────────────→ END
```

**节点函数:**
```python
def call_model(state):
    """调用模型节点"""
    messages = state["messages"]
    response = model.invoke(messages)  # 调用真实模型
    return {"messages": [response]}    # 返回增量

def call_tools(state):
    """执行工具节点"""
    messages = state["messages"]
    last = messages[-1]  # 最后一条消息（AI 消息，带 tool_calls）
    tool_results = []
    for tool_call in last.tool_calls:
        result = execute_tool(tool_call)  # 执行工具
        tool_results.append(ToolMessage(content=result, ...))
    return {"messages": tool_results}

def should_continue(state):
    """路由函数：决定继续还是结束"""
    last = state["messages"][-1]
    # 如果最后一条消息有 tool_calls，去 tools
    # 否则去 END
    return "tools" if hasattr(last, "tool_calls") and last.tool_calls else END
```

**初始输入:**
```python
input = {"messages": [HumanMessage("北京今天适合穿什么?")]}
```

**messages channel 使用 `add_reducer`**（追加模式）

**每一行就是 `stream()` 的 while 循环转一圈:**

| 阶段 | `active` | `tasks` | `_run_superstep` 干了什么 | `writes` | `_commit` 后 `messages` | 版本 | `_next_active` 算出 |
|---|---|---|---|---|---|---|---|
| **初始化** | — | — | 将 input 写入 channels | `{messages:[Human]}` | `[Human("北京...?")]` | v1 | `_resolve_next(START)`→`["model"]` |
| **超步 1** | `["model"]` | `["model"]` | model 看到 `[Human]`,<br>第1次调模型,<br>返回 AI 消息带 tool_calls | `{messages:[AI]}` | `[Human, AI(tool_calls=[get_weather(...)])]` | v2 | `should_continue`:有 tool_calls→`["tools"]` |
| **超步 2** | `["tools"]` | `["tools"]` | tools 看到 `[Human,AI]`,<br>执行 get_weather(北京),<br>返回 Tool 消息 | `{messages:[Tool]}` | `[Human, AI, Tool("5°C,有风")]` | v3 | 固定边 `tools→model`→`["model"]` |
| **超步 3** | `["model"]` | `["model"]` | model 看到 `[Human,AI,Tool]`,<br>第2次调模型,<br>返回最终答案（无 tool_calls） | `{messages:[AI]}` | `[Human, AI, Tool, AI("记得保暖")]` | v4 | `should_continue`:无 tool_calls→`END`→`[]` |
| **结束** | `[]` | — | while 条件为空→退出 | — | 最终 4 条消息 | v4 | — |

**逐超步详解:**

**初始化阶段:**
```python
channels = {"messages": Channel(add_reducer, None, v0)}
self._commit(channels, {"messages": [Human("北京...?")]})
# messages.update([Human]) → messages.value = [Human], version = 1
active = ["model"]  # START 的出边
```

**超步 1: 第一次调模型**
```python
# ① 规划
tasks = ["model"]

# ② 执行
snapshot = {"messages": [Human]}  # 当前快照
updates = call_model(snapshot)    # 调模型，返回 {"messages": [AI(tool_calls=[...])]}
writes = {"messages": [AI(tool_calls=[...])]}

# ③ 提交
channels["messages"].update([AI])  # [Human] + [AI] = [Human, AI], version = 2

# ④ 下一批
should_continue({"messages": [Human, AI]})  # AI 有 tool_calls → "tools"
active = ["tools"]
```

**超步 2: 执行工具**
```python
# ① 规划
tasks = ["tools"]

# ② 执行
snapshot = {"messages": [Human, AI]}  # 当前快照（超步1提交后的状态）
updates = call_tools(snapshot)         # 执行工具，返回 {"messages": [Tool("5°C...")]}
writes = {"messages": [Tool("5°C...")]}

# ③ 提交
channels["messages"].update([Tool])  # [Human, AI] + [Tool] = [Human, AI, Tool], version = 3

# ④ 下一批
# tools 有固定边指向 model
active = ["model"]
```

**超步 3: 第二次调模型**
```python
# ① 规划
tasks = ["model"]

# ② 执行
snapshot = {"messages": [Human, AI, Tool]}  # 当前快照（包含工具结果）
updates = call_model(snapshot)               # 第2次调模型，返回最终答案
writes = {"messages": [AI("记得保暖")]}

# ③ 提交
channels["messages"].update([AI])  # [Human, AI, Tool] + [AI] = [Human, AI, Tool, AI], version = 4

# ④ 下一批
should_continue({"messages": [..., AI("记得保暖")]})  # AI 无 tool_calls → END
active = []  # 过滤掉 END
```

**循环结束:**
```python
while active:  # active = [] → False
    # 退出循环
```

**把这张表和第 1 章那个 `while` 循环对照,会有"原来如此"的瞬间:**

1. **超步 1、3 都跑 `model`** —— 同一节点被跑两次
   - 在 `while` 循环里：这是"回到开头再调一次模型"
   - 在引擎里：纯粹是因为"`tools` 的边把 `model` 又激活了"
   - **节点可被反复激活,这就是环**

2. **决定"继续还是停"的是那两次 `should_continue`**
   - 它就是 `while` 的循环条件
   - 只不过从代码里的 `if` 变成了图里的条件边

3. **版本从 v1 涨到 v4**
   - 每超步成功提交一次 +1
   - 注意我们**没有去比较这个版本来决定跑谁**
   - 我们看 `_next_active` 解析边的结果
   - 版本在这里只默默记账,R3 章存检查点才派上用场

### 边触发 vs 版本订阅:把两种模型算给你看

3.2 节埋了伏笔:真实 LangGraph 用"版本订阅"触发节点,我们用"边"。这是你将来读真实源码最容易卡住的点,所以这里不下结论,**把两种模型放在同一个例子上一步步算**,你自己看它们何时一样、何时不一样。

先把两套规则讲明白:

- **边触发(我们的)**:节点 X 跑完,看 X 的出边连到谁,谁就进下一批。规则作用在"节点"上。
- **版本订阅(LangGraph)**:每个节点**订阅**若干 channel,并记下"我上次跑时,这些 channel 的版本是多少"。每个超步结束,引擎扫一遍:**谁订阅的 channel 里,有任何一个的当前版本 > 它上次见过的版本,谁就进下一批**。规则作用在"channel 版本"上。

**例一:就用示例 B,看它俩给出一样的序列。**

LangGraph 编译时会把边翻译成订阅:`model` 订阅"入口/tools 写的 channel",`tools` 订阅"model 写的 channel"(都通过 `messages` 体现)。逐超步算版本订阅:

```
超步1后: messages v2(model 刚写)。tools 上次见 v0 < v2 → tools 触发。  ← 和边触发同样得到 [tools]
超步2后: messages v3(tools 刚写)。model 上次见 v1 < v3 → model 触发。  ← 同样得到 [model]
超步3后: messages v4(model 刚写)。但 should_continue→END,无人再订阅 → 停。 ← 同样停
```

序列完全一致:`model→tools→model→停`。**对单链/带环这种"一个写、一个读"的结构,两种模型产出的执行序列逐超步相同**。所以你用边把整个引擎吃透,绝不亏。

**例二:一个边触发会算错、版本订阅才对的结构——扇入(fan-in)。**

现在看一个我们的简化引擎**会出问题**的图。节点 D 需要 A、B、C 三个上游**都完成**后才跑一次(典型的"汇总"节点):

```
   A ─┐
   B ─┼─→ D     D 想要的语义:A、B、C 全到齐,我才跑,且只跑一次
   C ─┘
```

A、B 耗时短(0.1s),C 耗时长(0.5s),分别落在不同超步完成。看两种模型的行为:

```
边触发(我们的):
  A 跑完 → 它的边指向 D → D 进下一批 → D 立刻跑了!(此时 C 还没好,D 看到的是半成品)
  ……C 跑完 → 边又指向 D → D 又跑一次。
  结果:D 被触发了【多次】,且第一次跑时数据不全。语义错了。

版本订阅(LangGraph):
  D 订阅 A、B、C 写的那个 channel,但 LangGraph 允许声明 "要等多个上游"。
  引擎看到 D 的上游里还有没涨版本的(C 还没写)→ D 不触发。
  直到 C 也写了、三个上游版本都涨过 → D 才触发,且只触发一次,数据齐全。
```

这就是两种模型**真正分叉**的地方:边触发是"上游任一完成就推进",天然适合链和环,但表达"等齐多个上游"很笨拙(你得手动加一个计数节点去攒);版本订阅把"我依赖哪些 channel、它们都更新了吗"做进了触发机制本身,所以扇入是免费的。

> 这正是我们简化引擎的主要代价,也是为什么真实 LangGraph 选版本订阅:它要支持任意 DAG 的扇入/扇出,边触发表达不了"等齐"。我们的目标是讲清 Agent 那条"model↔tools"的链+环,边触发足够且更直观,所以我们接受这个代价。

把对照收成一张表:

| | 我们的简化引擎(tinygraph) | 真实 LangGraph |
|---|---|---|
| "下一批跑谁"由谁决定 | **边**:解析当前节点的出边 | **版本订阅**:节点订阅的 channel 版本涨了就触发 |
| 环怎么表达 | 显式连回边 `add_edge("tools","model")` | 自然涌现:写 channel → 订阅者版本落后 → 被触发 |
| 扇入(等齐多个上游) | **表达不了**,得手动加计数节点 | 免费:引擎等所有订阅的 channel 都更新 |
| 版本号的作用 | 只用于检查点存档/恢复 | **核心**:既是触发依据,也用于检查点 |
| 上手门槛 | 低,像流程图 | 高,心智模型更抽象 |

机制层面补一句事实:真实 LangGraph 编译 `StateGraph` 时,会把你写的边翻译成 channel 订阅关系——**边其实是"控制 channel"上的订阅**。所以在它那里,"边"是表层 API,"版本订阅"是底层机制,两者统一。我们只实现了表层、跳过了底层翻译,这是 tinygraph 最主要的简化,第 11 章会再提。

## 3.6 跑起来:并行执行 + 带环 Agent

`examples/03_graph_runtime.py` 有两个示例。

### 示例 A:并行执行,验证确定性合并

三个节点都从 `START` 激活,落在同一超步并行执行,写入按固定顺序经 `add_reducer` 合并:

```python
schema = {"results": add_reducer}
g = StateGraph(schema)
for name, fn in [("bj", fetch_beijing), ("sh", fetch_shanghai), ("gz", fetch_guangzhou)]:
    g.add_node(name, fn)
    g.add_edge(START, name)    # 三个都从 START 激活 → 同一超步并行
    g.add_edge(name, END)
final = g.compile().invoke({"results": []})
# → ['北京: 5°C', '上海: 12°C', '广州: 22°C']  顺序永远可复现
```

这正是 3.3 那个会输出 `['上海','广州','北京']` 的 bug 的"修好版"——同样并行、同样三个节点,但 BSP 让结果永远是声明顺序。你可以把两段并排跑,亲眼对比。

### 示例 B:带环的 Agent 图(Agent 的图化版本)

```python
schema = {"messages": add_reducer}
g = StateGraph(schema)
g.add_node("model", call_model)        # 调模型
g.add_node("tools", call_tools)        # 执行工具
g.add_edge(START, "model")
g.add_conditional_edges("model", should_continue, {"tools": "tools", END: END})
g.add_edge("tools", "model")           # ← 这条边构成环

def should_continue(state):
    last = state["messages"][-1]
    return "tools" if getattr(last, "tool_calls", None) else END
```

把这个图和第 1 章的 `while` 循环对照,逻辑完全等价:`while` 的循环条件 = 条件边 `should_continue`;`while` 的循环体 = `model`、`tools` 两节点;`tools→model` 那条边 = `while` 的"回到开头"。我们没改 Agent 的逻辑,只是把它从"焊死的控制流"翻译成"数据化的图"。

运行 `python 03_graph_runtime.py`:

```
=== 示例 A:并行执行 ===
合并后的 results: ['北京: 5°C', '上海: 12°C', '广州: 22°C']

=== 示例 B:带环的 Agent 图 ===
  HumanMessage(content='北京今天适合穿什么?', ...)
  AIMessage(tool_calls=[get_weather({'city': '北京'})])
  ToolMessage(content='5°C, 有风', ...)
  AIMessage('北京今天 5°C 有风,记得保暖。')

最终回答: 北京今天 5°C 有风,记得保暖。
```

环正确转了:`model`(要调工具)→ `tools` → `model`(给出回答)→ `END`。

## 3.7 我们得到了什么,还差什么

把 Agent 图化后,R1 章六个局限已解决或具备解决基础:

- **状态显式化**:`messages` 现在是 channel 里可序列化的值,不再藏在局部变量 → 持久化有了基础(R3 章兑现)。
- **并行**:同一超步的节点自动并行且确定性合并 → 局限三解决。
- **流式的骨架**:每超步后 `yield`,外部能逐步观察 → 局限四有了着力点(R4 章扩展)。
- **控制流外置**:`while` 变成了图加引擎 → "步骤之间的空隙"出现了。

还差临门几脚:

- 状态显式了,但**还没真存盘**。进程一退 channel 还是没了。→ R3 章:Checkpointer。
- 还**不能在超步之间暂停几天再恢复**。→ R4 章:interrupt。
- 流式现在只能看"状态快照",还**没有逐 token、多模式**。→ R4 章扩展。

注意这些剩下的事现在都**有地方下手了**——因为状态显式、执行离散。这正是图运行时的价值:它把"不可能"变成了"在 `yield` 那一行加几行代码"。

## 3.8 自测:你真的能手写引擎了吗

不看答案先想——能答上来,说明你不是"读过"而是"拥有"了这个引擎。

**Q1. 为什么节点只返回部分更新(`{"messages":[ai]}`),而不是整个新 state?**

<details><summary>想清楚再展开</summary>

因为合并是 channel(reducer)的职责,不是节点的。节点只管"我产出了什么",怎么并进全局状态由 reducer 定。好处:一是节点不用知道别的字段长什么样、不用搬运它没碰的字段;二是并行的多个节点各返回各的增量,引擎按固定顺序喂 reducer,天然支持确定性合并。若节点返回整个 state,两个并行节点就会互相覆盖对方没改的字段——这正是 3.3 漏洞一的另一种形式。
</details>

**Q2. 3.3 里那个不做隔离的引擎为什么会输出 `2`?BSP 的哪一个具体设计修好了它?**

<details><summary>想清楚再展开</summary>

输出 `2` 是丢失更新:b 在 a "读 0" 之后、"写回 1" 之前也读到了 0,于是两人都写回 1,a 的加法被覆盖。BSP 用两件事修它:一是执行阶段每个节点拿 `dict(snapshot)` 独立副本,b 改自己的副本不影响 a;二是写入先攒着、屏障后由引擎统一提交,而不是节点各自直接改 channel。两者合起来,"a 写、b 读到 a 写前的值"这件事本超步内不再有意义——同超步所有节点本就该看同一份输入。
</details>

**Q3. 三个节点并行写同一个 `add_reducer` channel,为什么结果可复现?具体哪两行保证的?**

<details><summary>想清楚再展开</summary>

两道保险:`_run_superstep` 里 `for name in tasks` 按固定 tasks 顺序收集结果,而非"谁先完成先收谁";`_commit` 里 `for key in sorted(writes.keys())` 按 channel 名排序提交。所以无论三个线程谁先跑完,喂给 reducer 的写入顺序都固定。这就是确定性并发:并行加速,但合并顺序与执行快慢无关。
</details>

**Q4. 我们的引擎里没有任何 `while True`,Agent 的循环怎么转起来的?**

<details><summary>想清楚再展开</summary>

靠**边**。`add_edge("tools","model")` 这条回边让 `tools` 跑完后 `_next_active` 把 `model` 重新算进下一批。`stream()` 的 `while active:` 只要还有激活节点就继续,于是 `model→tools→model` 自然循环,直到 `should_continue` 返回 `END`、过滤后下一批为空、`while` 退出。控制流从"代码里的 while"变成"数据里的图"。
</details>

**Q5. 给你一个"D 要等 A、B、C 三个上游都完成才跑一次"的扇入图,我们的边触发引擎会怎样?为什么真实 LangGraph 不会?**

<details><summary>想清楚再展开</summary>

我们的引擎会出错:A 一跑完,它指向 D 的边就把 D 激活,D 立刻跑了——此时 C 还没好,D 看到半成品;之后 C 跑完又把 D 激活一次,D 被跑了多次。边触发是"上游任一完成就推进",表达不了"等齐"。真实 LangGraph 用版本订阅:D 订阅 A/B/C 写的 channel,引擎看到还有上游没涨版本就不触发 D,直到三个都写过才触发且只触发一次。要在我们的引擎里实现扇入,得手动加一个计数节点去攒——这就是 3.5 末尾说的简化代价。
</details>

**Q6(进阶). 把 `_run_superstep` 收集结果改成"谁先完成先收"(`as_completed`),会破坏什么?会更快吗?**

<details><summary>想清楚再展开</summary>

破坏**确定性**:`add_reducer` 的追加顺序变成依赖线程调度,同样输入可能得到 `[北京,广州,上海]` 或 `[广州,北京,上海]`,不可复现,调试和检查点恢复都会出问题——就是 3.3 漏洞二。"更快"也几乎是错觉:同步屏障要求本超步**所有**节点跑完才能提交,总耗时由最慢节点决定,和收集顺序无关。这正是 LangGraph 当年踩的"并发节点非确定性"的坑。
</details>

## 3.9 本章小结

- 我们把 Agent 从"while 循环"改写成"**State + Channel + Node + Edge + 引擎**"的图,并把引擎从 12 行的 v0 一步步长到能跑的成品。
- **Channel = 值 + 单调版本号**。真实 LangGraph 靠"订阅的 channel 版本是否更新"触发节点;我们简化成**用边触发**,版本号只用于检查点。3.5 末把两种模型算在同一个例子上:单链/环上完全等价,扇入处才分叉。
- **Reducer** 决定并行写入如何合并;`last_value`(覆盖)、`add_reducer`(追加,对应 `add_messages`)。我们先**亲手跑出**了不做隔离时的丢失更新和乱序两个 bug,再看 BSP 怎么修。
- **BSP 超步**分三段:规划 → 并行执行(独立副本、攒写入)→ 屏障后确定性提交(固定顺序 reducer)。这给出**确定性并发**:并行加速但结果可复现。
- **控制流从代码里的 `while` 变成数据里的图**;循环靠"把边连回去"表达,引擎本身没有 `while True`。能独立推出 3.5 那张逐超步追踪表,就算真正掌握了引擎。
- 每个超步后的 `yield` 是**步骤之间的空隙**——流式、检查点、中断都挂这里。本章先做流式,下一章用它做存档。
