## 4.1 检查点要存什么

### 核心概念：检查点 (Checkpoint)

**检查点是什么？**
检查点就像游戏里的"存档点"，记录某一时刻 Agent 的完整状态，包括：
- 数据（聊天历史、中间结果）
- 进度（执行到哪一步了）

**为什么需要检查点？**

第 1 章的循环有个致命问题：
```python
def agent_loop():
    messages = []  # 数据在这
    while True:    # 进度在这（指令指针）
        ai = model.invoke(messages)
        ...
        # 问题：程序一退出，数据和进度都没了
```

进度藏在 Python 的指令指针里，无法保存。即使保存了 `messages`，也不知道"循环执行到哪了"。

**图运行时的解决方案：**
R2 章把"执行进度"从指令指针变成了数据：
```python
# 进度现在是普通数据
next_nodes = ["model"]  # 下一步要跑 model 节点

# 数据也是显式的
state = {"messages": [...], "count": 3}
```

两者都是可序列化的 Python 对象，可以保存到磁盘、数据库，随时恢复！

### 检查点的数据结构

R1 章想清楚了一件关键的事:持久化需要的不是"数据",而是"数据 + 执行到哪一步了"。现在图运行时把这两样都显式化了,所以一份检查点要存**四样东西**。

这是 `checkpoint.py` 的第一块,**完整、可直接敲下来**:

```python
# tinygraph/checkpoint.py
import json, time, uuid
from dataclasses import dataclass, field, asdict, is_dataclass
from typing import Any, Dict, List, Optional

@dataclass
class Checkpoint:
    """
    图状态在某一超步结束时的完整快照
    
    类比：游戏存档
    - 保存了游戏角色的所有属性（数据）
    - 保存了当前关卡和位置（进度）
    - 可以随时读档恢复
    """
    
    # ============ 基本标识 ============
    thread_id: str
    """
    执行线 ID，标识这是哪个会话的检查点
    
    是什么？
        一个字符串，例如 "user-123" 或 "session-abc"
        
    为什么需要？
        多个用户同时使用 Agent，每个用户的会话要隔离
        就像游戏存档槽：槽1、槽2、槽3...
        
    例子：
        thread_id="user-alice"  # Alice 的会话
        thread_id="user-bob"    # Bob 的会话（完全独立）
    """
    
    checkpoint_id: str
    """
    本检查点的唯一 ID
    
    是什么？
        一个唯一字符串，例如 "1702345678901-a1b2c3d4"
        
    为什么需要？
        1. 唯一标识每个存档点
        2. 通过 parent_id 串成链，支持"时间旅行"
        
    生成方式：
        时间戳 + 随机UUID：既保证唯一，又大致有序
    """
    
    # ============ 核心数据（四样东西）============
    
    channel_values: Dict[str, Any]
    """
    ① 各 channel 的当前【值】
    
    是什么？
        状态数据的实际内容
        例如: {"messages": [...], "count": 3}
        
    为什么需要？
        这是"数据"部分，Agent 运行产生的所有信息
        
    类比：
        游戏角色的血量、装备、金币...
    """
    
    channel_versions: Dict[str, int]
    """
    ② 各 channel 的【版本号】
    
    是什么？
        每个 channel 被修改的次数
        例如: {"messages": 5, "count": 2}
        
    为什么需要？
        1. 真实 LangGraph 靠版本号触发节点（R2章讲过）
        2. 确保恢复后的状态和存盘时逐位相同
        3. 可以检测状态是否被修改
        
    例子：
        messages 版本=5：表示被成功修改过 5 次
        恢复时连版本一起恢复，完全一致
    """
    
    next_nodes: List[str]
    """
    ③ 下一超步要激活哪些节点（执行进度）
    
    是什么？
        一个节点名列表，例如 ["model"] 或 []
        
    为什么需要？
        这就是"执行到哪一步了"！
        - ["model"]: 下次恢复时要跑 model 节点
        - []: 执行已结束，没有下一步了
        
    关键点：
        这就是第 1 章循环里无法保存的"指令指针"
        现在它变成了一个普通的字符串列表！
        
    类比：
        游戏存档里的"当前任务"、"下一个关卡"
    """
    
    parent_id: Optional[str] = None
    """
    ④ 父检查点 ID（用于串成链）
    
    是什么？
        上一个检查点的 checkpoint_id
        
    为什么需要？
        把同一个 thread 的所有检查点串成链：
        
        检查点1 ← 检查点2 ← 检查点3 ← 检查点4
                  (parent)  (parent)  (parent)
        
    用途：
        1. 列出完整历史：看看 Agent 走过的所有步骤
        2. 时间旅行：回到过去的某个检查点重新执行
        
    例子：
        检查点A: parent_id=None （第一个，没有父节点）
        检查点B: parent_id=A的ID （B 是 A 的子节点）
        检查点C: parent_id=B的ID （C 是 B 的子节点）
    """
    
    # ============ 辅助信息 ============
    step: int = -1
    """超步编号，用于调试和显示"""
    
    ts: float = field(default_factory=time.time)
    """时间戳，记录检查点创建时间"""
    
    # ============ 序列化方法 ============
    
    def to_json(self) -> str:
        """
        序列化：把检查点转成 JSON 字符串，可以存到文件或数据库
        
        返回：
            一行 JSON 字符串
            例如: '{"thread_id":"t1","checkpoint_id":"...","channel_values":{...}}'
        """
        return json.dumps(asdict(self), default=_json_default, ensure_ascii=False)
    
    @staticmethod
    def from_json(s: str) -> "Checkpoint":
        """
        反序列化：从 JSON 字符串还原检查点对象
        
        参数：
            s: JSON 字符串
            
        返回：
            Checkpoint 对象
        """
        return Checkpoint(**json.loads(s))


def new_checkpoint_id() -> str:
    """
    生成新的检查点 ID
    
    返回：
        格式: "时间戳-uuid"
        例如: "1702345678901-a1b2c3d4"
        
    设计考虑：
        1. 时间前缀：同一 thread 内检查点大致按时间有序
        2. uuid 后缀：确保全局唯一（即使同一毫秒创建多个）
    """
    timestamp = int(time.time() * 1000)  # 毫秒级时间戳，13位数字
    random_part = uuid.uuid4().hex[:8]   # UUID 的前8个字符
    return f"{timestamp:013d}-{random_part}"
```

### 理解四个核心字段

让我们用一个具体例子理解这四个字段：

```python
# Agent 执行到第 3 个超步后的检查点
checkpoint = Checkpoint(
    thread_id="user-alice",
    checkpoint_id="1702345678901-abc123",
    
    # ① 数据：当前状态
    channel_values={
        "messages": [
            HumanMessage("北京天气?"),
            AIMessage(tool_calls=[...]),
            ToolMessage("5度")
        ],
        "count": 3
    },
    
    # ② 版本：各 channel 被修改的次数
    channel_versions={
        "messages": 3,  # messages 被修改过 3 次
        "count": 1      # count 被修改过 1 次
    },
    
    # ③ 进度：下一步要跑哪个节点
    next_nodes=["model"],  # 下次恢复时要跑 model 节点
    
    # ④ 链接：指向上一个检查点
    parent_id="1702345678900-xyz789",
    
    step=3,
    ts=1702345678.9
)
```

**恢复时会发生什么？**

```python
# 1. 从磁盘读取检查点
checkpoint = load_checkpoint("user-alice")

# 2. 恢复状态
channels["messages"].value = checkpoint.channel_values["messages"]
channels["messages"].version = checkpoint.channel_versions["messages"]

# 3. 恢复进度
active = checkpoint.next_nodes  # ["model"]

# 4. 继续执行
while active:
    # 从 model 节点开始继续跑...
    ...
```

### 关键对比：循环 vs 图运行时

| | 第 1 章循环 | R2 章图运行时 |
|---|---|---|
| **数据存储** | 局部变量 `messages` | 显式 dict `state` |
| **数据能否保存** | ❌ 程序退出就没了 | ✅ 可序列化，随时保存 |
| **执行进度** | 指令指针（不可见） | `next_nodes` 列表 |
| **进度能否保存** | ❌ 无法序列化 | ✅ 普通字符串列表 |
| **能否断点恢复** | ❌ 不可能 | ✅ 完全支持 |

**这就是为什么"把控制流取出来变成图"之后，持久化突然变得轻而易举**——进度从"代码里的位置"变成了"数据里的值"。

(`_json_default` 负责把消息这种 dataclass 转成 JSON,4.4 节再写。)

(对照真实框架:LangGraph 的 `StateSnapshot` 有 `values`、`next`(空元组表示完成)、`config`、`metadata`、`parent_config`、`tasks` 等字段,和我们的几乎一一对应。真实实现默认用 MsgPack 序列化、可加密;我们用 JSON 求直观。)

## 4.2 thread_id:一条独立的执行线

### 什么是 thread_id？

**thread_id 是执行线的唯一标识符**，用于隔离不同会话的数据。

**类比理解：**
- 想象一个多人在线游戏，每个玩家有自己的存档槽
- `thread_id` 就是存档槽的编号："玩家1"、"玩家2"...
- 每个玩家的进度完全独立，互不干扰

**为什么需要 thread_id？**

场景：多个用户同时使用你的 Agent
```python
# 用户 Alice 和 用户 Bob 同时在聊天
用户 Alice: "北京天气怎么样？"
用户 Bob:   "上海有什么好吃的？"

# 如果没有 thread_id：
# Alice 和 Bob 的消息会混在一起！
messages = [
    HumanMessage("北京天气?"),  # Alice 的
    HumanMessage("上海美食?"),  # Bob 的
    AIMessage("北京5度..."),     # 给 Alice 的回复
    AIMessage("上海有小笼包...") # 给 Bob 的回复
]
# 乱套了！

# 有了 thread_id：
thread_id="alice" 的 messages: [HumanMessage("北京天气?"), AIMessage("北京5度...")]
thread_id="bob" 的 messages:   [HumanMessage("上海美食?"), AIMessage("上海有小笼包...")]
# 各管各的，井水不犯河水
```

### 如何使用 thread_id？

调用时通过 config 传入:

```python
# Alice 的会话
config_alice = {"configurable": {"thread_id": "alice"}}
app.invoke({"messages": [HumanMessage("北京天气?")]}, config_alice)

# Bob 的会话（完全独立）
config_bob = {"configurable": {"thread_id": "bob"}}
app.invoke({"messages": [HumanMessage("上海美食?")]}, config_bob)
```

**关键特性：**

1. **同一 thread_id 多次调用 = 续接历史**
   ```python
   # 第 1 次调用
   config = {"configurable": {"thread_id": "alice"}}
   app.invoke({"messages": [HumanMessage("你好")]}, config)
   # 保存检查点：messages=[Human("你好"), AI("你好，我是助手")]
   
   # 第 2 次调用（同一个 thread_id）
   app.invoke({"messages": [HumanMessage("我叫Alice")]}, config)
   # 自动加载上次的检查点，续接：
   # messages=[Human("你好"), AI("你好，我是助手"), Human("我叫Alice"), ...]
   ```
   
   这就是"对话记忆"的实现方式！

2. **不同 thread_id = 完全隔离**
   ```python
   thread_alice = {"configurable": {"thread_id": "alice"}}
   thread_bob = {"configurable": {"thread_id": "bob"}}
   
   # Alice 和 Bob 的会话完全独立
   # 就像两个独立的游戏存档
   ```

### thread_id 的命名建议

```python
# ✅ 好的命名
thread_id = f"user-{user_id}"           # 绑定用户
thread_id = f"session-{session_id}"     # 绑定会话
thread_id = f"task-{task_id}"           # 绑定任务

# ❌ 不好的命名
thread_id = "default"                   # 所有用户共用，会混乱
thread_id = str(random.random())        # 随机生成，无法续接
```

### 重要警告：同一 thread_id 的并发问题

这里有一个生产环境会咬人的问题:**同一 `thread_id` 的并发调用**。

**问题场景：**

我们的模型假设：一条 thread 是**严格串行**的执行线
- 第 1 次调用完成 → 保存检查点 A
- 第 2 次调用从检查点 A 继续

但生产环境中，用户可能：
- 手快连点两下
- 前端自动重试
- 移动端网络抖动重发

导致两个请求**同时**用同一个 `thread_id` 进来！

**Bug 演示：**

下面这段代码会重现这个问题——两个"请求"并发地基于同一检查点各跑各的、各自 `put`:

```python
import threading, time
from tinygraph.checkpoint import InMemorySaver, Checkpoint, new_checkpoint_id

# 创建内存存储
saver = InMemorySaver()

# 先放一个共同的起点检查点：count=0
saver.put(Checkpoint(
    thread_id="t1",
    checkpoint_id=new_checkpoint_id(),
    channel_values={"count": 0},
    channel_versions={"count": 1},
    next_nodes=["step"],
    step=0
))

def request(add):
    """模拟一个请求：读检查点 → 计算 → 保存新检查点"""
    
    # ① 两个请求都读到 count=0 这个检查点
    base = saver.get("t1")
    print(f"[请求 +{add}] 读到 count={base.channel_values['count']}")
    
    # ② 各自干活（这里有时间间隙，模拟网络/计算耗时）
    time.sleep(0.01)
    
    # ③ 各自计算新值
    new_values = dict(base.channel_values)
    new_values["count"] += add
    print(f"[请求 +{add}] 计算结果 count={new_values['count']}")
    
    # ④ 各自保存检查点
    saver.put(Checkpoint(
        thread_id="t1",
        checkpoint_id=new_checkpoint_id(),
        channel_values=new_values,
        channel_versions={"count": 2},
        next_nodes=[],
        step=1,
        parent_id=base.checkpoint_id
    ))
    print(f"[请求 +{add}] 保存完成")

# 启动两个并发请求
t1 = threading.Thread(target=request, args=(10,))  # 请求1：想 +10
t2 = threading.Thread(target=request, args=(1,))   # 请求2：想 +1
t1.start()
t2.start()
t1.join()
t2.join()

# 查看最终结果
final = saver.get("t1")
print(f"\n最终 count = {final.channel_values['count']}")
print(f"期望: 11 (0+10+1)")
print(f"实际: {final.channel_values['count']} ({'✗ 错误！' if final.channel_values['count'] != 11 else '✓'})")
```

**运行结果：**
```
[请求 +10] 读到 count=0
[请求 +1] 读到 count=0
[请求 +10] 计算结果 count=10
[请求 +1] 计算结果 count=1
[请求 +10] 保存完成
[请求 +1] 保存完成

最终 count = 1  ← 丢失了请求1的更新！
期望: 11 (0+10+1)
实际: 1 (✗ 错误！)
```

**为什么会这样？**

```
时间线    请求1 (+10)           请求2 (+1)          检查点 count
────────────────────────────────────────────────────────────
t1       读检查点 count=0                          0
t2                            读检查点 count=0      0
t3       计算 0+10=10                              0
t4                            计算 0+1=1            0
t5       保存 count=10                             10 ✓
t6                            保存 count=1          1  ✗ (覆盖了!)
```

后保存的检查点把先保存的覆盖掉了！

**真实 Agent 的灾难：**

如果这是真实 Agent，丢失的不仅是数字：
```python
# 请求1：模型返回要调用工具
messages = [Human("天气?"), AI(tool_calls=[...])]
# 保存检查点1

# 请求2：同时进来，也基于初始状态
messages = [Human("你好")]
# 保存检查点2，覆盖了检查点1

# 结果：AI 的 tool_calls 消息丢了！
# 下次恢复时 messages 链断裂
# model.invoke() 直接报错："找不到对应的工具调用"
```

### 解决方案

**方案1：应用层串行化（推荐）**
```python
# 用锁或队列确保同一 thread 串行处理
thread_locks = {}  # {thread_id: Lock}

def process_request(thread_id, input):
    if thread_id not in thread_locks:
        thread_locks[thread_id] = threading.Lock()
    
    with thread_locks[thread_id]:  # 同一 thread 排队
        return app.invoke(input, {"configurable": {"thread_id": thread_id}})
```

**方案2：数据库层并发控制**
```python
# 真实 LangGraph 的做法：
# - Postgres 后端：用行级锁或乐观锁
# - SQLite 后端：利用事务的串行特性
# 确保"同一 thread 同时只有一个 writer"
```

**方案3：检测并拒绝**
```python
# 简单但粗暴：检测到并发就拒绝
if is_thread_active(thread_id):
    raise ConflictError(f"Thread {thread_id} is busy")
```

### 关键原则

> **thread 是串行单元**
> 
> 一条 thread 在任何时刻只能有一个写操作。
> 
> 要么在应用层用锁/队列保证串行，
> 要么依赖后端的并发控制，
> 千万别假设"同一 thread 不会被并发访问"。

我们的教学实现没处理这点；真实 LangGraph 在 Postgres 后端用乐观锁或行级锁,确保"同一 thread 同时只有一个 writer"。落地要点是:thread 是串行单元,要么在应用层用锁或队列保证同一 thread 串行处理,要么依赖后端的并发控制,千万别假设"同一 thread 不会被并发访问"——上面那段代码就是反例。

## 4.3 Checkpointer 接口:内存版与 SQLite 版

### 是什么？

**Checkpointer(检查点存储器)** 是一个**抽象接口**，定义了"如何存取检查点"的三个核心操作：
- `put(checkpoint)` —— 保存一个检查点
- `get(thread_id, checkpoint_id=None)` —— 读取最新或指定的检查点
- `list(thread_id)` —— 列出某个thread的全部检查点历史（最新在前）

它的两个具体实现：
- **InMemorySaver** —— 存在内存里的 dict，进程结束就消失，适合开发调试
- **SqliteSaver** —— 存在 SQLite 数据库文件里，可跨进程持久化，适合生产环境

### 为什么？

**问题1：为什么需要一个接口，而不是直接写死用 SQLite？**

因为"何时存档"（引擎的逻辑）和"存到哪里"（存储介质的选择）是两个**正交**的关注点：
- 开发时你想快速迭代，不需要真数据库 → 用 `InMemorySaver`
- 生产环境要跨进程恢复 → 换成 `SqliteSaver`
- 分布式部署要多机共享 → 再换成 `PostgresSaver`

如果引擎里写死了 `conn.execute("INSERT INTO...")`，每次换存储就得改引擎代码。而有了接口：
```python
# 引擎只依赖接口
self.checkpointer.put(cp)   # 不关心背后是内存、SQLite 还是 Postgres

# 使用时按需选择
app = Pregel(..., checkpointer=InMemorySaver())      # 开发
app = Pregel(..., checkpointer=SqliteSaver("db.sqlite"))  # 生产
```

这就是经典的"机制与策略分离"：
- **机制（引擎）**：定义"在超步后存档、在入口处恢复"
- **策略（Checkpointer）**：决定"存进内存/SQLite/Postgres"

两者通过接口解耦，换存储零成本。

**问题2：为什么 `list` 要"最新在前"？**

因为最常见的操作是"拿最近几步的历史"（比如 UI 展示对话记录）。如果旧的在前，用户得翻到最后才能看到最新状态，体验很差。`list` 返回逆序列表 `[最新, 次新, ..., 最旧]`，取前 N 个就是最近 N 步。

### 怎么用？

#### 1. 基类定义接口契约

这是 `checkpoint.py` 的第二块代码：

```python
# tinygraph/checkpoint.py（接4.1节的 Checkpoint 类之后）

class BaseCheckpointSaver:
    """检查点存储器的抽象基类
    
    定义了三个核心操作，具体的存储介质（内存、SQLite、Postgres）
    通过继承这个基类来实现。
    """
    
    def put(self, checkpoint: Checkpoint) -> None:
        """保存一个检查点
        
        参数:
            checkpoint: 要保存的检查点对象
                - 包含 thread_id（存储的 key）
                - 包含 checkpoint_id（本次存档的唯一标识）
                - 包含完整的状态快照（值、版本、进度、父链接）
        
        注意: 永远是"追加"新检查点，不能原地修改已有的！
              这是"回到历史"能力的基础（见4.6节场景C）
        """
        raise NotImplementedError
    
    def get(self, thread_id: str, checkpoint_id: Optional[str] = None) -> Optional[Checkpoint]:
        """读取检查点
        
        参数:
            thread_id: 执行线ID
            checkpoint_id: 可选，指定要读哪个检查点
                - 如果是 None → 返回该 thread 的【最新】检查点
                - 如果指定了 → 返回该 thread 历史链中 id 匹配的那个
        
        返回:
            找到了 → Checkpoint 对象
            没找到 → None（比如 thread 不存在，或指定的 id 不在历史里）
        
        用途:
            - input=None 断点恢复: get(thread_id) 拿最新的
            - 回到历史某一步: get(thread_id, "cp_xxx") 拿指定的
        """
        raise NotImplementedError
    
    def list(self, thread_id: str) -> List[Checkpoint]:
        """列出某个 thread 的全部检查点历史
        
        参数:
            thread_id: 执行线ID
        
        返回:
            检查点列表，【最新在前】（逆时间序）
            - [0] 是最新的（对应最后一个超步）
            - [-1] 是最旧的（对应第一个超步）
            - 如果 thread 不存在，返回空列表 []
        
        用途:
            - UI 展示对话历史: 取前10个渲染
            - 找到某个特定状态: 遍历列表，按条件筛选
        """
        raise NotImplementedError
```

#### 2. 内存版实现：dict + list

**InMemorySaver** 用一个两层嵌套的数据结构：`{thread_id: [检查点列表]}`。

```python
class InMemorySaver(BaseCheckpointSaver):
    """内存存储实现：进程内快速读写，但重启即消失
    
    数据结构: self._store = {
        "thread-1": [cp0, cp1, cp2, ...],  # 按时间顺序追加
        "thread-2": [cp0, cp1, ...],
    }
    
    特点:
        优点: 读写快、无需依赖外部数据库、适合单元测试和开发
        缺点: 进程结束数据丢失、不能跨进程共享
    """
    
    def __init__(self):
        # {thread_id: [Checkpoint, Checkpoint, ...]}
        # 每个 thread 的检查点列表按写入顺序排列（旧 → 新）
        self._store: Dict[str, List[Checkpoint]] = {}
    
    def put(self, cp: Checkpoint) -> None:
        """追加一个新检查点到对应 thread 的列表尾部
        
        时间复杂度: O(1) —— 直接 append
        """
        # setdefault: 如果 cp.thread_id 不存在，先创建空列表
        # append: 追加到列表尾部（最新的在最后）
        self._store.setdefault(cp.thread_id, []).append(cp)
        
        # 注意: 这里是【追加】，不是【覆盖】！
        # 如果用 self._store[cp.thread_id] = [cp]，就会丢掉所有历史
    
    def get(self, thread_id: str, checkpoint_id: Optional[str] = None) -> Optional[Checkpoint]:
        """读取检查点
        
        两种模式:
            checkpoint_id=None → 返回最新的（列表最后一个）
            checkpoint_id="cp_xxx" → 从新往旧查找匹配的
        """
        # 拿到这个 thread 的检查点列表（可能不存在 → 空列表）
        chain = self._store.get(thread_id, [])
        
        if not chain:
            # thread 不存在或还没有任何检查点
            return None
        
        if checkpoint_id is None:
            # 没指定 id → 返回最新的（列表最后一个）
            return chain[-1]
        
        # 指定了 id → 从新往旧查找（reversed 让我们从尾部往前遍历）
        for cp in reversed(chain):
            if cp.checkpoint_id == checkpoint_id:
                return cp
        
        # 没找到匹配的 id
        return None
    
    def list(self, thread_id: str) -> List[Checkpoint]:
        """返回该 thread 的全部检查点，【最新在前】
        
        实现: 把存储的列表（旧→新）反转成（新→旧）
        """
        chain = self._store.get(thread_id, [])
        # reversed() 返回迭代器，list() 转成列表
        # 结果: [最新, 次新, ..., 最旧]
        return list(reversed(chain))
```

**关键细节**：
- `put` 永远是 `append`，不是 `self._store[thread_id] = [cp]`（那会清空历史）
- `get` 不指定id时返回 `chain[-1]`（最新的），因为 append 导致最新的在尾部
- `list` 要 `reversed()`，因为内部存储是旧→新，但接口契约要求新→旧

#### 3. SQLite 版实现：序列化到表

**SqliteSaver** 把检查点转成 JSON 字符串，存进一张简单的表。

```python
import sqlite3

class SqliteSaver(BaseCheckpointSaver):
    """SQLite 存储实现：持久化到文件，可跨进程恢复
    
    表结构:
        CREATE TABLE checkpoints (
            thread_id TEXT,        -- 哪条执行线
            checkpoint_id TEXT,    -- 本检查点的唯一ID
            step INTEGER,          -- 超步计数（用于排序）
            data TEXT,             -- 整个 Checkpoint 对象的 JSON 字符串
            PRIMARY KEY (thread_id, checkpoint_id)  -- 联合主键
        )
    
    特点:
        优点: 进程重启后数据仍在、单文件易备份、无需额外服务
        缺点: 并发写入性能有限、不适合多机分布式部署
    """
    
    def __init__(self, path: str = ":memory:"):
        """初始化数据库连接并创建表
        
        参数:
            path: 数据库文件路径
                - ":memory:" → 内存数据库（仅用于测试，关闭连接即消失）
                - "/tmp/demo.sqlite" → 文件数据库（真正持久化）
        """
        # 连接数据库（不存在会自动创建）
        self.conn = sqlite3.connect(path)
        
        # 创建表（如果已存在则跳过）
        self.conn.execute("""
            CREATE TABLE IF NOT EXISTS checkpoints (
                thread_id TEXT,
                checkpoint_id TEXT,
                step INTEGER,
                data TEXT,
                PRIMARY KEY (thread_id, checkpoint_id)
            )
        """)
        self.conn.commit()
    
    def put(self, cp: Checkpoint) -> None:
        """序列化检查点并插入表
        
        注意: INSERT OR REPLACE 的语义
            - 如果 (thread_id, checkpoint_id) 已存在 → 覆盖（但我们从不重复写同一id）
            - 如果不存在 → 插入新行
        """
        self.conn.execute(
            "INSERT OR REPLACE INTO checkpoints VALUES (?, ?, ?, ?)",
            (
                cp.thread_id,          # 第1列: thread_id
                cp.checkpoint_id,      # 第2列: checkpoint_id
                cp.step,               # 第3列: 超步计数（用于排序）
                cp.to_json()           # 第4列: 整个对象 → JSON 字符串
            )
        )
        self.conn.commit()  # 立即提交（确保写入磁盘）
    
    def get(self, thread_id: str, checkpoint_id: Optional[str] = None) -> Optional[Checkpoint]:
        """从表中查询并反序列化检查点
        
        两种查询:
            checkpoint_id=None → ORDER BY rowid DESC LIMIT 1（最新插入的）
            checkpoint_id="xxx" → WHERE 匹配指定 id
        """
        if checkpoint_id is None:
            # 查询该 thread 的最新一条记录
            # rowid 是 SQLite 的隐藏自增列，DESC 让最新的排最前
            row = self.conn.execute(
                "SELECT data FROM checkpoints WHERE thread_id=? ORDER BY rowid DESC LIMIT 1",
                (thread_id,)
            ).fetchone()
        else:
            # 查询指定 checkpoint_id 的记录
            row = self.conn.execute(
                "SELECT data FROM checkpoints WHERE thread_id=? AND checkpoint_id=?",
                (thread_id, checkpoint_id)
            ).fetchone()
        
        if row is None:
            # 没找到匹配的记录
            return None
        
        # row[0] 是 data 列（JSON 字符串）
        # Checkpoint.from_json() 反序列化回对象（见4.1节）
        return Checkpoint.from_json(row[0])
    
    def list(self, thread_id: str) -> List[Checkpoint]:
        """查询该 thread 的全部检查点，【最新在前】
        
        ORDER BY rowid DESC: 让最后插入的排最前
        """
        rows = self.conn.execute(
            "SELECT data FROM checkpoints WHERE thread_id=? ORDER BY rowid DESC",
            (thread_id,)
        ).fetchall()
        
        # 每一行的 row[0] 是 JSON 字符串，反序列化成对象
        return [Checkpoint.from_json(row[0]) for row in rows]
```

**为什么用 `rowid` 排序而不是 `step`？**

因为 `step` 只在单个 thread 内单调递增，但如果回到历史分叉（见4.6场景C），分叉出来的新 thread 可能复用旧的 `step` 值。`rowid` 是 SQLite 的全局自增主键，严格按插入顺序递增，能正确反映"哪个检查点是最后写入的"。

#### 4. 两者的对比

| 特性 | InMemorySaver | SqliteSaver |
|------|---------------|-------------|
| **存储介质** | 内存 dict | SQLite 文件 |
| **持久化** | 进程结束即消失 | 写入磁盘，重启后仍在 |
| **跨进程** | 不支持（每个进程独立） | 支持（多进程读同一文件） |
| **读写速度** | 极快（纳秒级） | 快（微秒级，有磁盘I/O） |
| **适用场景** | 单元测试、开发调试 | 生产环境、需要恢复 |
| **并发控制** | 无（Python GIL保护） | SQLite 事务保护 |

**重要：两者遵守同一接口**

引擎代码里只有这一行：
```python
self.checkpointer.put(cp)  # 不关心是内存还是 SQLite
```

创建引擎时传入不同的实现即可切换：
```python
# 开发时用内存版
app = Pregel(..., checkpointer=InMemorySaver())

# 生产时换成 SQLite 版 —— 引擎代码一个字都不用改！
app = Pregel(..., checkpointer=SqliteSaver("/data/app.db"))
```

这就是"面向接口编程"的威力：**机制与策略分离**，换存储零成本。

### 对照真实框架

真实 LangGraph 的存储接口更丰富：
- `InMemorySaver` / `SqliteSaver` / `PostgresSaver` 三种实现
- 接口方法名略有不同：`put` / `get_tuple` / `list` / `put_writes`
- 还有异步版本：`aget` / `aput` / `alist`
- **生产环境官方推荐 PostgresSaver**，因为：
  - 支持真正的行级锁（解决4.2节的并发问题）
  - 更强的并发写入能力
  - 支持分布式部署（多个 worker 共享一个 Postgres）

我们的教学实现只做了内存版和 SQLite 版，已经足够理解核心原理。要扩展到 Postgres，只需：
1. 继承 `BaseCheckpointSaver`
2. 在 `put`/`get`/`list` 里换成 `psycopg2` 的 SQL 语句
3. 传给引擎即可 —— 接口保证了上层无需改动

## 4.4 序列化:消息对象与 JSON 的往返

### 是什么？

**序列化（Serialization）** 是把内存里的"活对象"转成可存储的字节流的过程，**反序列化（Deserialization）** 是把字节流还原回对象。

在我们的场景里：
- 内存里有 `AIMessage(content="你好", tool_calls=[...])`（Python 对象）
- 要存进 SQLite 必须转成字符串 → 序列化成 JSON `{"content": "你好", "tool_calls": [...], "__type__": "AIMessage"}`
- 从数据库读回来时，JSON 字符串 → 反序列化回 `AIMessage` 对象

这个"对象 → JSON → 对象"的往返，必须做到**逐字段相同**，否则恢复出来的状态就是坏的。

### 为什么？

**问题1：为什么不能直接 `json.dumps(msg)`？**

因为 JSON 只认识基本类型（`dict`/`list`/`str`/`int`/`bool`/`None`），不认识我们自定义的 dataclass。直接序列化会报错：

```python
import json
from tinygraph.messages import AIMessage

msg = AIMessage(content="你好")
json.dumps(msg)  
# TypeError: Object of type AIMessage is not JSON serializable  ← 炸了
```

**问题2：即使用 `asdict()` 转成 dict，读回来怎么知道是 AIMessage 还是 HumanMessage？**

```python
from dataclasses import asdict
d = asdict(msg)  # → {"content": "你好", "id": "...", "tool_calls": None}
# 字段都在，但类型信息丢了！读回来时不知道该 new AIMessage 还是 HumanMessage
```

所以必须**打上类型标记**：在序列化时加一个特殊字段 `"__type__": "AIMessage"`，反序列化时根据这个标记还原成正确的类。

**问题3：为什么要支持嵌套？**

因为 `AIMessage` 里可能有 `tool_calls` 字段，它是一个 `List[ToolCall]`，`ToolCall` 又是个 dataclass。如果只处理一层，`tool_calls` 会变成普通 dict 列表而不是 `ToolCall` 对象，`msg.tool_calls[0].name` 就会报错（dict 没有 `.name` 属性）。

### 怎么用？

#### 1. 序列化：打上类型标记

这是 `checkpoint.py` 的最后一块代码：

```python
# tinygraph/checkpoint.py
from dataclasses import is_dataclass, asdict

def _json_default(o):
    """JSON 序列化时的自定义处理函数
    
    当 json.dumps 遇到不认识的对象时，会调用这个函数。
    
    参数:
        o: 要序列化的对象
    
    返回:
        可以被 JSON 序列化的数据（dict/list/str/int...）
    
    异常:
        TypeError: 如果对象既不是 dataclass 也不是基本类型
    
    工作原理:
        1. 检查是不是 dataclass（我们的 AIMessage/HumanMessage/ToolCall 都是）
        2. 用 asdict() 把对象的所有字段转成 dict
        3. 加一个特殊字段 "__type__": 类名（比如 "AIMessage"）
        4. 返回这个 dict（它可以被 JSON 序列化）
    """
    if is_dataclass(o):
        # asdict() 把 dataclass 的所有字段转成 dict
        # 比如 AIMessage(content="你好", id="x", tool_calls=None)
        # → {"content": "你好", "id": "x", "tool_calls": None}
        d = asdict(o)
        
        # 打上类型标记：记住这是哪种消息类
        # type(o).__name__ 拿到类名（"AIMessage" / "HumanMessage" / ...）
        d["__type__"] = type(o).__name__
        
        # 现在 d = {"content": "你好", "id": "x", "tool_calls": None, "__type__": "AIMessage"}
        # 这个 dict 可以被 json.dumps 序列化
        return d
    
    # 如果不是 dataclass，说明传入了不支持的类型
    raise TypeError(f"无法序列化: {type(o)}")

# 使用时传给 json.dumps 的 default 参数：
# json.dumps({"messages": [msg]}, default=_json_default)
```

**为什么要单独写个函数，而不是在 Checkpoint.to_json() 里硬编码？**

因为 `default` 参数是 JSON 库的标准扩展点：
- 当 `json.dumps` 遇到不认识的对象（比如 `AIMessage`）
- 它会自动调用 `_json_default(msg)`
- 得到一个 dict，然后继续序列化

这样**递归嵌套也能自动处理**：
```python
msg = AIMessage(
    content="查天气",
    tool_calls=[ToolCall(name="get_weather", args={"city": "北京"}, id="c1")]
)
# json.dumps 会这样工作：
# 1. 遇到 AIMessage → 调用 _json_default → 得到 dict
# 2. 遍历 dict 的字段，遇到 tool_calls 里的 ToolCall → 再调用 _json_default
# 3. 最终整个嵌套结构都被转成 dict + 类型标记
```

#### 2. 反序列化：按标记还原

```python
# tinygraph/messages.py
from typing import Any

# _MESSAGE_TYPES: 类型名 → 类的映射表
# 比如 {"AIMessage": AIMessage, "HumanMessage": HumanMessage, ...}
# 这个 dict 在 messages.py 里定义，包含所有消息类
_MESSAGE_TYPES = {
    "AIMessage": AIMessage,
    "HumanMessage": HumanMessage,
    "ToolMessage": ToolMessage,
}

def revive(obj: Any) -> Any:
    """反序列化：把 JSON 数据还原成对象
    
    递归处理嵌套结构（list 和 dict）。
    
    参数:
        obj: JSON 反序列化后的数据（dict/list/str/int/...）
    
    返回:
        还原后的对象（可能是 AIMessage/ToolCall/...或保持原样）
    
    工作原理:
        1. 如果是 list → 递归处理每个元素
        2. 如果是 dict 且有 "__type__" 标记 → 根据类型还原成对象
        3. 否则 → 原样返回
    
    示例:
        输入: {"content": "你好", "__type__": "AIMessage"}
        输出: AIMessage(content="你好")
    """
    # 情况1: 列表 → 递归处理每个元素
    if isinstance(obj, list):
        return [revive(x) for x in obj]
    
    # 情况2: 字典 → 检查是否有类型标记
    if isinstance(obj, dict):
        t = obj.get("__type__")  # 拿到类型标记（可能是 None）
        
        if t in _MESSAGE_TYPES:
            # 这是一个被标记的消息对象！需要还原
            
            # 1. 提取所有字段（除了 "__type__"）并递归处理它们的值
            #    比如 {"content": "你好", "tool_calls": [...], "__type__": "AIMessage"}
            #    → data = {"content": "你好", "tool_calls": [...]}
            data = {k: revive(v) for k, v in obj.items() if k != "__type__"}
            
            # 2. 特殊处理 tool_calls 字段（如果存在）
            #    因为它是 List[ToolCall]，需要手动转成 ToolCall 对象
            if "tool_calls" in data and data["tool_calls"] is not None:
                # data["tool_calls"] 现在是 [{"name": "...", "args": {...}, "id": "..."}, ...]
                # 转成 [ToolCall(...), ToolCall(...), ...]
                data["tool_calls"] = [ToolCall(**tc) for tc in data["tool_calls"]]
            
            # 3. 根据类型标记找到对应的类，用字段数据创建对象
            #    比如 t="AIMessage" → _MESSAGE_TYPES["AIMessage"](**data)
            #    相当于 AIMessage(content="你好", tool_calls=[...])
            return _MESSAGE_TYPES[t](**data)
        
        # 没有类型标记，或者标记不认识 → 普通 dict，递归处理它的值
        return {k: revive(v) for k, v in obj.items()}
    
    # 情况3: 基本类型（str/int/bool/None）→ 原样返回
    return obj
```

**为什么要递归处理？**

因为检查点的 JSON 结构是这样的：
```json
{
  "channel_values": {
    "messages": [
      {"content": "你好", "__type__": "HumanMessage"},
      {
        "content": "查天气",
        "tool_calls": [
          {"name": "get_weather", "args": {"city": "北京"}, "id": "c1"}
        ],
        "__type__": "AIMessage"
      }
    ]
  }
}
```

`revive` 会这样工作：
```
1. revive({channel_values: {...}})  ← 最外层 dict
2.   → 递归处理 channel_values 的值
3.     revive({messages: [...]})  ← 又是个 dict
4.       → 递归处理 messages 的值
5.         revive([...])  ← 列表
6.           → 递归处理每个元素
7.             revive({content: "你好", __type__: "HumanMessage"})
8.               → 发现 __type__ → 还原成 HumanMessage(content="你好")
9.             revive({content: "查天气", tool_calls: [...], __type__: "AIMessage"})
10.              → 发现 __type__ → 还原 tool_calls → 还原成 AIMessage(...)
```

#### 3. 引擎中的使用：从检查点重建 channel

```python
# pregel.py
def _channels_from_checkpoint(self, cp: Checkpoint):
    """从检查点恢复 channel 状态
    
    参数:
        cp: 检查点对象（包含序列化的 channel 值和版本号）
    
    返回:
        channels: 重建后的 channel dict（值和版本都恢复了）
    
    工作流程:
        1. 创建一批全新的空 channel
        2. 把检查点里的值（JSON 数据）经 revive() 还原成对象
        3. 填回 channel.value
        4. 版本号也填回去
    """
    # 1. 创建空 channel（和图定义时一样的结构）
    channels = self._fresh_channels()
    
    # 2. 遍历每个 channel，恢复它的值和版本
    for key, ch in channels.items():
        if key in cp.channel_values:
            # 关键: 用 revive() 把 JSON 数据还原成对象
            # cp.channel_values[key] 是从数据库读出来的 JSON 数据（dict/list/...）
            # revive() 后变成真正的对象（AIMessage/ToolCall/...）
            ch.value = revive(cp.channel_values[key])
            
            # 版本号也恢复
            ch.version = cp.channel_versions.get(key, 0)
    
    return channels
```

#### 4. 验证：跑通往返

别只听我说，跑一遍看这个往返是否真的**逐位还原**：

```python
import json
from tinygraph.messages import AIMessage, ToolCall, revive
from tinygraph.checkpoint import _json_default

# 1. 创建一个复杂的消息对象
msg = AIMessage(
    content="我来查天气",
    tool_calls=[ToolCall(name="get_weather", args={"city": "北京"}, id="c1")]
)

# 2. 序列化成 JSON 字符串
s = json.dumps({"messages": [msg]}, default=_json_default, ensure_ascii=False)
print(s)
# 输出:
# {"messages": [{"content": "我来查天气", "id": "...", 
#   "tool_calls": [{"name": "get_weather", "args": {"city": "北京"}, "id": "c1"}], 
#   "__type__": "AIMessage"}]}

# 3. 反序列化回对象
back = revive(json.loads(s))["messages"][0]

# 4. 验证类型和内容
print(type(back).__name__)              # → "AIMessage"（类型正确）
print(back.tool_calls[0].args)          # → {'city': '北京'}（嵌套的 ToolCall 也还原了）
print(back == msg)                      # → True（逐字段相同！）
```

**`back == msg` 是 `True`** —— 状态彻底脱离了进程内存，变成磁盘上一段自包含的字节，读回来还原成**逐字段相同**的对象。这就是"可移植检查点"的本质。

### 隐形边界：不是什么都能塞进 state

既然 state 要走 JSON 往返，它就必须全程可序列化。新手最容易踩的坑是往 state 里塞一个"活的对象"。

#### 坑1：直接炸掉（幸运）

```python
import threading, json
from tinygraph.checkpoint import _json_default

# 把一个锁塞进 state
state = {"lock": threading.Lock(), "count": 0}
json.dumps(state, default=_json_default)
# TypeError: 无法序列化: <class '_thread.lock'>   ← 当场炸，存都存不进去
```

`json.dumps` 直接抛 `TypeError`，这还算"幸运"——至少错得明显，你知道哪里有问题。

#### 坑2：静默腐败（危险）

更阴险的是另一类：有些活对象（比如一个持有数据库连接的 dataclass）能被 `asdict` 转成 dict、顺利存下去，**但 revive 回来已经是个死对象**。

```python
from dataclasses import dataclass
import sqlite3

@dataclass
class DBWrapper:
    conn: sqlite3.Connection  # 数据库连接（活对象）

# 创建一个包含连接的对象
state = {"db": DBWrapper(conn=sqlite3.connect(":memory:"))}

# 序列化 → 竟然成功了！（因为 asdict 把 conn 转成了某种 dict）
s = json.dumps(state, default=_json_default)

# 反序列化 → 也成功了！（但...)
back = revive(json.loads(s))
db = back["db"]

# 一用就崩！
db.conn.execute("SELECT 1")  
# 错误: 连接已失效 / 或者指向错误的文件描述符 / 或者是个残缺的 dict
```

问题在于：
- **存档时**：连接是活的（指向内存里的某个文件描述符）
- **序列化**：把文件描述符的编号（比如 `<fd=42>`）转成了 JSON
- **反序列化**：把编号还原回去，但进程早就变了，fd=42 现在可能指向别的东西（或者根本不存在）
- **使用时**：连接是死的，一用就崩

更糟的是，错误可能不会在 `revive` 时立即暴露，而是在后续使用时才崩溃——此时你已经忘了是哪个检查点存坏了，排查极难。

#### 判据：能否跨时空还原？

简单问自己一个问题：

> **这个对象能否被序列化成字节，然后在几天后、在另一台机器上、在一个全新的进程里，原样还原？**

| 对象类型 | 可以放进 state | 原因 |
|---------|--------------|------|
| `int`, `str`, `bool` | ✅ | JSON 原生支持 |
| `list`, `dict` | ✅ | JSON 原生支持 |
| `AIMessage`, `ToolCall` | ✅ | 我们实现了序列化/反序列化 |
| `threading.Lock` | ❌ | 锁是进程内的同步原语，无法跨进程 |
| `open("file.txt")` | ❌ | 文件句柄绑定到当前进程，fd 无法还原 |
| `sqlite3.Connection` | ❌ | 数据库连接是活的网络/文件句柄 |
| `asyncio.Task` | ❌ | 协程对象绑定到事件循环，无法序列化 |
| `requests.Session` | ❌ | HTTP 会话包含连接池，无法跨进程 |

**原则：state 只存数据，不存资源**

- ✅ **数据**：纯粹的值（数字、字符串、消息对象）→ 放进 state
- ❌ **资源**：需要操作系统/运行时支持的"活对象"（连接、句柄、锁）→ 在节点函数内部按需创建、用完即弃

```python
# ❌ 错误：把连接放进 state
def node(state):
    conn = sqlite3.connect("db.sqlite")
    state["db_conn"] = conn  # 别这么干！
    return state

# ✅ 正确：连接是局部变量，用完就关
def node(state):
    conn = sqlite3.connect("db.sqlite")  # 每次调用时创建
    result = conn.execute("SELECT ...").fetchall()
    conn.close()  # 用完关掉
    state["query_result"] = result  # 只把数据（result）放进 state
    return state
```

### 对照真实框架

真实 LangGraph 默认用 **MessagePack** 而非 JSON，原因：
- **更高效**：序列化/反序列化速度快，字节流更紧凑
- **支持二进制**：可以直接序列化 `bytes`（JSON 要 base64 转码）
- **可扩展**：支持自定义 `Serializer` 注册新类型

但核心原理完全一样：
1. 序列化时打类型标记（MessagePack 的 ext types）
2. 反序列化时按标记还原
3. **"活对象不可入 state"这条铁律两者完全一样**

如果你要处理图片/音频等二进制数据，可以考虑换成 MessagePack；但对文本为主的 Agent，JSON 已经够用且更易调试（人类可读）。

## 4.5 引擎改造:在超步之间存档与恢复

### 是什么？

把R2章的"一次性执行引擎"升级成"可存档、可恢复的引擎"，需要改两个地方：
1. **改造一**：每个超步结束后存一个检查点（把进度写进数据库）
2. **改造二**：入口处识别三种输入形态（全新开始 / 断点恢复 / 接着对话）

### 为什么？

R2章的引擎有个致命问题：**只能从头跑到尾，中间崩了就得全部重来**。

```python
# R2章的引擎
app.invoke({"messages": [...]})  # 跑完返回结果
# 如果中途崩了 → 进程消失 → 状态全丢 → 只能从头再来
```

这在生产环境是灾难：
- 一个需要调用5次工具的任务，如果第4次崩了，前3次的结果全白费
- 用户发了10轮对话，服务器重启后对话历史全忘了

加上检查点后：
- 每个超步结束时存一次档（数据写进数据库）
- 崩溃后从最新检查点恢复（精确接着上次的进度继续）
- 多轮对话时自动载入历史（用户感觉你"记得"之前的内容）

### 怎么用？

#### 改造一：每个超步后存一个检查点

在主循环的 `yield` 旁边，加一句存档：

```python
# pregel.py 主循环（这是R2章的主循环，现在在提交后加一句存档）

# BSP 主循环
while active:
    steps += 1
    
    # ① 计划阶段：并行执行所有活跃节点
    tasks = []
    for node_name in active:
        node = self.nodes[node_name]
        task = node(self._state_snapshot(channels))  # 读快照
        tasks.append((node_name, task))
    
    # ② 执行阶段：收集所有写入
    writes = {}
    for node_name, result in tasks:
        self._collect_writes(result, writes, node_name)
    
    # ③ 提交阶段：经 reducer 合并到 channel
    self._commit(channels, writes)
    
    # 产出当前状态（流式输出）
    state_now = self._state_snapshot(channels)
    yield state_now
    
    # 计算下一批活跃节点
    active = self._next_active(tasks, state_now)
    
    # ========== 新增：存档 ==========
    if self.checkpointer is not None:
        # 创建检查点对象（包含当前状态 + 执行进度 + 父链接）
        cp = self._make_checkpoint(
            thread_id=thread_id,      # 执行线ID
            channels=channels,        # 当前的 channel 状态
            active=active,            # 下一批要跑的节点（执行进度）
            parent_id=parent_id,      # 上一个检查点的ID（链式）
            steps=steps               # 超步计数
        )
        
        # 存进数据库
        self.checkpointer.put(cp)
        
        # 更新 parent_id：下一个检查点的父 = 这个检查点
        # 这样检查点自然串成链: cp0 → cp1 → cp2 → ...
        parent_id = cp.checkpoint_id
```

**关键点1：`active` 就是被存进 `next_nodes` 的东西**

```python
# 超步结束时，active 可能是：
active = ["agent"]           # 下一步要跑 agent 节点
active = ["tools"]           # 下一步要跑 tools 节点
active = []                  # 没有下一步了，执行结束

# 存进检查点：
cp.next_nodes = active       # 把"下一步跑谁"存下来

# 恢复时：
active = list(cp.next_nodes)  # 从存下来的进度继续
```

这就是"执行进度"的本质：不是"跑了哪些节点"（那是历史），而是"接下来要跑哪些节点"（那是未来）。

**关键点2：`parent_id` 把检查点串成链**

```python
# 第1个超步结束：
cp0 = Checkpoint(..., parent_id=None)         # 没有父节点
checkpointer.put(cp0)
parent_id = cp0.checkpoint_id                  # "cp0"

# 第2个超步结束：
cp1 = Checkpoint(..., parent_id="cp0")         # 父节点是 cp0
checkpointer.put(cp1)
parent_id = cp1.checkpoint_id                  # "cp1"

# 第3个超步结束：
cp2 = Checkpoint(..., parent_id="cp1")         # 父节点是 cp1
checkpointer.put(cp2)

# 形成链：
# cp0 ──parent_id── cp1 ──parent_id── cp2
```

这条链是"回到历史"的基础（见4.6场景C）。

#### 改造二：入口处理"三种 input"

R2章 `stream()` 的开头只认一种输入：一个 dict，从头跑。加上检查点后，`input` 有了**三种**形态，引擎在开头分流：

| 输入形态 | 含义 | 典型场景 |
|---------|------|---------|
| `input={"messages": [...]}` 且 thread 无历史 | 全新开始 | 第一次对话 |
| `input=None` | 断点恢复 | 进程崩溃后重启，继续未完成的任务 |
| `input={"messages": [...]}` 且 thread 有【已结束】的历史 | 接着对话 | 多轮对话，记住之前的内容 |

**核心逻辑：**

```python
# pregel.py stream() 开头
def stream(self, input, config=None, stream_mode="updates"):
    # 1. 从 config 提取 thread_id
    #    比如 config={"configurable": {"thread_id": "chat-123"}}
    #    → thread_id = "chat-123"
    thread_id = self._thread_id(config)
    
    # 2. 判断是哪种输入形态
    resume_cp = None    # 要恢复的检查点（input=None 时）
    prior_cp = None     # 上一轮【已结束】的检查点（input=dict 但 thread 有历史时）
    
    if input is None and self.checkpointer is not None:
        # ========== 情况②：断点恢复 ==========
        # 用户传了 input=None，明确要求"从最新检查点恢复"
        resume_cp = self.checkpointer.get(thread_id)  # 读最新检查点
        if resume_cp is None:
            # 但这个 thread 没有任何检查点 → 无法恢复
            raise ValueError(f"thread {thread_id} 没有可恢复的检查点")
    
    elif isinstance(input, dict) and self.checkpointer is not None:
        # input 是个 dict，但可能是"全新开始"也可能是"接着对话"
        # 区分方法：看这个 thread 有没有【已结束】的检查点
        prior = self.checkpointer.get(thread_id)  # 读最新检查点（可能是 None）
        
        if prior is not None and not prior.next_nodes:
            # ========== 情况③：接着对话 ==========
            # prior 存在 且 next_nodes 为空 → 上一轮真正跑完了（不是崩在半截）
            prior_cp = prior
        # 否则：prior 不存在 或 next_nodes 非空
        #      → 情况①（全新开始）或上一轮崩了（不能叠新输入）
    
    # 3. 根据判断结果，决定如何初始化 channels / active / steps / parent_id
    if resume_cp is not None:
        # ========== 情况②：从检查点续跑 ==========
        channels = self._channels_from_checkpoint(resume_cp)  # 恢复状态
        active = list(resume_cp.next_nodes)                  # 从存下来的进度继续
        steps = resume_cp.step                               # 接着之前的步数
        parent_id = resume_cp.checkpoint_id                  # 新检查点挂在它后面
    
    else:
        if prior_cp is not None:
            # ========== 情况③：多轮对话 ==========
            channels = self._channels_from_checkpoint(prior_cp)  # 载入上轮结束状态
            parent_id = prior_cp.checkpoint_id                  # 链接历史
            steps = prior_cp.step                               # 接着之前的步数
        else:
            # ========== 情况①：全新开始 ==========
            channels = self._fresh_channels()  # 空 channel
            parent_id = None                   # 没有父节点
            steps = 0                          # 从第0步开始
        
        # 情况①和③都需要把本次输入并进 channel
        init = {}
        self._collect_writes(input, init)      # 把 input 转成 writes
        self._commit(channels, init)           # 经 reducer 并进去
        active = self._resolve_next(START, self._state_snapshot(channels))  # 从 START 出发
    
    # 4. 进入 BSP 主循环（while active: ...）
    # ...（就是改造一里的循环）
```

**三种形态的细节对比：**

| 对比项 | 情况① 全新开始 | 情况② 断点恢复 | 情况③ 接着对话 |
|--------|--------------|--------------|--------------|
| **输入** | `input=dict` | `input=None` | `input=dict` |
| **thread 历史** | 无（或有但未结束） | 有（可能未结束） | 有且已结束 |
| **channels 来源** | `_fresh_channels()` 空的 | `_channels_from_checkpoint()` 恢复 | `_channels_from_checkpoint()` 恢复 |
| **是否并入新输入** | ✅ 是 | ❌ 否（用检查点里的状态） | ✅ 是（追加到历史上） |
| **active 来源** | `_resolve_next(START, ...)` 从头算 | `resume_cp.next_nodes` 用存下来的 | `_resolve_next(START, ...)` 从头算 |
| **典型场景** | 第一次对话 / 新任务 | 崩溃后恢复 | 多轮对话 |

**为什么情况②和情况③都要恢复 channels，但处理方式不同？**

- **情况②（断点恢复）**：
  - 上一轮**没跑完**（`next_nodes` 非空，比如 `["tools"]`）
  - 不能叠新输入，因为那会破坏执行序列
  - 必须原样恢复 → 从 `next_nodes` 接着跑
  
  ```python
  # 假设崩溃前：模型刚决定要调工具，但还没执行
  # cp.next_nodes = ["tools"]
  # cp.channel_values["messages"] = [Human("天气?"), AI(tool_calls=[...])]
  
  # 如果这时叠新输入 → 会变成：
  # messages = [Human("天气?"), AI(tool_calls=[...]), Human("你好")]  ← 错乱！
  # 一个悬空的 tool_calls 后面跟了个新问题，执行序列是坏的
  ```

- **情况③（接着对话）**：
  - 上一轮**跑完了**（`next_nodes` 为空）
  - 可以安全地追加新输入（reducer 会处理）
  - 载入历史 → 叠新输入 → 从 START 重新算 active
  
  ```python
  # 第一轮结束：
  # cp.next_nodes = []
  # cp.channel_values["messages"] = [Human("天气?"), AI("北京晴天")]
  
  # 第二轮进来，input={"messages": [Human("明天呢?")]}
  # 经 add_reducer 追加 → messages = [
  #     Human("天气?"), AI("北京晴天"),   ← 历史
  #     Human("明天呢?")                   ← 新输入
  # ]
  # 模型第二轮看到完整历史，能理解"明天呢?"的上下文
  ```

**判据是 `not prior.next_nodes`** —— 只有 `next_nodes` 为空（真正跑完）才当"接着对话"。这条 `if` 把"续对话"和"续崩溃"两件容易混的事干净分开了。

#### 额外的状态查询 API

我们还顺手加了两个方法：

```python
# 取最新检查点（对应 LangGraph 的 get_state）
snap = app.get_state(config)
print(snap.channel_values["count"])  # 查看当前状态
print(snap.next_nodes)               # 查看下一步要跑谁

# 列出全部检查点，最新在前（对应 LangGraph 的 get_state_history）
history = app.get_state_history(config)
for cp in history:
    print(f"step={cp.step}, count={cp.channel_values['count']}, next={cp.next_nodes}")
```

这两个方法是"回到历史"（场景C）的基础。

#### 跟着引擎恢复一遍（input=None 的内部时序）

"断点恢复"听着玄，拆成步骤后会发现它平淡得令人安心。假设一个"每步 count+1、走 3 步"的图，在 count=2 时进程崩了，数据库里留下了一串检查点。现在新进程调用：

```python
app.invoke(None, {"configurable": {"thread_id": "job-42"}})
```

引擎内部依次发生：

```
时间线  |  操作                                    |  说明
────────┼──────────────────────────────────────────┼───────────────────
t1      │ _thread_id(config)                       │ 提取出 "job-42"
        │  → thread_id = "job-42"                  │
────────┼──────────────────────────────────────────┼───────────────────
t2      │ input is None 且有 checkpointer           │ 判断：走"恢复"分支
        │  → resume_cp = checkpointer.get("job-42")│
────────┼──────────────────────────────────────────┼───────────────────
t3      │ 从数据库读回最新检查点 cp：               │ 这是崩溃那一刻的快照
        │   cp.channel_values = {                  │
        │     "count": 2,                          │  ← 数据
        │     "log": ["step->1", "step->2"]        │
        │   }                                      │
        │   cp.channel_versions = {                │
        │     "count": 2, "log": 2                 │  ← 版本号
        │   }                                      │
        │   cp.next_nodes = ["step"]               │  ← 执行进度（关键！）
        │   cp.step = 2                            │  ← 超步计数
────────┼──────────────────────────────────────────┼───────────────────
t4      │ _channels_from_checkpoint(cp):           │ 重建内存中的 channels
        │   1. 创建空 channels                     │
        │   2. 把 cp.channel_values 经 revive()   │  JSON → 对象
        │      填回 channel.value                  │
        │   3. 把 cp.channel_versions 填回        │
        │      channel.version                     │
        │ 此刻引擎内存里的状态 = 崩溃那一刻逐位相同 │
────────┼──────────────────────────────────────────┼───────────────────
t5      │ active   = list(cp.next_nodes) = ["step"]│ 从存下来的进度接着跑
        │ steps    = cp.step = 2                   │ 接着之前的步数
        │ parent_id= cp.checkpoint_id              │ 新检查点挂在它后面
────────┼──────────────────────────────────────────┼───────────────────
t6      │ 进入 while active: 循环                  │ 开始执行
        │   steps → 3                              │  超步+1
        │   跑 step 节点                           │  count+1 → 3
        │   should_continue 判定走完               │  返回 END
        │   active → []                            │  没有下一步了
        │   退出循环                               │  执行结束
```

**关键观察：整个过程没有任何"重放历史"**

引擎不会：
- ❌ 重跑 step1（count 0→1）
- ❌ 重跑 step2（count 1→2）
- ❌ 从 START 节点重新开始

而是：
- ✅ 直接把"崩溃那一刻的快照"装回内存
- ✅ 从 `next_nodes = ["step"]` 指定的地方继续
- ✅ 只跑 step3（count 2→3）

**对照R1章的循环：为什么它做不到？**

第1章的 `while True` 循环把"下一步跑谁"藏在 Python 的指令指针里：

```python
# 第1章的循环
while should_continue(state):
    state = call_model(state)     # ← 如果崩在这里
    state = call_tools(state)     #   重启后不知道该从哪继续
```

指令指针是 CPU 寄存器里的一个值，随进程消失。你无法"把指令指针存进数据库"。

而现在：
```python
# R3章的引擎
cp.next_nodes = ["step"]  # "下一步跑谁"变成了普通数据（列表）
# 这个列表可以存进数据库、可以读回来
```

这就是"把控制流外置成数据"带来的结果：
- **控制流外置** = `next_nodes` 这个列表
- **数据** = 可以序列化、可以持久化
- **恢复** = 读一条记录 + 从 `next_nodes` 起步

仅此而已。没有魔法，只是把"程序计数器"从寄存器搬到了数据库。

#### 正确性细节：超步计数也要接着走

注意 t5 那一步：

```python
steps = cp.step  # 接着崩溃点的步数，而不是从 0 重数
```

为什么重要？因为引擎有 `recursion_limit` 安全阀（防死循环）：

```python
# pregel.py 主循环里
while active:
    steps += 1
    if steps > self.recursion_limit:
        raise RecursionError(f"超过 {self.recursion_limit} 步，可能死循环")
    # ...
```

如果每次恢复都从 `steps=0` 重数：
- 一个需要跑 100 步的长任务
- 中途崩了 3 次，每次恢复
- `steps` 一直被清零 → 永远不会触发 `RecursionError`
- 真正的死循环也被掩盖了

所以 `steps = cp.step` 保证："崩溃-恢复"多次的长任务，计数依然连续、安全阀依然有效。

## 4.6 跑起来:三个场景

`examples/04_checkpoint.py` 用一个"每步 count+1、走 3 步"的小图演示三件事。

### 场景 A:thread + 状态查询

```python
saver = InMemorySaver()
app = build_counter_graph(saver)
config = {"configurable": {"thread_id": "session-1"}}
final = app.invoke({"count": 0, "log": []}, config)     # count → 3
snap = app.get_state(config)                            # 从检查点读回
# snap.channel_values["count"] == 3
```

### 场景 B:跨进程持久化(模拟服务器重启)

这是最能体现价值的场景。"进程1"跑两步就崩溃,"进程2"重开数据库续跑:

```python
# —— 进程1:用 SQLite,跑两步就 "崩溃" ——
saver1 = SqliteSaver("/tmp/demo.sqlite")
app1 = build_counter_graph(saver1)
config = {"configurable": {"thread_id": "job-42"}}
gen = app1.stream({"count": 0, "log": []}, config, stream_mode="values")
next(gen); next(gen)                 # 只走两步,然后丢弃(模拟崩溃)
del gen, app1, saver1

# —— 进程2:重开同一个数据库,从检查点恢复 ——
saver2 = SqliteSaver("/tmp/demo.sqlite")
app2 = build_counter_graph(saver2)
snap = app2.get_state(config)        # count=2, next_nodes=['step']
final = app2.invoke(None, config)    # input=None → 续跑!→ count=3
```

运行输出:

```
进程1:跑了两步后崩溃。
进程2:从数据库恢复,当前 count=2, 接下来要跑 ['step']
进程2:续跑完成,最终 count: 3 | log: ['step->1', 'step->2', 'step->3']
```

注意 `log` 是 `['step->1', 'step->2', 'step->3']`——进程2 **没有重做** step1、step2(否则会出现重复),它精确地从第 3 步接着跑。这正是 `next_nodes` 记录执行进度的作用。对有副作用的工具(发邮件、扣款),"不重做已完成的步骤"是生死攸关的正确性保证。

### 场景 C:回到历史

每个超步都存了检查点,于是能列出完整历史、回到任意一步:

```python
history = app.get_state_history(config)   # 最新在前
# step=3 count=3 next=[]
# step=2 count=2 next=['step']
# step=1 count=1 next=['step']
# step=0 count=0 next=['step']

# 挑 count=1 那个检查点,从它恢复
target = [cp for cp in history if cp.channel_values["count"] == 1][0]
branch_config = {"configurable": {"thread_id": "tt-1",
                                  "checkpoint_id": target.checkpoint_id}}
snap = app.get_state(branch_config)       # 读回 count=1 的那一刻
```

把这条"靠 `parent_id` 串起来的链"画出来,"分叉"就一目了然了:

```
   主线(thread "session-1"):每个超步 put 一个新检查点,parent 指向前一个

   cp0 ──parent── cp1 ──parent── cp2 ──parent── cp3
  count=0        count=1        count=2        count=3
  next=[step]    next=[step]    next=[step]    next=[]   ← 执行结束
                   │
                   │ 从 cp1 恢复(checkpoint_id=cp1),换条 thread 往下走
                   ▼
                 cp1' ──parent── cp2' ──parent── cp3'      ← 新分叉,
                count=1         count=11        count=21       原主线【原封不动】保留
              (从这里改了逻辑/输入,走出不一样的未来)
```

关键有两点:一是每个检查点是**不可变快照**——`put` 永远写一个新 id,从不原地改旧的;二是 `parent_id` 让它们串成一条**可回溯的链**。于是你能回到任意一点(读 cp1),甚至从那点分叉出一条新线(cp1'→cp2'→...),而原来那条 cp1→cp2→cp3 完好无损,可以两条并排对比"如果当时那么选会怎样"。这就是"对话走错了,倒带到三步前换个问法重来"的底层机制。

(对照真实框架:LangGraph 的 `get_state` / `get_state_history` / `update_state` 三件套就是干这个的。`update_state` 还能在某个历史点改一下状态再往下走,实现反事实探索;它不是改旧检查点,而是基于某点派生一个新检查点、开出新分支。我们实现了前两个,`update_state` 留作练习。)

## 4.7 我们解决了什么

R1 章六个局限,现在解决了三个:

- **持久化**(局限一):状态加进度都存进了可序列化的检查点,跨进程、跨机器、跨时间都能恢复。
- **回到历史**(局限五):每步一个不可变快照、串成链,可列出、可回溯、可分叉。
- **容错的基础**(局限六的一半):恢复时不重做已完成的超步,重试不会重复副作用。

但还差一个最微妙的:**主动地、在某个节点中间暂停下来等外部输入**(比如等人审批),然后恢复。注意这和"崩溃后恢复"不同——崩溃是被动的,而审批是主动在某个点喊停。这需要一个新原语 `interrupt()`。好在我们已经把地基打好了:有了检查点,"暂停"不过就是"提前存个档然后退出","恢复"就是 4.5 节那套 `input=None` 续跑。下一章把这最后一块拼上,同时把流式做完整。

## 4.8 自测:你真的理解检查点了吗

**Q1. 检查点存了 channel 值、版本号、`next_nodes`、`parent_id` 四样。如果偷懒不存 `next_nodes`,恢复时会发生什么?**

<details><summary>想清楚再展开</summary>

恢复时引擎不知道"接着跑谁",只能从头(`_resolve_next(START)`)重跑整张图。对纯计算图顶多浪费算力;对有副作用的图(已经发过的邮件、已经扣过的款)会**重复执行**,酿成事故。`next_nodes` 就是"执行进度",是检查点区别于"普通数据备份"的核心——它存的不只是"数据是什么",还有"执行到哪了"。
</details>

**Q2. 场景 B 里 `log` 是 `['step->1','step->2','step->3']` 而不是带重复的。这个"没有重复"由哪一行代码保证?**

<details><summary>想清楚再展开</summary>

由恢复分支里的 `active = list(resume_cp.next_nodes)` 和 `steps = resume_cp.step` 保证。引擎不是"从头重放到崩溃点再继续",而是直接把崩溃那一刻的 channel 值装回内存、从 `next_nodes` 起步。step1、step2 的写入早已提交进 `log` 并随检查点存盘,恢复时原样读回,所以不会被重新执行。
</details>

**Q3. `InMemorySaver` 和 `SqliteSaver` 实现完全不同,为什么上层引擎一行都不用改就能换用?**

<details><summary>想清楚再展开</summary>

因为两者遵守同一个 `BaseCheckpointSaver` 接口(`put`/`get`/`list`)。引擎只依赖这三个方法的**契约**,不关心背后是 dict 还是 SQL。这是"机制与策略分离":引擎定义"何时存"(机制),saver 决定"存到哪"(策略)。想换 Postgres?写个遵守同接口的 `PostgresSaver` 塞进去即可,引擎无感。
</details>

**Q4. 回到历史靠 `parent_id` 把检查点串成链。为什么检查点必须是不可变的?如果允许原地修改某个历史检查点会怎样?**

<details><summary>想清楚再展开</summary>

因为这个能力依赖"每个检查点都忠实记录了那一刻的状态"。若允许原地改,历史就被篡改了——你"回到 count=1 那一刻"看到的可能已不是当时的真实状态,分叉、对比、复现全部失效。所以每个超步都 `put` 一个**新**检查点(新 id),旧的永不改动。真实 LangGraph 的 `update_state` 也不是改旧检查点,而是基于某点派生一个新检查点、开出新分支。
</details>

**Q5. `input=None` 是"断点恢复",`input=dict` 且 thread 有历史是"接着对话"——引擎靠哪个条件区分这两种?如果两者都按"载入旧状态+追加输入"处理,会错在哪?**

<details><summary>想清楚再展开</summary>

靠 `not prior.next_nodes`:只有上一轮的 `next_nodes` 为空(真正跑完)才当"接着对话"。如果不分、一律"载入+追加",当上一轮其实是**崩在半截**(`next_nodes` 非空,比如 `['tools']`)时,你又塞一条新的 Human 进去,就会在"模型已决定调工具、还没执行"的半截状态上叠一条用户消息——`messages` 链错乱(一条 tool_call 悬空、又冒出个新问题),恢复出来的执行序列是坏的。所以"续崩溃"必须原样从 `next_nodes` 起步、不加新输入,"续对话"才追加——这正是情况②和情况③用同一套 channel 重建、却走两条分支的原因。
</details>

## 4.9 本章小结

- 检查点存四样:**channel 值、版本号、`next_nodes`(执行进度)、`parent_id`(链)**。其中 `next_nodes` 就是第 1 章的循环存不下来的指令指针,现在变成了普通数据。我们把 `checkpoint.py` 完整写了出来(Checkpoint + 两个 saver + 序列化),可直接 `python` 跑通本章所有 demo。
- **`thread_id`** 隔离不同执行线;同一 thread 的检查点串成历史链。我们**跑出**了同 thread 并发会互相覆盖的 bug——thread 必须串行处理。
- **Checkpointer 接口**(`put`/`get`/`list`)有内存版和 SQLite 版;序列化靠"打 `__type__` 标记 + `revive` 还原",我们**跑出**了往返后 `back == msg` 逐字段相同、以及活对象入 state 当场 `TypeError`。
- 引擎改造只需两处:**超步后存档** + **入口分三种 input**(全新 / `input=None` 断点恢复 / `input=dict` 接着对话)。第三种就是"对话记忆"的真正落地。
- 兑现了持久化、跨进程恢复(不重做已完成步骤)、回到历史三大能力。
- 还差"主动暂停等外部输入"(`interrupt`)——下一章完成。
