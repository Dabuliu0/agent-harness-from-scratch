# 第 8 章 · 子代理与多智能体

> 第 3 章留了个尾巴:上下文工程三大技术,压缩和笔记讲完了,还欠"子代理隔离"。本章补上它,顺便把"多智能体"这个被过度神化的话题拆到只剩机制:**子代理 = 一个以工具形态暴露的全新 Agent 循环**。一个 `task` 工具、六十行代码,你就有了上下文隔离、并行扇出和编排拓扑的全部地基——没有一件新机制,全是前七章零件的组合。代码:`tinyharness/subagents.py`。

## 8.1 子代理的第一动机:上下文隔离,不是并行

普遍的误解把多智能体当成"并行提速"或"角色扮演"。看真实系统的账本,第一动机是**上下文经济学**:

一个典型的调研子任务("在这个仓库里找出所有直接读环境变量的位置并评估风险")需要:grep 十几次、读几十个文件、试错几轮——**几万 token 的探索过程**。但主对话需要的只是**那一小段结论**("共 17 处,3 处高危,清单如下")。把探索塞进主历史,是拿最贵的地皮堆建筑垃圾:token 白烧(第 3 章:历史每轮整卷重发),注意力被稀释(context rot),压缩时还得费劲把它们摘出去。

子代理的解法干脆:**探索发生在别人的上下文里。** 就像派一个实习生去图书馆翻一整天资料:他自己的草稿纸上写写画画三百页,最后交给你的只有一张摘要卡片——你的笔记本上贴的是卡片,不是那三百页复印件。子代理拿一个全新的、空的窗口,烧几万 token 去翻,结束时只把结论作为工具结果返回主历史。Anthropic 的多智能体研究系统就是这个账:每个子代理烧数万 token,回传一两千 token 的浓缩结论,主代理只负责调度与综合——在广度型调研任务上,多智能体比单 Agent 提升 90%+(代价是总 token 多花几倍,后面 8.6 会回到这笔账)。

这就是第 3 章说的"让别人替你烧上下文"。隔离是本体,并行是随之而来的赠品。

## 8.2 task 工具:多智能体的全部机制

实现小到令人怀疑:定义子代理档案,再造一个 `task` 工具。

```python
# tinyharness/subagents.py
@dataclass
class SubagentDef:
    name: str
    description: str        # 写给【主模型】看:什么任务该派给我
    system_prompt: str      # 子代理自己的身份指令
    tools: Sequence[Tool] = ()   # 子代理的工具箱(通常比主代理窄)
    model: Optional[object] = None      # None = 沿用主代理的模型
    max_turns: int = 20
    max_context_tokens: int = 40_000
```

`make_task_tool` 全文——六十行里多智能体的全部机制。分三段读:先是查档与花名册(把子代理定义整理成注册表),然后是 task 函数本体(**新建一个完整的 Agent 循环**,跑完只交结论),最后打包成一个普通工具:

```python
def make_task_tool(
    agents: Sequence[SubagentDef],
    default_model: object,
    *,
    gate: Optional[Gate] = None,        # 父代理的闸门原样下传(权限只收不放)
    on_event: Optional[Callable[[str, Event], None]] = None,   # 子代理事件外送
    max_depth: int = 2,
    _depth: int = 0,
) -> Tool:
    registry: Dict[str, SubagentDef] = {a.name: a for a in agents}
    roster = "\n".join(f"- {a.name}: {a.description}" for a in agents)  # 花名册

    def task(agent: str, prompt: str) -> str:
        spec = registry.get(agent)
        if spec is None:
            return f"[错误] 没有名为 {agent!r} 的子代理,可用: {', '.join(registry)}"
        tools = list(spec.tools)
        if _depth + 1 < max_depth and len(registry) > 0:   # ★ 深度构造期封顶
            tools.append(make_task_tool(agents, default_model, gate=gate,
                                        on_event=on_event, max_depth=max_depth,
                                        _depth=_depth + 1))
        sub = Agent(                                       # ★ 一个全新的循环
            model=spec.model or default_model,
            tools=tools,
            system_prompt=spec.system_prompt,
            max_turns=spec.max_turns,
            context=ContextManager(max_context_tokens=spec.max_context_tokens),
            gate=gate,
            name=f"{spec.name}@{_depth + 1}",
        )
        for e in sub.run(prompt):
            if on_event is not None:
                on_event(sub.name, e)   # 过程外送观测,不进主历史
        return final_text(sub.last_messages) or "(子代理没有产出文本)"
```

以上是 task 函数本体。最后一步,把它打包成一个普通工具——留意 description 里直接嵌着花名册:

```python
    return Tool(
        name="task",
        description=(
            "把一个独立子任务委派给专职子代理执行,返回其最终结论。"
            "适用于:需要大量探索/阅读但主对话只需要结论的任务;"
            "可以在一轮里发多个 task 调用并行推进互不依赖的子任务。\n"
            "agent: 子代理名字,必须是下列之一\n" + roster + "\n"
            "prompt: 交给子代理的完整任务描述(它看不到当前对话,必须自包含)"
        ),
        parameters={"type": "object",
                    "properties": {"agent": {"type": "string"},
                                   "prompt": {"type": "string"}},
                    "required": ["agent", "prompt"]},
        func=task,
    )
```

细读几处:**花名册直接拼进 description**——上面设计点 ① 说的"委派说明书"就是这段原文,"必须是下列之一"后面跟着每个子代理的自我介绍;查无此人时**报错列出可用名单**——第 2 章立过的习惯,报错要给模型指条活路;子代理命名 `f"{spec.name}@{_depth + 1}"`,让 on_event 的观测输出能分清层级;结论为空时兜底返回 `"(子代理没有产出文本)"`——工具结果永远不能是空字符串,模型见到空结果会不知所措。

主模型视角里,`task` 和 `read_file` 没有任何区别——都是"发调用、拿结果"。**多智能体对内核完全透明**:循环不改、执行器不改、事件不改。这是"机制下沉"的又一次验收:内核提供的抽象(工具)足够正交,上层想象力就自由。

三个设计点,每个都对应真实系统的取舍:

**① `description` 是委派说明书,写给主模型。** `task` 工具的 description 里嵌着子代理花名册(名字 + 各自的 description)。主模型靠这几行字决定"什么活派给谁"——和第 2 章"工具即接口设计"同一条纪律,只是这次接口的另一端也是模型。Claude Code 的自定义 subagents(`.claude/agents/*.md` 的 frontmatter description)同款机制。

**② `prompt` 必须自包含,因为子代理看不到主对话。** 这是隔离的另一面,也是新手最常踩的坑:主模型如果只说"按刚才讨论的做",子代理会一脸茫然——它没有"刚才"。所以 description 里明写:"它看不到当前对话,任务描述必须自包含"。**隔离买来干净上下文,代价是委派质量要求变高**——主模型得学会写好任务书(真实系统在 system prompt 里花大量篇幅教主模型怎么写委派)。

**③ 回传的只有最终文本。** 子代理的几十轮工具调用、中间推理,统统不进主历史;`on_event` 回调允许 UI 显示子代理进度(用户想看),但那是观测通道,不是上下文通道。**"边界上传什么"是多智能体设计的第一决策**:传结论,不传过程。

## 8.3 并行扇出:第 2 章埋的种子在这里开花

主模型一轮发出多个 `task` 调用:

```
AIMessage(tool_calls=[
    task(agent="researcher", prompt="调研 A 方案的社区活跃度…"),
    task(agent="researcher", prompt="调研 B 方案的性能基准…"),
    task(agent="reviewer",   prompt="审查 src/auth/ 的安全问题…"),
])
```

然后——什么都不用做。第 2 章的执行器本来就并行执行一批工具调用(线程池),现在每个"工具"是一个完整的 Agent 循环,于是**三个子代理自动并行**,结果照旧按请求顺序回填(确定性,第 2 章的保序在多智能体下更值钱)。当初那句"并行子代理届时免费"兑现了。

这正是 2026 年生产系统的形态:Claude Code 一次 session 可以扇出成批 subagent 跑夜间任务;多智能体研究系统的 lead agent 并行派 3-5 个搜索子代理。扇出的宽度由模型自己决定(它一轮想发几个 task 就发几个)——**编排逻辑在模型的决策里,不在你的代码里**,家族 A 的哲学贯彻到底。

## 8.4 安全与资源:收窄,封顶,分灶

子代理引入的新风险面,三条纪律管住:

- **权限只收不放。** 父代理的 `gate` 原样传给子代理——父不能干的,子也不能干;再叠加 `SubagentDef.tools` 的窄工具箱(调研型子代理只给只读工具),子的能力 ≤ 父。真实系统同理(Claude Code 子代理继承并可进一步限制权限)。
- **深度静态封顶。** 子代理还能派孙代理吗?能,但 `make_task_tool` 用构造期递归控制:只有 `depth+1 < max_depth` 时,子代理的工具箱里才会再放一把 task 工具。**深度控制做在构造期而不是运行期**——不存在"运行时数漏了"的 bug 面。
- **各人上下文各人管。** 每个子代理独立 `ContextManager`(自己的预算、自己的压缩),烧穿了也殃及不到主窗口;`max_turns` 独立兜底。

## 8.5 编排拓扑:一张地图放平心态

主线实现的是 **orchestrator-worker(编排者-工人)**:主代理决策与综合,子代理干活回报,控制权始终在主代理。这是家族 A 的主流拓扑,覆盖绝大多数真实需求。地图上还有几个名字,见到不慌:

| 拓扑 | 控制权 | 一句话 | 哪里常见 |
|---|---|---|---|
| Orchestrator-worker | 始终在主代理 | 派活、收结论、再决策 | Claude Code Task、研究系统(本章) |
| Supervisor | 中心路由节点 | 每轮回到中心,决定下一个专家 | LangGraph 官方封装(R7) |
| Handoff | 转移 | A 干完把**整个对话**交给 B | OpenAI Agents SDK 的招牌原语 |
| Swarm | 去中心 | 谁接手由当前上下文定 | 实验性居多 |

两个坐标轴看穿它们:**控制权在哪**(中心/转移/无中心)与**边界上传什么**(handoff 传完整对话,orchestrator-worker 只传任务书和结论)。家族 B 用图表达这些拓扑(子图即节点,边即控制权流转,R7 章);家族 A 用工具表达(task 即派活,handoff 也不过是个特殊工具)。**表达手段不同,拓扑学同一套。**

## 8.6 什么时候值得上多智能体(工程判断,比机制重要)

多智能体不是免费午餐,这笔账 2026 年已经算得很清楚:

- **成本**:研究系统的数据,多智能体消耗约为单 Agent 的 **15 倍** token。隔离的每一分收益都是用总量换的。
- **收益条件**:任务能**并行分解**、子任务间**弱耦合**、探索量**超出单窗口**——广度调研、多仓库审计、批量迁移,是甜区。
- **反例**:强顺序依赖的任务(每步依赖上步产物的编码任务)上多智能体,协调成本吃掉全部收益,还引入"子代理各写各的、合不拢"的新失败模式。所以 Claude Code 写代码主要还是单主循环 + 定点派调研型子任务,而不是"五个程序员代理开会"。

判断口诀:**先问"这活能拆给互不聊天的实习生们吗"**——能拆,上子代理;不能拆,好好用一个窗口(压缩 + 笔记,第 3 章)。"从简单开始"(第 0 章)在多智能体上尤其值钱,因为它是最容易为炫技买单的地方。

顺带把两个更远的名词放进地图:**后台任务**(子代理跑很久,主代理先干别的,完成后以事件通知——把 task 的同步等待改成 future,是个好练习);**A2A**(Agent2Agent 协议,跨组织的 Agent 互相调用的标准化,MCP 解决"Agent↔工具",A2A 想解决"Agent↔Agent",2026 年仍在早期)。

## 8.7 跑起来:两本账,一只秒表

`examples/k08_subagents.py`,离线两幕。第一幕的角色配置:

```python
researcher = SubagentDef(
    name="researcher",
    description="仓库调研:搜索、阅读、汇总结论",
    system_prompt="你是调研员,只输出结论",
    tools=[grep_repo],              # 只读工具箱:能力 ≤ 父
    model=researcher_model(),       # 剧本:grep 两次(每次结果几千字符),回一段结论
)
task_tool = make_task_tool([researcher], parent_model,
                           on_event=lambda name, e: sub_events.append((name, e.type)))
parent = Agent(model=parent_model, tools=[task_tool])
parent.invoke("这个仓库还有哪些待办?")
```

第二幕主剧本一轮发 3 个 `task`(每个子代理调一次 0.3 秒的 `slow_probe`),掐表。实际输出:

```
== 隔离:子代理翻箱倒柜,主历史只落一段结论 ==
  子代理内部事件 13 个(工具调用、结果……全在子代理窗口里)
  主代理历史仅 4 条,其中工具结果 1 条(=子代理结论)
  最终回答: 调研完成:结论:仓库共 4 处待办标记,集中在 src/a.py 与 src/b.py,建

== 并行:一轮 3 个 task,0.3 秒的活并行只花 ~0.3 秒 ==
  耗时 0.31s(串行要 0.9s+);结果保序: db-1: 正常 | db-2: 正常 | db-3: 正常
```

两本账当场对上:子代理里 13 个事件(两轮 grep,每轮结果几千字符的"建筑垃圾")对主历史 **4 条消息**(user / AI 发 task / task 结果一条 / AI 总结)——爆炸发生在别人家,主窗口只闻到结论的香味。秒表那行则是第 2 章线程池的迟到红利:0.31s ≈ 最慢的那个,不是 0.9s 的总和;且 `db-1 | db-2 | db-3` 的顺序与请求顺序一致——**并行执行,保序回填**,三个子代理无一例外。

顺带看一眼第二幕的小陷阱:三个并行子代理**共用同一个模型实例**。如果剧本模型是"逐条 pop 台词"的有状态款,三个子代理就会互相抢台词——这叫**竞态(race condition)**:多个并发执行者操作同一份可变状态,结果取决于谁碰巧快一步,每次跑都可能不一样。所以 k08 专门写了个无状态的 `ProbeModel`(没见过工具结果就发调用,见过就复述,不依赖任何共享剧本)。并发下"状态归谁"的问题,连玩具代码都躲不开。

真实模型实验(需 key):给 mini_code 配一个 researcher 子代理,让主代理"调研这个仓库里所有 TODO 注释并分类"——观察它怎么写委派任务书、扇出几个、综合得怎么样。

## 8.9 源码解析与代码逻辑

> 动手是"抄得出来";这一节是"讲得清楚"。
> 打开:`tinyharness/subagents.py`。核心认知:**没有新运行时**,只是一个会内部 `Agent.run` 的 Tool。

### 生活类比

主代理是**项目经理**,`task` 是**派工单**。  
实习生(子 Agent)自带空白笔记本(新 `messages`)、限额电话卡(独立 `ContextManager`)、只能用你发的工具箱,门禁卡权限≤你的(`gate` 下传)。  
干完只交**一页结论**回会议室;翻找过程不进主会议纪要。  
一次派三张工单 → 第 2 章线程池让三人同时干,交卷仍按派单顺序摆上桌。

```
主模型 tool_calls: [task(A), task(B)]
  → run_tool_calls 并行
       每个 task:
         查 SubagentDef → 组 tools(可能递归塞更深 task)
         Agent(... gate=父gate, context=新预算).run(prompt)
         on_event 外送子事件(可选)
         return final_text(子历史)   ← 仅此字符串进主 ToolMessage
```

### 源码地图

| 符号 | 带走一件事 |
|---|---|
| `SubagentDef` | description 写给**主模型**看(派活说明书) |
| `make_task_tool` | 工厂返回名为 `task` 的 `Tool` |
| 静态 `_depth` / `max_depth` | 构造期决定是否再塞 task,运行时数不漏 |
| `gate` 参数 | 原样下传,权限只收不放 |
| `on_event` | 观测用,默认不进主历史/主 session |

### 主路径:`task` 闭包

```python
# tinyharness/subagents.py(逻辑节选)
spec = registry.get(agent) or 错误字符串
tools = list(spec.tools)
if _depth + 1 < max_depth and registry:
    tools.append(make_task_tool(..., _depth=_depth + 1))  # 更深一层才有 task
sub = Agent(model=spec.model or default_model, tools=tools,
            system_prompt=..., max_turns=..., 
            context=ContextManager(max_context_tokens=spec.max_context_tokens),
            gate=gate, name=f"{spec.name}@{_depth+1}")
for e in sub.run(prompt):
    on_event and on_event(sub.name, e)
return final_text(sub.last_messages) or "(子代理没有产出文本)"
```

- **prompt 必须自包含**:子 run 不接收主 `messages`。  
- **工具集由档案决定**:比父更窄是定义方责任;代码只保证 gate 不放宽。  
- **深度**:到 `max_depth` 时子工具箱根本没有 `task`,无法再派——静态封顶。

### 并行从哪来

主模型一轮多个 `task` → 与多个 `read_file` 无异 → `run_tool_calls` 线程池。  
关掉 `Agent.parallel_tools` 则串行,秒表立刻变慢——证明并行属于执行器,不属于 subagents 模块。

### 分支与失败态

| 若出现… | 结果 |
|---|---|
| 未知 agent 名 | 错误字符串(非异常) |
| 子 run 无 AI 文本 | 占位 "(子代理没有产出文本)" |
| 共享有状态 FakeModel | 多 task 抢剧本(k08 陷阱) |
| 父 gate 拒绝某工具 | 子内同样拒绝 |
| `_depth+1 >= max_depth` | 不再追加 task 工具 |

### 与前后章

- **上游 · 第 2 章并行保序、第 3 章隔离作为压缩之外的手段、第 6 章 gate。**  
- **下游 · 第 9 章** `make_task_tool(subagents, model, gate=self.gate)`。  
- **对照 handoff**:本模块是「结论回传」;完整历史移交是另一种工具语义(练习)。

### 只要记住的 5 行逻辑

1. **第一价值是上下文隔离,并行是赠品。**  
2. **`task` = 新 Agent 循环藏在 Tool.func 里。**  
3. **主历史只收 final_text 一条 ToolMessage。**  
4. **gate 下传、工具集收窄、深度构造期封顶。**  
5. **多 task 扇出零新机制,全靠 `run_tool_calls`。**

### 对照验收

`test_subagents`:主历史 tool 条数;深度 2 时孙代无 task;k08 两本账与开关并行秒表。

## 8.10 自测

**Q1. 子代理的第一价值是什么?"并行"排第几?**

<details><summary>想清楚再展开</summary>

第一价值是上下文隔离:探索的几万 token 烧在子代理的窗口里,主历史只落结论——买的是主窗口的注意力质量和 token 经济。并行是搭线程池便车的赠品,排第二。把并行当第一动机,会在强顺序任务上错误地引入多智能体。
</details>

**Q2. 为什么委派 prompt 必须自包含?这是缺陷还是特性?**

<details><summary>想清楚再展开</summary>

因为子代理拿的是全新上下文,看不到主对话——这正是隔离的定义,特性而非缺陷。代价是委派质量要求变高:主模型必须把背景、目标、边界写进任务书。隔离与委派成本是一对不可拆的交易。
</details>

**Q3. "用五个角色代理协作写一个功能"通常为什么不划算?**

<details><summary>想清楚再展开</summary>

编码是强顺序、强共享状态的任务:每步依赖上步产物,拆给互不通信的子代理会产生协调成本和"各写各的合不拢"的失败模式,15 倍 token 换来负收益。甜区是可并行分解、弱耦合、探索量大的任务(调研/审计/批量处理)。口诀:能拆给互不聊天的实习生吗?
</details>

## 8.11 本章小结

- **子代理 = 以工具形态暴露的全新 Agent 循环**:task 工具六十行,对内核完全透明——多智能体没有新机制。
- **第一动机是上下文隔离**:探索烧在子窗口,主历史只落结论;"边界上传什么"(结论,非过程)是第一设计决策。
- **委派说明书两头都是模型**:花名册 description 教主模型派活;prompt 必须自包含,因为子代理没有"刚才"。
- **并行是赠品**:一轮多个 task → 第 2 章线程池自动扇出、保序回填;扇出宽度由模型决定。
- **三条安全纪律**:gate 下传权限只收不放、深度构造期封顶、上下文预算分灶。
- **工程判断**:~15 倍 token 成本;甜区 = 可并行分解 + 弱耦合 + 探索量大;强顺序任务守住单循环。
- **源码阅读顺序**:`SubagentDef` → `task` 闭包建子 Agent → 深度/gate → 对照并行执行器。

内核、上下文、会话、权限、钩子、技能、子代理——零件全齐了。下一章补上最后一块(接入外部工具生态的 MCP),然后把一切组装成完整的 Harness。
