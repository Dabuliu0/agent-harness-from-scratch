# 第 10 章 · 第二条路线:图运行时

> 主线闭环了,现在补上地图的另一半。第 1 章说过,那个循环有一组结构性局限;这九章下来,harness 用"事件日志 + 消息边界 + 壳"解掉了其中一部分——但**不是全部**。本章做三件事:重新盘点六个局限、看清 harness 路线解到什么程度;给出"什么时候必须换图运行时"的选型判据;然后把你送进深入篇(runtime/R1-R7)——在那里亲手造一个 LangGraph。本章不写代码,是主线与深入篇之间的桥。

## 10.1 六个局限,九章之后的重新盘点

深入篇 R1(原两层教程第 2 章)列过循环的六大局限,当时的结论是"全部源于状态和控制流被焊死在进程里"。现在我们有 harness 了,逐条重审——这张表是全书最重要的一张对账单:

| # | 局限 | harness 路线(主线)解到什么程度 | 残余差距(图运行时的主场) |
|---|---|---|---|
| 1 | 存不到磁盘 | ✅ 事件日志:每事件落盘,历史可完整重建(第 5 章) | 已基本解决;图的检查点额外记录**步内进度**(next_nodes) |
| 2 | 无法暂停恢复 | ◐ 打断/崩溃在**消息边界**恢复;审批靠回调阻塞或会话挂起(第 4-6 章) | `interrupt()` 语义更强:任意节点处存盘退出,几天后另一台机器恢复,天然适配"审批等三天"(R4) |
| 3 | 不能并行 | ◐ 一轮内的**工具调用**并行且保序(第 2 章);子代理并行(第 8 章) | 并行的单位只能是"工具"。图能让任意**步骤**并行(多节点同超步),用 Reducer 定义合并语义(R2) |
| 4 | 过程不可见 | ✅ 事件流:全程可见、可流式、可审计(第 4 章) | 已基本解决;图额外提供"每超步状态快照"粒度 |
| 5 | 不能回到历史 | ◐ fork 日志前缀 = 从任意事件分叉(第 5 章) | 检查点时间旅行还能**编辑历史状态**再继续("回到第 5 步,改掉那个变量,重跑")(R3) |
| 6 | 出错只能整体重来 | ✗ 恢复到消息边界,半轮内已执行的副作用可能重做(第 5 章),靠工具幂等兜底 | 检查点 + pending writes:同一步里成功的节点不重做,**节点级重试**(R3/R7) |

诚实的结论:**harness 路线解决了 1 和 4,缓解了 2、3、5,基本没碰 6。** 它的哲学是"够用 + 简单":消息边界粒度的恢复、工具粒度的并行,对交互式 Agent(有人盯着的 Claude Code 场景)绰绰有余。但把场景换成**无人值守的长事务**——跑三天的数据管道、要等审批一周的企业流程、失败重试必须精确到步的批处理——"消息边界"这个粒度就太粗了,你需要把执行切成更细的、有名字的、可单独存档重试的**步骤**。

这正是图运行时的出发点:**把控制流本身变成数据**(节点 + 边),于是每一步都是可存档、可重试、可并行、可回溯的一等公民。

## 10.2 选型判据:什么时候用哪条路线

四个问题问下来,答案就出来了:

**① 步骤能事先列出来吗?**
列不出来(修 bug、调研、开放任务)→ 循环 + harness,模型比你的图聪明。列得出来且顺序就是业务(审批流、管道)→ 图,模型自由发挥是缺陷。

**② 恢复语义要多强?**
"崩了从最近的消息边界续上,大不了模型重看一眼现场" 够用 → harness。"任何一步崩溃,已完成步骤绝不重做,副作用精确一次" → 图(或图背后的 durable execution 引擎)。

**③ 谁在回路里?**
人盯着、随时能纠偏 → harness 的交互式形态是甜区。无人值守跑长活 → 图的确定性和可审计每一步更让人睡得着。

**④ 团队要什么样的可解释性?**
"看事件日志复盘" 能接受 → harness。"合规要求每个决策点是显式节点、能画出流程图给审计看" → 图。

经验法则(与 2026 年行业实践一致):**产品形态像"助手/copilot/编码代理"的,选家族 A;形态像"业务流程自动化/管道"的,选家族 B;两者都像的,常见组合是"图做骨架、循环做器官"——外层用图钉死业务硬约束,某几个节点内部跑一个自由的 agent 循环。** LangChain 1.x 的 `create_agent` 正是这个组合的产品化:图运行时打底,上面跑标准 agent 循环。

## 10.3 图运行时的核心洞察(先给地图再上路)

深入篇六章会从零造出整个运行时,这里先把三个核心洞察给你,读起来就不是陌生行军:

1. **Agent 的控制流带环,DAG 调度器处理不了。** model→tools→model 转几圈由模型定,没有拓扑排序。所以要用支持环的 **Pregel/BSP(整体同步并行)** 模型:执行切成一个个"超步",超步内并行、超步间同步提交(R1 末尾、R2)。
2. **并行写状态,靠 Channel + Reducer 拿回确定性。** 多个节点同一超步写同一个 key,用声明式的合并函数(追加?覆盖?求和?)决定结果——你在第 2 章见过它的最小特例(工具结果保序),图把它推广成了正式抽象(R2)。
3. **"超步之间的空隙"是一切能力的插入点。** 存档(检查点)、暂停(interrupt)、汇报(stream)、重试,全都发生在两个超步之间——和主线"每个 yield 都是缝隙"(第 4 章)是同一个思想,只是图把缝隙做成了带事务语义的提交点(R3/R4)。

你会发现深入篇处处有主线的影子(R0 导读里有一张完整的对读表)。这不是巧合:**两条路线是同一组问题在不同形式化程度下的解**。学完两边,你对"状态、控制流、恢复、并发"这四件事的理解会合成一张完整的图——那才是框架作者的视角。

## 10.6 本章小结

- **对账单**:harness 解决了持久化与可见性,缓解了暂停/并行/回溯,没解决细粒度重试;差距全部指向"步骤"这个更细的执行单位。
- **选型四问**:步骤可枚举吗?恢复要多强?人盯不盯?审计要什么形状?助手形态选 A,流程形态选 B,复杂系统"图做骨架、循环做器官"。
- **图运行时三洞察**:带环所以 Pregel/BSP;并行确定性靠 Channel+Reducer;超步间隙是一切能力的插入点——与主线"yield 即缝隙"同源,形式化程度不同。
- **目录桥**:主线代码停在 tinycore/tinyharness;深入篇转向 runtime 文稿 + runtimev1/tinygraph|tinyagent。
