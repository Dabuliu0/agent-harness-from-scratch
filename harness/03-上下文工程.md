# 第 3 章 · 上下文工程

> 循环能转、工具能干活之后,决定 Agent 成色的就是一件事:**每一轮,模型到底看到什么。** 这件事在 2026 年有个正式学科名——上下文工程(context engineering),它是 prompt 工程的继任者:prompt 工程管"指令怎么写",上下文工程管"整个窗口里放什么、留什么、扔什么"。本章手写它的全套机制:system prompt 装配、项目记忆文件、token 测量、两档压缩、结构化笔记。代码:`tinycore/context.py`。

## 3.1 为什么上下文是稀缺资源

一个反直觉的事实:上下文窗口从 8K 一路涨到 100 万 token,但"往里多塞东西"反而越来越明确地是**错的**。两个原因:

**① 注意力被摊薄(context rot)。** Transformer 里每个 token 要和其他所有 token 计算关联,n 个 token 就是 n² 对关系。窗口越满,模型的"注意力预算"摊得越薄——像一个班从 10 个学生扩到 500 个,老师还是那一位,分到每个学生身上的关注必然稀释。实验反复证实:随着上下文变长,模型对其中信息的精确回忆能力**下降**,长窗口的尾部尤其如此。窗口是物理容量,不是有效容量。

**② token 是真金白银。** 输入 token 按量计费,而且 Agent 的历史是**每轮整卷重发**的(第 1 章):一个 10 万 token 的历史跑 20 轮,就是 200 万输入 token。上下文管理直接就是成本管理。

Anthropic 的工程博客把上下文工程的目标压成一句话,值得贴在显示器上:

> **找到那组最小的高信号 token 集,最大化你想要的结果的概率。**

围绕这句话,行业收敛出三大技术:**压缩(compaction)**、**结构化笔记(外部记忆)**、**子代理隔离**。前两个本章手写,第三个是第 8 章的主角。

## 3.2 上下文的解剖:一次模型调用里到底有什么

先建立解剖学。第 1 章说过模型是无状态的——所谓"上下文",就是**每一轮现场重建、用完即弃的一次性输入**。拆开看,它由四部分组成:

```
┌───────────────────────────────────────────┐
│ system prompt        ← 每轮装配(本章 3.3)   │  身份指令、环境信息、
│                                            │  项目记忆、技能清单…
├───────────────────────────────────────────┤
│ 工具 schema           ← bind_tools 自动带   │  每个工具的说明书,
│                                            │  也占 token!
├───────────────────────────────────────────┤
│ 对话历史 messages     ← 唯一"越滚越长"的部分 │  user/assistant/tool,
│                                            │  压缩的主战场(3.6)
├───────────────────────────────────────────┤
│ 本轮新输入            ← 用户消息/注入        │
└───────────────────────────────────────────┘
```

看清这张图,"上下文管理"就从玄学变成了四个具体问题:system 该放什么(3.3-3.4)、工具该带几个(第 7 章技能给出渐进披露的答案)、历史怎么不爆(3.6)、以及怎么知道快爆了(3.5)。

顺便消除一个普遍误解:工具 schema 也占上下文。挂 50 个工具、每个说明书 200 token,还没开始对话就烧掉 1 万 token,而且模型面对大工具堆时选择质量会下降。**工具不是越多越好**——这个问题的正解(按需披露)放在第 7 章。

## 3.3 system prompt:装配,而不是存储

`tinycore` 有个和多数入门实现不同的设计,第 1 章埋过伏笔:**system prompt 不进 `messages` 历史,每轮由 ContextManager 现场装配**。打个比方:指令是写在办公室白板上的,每天上班现看一眼(装配)——而不是抄进日记第一页永久封存(存历史)。白板今天改了,明天照新的办;日记里的旧指令则会一直跟着你。

```python
# tinycore/context.py
@dataclass
class ContextManager:
    max_context_tokens: int = 60_000
    compact_threshold: float = 0.75
    keep_recent: int = 12
    memory_cwd: Optional[str] = None     # 从哪加载 AGENTS.md
    extra_context: str = ""              # harness 注入的附加段(技能清单等)

    def assemble(self, system_prompt: str, messages: Messages) -> Messages:
        parts = [system_prompt.strip()] if system_prompt else []
        if self.memory_cwd:
            mem = load_memory_files(self.memory_cwd)
            if mem:
                parts.append("# 项目记忆\n" + mem)
        if self.extra_context:
            parts.append(self.extra_context.strip())
        sys = "\n\n".join(parts)
        return ([SystemMessage(content=sys)] if sys else []) + list(messages)
```

为什么"装配"优于"存进历史第一条"?三个理由,一个比一个硬:

1. **改了立即生效。** 记忆文件、技能清单是会变的。存进历史,改动要等新会话;每轮装配,下一轮就是新版。
2. **恢复会话不带陈旧指令。** 第 5 章从日志恢复会话时,历史里如果躺着三个月前的 system prompt,它会和当前版本打架。历史只存"发生过的对话",指令永远取当前值。
3. **一份不重复。** 历史里存 system,压缩、重放、分叉时都要小心翼翼绕开它;不存,这些逻辑都简单一截。

装配的分层结构(身份指令 → 项目记忆 → 附加注入)也是刻意的:它就是 Claude Code 组装 system prompt 的次序——产品指令、CLAUDE.md、环境信息、技能与 hook 注入,层层叠加。我们的 `extra_context` 字段现在空着,第 7 章技能清单、钩子注入都从这里进来。

## 3.4 项目记忆文件:记忆放在文件系统里,不在模型里

"Agent 怎么知道这个项目用 pnpm 不用 npm、测试怎么跑、哪些目录不能碰?"2026 年全行业的答案惊人一致:**写在仓库里的 markdown 文件**——Claude Code 叫 `CLAUDE.md`,跨厂商惯例叫 `AGENTS.md`(OpenAI、Google 等几十家已采纳)。harness 启动时自动读入,拼进 system prompt。

```python
# tinycore/context.py —— 完整实现
def load_memory_files(cwd: str,
                      names: Tuple[str, ...] = ("AGENTS.md", "CLAUDE.md")) -> str:
    """从 cwd 逐级向上收集项目记忆文件,外层在前、内层在后。"""
    chunks: List[str] = []
    d = os.path.abspath(cwd)
    seen = []
    while True:                                  # 一路向上走到文件系统根
        for name in names:
            p = os.path.join(d, name)
            if os.path.isfile(p):
                seen.append(p)
                break                            # 同目录多个候选只取第一个
        parent = os.path.dirname(d)
        if parent == d:                          # 到根了(dirname("/") == "/")
            break
        d = parent
    for p in reversed(seen):                     # 反转:根目录的在前,cwd 的在后
        with open(p, "r", encoding="utf-8") as f:
            chunks.append(f"<memory source={p!r}>\n{f.read().strip()}\n</memory>")
    return "\n\n".join(chunks)
```

跑一下建立体感——假设目录结构与文件如下:

```
/work/repo/AGENTS.md            → "统一用 pnpm;禁改 legacy/"
/work/repo/packages/web/AGENTS.md → "本包测试命令:pnpm test:web"
```

在 `packages/web` 下调用,得到(注意顺序:仓库级在前、子包级在后):

```
<memory source='/work/repo/AGENTS.md'>
统一用 pnpm;禁改 legacy/
</memory>

<memory source='/work/repo/packages/web/AGENTS.md'>
本包测试命令:pnpm test:web
</memory>
```

两个设计点:

- **逐级向上收集**:`~/work/repo/packages/web/` 下启动,会依次收集 `repo/AGENTS.md`(仓库级规范)和 `packages/web/AGENTS.md`(子项目细则)。**内层排在后面**——离工作目录越近的越具体,出现顺序即优先级(模型对后出现的指令更敏感,冲突时以内层为准)。
- **来源标注**:每段包上 `<memory source=...>`,模型知道这段话从哪来,用户调试时也能一眼看出是哪个文件在起作用。

这套机制的哲学值得单独说:**记忆的正确位置是文件系统,不是模型,也不是黑盒数据库。** 文件可 review、可版本控制、可团队共享("给 Agent 的 onboarding 文档进 PR 一起评审"已是 2026 年的普遍工程实践),而且天然接上第 2 章的工具——Agent 自己也能读写自己的记忆(`edit_file("AGENTS.md", ...)`,这正是 Claude Code `/memory` 的本质)。

## 3.5 测量:测不到就管不了

压缩的触发要靠数字说话。真实 token 数只有 provider 的分词器知道,但工程上两级近似足够做决策:

```python
# tinycore/context.py —— 完整实现
def estimate_tokens(messages: Messages) -> int:
    """估算这串消息的 token 规模:精确锚点 + 增量粗估。"""
    base, start = 0, 0
    for i in range(len(messages) - 1, -1, -1):        # 从后往前找锚点
        m = messages[i]
        if isinstance(m, AIMessage) and m.usage.input_tokens:
            base = m.usage.input_tokens + m.usage.output_tokens   # ① 精确部分
            start = i + 1
            break
    rough = sum(len(m.content or "") // 4 + 8 for m in messages[start:])   # ② 粗估部分
    return base + rough
```

聪明处在 ①:第 1 章的 `AIMessage.usage` 在这里兑现——**上一轮 API 已经替你精确数过一次了**。一条 AI 消息的 `input_tokens` 是"它之前的全部历史"的精确 token 数,`output_tokens` 是它自己的——两者相加,恰好等于"到这条消息为止的整个历史"。拿它当锚点,只粗估锚点之后的增量,误差被限制在最近几条消息内。纯启发式(字符 ÷4 + 每条 8 的消息结构开销,中英混排的保守值)只在冷启动时兜底。

拿一串具体消息走一遍算法:

```
messages = [Human(200字), AI(usage: in=180, out=50), Tool(4000字), Human(30字)]
                              ↑ 锚点在 i=1
估算 = (180 + 50)                    ← 精确:截至 AI 消息的全部
     + (4000//4 + 8) + (30//4 + 8)   ← 粗估:锚点之后的 Tool 与 Human
     = 230 + 1008 + 15 = 1253 tokens
```

要点:粗估的只有"上一轮之后新进来的消息"(通常就是几条工具结果 + 一条用户输入),所以误差不随对话变长而累积——**对话越长,这个估算反而越准**,因为精确锚点占比越大。

`ContextManager.should_compact` 由此只是一行比较:估算值超过 `max_context_tokens × compact_threshold`(默认 75%)就该压了。留 25% 余量不是保守——压缩本身也要一次模型调用,得给它留出空间,而且要在"撞墙"之前从容地压,而不是撞了再压。

## 3.6 压缩:两档手术

### 第一档:工具结果清理(最轻,先用它)

回想上下文解剖图:历史里最占地方的是工具结果,而一个工具结果被模型消费过之后,**极少需要再读原文**——结论已经沉淀进后续的 AI 消息里了("我读了 config.py,发现端口写死成 8080")。所以第一档手术只动工具结果:

```python
# tinycore/context.py —— 完整实现
@staticmethod
def clear_old_tool_results(messages: Messages, keep_recent: int = 8,
                           placeholder: str = "[旧工具结果已清理,共 {n} 字符]") -> Messages:
    """把久远的工具结果原文替换成占位符,消息结构原样保留。"""
    out: Messages = []
    boundary = max(0, len(messages) - keep_recent)      # 最近 keep_recent 条不动
    for i, m in enumerate(messages):
        if i < boundary and isinstance(m, ToolMessage) and len(m.content) > 200:
            out.append(ToolMessage(content=placeholder.format(n=len(m.content)),
                                   tool_call_id=m.tool_call_id,   # ★ 配对关系必须保留
                                   name=m.name))
        else:
            out.append(m)
    return out
```

三个细节都有讲究:`> 200` 的门槛让短结果("已编辑 xx")原样保留——清它们省不了几个 token 还丢信息;**新建 ToolMessage 而不是原地改**,原对象可能还被会话日志等别处引用(不可变数据的纪律);`tool_call_id` 原样带上——结构不动(id 配对关系都在),只把陈年原文换成占位符。这是无损性价比最高的一刀:Anthropic 把同样的机制做成了 API 级功能(tool result clearing),Claude Code 五级压缩管线里最先动的也是它。占位符照例带元信息("共 N 字符")——模型真需要时,可以用工具重新获取。

### 第二档:compaction(摘要重启)

清理不够时上第二档:把早期历史交给模型摘要成一段"前情提要",替换掉原文:

```python
# tinycore/context.py
def compact(self, messages, model) -> Messages:
    cut = _safe_cut(messages, self.keep_recent)      # ① 找安全切点
    head, tail = messages[:cut], messages[cut:]
    summary = model.invoke([SystemMessage(_SUMMARIZE_PROMPT),
                            HumanMessage(_render_transcript(head))])   # ② 摘要
    recap = HumanMessage("[前情提要——早前对话已压缩,以下是摘要]\n" + summary.content)
    return [recap] + list(tail)                       # ③ 摘要 + 最近若干条
```

三个环节各有讲究:

**① 切点必须"安全"。** 不能把一条带 `tool_calls` 的 AI 消息和它的工具结果拆开——provider 会直接拒绝这种"孤儿工具结果"。`_safe_cut` 从 `len - keep_recent` 往回退,直到保留段不以 `ToolMessage` 开头:

```python
def _safe_cut(messages, keep_recent):
    cut = max(0, len(messages) - keep_recent)
    while cut > 0 and isinstance(messages[cut], ToolMessage):
        cut -= 1
    return cut
```

这个"消息边界不是处处平等,有些位置不可切"的意识,第 5 章崩溃恢复时会再次用到——同一个不变量:**任何时刻落盘/重建的历史,必须是 provider 眼里合法的序列**。

**② 摘要 prompt 决定压缩质量。** 这是全书第一段"值得逐字推敲"的 prompt,原文照录:

```python
# tinycore/context.py
_SUMMARIZE_PROMPT = """\
你是对话压缩器。把下面这段 Agent 工作记录压缩成一份"前情提要",供同一个 Agent \
继续工作使用。必须保留:用户的原始目标与约束、已完成的事与关键结论、正在进行的事、\
尚未解决的问题、重要的文件路径/命令/数据。省略:寒暄、失败后已被纠正的弯路细节、\
工具输出的原文(只留结论)。用条目式中文输出。"""

def _render_transcript(messages: Messages) -> str:
    """把消息列表渲染成给压缩器读的纯文本(工具调用只留摘要行)。"""
    lines = []
    for m in messages:
        if isinstance(m, AIMessage) and m.tool_calls:
            calls = "; ".join(f"{c.name}({c.args})" for c in m.tool_calls)
            lines.append(f"[assistant 调用工具] {calls}")
            if m.content:
                lines.append(f"[assistant] {m.content}")
        else:
            lines.append(f"[{m.role}] {m.content}")
    return "\n".join(lines)
```

拆解它的取舍:开头一句**说明用途和读者**("供同一个 Agent 继续工作使用"——摘要是写给机器的工作交接,不是给人的会议纪要,风格要求完全不同);"必须保留"五项里**用户的原始目标排第一**——压缩最危险的丢失就是"用户最初到底要什么",它一丢,Agent 后半程会渐渐跑偏(真实产品的 compaction prompt 同样把 user intent 放模板第一条);"省略"三项专治历史里的三大注水源:客套、已纠正的弯路、工具原文(结论已沉淀进后续 AI 消息,原文纯属遗物)。`_render_transcript` 也在配合省 token:喂给压缩器的记录里,工具调用只render 成一行摘要。**压缩丢什么比留什么更需要设计**——你以后调 compaction 质量,九成时间花在这段 prompt 上。

**③ 摘要以 HumanMessage 进入历史。** 不是 system(它是"发生过的事"不是"指令"),带显式标记 `[前情提要]`,模型和读日志的人都一眼可辨。

**④ 陈旧锚点陷阱(一个被真实运行揪出来的 bug)。** 本书初版的 `compact` 少写了三行,第一次跑示例就露馅:压缩事件打出 `COMPACTION: 1554 → 1554`——压完估算纹丝不动。原因值得写进你的直觉库:保留尾段里的 AI 消息,其 `usage.input_tokens` 记的是**压缩前**完整历史的账;3.5 节的 `estimate_tokens` 恰恰优先信任这种锚点,于是压缩后它仍然按旧账高估。**压缩即换纪元,旧纪元的账单必须作废**:

```python
# compact() 的最后三行:清掉尾段的旧账单
fresh_tail = [replace(m, usage=Usage()) if isinstance(m, AIMessage) else m
              for m in tail]
return [recap] + fresh_tail
```

清零后,估算退回启发式兜底,下一轮模型调用会带来新纪元的第一个精确锚点,一切归位(预算统计不受影响——它在每轮 `turn_end` 已经累计过了)。这个 bug 的教训比它本身值钱:**带缓存/锚点性质的优化,都要回答"什么事件会让缓存失效"**——这里的答案是 compaction。

效果有多大?Anthropic 给过一个生产数据:服务端 compaction 在 100 轮 web 搜索评测里省了 **84%** 的 token。我们这个几十行的实现,机制与之同构。

### 接进循环

回看第 1 章 `loop.py` 里预留的位置——每轮调模型**之前**:

```python
# tinycore/loop.py(节选)
if self.context and self.context.should_compact(messages):
    before = estimate_tokens(messages)
    messages = self.context.compact(messages, self.model)
    yield Event(ev.COMPACTION, {"before_tokens": before,
                                "after_tokens": estimate_tokens(messages)})
```

挂上即生效:

```python
agent = Agent(model=model, tools=tools,
              context=ContextManager(max_context_tokens=60_000, memory_cwd="./ws"))
```

压缩发生时吐一个 `COMPACTION` 事件——用户该**看见**它(mini_code 里渲染成一行灰字),因为压缩后模型的"记性"会有可感知的变化,静默压缩会让用户以为模型抽风。

## 3.7 结构化笔记:把状态写进文件系统

压缩再好也是有损的。第三个技术从另一个方向解题:**别让关键状态只活在上下文里。** 让 Agent 把计划、进展、结论写进文件——文件不占上下文(要用再读),不怕压缩(它不在被压的历史里),跨会话存活(第 5 章恢复后照样在)。

第 2 章的 `todo_write` 就是为此准备的。配合 system prompt 里的一句话规范(我们的 harness 默认词里就有):

> 多步任务先用 todo_write 列计划,完成一步更新一步。

于是长任务的轨迹变成:模型先写下 5 步计划 → 每完成一步更新状态 → **compaction 发生后,摘要 + todo 文件足以让它精确接续**,而不是靠摘要里模糊的"好像做到第三步了"。Claude Code 的 TodoWrite、Devin 的 planning、Manus 干脆让 Agent 反复重写一个 todo.md 再读回来——同一个思想:**上下文会挥发,文件系统不会**。工程里还有个免费加强版:让 Agent 常做 `git commit`,提交历史本身就是最好的进度笔记(压缩后 `git log` 一眼回到现场)。

到此,上下文工程三大技术已经齐了两个半:压缩(本章)、结构化笔记(本章)、子代理隔离(第 8 章——那是"让别人替你烧上下文"的艺术)。

## 3.8 跑起来:离线看一次完整的压缩

`examples/k03_context.py` 用 FakeModel 把整个机制演一遍(压缩机制不需要智能,剧本模型足够):`max_context_tokens=1500`,剧本连读三篇长文档灌满窗口。有个剧本编排细节先提醒:**compact 内部那次摘要调用也消耗剧本**,所以剧本顺序是"三次读文档 → 摘要台词 → 最终回显"。实际输出:

```
== 运行(观察 token 增长与压缩事件) ==
  轮 1 结束
  轮 2 结束
  轮 3 结束
  ★ COMPACTION: 1554 → 1058 tokens

最终回答: 我本轮看到 6 条消息;第一条是 system,开头「# 项目记忆
<memory s…」

结束时历史 ≈ 1064 tokens,结构:
  user: [前情提要——早前对话已压缩,以下是摘要]
- 用户要读 A/B/C 三篇文档并总结;A
  assistant: (工具调用)
  tool: 《文档B》正文:这是很长的文档内容。这是很长的文…
  assistant: (工具调用)
  tool: 《文档C》正文:这是很长的文档内容。这是很长的文…
  assistant: 我本轮看到 6 条消息;第一条是 system,…
```

三处对号入座:压缩发生在第 4 轮调模型**之前**(前三轮把估算顶过了 1500×0.75 的阈值);历史开头的原始长文被一条 `[前情提要]` 替换,文档 A 的原文已经不在了;spy 台词证明模型看到的第一条是**装配出来的 system**(带 AGENTS.md 的项目记忆)——它不在历史里,是每轮现拼的。

再做两个实验:

1. 在工作区放一个 `AGENTS.md` 写上"回答一律以『收到:』开头",挂 `memory_cwd` 后跑一轮,再改文件内容跑第二轮——**装配式 system 让改动下一轮即生效**,不用重开会话。
2. 用真实模型跑一个 20+ 轮的任务(比如让它逐个读十个文件再总结),观察 `usage` 数字的增长、compaction 触发点,以及压缩后它是否还记得最初目标——如果跑偏了,回去改 `_SUMMARIZE_PROMPT`,这就是上下文工程的日常。

## 3.9 动手:把本章抄成代码(验收标准)

写 `tinycore/context.py`(~170 行),建议顺序:

1. `estimate_tokens`(锚点 + 粗估)——自查:手算 3.5 节那个 4 条消息的例子,和函数输出一致。
2. `load_memory_files`(逐级向上 + 反转)——自查:造两级 AGENTS.md,输出顺序外层在前。
3. `ContextManager.assemble`(指令→记忆→附加,三段拼装)——自查:用 FakeModel 跑一轮,翻 `model.calls[0][0]`,看到拼好的 SystemMessage。
4. `_safe_cut` → `_render_transcript` → `_SUMMARIZE_PROMPT` → `compact`(含清账单三行)——自查:构造一个"切点落在工具批中间"的历史,手工核对 `_safe_cut` 回退到了 AI 消息之前。
5. `clear_old_tool_results`——自查:清理后 `tool_call_id` 原样保留、短结果未动。
6. 最后把压缩接进你的循环(第 1 章 Agent 的 `context` 参数位),跑 `k03_context.py` 比对输出。

改造练习(可选,难度递增):把触发阈值从"估算值"换成"上一轮 usage 的精确值 + 安全余量";compaction 前自动调一次 `clear_old_tool_results`(两档联动,Claude Code 的做法);给 recap 加"保底注入"——无论摘要质量如何,把用户第一条消息原文附在前情提要末尾(治"忘了初心"的最后一道保险)。

## 3.10 源码解析与代码逻辑

> 动手是"抄得出来";这一节是"讲得清楚"。
> 正文已按装配/测量/压缩分块讲过——这里收成**决策序**与几处最容易写错的铰链。
> 打开仓库:`tinycore/context.py`,并对照 `tinycore/loop.py` 里调用它的 ② 段。

### 生活类比

上下文像**出差行李箱**:容量有限(预算);登机前现场装洗漱包(每轮 `assemble`);超重先扔旧收据再写行程摘要(`clear` → `compact`);公司手册放酒店前台文件夹(`AGENTS.md`),不缝在行李箱夹层里。

```
loop 每轮开头
    │
    ├─ should_compact(messages)? ──是──► compact(model) ──► 可能 yield COMPACTION
    │                                      │
    │                                      └─ _safe_cut → 摘要 head → [recap]+fresh_tail
    │
    └─ working = assemble(system_prompt, messages)
         = [System(指令+记忆+extra)] + 历史
         → model.invoke/stream(working)
```

注意:`clear_old_tool_results` **没有**自动接进 `Agent.run`——它是给你/harness 在 compact 前手动或策略性调用的轻档手术。读源码时别假设循环会隐式清理。

### 源码地图

| 顺序 | 符号 | 带走一件事 |
|---|---|---|
| 1 | `estimate_tokens` | 从后往前找带 `usage.input_tokens` 的 AI 作锚,其后字符粗估 |
| 2 | `load_memory_files` | 向上收集路径,`reversed` 后根目录在前、近 cwd 在后 |
| 3 | `assemble` | 只拼 **当轮** System,不写回 `messages` |
| 4 | `_safe_cut` | 保留段不以 `ToolMessage` 开头 |
| 5 | `compact` | head 摘要成 HumanMessage recap;tail 清 usage 账单 |
| 6 | `clear_old_tool_results` | 旧 Tool 原文→占位符,`tool_call_id` 保留 |

### 主路径:装配

```python
# tinycore/context.py —— assemble
parts = [system_prompt.strip()] if system_prompt else []
if self.memory_cwd:
    mem = load_memory_files(self.memory_cwd)
    if mem: parts.append("# 项目记忆\n" + mem)
if self.extra_context:
    parts.append(self.extra_context.strip())
sys = "\n\n".join(parts)
return ([SystemMessage(content=sys)] if sys else []) + list(messages)
```

三段顺序固定:**身份指令 → 项目记忆 → harness 附加**(第 7 章技能清单走 `extra_context`)。  
历史原样拼接在后——压缩改的是 `messages`,装配只读它。

### 主路径:测量与是否压缩

```python
def should_compact(self, messages):
    return estimate_tokens(messages) > self.max_context_tokens * self.compact_threshold
```

默认 60k × 0.75 = 45k 触发,给摘要调用本身留余量。  
`estimate_tokens` 逻辑:

1. 倒序找最近一条 `AIMessage.usage.input_tokens > 0`
2. `base = input + output`(上一轮「模型看见的整卷」精确账)
3. 该条之后的新消息用 `len//4 + 8` 粗估累加

没有 usage 时整卷粗估——FakeModel 会填粗 usage,离线也能触发压缩(见 k03)。

### 主路径:compact 三步

**① 安全切点**

```python
# tinycore/context.py
cut = max(0, len(messages) - keep_recent)
while cut > 0 and isinstance(messages[cut], ToolMessage):
    cut -= 1
```

若 `keep_recent` 恰切在某次工具结果上,向前退到配对 AI 之前(或更早),避免孤儿 `ToolMessage`。

**② 摘要**

`head = messages[:cut]` 经 `_render_transcript` 变成纯文本(工具调用写成一行摘要,不扔整段结果原文进压缩 prompt),再 `model.invoke([System(_SUMMARIZE_PROMPT), Human(transcript)])`。

**③ 换纪元**

```python
recap = HumanMessage(content="[前情提要……]\n" + summary_ai.content)
fresh_tail = [
    replace(m, usage=Usage()) if isinstance(m, AIMessage) else m
    for m in tail
]
return [recap] + fresh_tail
```

- recap 用 **Human** 角色:像用户塞进来的工作笔记,后续模型继续聊。
- **清 usage**:tail 里 AI 的 usage 仍记着压缩前的 input 规模;不清则 `estimate_tokens` 锚在陈旧高水位,会**刚压完又判定超阈**。注释里的「陈旧锚点陷阱」就是这三行的 why。

`cut <= 1` 时直接原样返回——几乎无头可压。

### clear_old_tool_results

只动 `i < boundary` 且 `len(content) > 200` 的 `ToolMessage`:换成占位符,但 **新建** `ToolMessage` 时带上原 `tool_call_id`/`name`。  
结构合法、配对还在、token 大降。短结果不动,避免把「exit 0」这类也抹掉。

### 与 loop 的接缝(第 4 章已实现)

```python
# tinycore/loop.py ②
if self.context and self.context.should_compact(messages):
    messages = self.context.compact(messages, self.model)
    yield Event(COMPACTION, {...})
working = self.context.assemble(...) if self.context else ...
```

压缩改的是**持久历史** `messages`;装配产出的 `working` 只用于当轮调用。  
不挂 `context` 的 Agent = 全量历史 + 可选裸 system,行为退回第 1 章。

### 分支与失败态

| 若出现… | 落点 | 结果 |
|---|---|---|
| 无 memory 文件 | `load_memory_files` | 空串,assemble 不加记忆段 |
| 同目录 AGENTS+CLAUDE | 只取 names 元组里先命中的 | 默认 AGENTS 优先 |
| 摘要模型失败 | `compact` 内 `invoke` | 异常上抛(loop 会 ERROR) |
| tail 全是 Tool 开头且 cut 退到 0 | `_safe_cut` | 可能几乎整卷进 head |
| 未清 usage 的错误实现 | `estimate_tokens` | 压缩震荡/假阳性 |
| 只 clear 不 compact | 手工策略 | 结构在、仍可能超大 |
| `extra_context` 巨长 | assemble | 占 system 预算,需 harness 自律 |

### 与前后章

- **上游 · 第 1 章整卷重发 + Usage 字段**——测量锚点与「历史会爆」的根源。  
- **上游 · 第 2 章结果截断**——第一道闸;本章是历史级第二道。  
- **下游 · 第 4 章**——`COMPACTION` 事件让用户看见动刀。  
- **下游 · 第 5 章**——合法切点不变量 = 会话半轮修剪的同一精神。  
- **下游 · 第 7 章**——`extra_context` 挂技能目录。  
- **下游 · 第 8 章**——子代理自己的短历史,是另一种「不占主上下文」。

### 只要记住的 5 行逻辑

1. **system 每轮 `assemble`,永不进长期 `messages`。**  
2. **测不到就管不了:`usage` 锚 + 粗估驱动 `should_compact`。**  
3. **`_safe_cut` 禁止拆开 tool_calls 与 ToolMessage。**  
4. **compact = recap(Human) + 清过 usage 的 tail。**  
5. **clear 是轻档、默认不自动跑;与 compact 组合是策略不是内核强制。**

### 对照验收

手算一段带 usage 的历史对一下 `estimate_tokens`;构造切在工具批中间的列表断言 `_safe_cut`;跑 `examples/k03_context.py` 看压缩前后条数与 COMPACTION 事件。

## 3.11 自测

**Q1. 为什么 system prompt 要"每轮装配"而不是"存进历史第一条"?**

<details><summary>想清楚再展开</summary>

三个理由:记忆文件/技能清单变了下一轮即生效;第 5 章恢复会话时不会带出与当前版本打架的陈旧指令;历史里不存 system,压缩/重放/分叉的逻辑都不用绕开它。本质:历史记录"发生过的对话",指令取"当前值",两者生命周期不同,不该存在一起。
</details>

**Q2. compaction 的切点为什么不能落在任意消息之间?**

<details><summary>想清楚再展开</summary>

带 `tool_calls` 的 AI 消息和它的 ToolMessage 结果是配对的原子组:切在中间会产生"孤儿工具结果",provider 直接报错拒绝。`_safe_cut` 从目标位置回退到保留段不以 ToolMessage 开头为止。这个不变量(落盘/重建的历史必须是合法序列)第 5 章崩溃恢复会再次用到。
</details>

**Q3. 压缩、结构化笔记、子代理隔离三者各自的适用场景?**

<details><summary>想清楚再展开</summary>

压缩适合"必须在同一条对话里继续"的长交互(有损,注意保住原始目标);结构化笔记适合"有明确里程碑的长任务"(计划/进展写进文件,零上下文成本、跨压缩跨会话存活);子代理隔离适合"探索量大但主对话只要结论"的子任务(几万 token 的翻找留在子代理,主历史只落一段结论,第 8 章)。生产 harness 三个全用,按场景组合。
</details>

## 3.12 本章小结

- **上下文是稀缺资源**:注意力随 token 数摊薄(context rot),历史每轮整卷重发即成本。目标:最小高信号 token 集。
- **解剖**:一次调用 = system(装配)+ 工具 schema + 历史 + 新输入。只有历史越滚越长,它是压缩的主战场;工具 schema 也占预算。
- **装配优于存储**:system 每轮由 `assemble` 现场拼(指令 → 项目记忆 → 附加注入),改动即生效、恢复不带旧指令。
- **记忆在文件系统**:AGENTS.md 逐级向上收集、内层优先;可 review、可版本控制、Agent 自己也能改。
- **测量**:以最近一次 API 报告的 usage 为精确锚点 + 增量粗估;75% 阈值提前压,给压缩本身留余量。
- **两档压缩**:先清旧工具结果(结构保留、原文换占位符),再 compaction(安全切点 + 摘要 prompt 保目标丢弯路 + HumanMessage 进历史);压缩要吐事件让用户看见。
- **结构化笔记**:todo/笔记/git 提交把关键状态挪出易挥发的上下文——上下文会挥发,文件系统不会。
- **源码阅读顺序**:`estimate_tokens` → `assemble`/`load_memory_files` → `_safe_cut`/`compact` → 对照 loop ②;弄清 clear 不在自动路径上。
