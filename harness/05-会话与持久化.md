# 第 5 章 · 会话与持久化

> 从本章起造壳(tinyharness,L2)。第一块砖回答最基本的托管问题:**进程死了,对话还在吗?** Harness 路线的答案和你直觉里的"把状态存进数据库"不一样——不存状态,存**事件日志**:每发生一件事往文件尾追加一行 JSON,"当前状态"永远从日志**重放**推导。这一个决定同时买到了持久化、崩溃恢复、完整审计和分叉四样东西。代码:`tinyharness/session.py`。

## 5.1 存什么:状态快照 vs 事件日志

要让对话跨进程存活,有两种世界观:

- **存状态快照**:每步把"当前完整状态"序列化存下来,恢复 = 读最新快照。这是图运行时家族的检查点方案(深入篇 R3 整章)。它能力强(时间旅行、按步重试),但有个前提:得先把"状态"和"步"定义清楚——所以那条路线先造了图。
- **存事件日志(append-only log)**:只记录"发生过什么",每条事件在文件末尾追加一行,写过的行永不修改;任何时刻的状态 = 从头把日志重放一遍推导出来。这是 harness 家族的选择——Claude Code 的会话就是一个个 JSONL 文件(`~/.claude/projects/**/*.jsonl`),`--resume` 就是重放。

用记账打比方最容易分清这两种世界观。想知道钱包里有多少钱,一种办法是每天晚上拍一张钱包照片(快照);另一种是记流水账——只记"收入 50""支出 12",**余额从来不直接存,要用时从头把流水加一遍就得到了**(日志)。流水账看似绕,好处却硬:每笔都有据可查(审计),想知道"上周三时我有多少钱"随时能算(历史任意点),记错了也只会错最后一笔(抗崩溃)。本章选的就是流水账。

为什么循环路线偏爱日志?因为第 4 章已经把执行变成了**一条事件流**——把这条流原样写进文件,持久化就完成了,一行新抽象都不用发明。而且日志天然带三个赠品:

1. **抗崩溃**:追加写最坏丢最后一行,前缀永远完好(对比"改写一个大 JSON 文件"崩在半截的惨状);
2. **全过程审计**:日志里不止消息,还有工具调用、压缩、错误——出事后可以逐事件复盘"它当时到底干了什么";
3. **免费分叉**:复制文件前缀 = 从历史任意点开出平行世界。

(这对世界观在软件史上是老对手:数据库的快照 vs 写前日志 WAL、交易系统的 event sourcing——名字换了几茬,思想就是"照片派"与"流水账派"。第 10 章对比两家时会回到这里。)

## 5.2 Session:一个会话 = 一个 JSONL 文件

先解释文件格式:JSONL(JSON Lines)就是"每行一个独立 JSON 对象"的纯文本文件——不是一个大 JSON 数组,而是一行一条、各自完整。选它正是为了配合"只追加"的写法:新事件来了就在文件尾加一行,前面的行碰都不碰。

写侧的**全部家当**——追加一行、透明转发,没有第三个方法:

```python
# tinyharness/session.py —— 写侧完整代码
class Session:
    """一个会话 = 一个 JSONL 文件。append 记录事件,messages() 重放出历史。"""

    def __init__(self, path: str, session_id: Optional[str] = None) -> None:
        self.path = path
        self.id = session_id or os.path.splitext(os.path.basename(path))[0]

    def append(self, event: Event) -> None:
        line = json.dumps({"ts": event.ts, "type": event.type,
                           "data": to_jsonable(event.data)}, ensure_ascii=False)
        with open(self.path, "a", encoding="utf-8") as f:
            f.write(line + "\n")

    def record(self, event_stream):
        """透明消费者:边转发边落盘。"""
        for e in event_stream:
            self.append(e)
            yield e
```

注意 `append` **每次都重新 open**、写完即关。比常驻文件句柄慢一点,换来的是:任何一行写完,数据就真在磁盘上;进程死在两行之间,文件也处于完好状态。持久化代码里,"简单到不会出错"本身就是特性。

两处对应前几章的伏笔:

- `to_jsonable` 是第 1 章那对序列化函数——事件 payload 里的消息对象带着 `__type__` 标记落盘,读回来能还原成对象。**当初"消息必须可序列化"的纪律,在这里兑现。**
- `record()` 是第 4 章"消费者"哲学的直接产物:它把会话存储做成事件流上的一个**透明管道**——

```python
for e in session.record(agent.run(prompt)):
    render(e)        # UI 逻辑一行不改,持久化已经发生
```

内核不知道会话存在,UI 不知道会话存在,持久化就完成了。第 4 章把事件流定为内核唯一的对外接口时承诺过"新消费者随便加,内核零改动"——会话存储就是第一个来兑现这句承诺的新消费者。

日志长这样(每行一个事件,截断展示):

```jsonl
{"ts": 1753500001.2, "type": "run_start", "data": {"agent": "agent", "input": "修一下 hello.py"}}
{"ts": 1753500001.2, "type": "user_message", "data": {"message": {"__type__": "HumanMessage", "content": "修一下 hello.py", ...}}}
{"ts": 1753500003.8, "type": "assistant_message", "data": {"message": {"__type__": "AIMessage", "tool_calls": [{"name": "read_file", ...}], ...}}}
{"ts": 1753500003.9, "type": "tool_result", "data": {"message": {"__type__": "ToolMessage", "content": "    1\tprint('helo')", ...}}}
```

纯文本、人能读、`grep` 能查、git 能存——朴素形态背后全是运维便利。

## 5.3 重放:状态是推导出来的

日志里事件很多,但**构成对话历史的只有三种**:`user_message`、`assistant_message`、`tool_result`(其余是过程记录)。重放分两步:先把文件读回事件,再过滤出消息。读文件这一步就要开始防崩溃了,完整实现:

```python
# tinyharness/session.py
_MESSAGE_EVENTS = {ev.USER_MESSAGE, ev.ASSISTANT_MESSAGE, ev.TOOL_RESULT}

def events(self) -> List[Event]:
    """把 JSONL 读回事件列表。残行(崩溃产物)静默跳过。"""
    out: List[Event] = []
    if not os.path.exists(self.path):
        return out
    with open(self.path, "r", encoding="utf-8") as f:
        for line in f:
            line = line.strip()
            if not line:
                continue
            try:
                d = json.loads(line)
            except json.JSONDecodeError:
                continue        # ★ 最后一行可能因崩溃而残缺:跳过,前缀仍合法
            out.append(Event(d["type"], from_jsonable(d.get("data", {})),
                             d.get("ts", 0)))
    return out

def messages(self) -> Messages:
    """从事件日志重放出对话历史(resume 的地基)。末尾修剪见 5.4。"""
    msgs: Messages = [e.data["message"] for e in self.events()
                      if e.type in _MESSAGE_EVENTS]
    # …末尾合法性修剪(5.4 节全文)…
    return msgs
```

`from_jsonable` 在这里完成闭环。第 1 章写序列化时说过"第 5 章兑现":落盘时每条消息被 `to_jsonable` 打上 `__type__` 标记(搬家纸箱上的那行字),此刻按标记还原回对象,连嵌套的 `ToolCall` 和它的 id 都原样回来。**重放出的历史与当时的内存对象逐字段相同**——所以恢复后继续对话时,provider 完全看不出"这是个重启过的会话":在它眼里,这就是一段从没中断过的正常历史。

于是"恢复会话"就是:

```python
prior = session.messages()                   # 重放出历史
gen = agent.run(new_prompt, prior_messages=prior)   # 接着聊
```

注意一个第 3 章埋好的呼应:历史里**没有 system prompt**(它每轮装配)。所以恢复到今天的会话,吃的是今天的指令、今天的 AGENTS.md——三个月前的旧指令不会借尸还魂。存储与装配分离,在恢复场景下的价值最直观。

"多轮记忆"到此也彻底祛魅:第 1 章说记忆 = 持续累积的 messages;本章说 messages = 日志的投影。**所谓记忆,不过是一个 append-only 文件。**(跨会话的"长期记忆"——用户偏好、项目画像——则是另一个东西,第 3 章的记忆文件 + 第 11 章练习里的向量库,不要和会话内记忆混为一谈。)

## 5.4 崩溃恢复:合法前缀 + 末尾修剪

崩溃可能发生在任何一行之间。日志方案的恢复语义分两层:

**行级**:最后一行可能写了一半(断电)。读日志时 `json.loads` 失败的行直接跳过——**损失最多一行,前缀永远合法**。

**语义级**:更隐蔽的问题——崩溃可能停在"半轮":比如 AI 消息(带三个 tool_calls)已落盘,工具只执行了两个。重放出的历史若以这种残缺状态结尾,下一次调模型时 provider 会直接拒收。原因和第 3 章压缩找切点时一模一样:**带 tool_calls 的 AI 消息和它的工具结果是不可拆散的原子组**,缺了结果的调用叫"孤儿 tool_calls",provider 不认。所以 `messages()` 末尾有一段**修剪逻辑**,完整代码:

```python
# tinyharness/session.py —— messages() 的末尾修剪(接上文)
while msgs:
    last = msgs[-1]
    calls = getattr(last, "tool_calls", None)
    if calls:                        # 情形A:AI 要了工具,但一个结果都没有
        msgs.pop()                   #        → 裁掉这条 AI 消息,再看新的末尾
        continue
    if getattr(last, "role", "") == "tool":
        # 情形B:末尾是工具结果,但可能"凑不齐一整批"。
        # 先向前找到这批结果所属的 AI 消息:
        i = len(msgs) - 1
        while i >= 0 and msgs[i].role == "tool":
            i -= 1
        need = {c.id for c in getattr(msgs[i], "tool_calls", [])} if i >= 0 else set()
        got = {m.tool_call_id for m in msgs[i + 1:]}
        if need and need != got:     # 该有的和实际有的对不上 → 整个半轮裁掉
            del msgs[i:]
            continue
    break                            # 末尾合法,收工
return msgs
```

逐情形走一遍(拿三个具体的日志尾巴):

```
尾巴① […, AI(calls=[a,b,c])]                 → 情形A:pop 掉 AI → 合法
尾巴② […, AI(calls=[a,b,c]), Tool(a), Tool(b)] → 情形B:need={a,b,c} got={a,b}
                                                 不等 → del 整个半轮 → 合法
尾巴③ […, AI(calls=[a,b]), Tool(a), Tool(b)]  → 情形B:need==got → break,原样保留
```

注意两个实现细节:用**集合**比较而不是数量比较(防"同一个结果写了两次、另一个没写"这种诡异尾巴);`del msgs[i:]` 把 AI 消息和它的残缺结果**一起**裁——只裁结果留 AI,又回到情形 A,还得再转一圈。

裁掉的是"没做完的半轮"——恢复后模型会重新决策这一步。这里藏着一个诚实的取舍:半轮里**已经执行过的工具,副作用可能已经发生**(文件真的写了、命令真的跑了),重新决策就可能把同一件事再做一遍。做两遍要不要紧?取决于操作是否**幂等**——幂等(idempotent)是个值得记住的工程词:同一操作做一次和做多次效果相同。"把文件内容设为 X"是幂等的,重做无害;"往文件末尾追加一行"不幂等,重做一次就多一行。日志方案对此的态度是:恢复到合法边界就够了,剩下靠工具尽量幂等 + 模型自查兜底(模型恢复后往往会先 `read_file` 看看现场再动手)。图运行时对同一个问题给出了更强的答案:检查点连"这一步内做到哪了"都记下来,已成功的部分不重做(R3/R7)。**恢复语义的强度,是两家族真正的分水岭之一**,第 10 章把这笔账算全。

这也再次照亮第 4 章那个不变量:打断/崩溃随时发生,但因为写盘以事件为单位、恢复时修剪到消息边界,**对外可见的历史永远合法**。

## 5.5 SessionStore:恢复、分叉、清单

```python
store = SessionStore(".tinyharness/sessions")
s = store.create()                # 新会话(时间戳+随机后缀命名)
s = store.open("20260726-1030-a1b2c3")   # 恢复
s2 = store.fork("20260726-1030-a1b2c3")  # 分叉:复制日志,开平行世界
store.list()                      # 清单
```

实现全文——四个方法没有一个超过十行,因为"会话仓库"本质上就是"一个目录 + 文件命名约定":

```python
# tinyharness/session.py
class SessionStore:
    """会话仓库:一个目录,每个会话一个 .jsonl 文件。"""

    def __init__(self, root: str = ".tinyharness/sessions") -> None:
        self.root = root
        os.makedirs(root, exist_ok=True)

    def _path(self, session_id: str) -> str:
        return os.path.join(self.root, f"{session_id}.jsonl")

    def create(self, session_id: Optional[str] = None) -> Session:
        sid = session_id or time.strftime("%Y%m%d-%H%M%S-") + uuid.uuid4().hex[:6]
        return Session(self._path(sid), sid)

    def open(self, session_id: str) -> Session:
        path = self._path(session_id)
        if not os.path.exists(path):
            raise FileNotFoundError(f"会话不存在: {session_id}")
        return Session(path, session_id)

    def fork(self, session_id: str, upto_event: Optional[int] = None) -> Session:
        """从既有会话分叉:复制其日志(可截到第 upto_event 行),得到平行新会话。"""
        src = self.open(session_id)
        dst = self.create(f"{session_id}-fork-{uuid.uuid4().hex[:4]}")
        with open(src.path, "r", encoding="utf-8") as f:
            lines = f.readlines()
        if upto_event is not None:
            lines = lines[:upto_event]
        with open(dst.path, "w", encoding="utf-8") as f:
            f.writelines(lines)
        return dst

    def list(self) -> List[str]:
        return sorted(os.path.splitext(fn)[0]
                      for fn in os.listdir(self.root) if fn.endswith(".jsonl"))
```

两个小设计顺带看清:`create` 不碰磁盘(文件在第一次 `append` 时才出现)——空会话不留垃圾文件;`open` 只认文件存在与否,**没有任何"加载"动作**——因为状态本来就不在内存里,`Session` 对象只是一条路径的包装,这正是"日志是唯一事实源"的直接体现。

`fork` 值得多看一眼:实现只是**复制文件**(可选截到第 N 行),语义却是"从历史任意一点开出岔路"——原会话不动,新会话从复制点自由发展。想对比"如果当时换个问法会怎样",fork 两份各走各的。这是日志方案版的"时间旅行":图运行时靠不可变检查点链回到任意超步(R3),我们靠日志前缀回到任意事件——能力形态不同(检查点还能在分叉点**编辑状态**),思想同源:**历史不可变,分叉产生新时间线**。

## 5.6 跑起来:杀进程,再站起来

`examples/k05_sessions.py` 演四幕(全部离线),核心驱动只有这几行:

```python
store = SessionStore(root)
s = store.create("demo")
agent = Agent(model=FakeModel([[ToolCall("get_weather", {"city": "上海"})],
                               "上海晴,25 度。"]), tools=[get_weather])
for _ in s.record(agent.run("上海天气?")):     # 第一幕:边跑边落盘
    pass

s2 = store.open("demo")                        # 第二幕:"重启"后全新对象,只认文件
prior = s2.messages()
for _ in s2.record(agent2.run("我们刚才聊了什么?", prior_messages=prior)):
    pass                                       # 注意:续聊仍在往同一个文件追加

s2.append(Event(ev.ASSISTANT_MESSAGE, {        # 第三幕:伪造"崩在工具执行中"
    "message": AIMessage(content="", tool_calls=[ToolCall("get_weather", {"city": "广州"})])}))

fork = store.fork("demo")                      # 第四幕:分叉
```

实际输出:

```
第一幕:run 完成并落盘 → /var/folders/…/k05-xxxx/demo.jsonl
  日志 9 个事件,重放出 4 条历史

第二幕:恢复会话续聊 → 我记得:此前有 4 条历史,最后聊的是「上海晴,25 度。…」

第三幕:注入半轮后重放 → 6 条(残缺半轮已被修剪,历史仍合法)

第四幕:分叉 → 新会话 demo-fork-df0f,与原会话从此各自发展
  仓库现有会话: ['demo', 'demo-fork-df0f']
```

对着输出核三件事:

- **为什么 9 个事件只重放出 4 条历史?** 第一幕的事件流是 `run_start / user_message / assistant_message / tool_start / tool_result / turn_end / text_delta / assistant_message / run_end`(第 4 章那张"心电图")。重放只挑其中三种消息事件,取出 user、AI(带工具调用)、tool、AI 共 4 条。这就是 5.3 节说的"日志比历史厚":流水账里什么都记,算余额只用其中几列。
- **第二幕的"我记得"不是魔法。** 剧本模型只是数了数它收到的输入里有几条非 system 消息——数出来 4 条,恰好等于重放出的历史。所谓"记忆",真的就只是 `prior_messages` 那个列表,没有任何隐藏状态。
- **第三幕为什么还是 6 条?** 续聊后历史应有 6 条(原来 4 条 + 新的 user + 新的 AI)。接着我们故意往日志里塞了一条"要了工具但没有结果"的残缺 AI 消息,重放却**仍是 6 条**——修剪逻辑把伪造的第 7 条裁掉了。打开 JSONL 文件亲眼看:那行还躺在文件里(日志永不修改),只是重放时不算数。

值得做的实验:用编辑器把日志最后一行**删掉半行**(模拟断电),再 `store.open("demo").messages()`——行级防线接住它,不炸;`grep tool_result demo.jsonl` 感受"纯文本日志 + 标准工具就能审计"。

再体验产品形态:`mini_code.py` 每次 run 自动落盘,`--resume <id>` 恢复,`/sessions` 看清单——和 Claude Code 的 `--resume`/`--continue` 同构。

改造练习(可选):给 Event 加自增 `seq`(第 4 章练习),恢复时按 seq 排序,抵御时钟回拨;给 `mini_code.py` 加 `/rewind N` 命令——用现成的 `fork(id, upto_event=N)` 实现"回到第 N 个事件重来"(Claude Code 的 rewind 同款思路);大练习:把 JSONL 换成 SQLite(一事件一行),对比两种形态——grep 便利性让给了查询能力,体会"朴素文本"是选择而非将就。

## 5.8 源码解析与代码逻辑

> 动手是"抄得出来";这一节是"讲得清楚"。
> 正文已给出 `session.py` 接近全文——这里追**写路径 / 读路径 / 半轮修剪**三条逻辑,不重贴整文件。
> 打开仓库:`tinyharness/session.py`,并记得消息复活靠第 1 章的 `to_jsonable` / `from_jsonable`。

### 生活类比

会话日志像**银行流水**:只准在末尾记账(append-only);账户余额不是另存一格,而是**从头加流水推出来的**(replay);ATM 突然断电最多废掉最后半张凭条,以前的账仍合法;想开平行世界 = 复印流水到某页为止(`fork`)。

```
agent.run(...)  ──yield Event──►  session.record(...)  ──append JSONL──►  disk
                                      │
                                      └─ yield 原事件给 UI(透明管道)

恢复:
  SessionStore.open(id) → session.messages()
       events() 读行 → from_jsonable
       只收 USER/ASSISTANT/TOOL_RESULT
       末尾半轮修剪 → 合法 Messages
       再喂 Agent.run(..., prior_messages=...)
```

### 源码地图

| 顺序 | 符号 | 带走一件事 |
|---|---|---|
| 1 | `_MESSAGE_EVENTS` | 仅三种事件构成可重放历史 |
| 2 | `Session.append` | 一行 JSON:`ts/type/data`;data 经 `to_jsonable` |
| 3 | `Session.record` | for e in stream: append; yield e |
| 4 | `Session.events` | 跳过空行与坏 JSON(崩溃残行) |
| 5 | `Session.messages` | 过滤 + **语义级半轮修剪** |
| 6 | `SessionStore` | create/open/fork/list 目录约定 |

### 写路径

```python
# tinyharness/session.py —— append
line = json.dumps(
    {"ts": event.ts, "type": event.type, "data": to_jsonable(event.data)},
    ensure_ascii=False,
)
with open(self.path, "a", encoding="utf-8") as f:
    f.write(line + "\n")
```

- 每次打开追加,无 seek 改历史——简单换抗崩溃。
- `event.data` 里常嵌 `message` 对象,必须 `to_jsonable` 才能下盘;读回 `from_jsonable` 才能再进模型。

```python
def record(self, event_stream):
    for e in event_stream:
        self.append(e)
        yield e
```

UI 从 `for e in agent.run()` 改成 `for e in session.record(agent.run())`——**持久化是消费者,不是内核分支**。

### 读路径:`events` 行级容错

```python
try:
    d = json.loads(line)
except json.JSONDecodeError:
    continue  # 最后一行可能残缺
out.append(Event(d["type"], from_jsonable(d.get("data", {})), d.get("ts", 0)))
```

坏行丢弃,前面整行仍在 = **合法前缀**。这是崩溃恢复的第一道(行级)。

### 读路径:`messages` 语义修剪(最值得盯)

```python
msgs = [e.data["message"] for e in self.events() if e.type in _MESSAGE_EVENTS]
while msgs:
    last = msgs[-1]
    calls = getattr(last, "tool_calls", None)
    if calls:                      # 尾巴是「要了工具的 AI」→ 结果未齐
        msgs.pop(); continue
    if getattr(last, "role", "") == "tool":
        # 从尾部收齐连续 ToolMessage,与前方 AI 的 tool_calls id 集合比对
        ...
        if need and need != got:
            del msgs[i:]; continue
    break
return msgs
```

三种尾巴:

| 尾巴情形 | 动作 |
|---|---|
| 最后是带 `tool_calls` 的 AI | pop 掉这条 AI(半轮未完成) |
| 最后是 tool,但 id 集合 ≠ AI 声明的 need | 从该 AI 起整段删 |
| 最后是普通 AI 文本 / 完整工具批 | break,保留 |

与第 3 章 `_safe_cut`、第 4 章消息边界同一不变量:**给模型的历史必须是 provider 肯收的合法序列**。

**不进历史的事件**:`text_delta`、`tool_start`、`turn_end`、`compaction`、`run_start/end`… 仍在 JSONL 里供审计,重放对话时忽略。

### SessionStore

- `create`:时间戳 + 短 uuid 文件名。  
- `open`:不存在则 `FileNotFoundError`。  
- `fork`:读源行,`lines[:upto_event]` 写入新 id——**前缀拷贝 = 分叉**,无写时拷贝复杂状态机。  
- `list`:目录下 `*.jsonl` 去后缀排序。

### 分支与失败态

| 若出现… | 落点 | 结果 |
|---|---|---|
| 文件不存在 | `events` | `[]` |
| 中段空行 | strip 后 continue | 忽略 |
| data 缺 message 却类型在集合内 | 列表推导 | KeyError(正常日志不应发生) |
| 只记了 TOOL_START 没 RESULT | messages 修剪 | 丢掉未完成 AI 批 |
| fork `upto_event=0` | 空文件新会话 | 合法平行空世界 |
| 时钟乱序 | 仅靠文件顺序 | 无 seq 时以追加序为准(练习可加 seq) |

### 与前后章

- **上游 · 第 4 章事件流**——无事件流则无「落盘即消费者」。  
- **上游 · 第 1 章序列化**——`__type__` 往返。  
- **上游 · 第 3 章合法切点**——半轮修剪同构。  
- **下游 · 第 9 章 Harness.run**——内部 `session.record(agent.run(...))`。  
- **对照 · 第 10 章图检查点**——快照换更强步内恢复,日志换简单与审计。

### 只要记住的 5 行逻辑

1. **唯一事实源是 append-only JSONL,不是另存的 messages 快照。**  
2. **`record` 透明转发事件,UI 与落盘共享同一生成器。**  
3. **重放历史只取 user/assistant/tool_result 三种事件。**  
4. **行级跳过坏 JSON + 语义级裁半轮 = 崩溃后仍合法。**  
5. **fork = 复制日志前缀;resume = messages() 再当 prior_messages。**

## 5.9 自测

**Q1. 为什么循环路线选事件日志而不是状态快照?**

<details><summary>想清楚再展开</summary>

因为第 4 章已经把执行变成事件流,落盘即持久化,零新抽象;且追加写抗崩溃、日志即审计、复制前缀即分叉。快照方案需要先定义"状态"与"步"(图运行时先造图才有资格做检查点),换来的是更强的恢复语义(步内进度、按步重试、分叉点编辑)。两者是形式化程度的取舍,不是对错。
</details>

**Q2. 重放时为什么只看三种事件?text_delta 为什么不进历史?**

<details><summary>想清楚再展开</summary>

历史 = 模型下一轮的输入,只由完整消息构成(user/assistant/tool)。text_delta 是 assistant_message 的过程碎片(两者内容冗余),tool_start/turn_end/compaction 是过程记录。日志比历史"厚"是特性:审计要过程,重放只要结果。
</details>

**Q3. 恢复时发现最后是"AI 要了 3 个工具、日志里只有 2 个结果",怎么办?为什么?**

<details><summary>想清楚再展开</summary>

把这条 AI 消息连同 2 个结果一起修剪掉,恢复到上一个合法边界,让模型重新决策。因为带 tool_calls 的 AI 消息与其结果是原子组,残缺组会被 provider 拒收。代价是已执行工具的副作用可能重复——所以工具要尽量幂等;需要"步内精确恢复"时,那是图运行时检查点的主场(第 10 章)。
</details>

## 5.10 本章小结

- **不存状态,存事件**:append-only JSONL,状态永远从日志重放推导;抗崩溃、全审计、免费分叉,三个赠品来自同一个决定。
- **record() 是透明管道**:持久化 = 事件流的一个消费者,内核与 UI 均无感知——第 4 章"新消费者随便加"的承诺在此兑现。
- **重放只取三种消息事件**;system 不在历史里,恢复永远吃当前指令——存储与装配分离。
- **崩溃恢复两层**:行级跳过残行(前缀合法),语义级修剪半轮(消息边界不变量第三次出场);已发生副作用靠幂等与模型自查兜底,更强恢复语义是图运行时的卖点。
- **fork = 复制日志前缀**:历史不可变,分叉产生新时间线——日志版的时间旅行。
- **源码阅读顺序**:`append`/`record` → `events` → `messages` 修剪循环 → `SessionStore.fork`。
