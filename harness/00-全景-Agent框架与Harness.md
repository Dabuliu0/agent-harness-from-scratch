# 第 0 章 · 全景:Agent、框架与 Harness

> 本章不写代码,但它是整份教程的地基。读完你会拿到四样东西:一个能落地成代码的 Agent 定义;"框架" 和 "Harness" 这两个词的精确边界;一张 2026 年主流格局的地图(两大家族 + 一个协议层);以及贯穿全书的四层架构和三条方法论。后面每一章,都是在这张地图上填一块具体的地。

## 0.1 先把 "Agent" 这个词定义清楚

"Agent" 从 2023 年起被用得很泛。我们用一个能直接落地成代码的定义:

> **Agent = 一个让大模型在循环里反复决策、并能调用工具改变外部状态的程序。**

拆开是三个关键词:

1. **循环(loop)**。普通的模型调用是一问一答:给一个 prompt,得一个回答,结束。Agent 不是——它反复问模型 "现在该干什么",做一步,看结果,再问 "下一步该干什么",直到任务完成。循环是 Agent 区别于普通模型调用的本质。
2. **工具(tools)**。模型本身只会生成文本。要让它读文件、跑命令、查数据,就要给它一组 "工具"。注意:模型**不直接执行**工具,它只是**说** "我想调用 `read_file('a.py')`",由程序真正执行,再把结果喂回去。"模型只请求、程序才执行" 这道边界,是后面权限、审批、沙箱全部安全机制的地基。
3. **决策(decide)**。循环的每一轮,都是模型在决定:调哪个工具?还是可以给最终答案了?模型在 Agent 里扮演的角色是**推理引擎**。

### 自主性是一条谱系

"是不是 Agent" 不是非黑即白,而是 "控制流有多少交给了模型" 的连续谱:

```
固定 ←──────────────── 谁来决定控制流 ────────────────→ 自主
│              │                │                  │
纯 Workflow    Router          工具循环单 Agent      多 Agent / 开放式
固定步骤流水线  模型选一次分支    模型每轮决定调啥、     模型还能派生子任务、
(如 RAG 三步)  再走不同链       何时结束             调用别的 Agent
                              例:本教程主线         例:Claude Code 连跑
                                                   几小时的大型任务
```

工程判断也随之而来:**自主性不是越高越好**。每多给模型一分决策权,就多一分 "它可能决策错" 的风险和调试难度。成熟做法是够用就好——能用固定流程解决的别上 Agent,能用单 Agent 解决的别上多 Agent。这条 "从简单开始" 的原则来自 Anthropic 那篇著名的《Building effective agents》,是 2025 年以来整个行业公认的方法论起点。

判断一个系统是不是 Agent,判据只有一条:**控制流是不是由模型在运行时决定的**。把用户问题丢给模型、拿到回答就返回的接口,是 Chatbot;固定 "检索 → 拼 prompt → 生成" 三步的,是 Workflow;只有当模型能基于上一步的结果决定下一步动作时,才是 Agent。

## 0.2 框架与 Harness:一对必须分清的概念

2023-2024 年,大家管这类东西统称 "Agent 框架"。到 2026 年,行业词汇表里多了一个更精确的词:**Harness(执行壳)**。这个词的本义是马具/驾具——套在模型身上、让它能真正拉动现实世界的整套装备。它已经有了公认的构成定义:

> **一个 Agent Harness = agent 循环 + 工具接口 + 上下文管理 + 控制机制。**

这四要素正好切出两层:

- **前两样(循环 + 工具接口)是 "框架/内核"**:让模型能转起来、能动手。任何一个会写代码的人照着第 1、2 章都能在几百行内写出来。
- **后两样(上下文管理 + 控制机制)是 "Harness 的主体"**:让这个循环能被信任地放进真实世界——上下文不爆、权限有闸、会话可恢复、过程可审计。这是工程量的大头,也是产品差异的来源。

有两个数字能帮你建立体感:

- 对 Claude Code 等产品的观察都指向同一个事实:真正决定可用性的,不只有模型调用,还有上下文管理、权限、会话、工具执行和渲染等运行基础设施。
- 多个基准都说明:**同一个模型**放进不同 harness,实际效果会明显不同；工程差异往往来自模型之外的控制面。

这解释了为什么行业重心发生了转移:模型能力每隔几个月上一个台阶,而 "把模型能力兑换成真实生产力" 的兑换率,由 harness 决定。2026 年招聘市场上出现的 "harness engineering" 这个岗位名,说的就是这件事。

一个好用的类比(贯穿全书):**内核与壳**。Unix 里 kernel 提供机制(进程、文件、调度),shell 提供策略与交互。Agent 系统里,循环内核提供机制(转、调工具、吐事件),harness 提供策略(什么能执行、上下文放什么、会话怎么存)。我们的两个包就叫 `tinycore` 和 `tinyharness`,边界与此完全一致。

## 0.3 2026 年主流格局:两大家族 + 一个协议层

把市面上叫得出名字的 "Agent 框架" 全摆到桌上,按 "控制流交给谁" 分,恰好裂成两大家族。

### 家族 A:模型驱动循环 + Harness("模型即 Agent")

| 代表 | 是什么 |
|---|---|
| **Claude Code / Claude Agent SDK** | 家族 A 的定义性产品。内核是一个简单循环;产品力全在壳:权限系统、hooks、子代理、会话恢复、压缩、技能、MCP。SDK 就是把这个 harness 开放出来给你编程。 |
| **Codex CLI / OpenAI Agents SDK** | 同一哲学的 OpenAI 实现。Agents SDK 的原语:agents、handoffs(交接)、guardrails(护栏)、sessions;Codex 以 OS 级沙箱(macOS Seatbelt / Linux bubblewrap)著称,云端每任务一个容器。 |
| **Gemini CLI、OpenHands、Amp、Cursor 等** | 同族产品:一个循环内核 + 各有侧重的壳。 |

家族 A 的哲学:**控制流交给模型**。不画流程图、不搭状态机——给模型一台 "电脑"(工具 + 工作区),让它自己决定先看什么、再改什么、要不要重试。工程师的职责从 "编排每一步" 变成 "把壳做厚":上下文喂得准、权限卡得住、过程可恢复。

这一族的兴起和模型进化直接相关:2025 年之后的旗舰模型已经能稳定地长程规划,"帮模型规划" 的编排代码反而成了约束。Anthropic 官方文档里那句 "give the model a computer, not a workflow" 是这个哲学最简洁的表达。

### 家族 B:显式图 / 工作流运行时("控制流写进代码")

| 代表 | 是什么 |
|---|---|
| **LangGraph 1.x + LangChain 1.x** | 家族 B 的定义性框架(2025-10 双双 1.0)。LangGraph 是底层:把执行建模为 节点+边+可序列化状态,Pregel/BSP 引擎驱动,检查点持久化、中断恢复、时间旅行。LangChain 在其上提供 `create_agent` 工厂和中间件系统。Uber、LinkedIn、Klarna 等的生产 Agent 大量跑在这上面。 |
| **Microsoft Agent Framework** | AutoGen + Semantic Kernel 合并后的产物(2026-04 GA 1.0),图 + Actor 双模型,深度绑 Azure。 |
| **Google ADK** | Google 的 Agent 开发套件(已出到 1.x,Python/Java/Go),分层 agent 树 + 工作流原语,绑 Vertex。 |
| **CrewAI、Mastra(TS)等** | 角色分工(crew)或 TS 生态的工作流 + agent 混合体。 |

家族 B 的哲学:**控制流写进代码**。业务流程里有大量 "必须按这个顺序、必须过这道审、失败必须从这步重试" 的硬约束,把它们显式建模成图,换来的是确定性、可审计、可持久执行(durable execution)——一个跑到第 40 步的流程,进程杀掉,明天从第 40 步继续。

### 怎么理解这两家的关系

不是新旧之争,是**问题形状不同**:

- 任务**开放、探索性强**(修 bug、调研、重构),步骤事先列不出来 → 家族 A。你列不出图,模型比你的图聪明。
- 流程**固定、合规敏感、长事务**(信贷审批、订单流、数据管道加一步 LLM),步骤就是业务本身 → 家族 B。这时 "模型自由发挥" 是缺陷不是特性。

两家还在互相吸收:LangChain 1.0 用中间件把 "深度 Agent"(家族 A 形态)复刻进图运行时;Claude Agent SDK 也在补结构化编排能力。本教程主线造家族 A(它是 "框架 + harness" 这个题目的正宗解法),深入篇造家族 B 的核(它把状态与恢复解得最形式化),第 10 章给出完整的选型判据。

### 协议层:两大家族共用的地基

2025-2026 年最重要的行业事件,是**工具与知识的接入被标准化了**,三样东西两家通吃:

- **MCP(Model Context Protocol)**:Anthropic 2024 年底发起,2025 年被 OpenAI、Google、微软全线采纳,现在是工具接入的事实标准。一句话:JSON-RPC 协议,server 暴露 tools/resources/prompts,任何 Agent 应用都能即插即用。第 9 章手写一个最小客户端 + server。
- **AGENTS.md / CLAUDE.md**:项目记忆文件惯例——把 "这个项目怎么构建、规范是什么" 写进仓库,任何 harness 启动时自动读入。第 3 章实现。
- **Agent Skills(SKILL.md)**:把领域知识打包成可渐进披露的技能目录,2025 年由 Anthropic 提出后快速跨厂商化。第 7 章实现。

协议层的存在改变了竞争格局:工具生态不再锁定在某个框架上,harness 的竞争回到了 "壳本身做得好不好"。

## 0.4 全书骨架:四层架构

把两大家族放进同一张分层图,就得到本教程的骨架(也与业界 harness 分析文章的通用分法一致):

```
┌────────────────────────────────────────────────────────────┐
│ L3  宿主 / 产品层                                            │
│     CLI · IDE 插件 · Web · headless SDK · CI 机器人          │
│     (本教程:examples/mini_code.py,约 130 行)                │
├────────────────────────────────────────────────────────────┤
│ L2  Harness / 控制面            ★ 2026 年工程重心            │
│     会话与持久化 · 权限与审批 · 沙箱 · 钩子 · 子代理           │
│     技能 · MCP 接入 · 预算 · 可观测                          │
│     (本教程:tinyharness,第 5-9 章)                          │
├────────────────────────────────────────────────────────────┤
│ L1  内核 / 运行时(两种形态)                                  │
│     形态A:模型驱动循环 —— tinycore.loop(主线,第 1-4 章)    │
│     形态B:显式图引擎  —— tinygraph(深入篇 R2-R4)             │
│     + 工具系统 · 上下文装配 · 事件流                          │
├────────────────────────────────────────────────────────────┤
│ L0  模型接口层                                               │
│     messages · 原生工具调用协议 · 流式 · provider 适配        │
│     (本教程:tinycore.messages / models,第 1 章)           │
└────────────────────────────────────────────────────────────┘
```

配一条**边界判据**,以后每遇到一个新能力,都用它判断该写进哪一层:

> 问:"这个能力在关心什么?"
> - 关心 **"怎么跟模型说话"**(消息格式、工具调用协议、流式)→ **L0**。换掉任何上层它都成立。
> - 关心 **"这一次执行怎么转"**(循环、工具执行、上下文装配、事件产出)→ **L1**。它对 "单次 run" 负责。
> - 关心 **"跨 run、跨用户、可信运营"**(会话恢复、权限、审计、预算、扩展点)→ **L2**。它对 "长期托管" 负责。
> - 关心 **"以什么形态交付给人"**(终端、IDE、网页、API)→ **L3**。它只消费事件流、只经过 L2 门面。

举例:"逐 token 流式" 关心怎么跟模型说话 → L0;"并行执行一批工具调用" 对单次 run 负责 → L1;"用户批准过的命令下次不再问" 跨 run → L2;"审批按钮长什么样" → L3。这个判据是旧版 "机制/策略" 判据的四层扩展,深入篇的图运行时同样适用。

层间接口刻意窄:**L1 对外只有一条事件流(出)和一个 gate 闸门(入)**;L3 只许通过 L2 的门面进出。窄接口是这套系统能各层独立演进的原因——第 4、6 章会反复体会到。

## 0.5 三条方法论(全书的价值观)

**① 模型即 Agent:把能力交给模型,把控制留给壳。**
不要替模型规划它能自己规划的事(那是 2023 年小模型时代的补偿性设计);也不要把该硬控的事交给模型自觉(安全靠许愿等于没有)。工程师的杠杆点在壳:工具好不好用、上下文准不准、闸门严不严。判断一段编排代码该不该存在,问一句:"下一代模型出来,这段代码是资产还是包袱?"

**② 上下文是稀缺资源:上下文工程是核心学科。**
上下文窗口再大也是有限的,而且注意力会随 token 数增长而稀释(context rot)。上下文工程的目标被 Anthropic 总结为一句话:**找到那组最小的高信号 token 集**。三大技术——压缩(compaction)、结构化笔记(外部记忆文件)、子代理隔离——分别在第 3、3、8 章手写。它是 prompt 工程的继任者:prompt 工程管 "怎么写指令",上下文工程管 "整个窗口里放什么、留什么、扔什么"。

**③ 机制与策略分离:硬约束不是提示词。**
"请不要删除文件" 写在 system prompt 里是**许愿**;`rm` 命令在权限闸门被拒绝才是**控制**。凡是安全、预算、合规类的要求,必须落在模型碰不到的机制层(gate、沙箱、预算计数器),提示词只用来提高配合度。这条原则同时是分层依据:机制下沉(内核),策略上浮(harness),两层各自独立演进。

## 0.9 本章小结

- **Agent = 模型在循环里反复决策 + 调用工具改变世界**;是不是 Agent 只看控制流是否由模型在运行时决定;自主性是谱系,够用就好。
- **Harness 四要素**:agent 循环、工具接口、上下文管理、控制机制。前两样是框架(内核),后两样是壳；同一个模型能否稳定、可控地完成任务,很大程度取决于这层壳。
- **2026 格局**:家族 A(循环 + Harness:Claude Code / Agent SDK、Codex / Agents SDK)把控制流交给模型;家族 B(图运行时:LangGraph、MS Agent Framework、ADK)把控制流写进代码;MCP / AGENTS.md / Skills 是两家共用的协议层。
- **四层架构**:L0 模型接口、L1 内核(循环或图)、L2 Harness 控制面、L3 宿主。层间只隔 "一条事件流 + 一个 gate"。
- **三条方法论**:模型即 Agent(能力给模型,控制留给壳);上下文是稀缺资源(最小高信号 token 集);机制与策略分离(硬约束不是提示词)。
- **读码入口**:0.7 的目录导航;第 1–9 章末「源码解析与代码逻辑」按调用链补注释密度。
