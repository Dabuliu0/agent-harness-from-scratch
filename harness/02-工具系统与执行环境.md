# 第 2 章 · 工具系统与执行环境

> 第 1 章的 `get_weather` 证明了机制能转,但查天气改变不了世界。这一章给模型一台真正的"电脑":一个工作区、一套读/写/改/搜/执行的工具族,以及围绕执行的四个硬问题——**说明书怎么写、越界怎么防、并行怎么保序、报错怎么处理**。写完本章,你的 Agent 已经能在一个目录里干真活;而这套工具族的每个设计决策,都直接对应 Claude Code / Codex 内置工具的真实取舍。代码:`tinycore/toolkit.py` 与 `tinycore/tools.py` 的执行器部分。

## 2.1 工具是写给模型的接口,不是写给人的函数

先立方法论,再写代码。新手做工具最容易栽的跟头:把工具的 `description` 当成给人看的注释随手一写,然后困惑模型为什么老不调、老传错参。要记住——**模型决定"调不调、传什么",唯一依据是 name、description 和参数 schema**,它看不到函数体。工具的"门面"质量直接决定模型用得对不对。三条实战原则:

**① description 要写清"什么时候用我"和"参数什么含义",而不是复述函数名。**

```python
# 反例:等于没说。模型不知道 city 传中文还是拼音,也不知道返回什么
@tool
def get_weather(city: str) -> str:
    """获取天气。"""

# 正例:模型读完就知道何时用、怎么传
@tool
def get_weather(city: str) -> str:
    """查询指定城市的实时天气。需要天气信息时调用。
    city: 城市中文名,如 "北京"(不要传拼音)。返回温度、风力、天气状况。"""
```

**② 粒度要任务导向,别把一个动作拆成一堆碎工具。** 每多一次工具调用就多一轮模型往返(更慢更贵),中间也更容易出错。与其给 `open_file`/`read_lines`/`close_file` 让模型自己编排,不如直接给 `read_file(path)`。好工具的粒度接近"人会怎么描述这一步":"读这个文件"、"跑一下测试"。

**③ 参数用模型好填的形态,并把约束写进说明。** 枚举比自由字符串不易错;能给默认值就给;危险参数(比如 `force=True`)宁可不提供。调试直觉:模型老用错工具时,**先别怀疑模型笨,九成是说明书没写清**——把它当成"写给一个没见过你代码库的新同事的入职文档"来打磨。

这套方法论在 2026 年有个正式名字:**工具即接口设计(tools as interface design)**。Anthropic 的工程博客甚至建议:用 Agent 自己来评测和改写工具的 description——因为最终读者就是模型。

## 2.2 编码工具八件套:给模型一台电脑

2026 年主流 harness 的内置工具高度趋同,殊途同归地收敛到同一套核心:

| 工具 | 干什么 | 对应真实系统 |
|---|---|---|
| `read_file` | 带行号分页读文件 | Claude Code 的 Read、Codex 的读文件 |
| `write_file` | 新建/整体覆盖 | Write |
| `edit_file` | 精确唯一替换 | Edit(Claude Code)、apply_patch(Codex) |
| `list_dir` / `glob_files` | 看目录 / 通配找文件 | ls、Glob |
| `grep` | 正则搜内容 | Grep(内置 ripgrep) |
| `bash` | 执行 shell 命令 | Bash / shell |
| `todo_write` | 维护任务清单 | TodoWrite / update_plan |

这不是巧合:**文件系统 + shell 就是"通用计算机"的最小接口**。给模型这八件套加一个工作区,它就能做出 IDE 里大部分开发动作——这正是"give the model a computer"哲学的落地形态。

`tinycore/toolkit.py` 用一个工厂函数构造整套工具。下面的代码分两块贴,一块观察类、一块修改类——**别整块硬读,一个函数一个函数看**,每个都不超过 20 行,而且结构雷同:解析路径 → 干活 → 返回给模型看的字符串。先解释一个贯穿所有文件工具的词:**路径 jail**(jail = 监狱)——把工具能触碰的路径全部关在工作区这间"牢房"里,不管模型怎么写路径(`../`、绝对路径、软链接)都出不去,实现就是下面的 `_resolve` 函数。

先看骨架与第一组(观察类)的完整实现:

```python
# tinycore/toolkit.py —— 骨架 + 路径 jail + 观察类工具
def make_coding_tools(root, *, bash_timeout=60, max_output_chars=8_000,
                      enable_bash=True):
    """构造一套锁定在 root 工作区的编码工具。"""
    root = os.path.realpath(root)
    os.makedirs(root, exist_ok=True)

    def _resolve(path: str) -> str:
        """路径 jail:任何解析结果越出 root 一律拒绝(2.3 节细讲)。"""
        p = os.path.realpath(os.path.join(root, path))
        if p != root and not p.startswith(root + os.sep):
            raise PermissionError(f"路径越出工作区: {path!r}")
        return p

    @tool
    def read_file(path: str, offset: int = 0, limit: int = 200) -> str:
        """读取工作区内的文本文件,返回带行号的内容。
        path: 相对工作区的路径。offset/limit: 从第 offset 行起最多读 limit 行,
        大文件请分段读取而不是一次读完。"""
        with open(_resolve(path), "r", encoding="utf-8", errors="replace") as f:
            lines = f.readlines()
        window = lines[offset : offset + limit]
        body = "".join(f"{i + offset + 1:>5}\t{l}" for i, l in enumerate(window))
        tail = (f"\n…(共 {len(lines)} 行,仅显示 {offset + 1}-{offset + len(window)})"
                if len(lines) > offset + limit else "")
        return (body or "(空文件)") + tail

    @tool
    def list_dir(path: str = ".") -> str:
        """列出工作区内某目录的内容(目录以 / 结尾)。"""
        p = _resolve(path)
        entries = sorted(os.listdir(p))
        out = [e + "/" if os.path.isdir(os.path.join(p, e)) else e for e in entries]
        return "\n".join(out) or "(空目录)"

    @tool
    def glob_files(pattern: str) -> str:
        """按通配符递归查找文件名,如 "**/*.py"、"src/*.md"。返回相对路径列表。"""
        hits = []
        limit_reached = False
        for dirpath, dirnames, filenames in os.walk(root):
            dirnames[:] = [d for d in dirnames
                           if d not in (".git", "__pycache__", "node_modules")]
            for fn in filenames:
                rel = os.path.relpath(os.path.join(dirpath, fn), root)
                if fnmatch.fnmatch(rel, pattern) or fnmatch.fnmatch(fn, pattern):
                    hits.append(rel)
        return "\n".join(sorted(hits)[:200]) or "(无匹配)"

    @tool
    def grep(pattern: str, path: str = ".", max_matches: int = 50) -> str:
        """在工作区内按正则搜索文件内容,返回 "文件:行号:内容"。
        pattern: Python 正则。path: 限定搜索的子目录,默认全工作区。"""
        rx = re.compile(pattern)
        base = _resolve(path)
        hits = []
        for dirpath, dirnames, filenames in os.walk(base):
            dirnames[:] = [d for d in dirnames
                           if d not in (".git", "__pycache__", "node_modules")]
            for fn in filenames:
                fp = os.path.join(dirpath, fn)
                try:
                    with open(fp, "r", encoding="utf-8") as f:
                        for i, line in enumerate(f, 1):
                            if rx.search(line):
                                rel = os.path.relpath(fp, root)
                                hits.append(f"{rel}:{i}:{line.rstrip()}")
                                if len(hits) >= max_matches:
                                    limit_reached = True
                                    break
                except UnicodeDecodeError:
                    continue          # 二进制文件跳过
                if limit_reached:
                    break
            if limit_reached:
                break
        return "\n".join(hits) or "(无匹配)"
```

先解释一个初学者常问的结构问题:**为什么用"工厂函数 + 闭包",而不是一个 `Toolkit` 类?** 每个工具函数体里用到的 `root`、`_resolve`、`bash_timeout` 都来自外层 `make_coding_tools` 的局部变量——Python 闭包会把它们"封"进函数里。效果:每套工具**天生绑死**在自己的工作区上,不存在"忘了传 workspace 参数"或"运行中被改掉 root"的事故面;想要两个不同工作区,就调两次工厂,互不干扰。类当然也能做到,但闭包让"配置在构造时冻结"这个安全属性成为默认,而不是纪律。(顺便注意 `dirnames[:] = [...]` 这个写法:`os.walk` 允许你**原地修改** dirnames 来剪枝,`.git`、`node_modules` 这类目录整棵跳过——不剪枝的 grep 在真实仓库里会慢到没法用。)

接着是修改类与执行类,同样全量:

```python
# tinycore/toolkit.py(续)—— 修改类 + 任务清单 + bash
    @tool
    def write_file(path: str, content: str) -> str:
        """在工作区内创建或整体覆盖一个文件。仅用于新建文件或全量重写;
        修改既有文件请优先用 edit_file。"""
        p = _resolve(path)
        os.makedirs(os.path.dirname(p) or root, exist_ok=True)
        with open(p, "w", encoding="utf-8") as f:
            f.write(content)
        return f"已写入 {path}({len(content)} 字符)"

    @tool
    def edit_file(path: str, old: str, new: str) -> str:
        """对既有文件做精确替换:old 必须与文件中某段内容**完全一致且唯一**。
        找不到或出现多处都会报错——请提供更长的上下文片段来唯一定位。"""
        p = _resolve(path)
        with open(p, "r", encoding="utf-8") as f:
            text = f.read()
        n = text.count(old)
        if n == 0:
            raise ValueError(f"未找到要替换的内容(old 与文件不一致): {old[:80]!r}")
        if n > 1:
            raise ValueError(f"old 在文件中出现 {n} 次,无法唯一定位,请扩大片段")
        with open(p, "w", encoding="utf-8") as f:
            f.write(text.replace(old, new, 1))
        return f"已编辑 {path}"

    @tool
    def todo_write(content: str) -> str:
        """维护你的任务清单(覆盖式写入)。做多步任务时,先把计划写进来,
        每完成一步就更新状态——这份清单会帮你在长任务中保持方向。"""
        with open(os.path.join(root, ".agent_todo.md"), "w", encoding="utf-8") as f:
            f.write(content)
        return "任务清单已更新"

    @tool
    def bash(command: str) -> str:
        """在工作区目录下执行 shell 命令,返回 exit code 与输出(stdout+stderr 合并)。
        用于运行测试、git、构建等。命令有超时限制;产生大量输出时会被截断。"""
        # 注意:bash 无法被路径 jail 约束——这正是它必须过权限闸门的原因(第 6 章)
        r = subprocess.run(command, shell=True, cwd=root,
                           capture_output=True, text=True, timeout=bash_timeout)
        out = (r.stdout or "") + (r.stderr or "")
        if len(out) > max_output_chars:
            out = out[:max_output_chars] + f"\n…[输出已截断,共 {len(out)} 字符]"
        return f"(exit {r.returncode})\n{out.strip()}"

    tools = [read_file, write_file, edit_file, list_dir, glob_files, grep, todo_write]
    if enable_bash:
        tools.append(bash)
    return tools
```

到此 `toolkit.py` 完整(~170 行)。注意每个 docstring 都在**练第 2.1 节的三原则**:说清何时用("仅用于新建/全量重写")、教省着用("大文件请分段读取")、把失败模式写成规范("出现多处会报错——请扩大片段")。现在逐个复盘"为什么长这样"的设计决策——它们比代码本身值钱:

**`read_file` 为什么带行号和分页?** 行号让后续 `edit_file`/报错讨论有精确坐标("第 42 行那个判断");分页(offset/limit)是上下文经济学:一个 5000 行的文件全文进上下文就是几万 token,而模型往往只需要某一段。说明书里那句"大文件请分段读取"是写给模型的操作规范——好工具会**教模型省着用自己**。

**`edit_file` 为什么是"精确唯一替换",而不是按行号改或整文件重写?** 三个方案的对比是道经典设计题:

- *整文件重写*(只给 write_file):改一行也要模型输出整个文件——token 贵、慢,而且长文件重写容易抄错没动的部分。
- *按行号替换*:行号在模型上一次读文件之后可能已经变了(它自己刚编辑过前面几行!),错位编辑是灾难。
- *精确唯一替换*:`old` 串既是内容校验(文件变了就对不上,**失败而不是错改**),又是定位手段(无视行号漂移);"必须唯一"逼模型给足上下文,杜绝"想改第 3 处却改了第 1 处"。失败模式是显式报错,模型看到错误后会自己扩大片段重试。

这就是 Claude Code 的 Edit 工具的语义,我们原样复刻。**把"必然会发生的失败"设计成信息量丰富的报错,是工具设计的半壁江山**——马上在 2.4 节它有个正式名字。

**`bash` 为什么合并 stdout/stderr、附带 exit code、强制超时和截断?** 模型需要的是"这条命令的完整结局":退出码判断成败,合并输出保持时序(报错常横跨两个流)。超时防挂死(交互式命令、死循环);截断防上下文炸弹——一条 `npm install` 的输出能有几万行,20 万 token 的窗口一条命令就能灌满。

**`todo_write` 为什么算工具?** 它是第 3 章"结构化笔记"的入口:长任务里模型把计划写进文件、完成一步更新一步——把"接下来该干嘛"从易挥发的上下文转移到持久的文件系统。Claude Code 的 TodoWrite、Codex 的 update_plan 同理。现在先放进工具箱,第 3 章讲透它为什么关键。

## 2.3 安全边界的物理位置

第 1 章立了原则:模型只请求,框架才执行。本章把这个原则落到具体代码位置——`tinycore/tools.py` 的执行器:

```python
# tinycore/tools.py
def _execute_one(call, tools_by_name, gate):
    if gate is not None:                     # ① 闸门:策略注入的接缝
        verdict = gate(call)
        if isinstance(verdict, str):         #    拒绝(理由喂回模型)
            return ToolMessage(content=f"[已拒绝] {verdict}",
                               tool_call_id=call.id, name=call.name, is_error=True)
        if isinstance(verdict, ToolCall):    #    放行但参数已被改写
            call = verdict

    t = tools_by_name.get(call.name)         # ② 查无此工具也是喂回,不是崩
    if t is None:
        return ToolMessage(content=f"[错误] 不存在名为 {call.name!r} 的工具",
                           tool_call_id=call.id, name=call.name, is_error=True)
    try:
        return ToolMessage(content=t.invoke(call.args),
                           tool_call_id=call.id, name=call.name)
    except Exception:                        # ③ 执行失败 → 错误即消息
        return ToolMessage(content=f"[错误] 工具执行失败:\n{traceback.format_exc(limit=2)}",
                           tool_call_id=call.id, name=call.name, is_error=True)
```

三个点各自是一道防线:

**① gate 是内核唯一的策略接缝。** gate(闸门)像机场安检口:每个工具调用执行前都要过这一道,结果只有三种——放行(返回 `None`)、拦下(返回 `str`,字符串就是给模型看的拒绝理由)、没收违禁品后放行(返回改写后的 `ToolCall`,用修正过的参数执行)。内核不认识"权限""审批""钩子"这些词——第 6、7 章的整个控制面,都会被编译成一个 gate 函数从这里插进来。**机制(有个闸门位)在内核,策略(闸门怎么判)在壳**,这是第 0 章判据的第一次实战。

**② 路径 jail 是"构造期约束"。** 回看 `_resolve`:所有文件工具的路径都先 join 到 root、再 `realpath`(软链接目标也参与检查)、再检查前缀。这是**机制层安全**——不靠模型自觉,单次解析物理上做不到越界；但检查和后续 `open` 之间仍有 TOCTOU 窗口,生产环境还要做打开后校验、使用 O_NOFOLLOW 或交给 OS 沙箱。注意 `bash` 锁不住:命令天生能触达整个系统(`cd /; cat /etc/passwd`)。所以工具族里有一道清晰的分界:**文件工具靠构造保安全,bash 必须靠策略层把守**(第 6 章的权限规则 + 审批,生产中再加 OS 级沙箱)。分清"哪些安全能靠构造、哪些必须靠策略",是 harness 设计的基本功。

**③ 错误即消息(errors as messages)。** 工具抛异常不炸循环,而是包成 `is_error=True` 的 `ToolMessage` 喂回模型。为什么?因为**模型是当前最好的错误恢复器**:它看到 "file not found" 会先去 `list_dir`;看到 "old 出现 3 处" 会扩大片段重试;看到测试失败输出会去改代码。把异常抛给调用方,等于放弃了这台恢复器。留意 traceback 只截 2 层——报错也是上下文,同样要省着花。

## 2.4 并行执行:快,但必须保序

模型一轮经常发出多个互不依赖的调用(读五个文件、查三个城市),串行执行浪费的是真金白银的等待时间。执行器用线程池并行:

```python
# tinycore/tools.py
def run_tool_calls(calls, tools_by_name, *, gate=None, parallel=True, max_workers=8):
    if len(calls) <= 1 or not parallel:
        return [_execute_one(c, tools_by_name, gate) for c in calls]
    with ThreadPoolExecutor(max_workers=min(max_workers, len(calls))) as pool:
        futures = [pool.submit(_execute_one, c, tools_by_name, gate) for c in calls]
        return [f.result() for f in futures]     # ← 按【请求顺序】收集,不是完成顺序
```

最后一行是本节的灵魂。并行完成的先后是随机的:今天北京的查询先回来,明天上海先回来。如果按"谁先做完谁先记账"的顺序追加结果,**同样的输入会产生不同的历史**,喂给模型的内容就不同,回答也可能不同——不确定性是调试的噩梦,也让第 5 章的"重放"失去意义。解法是像老师收考卷:大家同时答题(并行),但收卷永远按学号顺序(按 `calls` 的原始顺序逐个 `f.result()`,它天然会等对应任务做完)。执行并行、结果保序,一行代码换来确定性。

(对照深入篇:图运行时把同一个问题推广成了正式抽象——多个节点并行写同一个状态时用 **Reducer** 定义确定性合并。R2 章会看到,这一行 `[f.result() for f in futures]` 就是 Reducer 思想的最小特例。)

还有一层含金量此刻埋下:第 8 章的子代理是靠一个 `task` 工具实现的——模型一轮发多个 `task` 调用,这个线程池就自动变成了**并行多智能体**。届时不需要任何新机制。

## 2.5 工具结果截断:上下文的第一道闸

工具结果是上下文的最大污染源——一次 `grep` 可能回来几千行,一次 `bash` 可能回来几万行。`Tool.invoke` 内置了兜底截断:

```python
# tinycore/tools.py
@dataclass
class Tool:
    max_result_chars: int = 20_000
    def invoke(self, args):
        result = str(self.func(**args))
        if len(result) > self.max_result_chars:
            omitted = len(result) - self.max_result_chars
            result = result[:self.max_result_chars] + f"\n…[已截断 {omitted} 字符]"
        return result
```

注意截断话术里带着**元信息**("已截断 N 字符"):模型知道还有更多,可以决定用更窄的查询再来一次。好的截断不是砍掉信息,而是把"全量"变成"摘要 + 如何获取更多"。同理,toolkit 里每个工具还有自己的领域截断:`grep` 限 `max_matches`、`read_file` 限 `limit` 行、`bash` 限 `max_output_chars`——多层设防,因为第 3 章会看到:**上下文一旦被灌脏,清理的代价远高于预防**。

### 先用一张生活图把文件关系钉住

把本章想成**后厨 + 安检 + 菜单**:

- `toolkit.py` 是**后厨菜谱**:八个具体工具,在构造时就被锁进工作区(路径 jail)。
- `tools.py` 的执行器是**出餐口**:模型只能递小票(`ToolCall`),真正开火、装盘、报错全在这里。
- `gate` 是**安检口**:第 6、7 章的权限和钩子以后都挂在这里,本章可以是 `None`。
- `k02_tools.py` 是**试吃间**:用 FakeModel 走一遍"写→跑→改→再跑",再直接打执行器演示越界和失败。

```
模型发出 List[ToolCall]
        │
        ▼
 run_tool_calls  ──(可选并行,结果保序)──►  多个 _execute_one
        │                                         │
        │                              ┌──────────┼──────────┐
        │                              ▼          ▼          ▼
        │                           gate?     查工具表    Tool.invoke
        │                              │          │       (func+截断)
        │                              └────┬─────┘
        │                                   ▼
        │                            ToolMessage(成功或 is_error)
        ▼
 按 calls 原顺序返回 List[ToolMessage]  →  主循环写进历史
```

`make_coding_tools(root)` 不在这条热路径上——它在**启动时**跑一次,产出 `List[Tool]`,再被收成 `{name: Tool}` 字典交给执行器。

### 本章源码地图(读顺序 ≠ 文件字母序)

| 阅读顺序 | 路径 | 体量 | 你要带走的一件事 |
|---|---|---|---|
| 1 | `tinycore/tools.py` 前半 | ~90 行 | 第 1 章已有:`Tool` / `@tool` / `_build_parameters`;本章补上 `invoke` 截断 |
| 2 | `tinycore/tools.py` 执行器 | ~70 行 | **安全边界的物理位置**:`Gate` → `_execute_one` → `run_tool_calls` |

### 主路径走读:一次成功的 `read_file`

假设模型本轮只发了一个调用:

`ToolCall(name="read_file", args={"path": "hello.py"}, id="c1")`

逐步发生的事:

**① 主循环把本轮 `ai.tool_calls` 交给执行器**

正式循环在 `tinycore/loop.py` 的 `Agent.run` 里(第 4 章会整段展开)。关键两行是:

```python
# tinycore/loop.py —— 工具批执行铰链(第 4 章全文)
results = run_tool_calls(
    ai.tool_calls,
    {t.name: t for t in self.tools},
    gate=self.gate,
    parallel=self.parallel_tools,
)
```

注意:`self.tools` 是列表,这里**现场**收成名字字典。查找是 O(1);模型幻觉出来的名字会在下一步变成错误消息,而不是 KeyError 炸循环。

**② `run_tool_calls`:一个调用 → 走串行短路**

```python
# tinycore/tools.py —— 串行 / 并行分岔
if len(calls) <= 1 or not parallel:
    return [_execute_one(c, tools_by_name, gate) for c in calls]
```

只有 0/1 个调用,或 `parallel=False` 时,不开线程池。省掉线程创建的固定成本。

**③ `_execute_one`:gate → 查表 → invoke**

本章 demo 通常 `gate is None`,整段闸门跳过。然后:

```python
# tinycore/tools.py —— 查表 + 成功执行
t = tools_by_name.get(call.name)
# … 若 t is None: 返回 is_error 的 ToolMessage …
return ToolMessage(content=t.invoke(call.args), tool_call_id=call.id, name=call.name)
```

三件事绑在一条成功返回上:

- `content` = 工具输出的字符串
- `tool_call_id=call.id` = 配对回请求(一轮多调用时靠它)
- `name=call.name` = 日志和模型都好看清"谁的结果"

**④ `Tool.invoke`:真正调 Python 函数 + 截断**

```python
# tinycore/tools.py —— invoke 只有两件事
result = str(self.func(**args))
if len(result) > self.max_result_chars:
    omitted = len(result) - self.max_result_chars
    result = result[: self.max_result_chars] + f"\n…[已截断 {omitted} 字符]"
return result
```

- `**args` 把模型给的 JSON 对象拆成关键字参数。
- 一切返回值先 `str(...)`:历史里只认文本。
- 默认 2 万字符封顶,截断话术带"省略了多少"——模型知道还能用更窄查询再来。

**⑤ 落到 `read_file` 闭包:`_resolve` 再读盘**

`make_coding_tools` 里每个文件工具都先过 jail:

```python
# tinycore/toolkit.py —— 路径 jail(软链接也逃不掉)
def _resolve(path: str) -> str:
    p = os.path.realpath(os.path.join(root, path))
    if p != root and not p.startswith(root + os.sep):
        raise PermissionError(f"路径越出工作区: {path!r}")
    return p
```

`read_file` 成功时:`open(_resolve(path))` → 按 `offset/limit` 切片 → 拼行号 → 可能加"共 N 行仅显示…"尾巴。  
`PermissionError` **不会**在这里被吞掉——它冒泡到 `_execute_one` 的 `except`,变成 `is_error=True` 的 ToolMessage。这就是 k02 里"读 `../../etc/passwd`"仍返回消息、不崩进程的原因。

**⑥ 结果回主循环**

`run_tool_calls` 返回的列表与 `calls` **等长且同序**。循环按序 `messages.append(r)`,再进入下一轮决策。模型下一眼看到的,就是带行号的文件内容,或一行 `[错误] …`。

### 并行路径:多个互不依赖的调用

模型一轮发 3 个 `read_file` 时,走另一分支:

```python
# tinycore/tools.py —— 并行提交,按请求顺序收集
with ThreadPoolExecutor(max_workers=min(max_workers, len(calls))) as pool:
    futures = [pool.submit(_execute_one, c, tools_by_name, gate) for c in calls]
    return [f.result() for f in futures]
```

逻辑拆开只有两句:

1. **`submit` 按 `calls` 下标排队** → `futures[i]` 永远对应 `calls[i]`。
2. **`f.result()` 也按同一个列表顺序取** → 谁先做完是调度的事,入账顺序仍是请求顺序。

`max_workers=min(8, len(calls))`:3 个调用最多 3 个线程,不空开。  
第 8 章的多个 `task` 调用,复用的就是这同一段——**不需要第二套并行运行时**。

### toolkit 八件套:构造期逻辑(不是热路径)

`make_coding_tools(root)` 一次构造、多次复用。读源码时抓住四层:

| 层 | 代码位置 | 逻辑 |
|---|---|---|
| 工作区锁定 | 函数开头 `root = realpath` + `makedirs` | 所有相对路径的锚点 |
| 共享 jail | 闭包 `_resolve` | 文件类工具唯一入口 |
| 观察四件 | `read_file` / `list_dir` / `glob_files` / `grep` | 只读;带行号、剪枝、命中上限 |
| 修改三件 + bash | `write_file` / `edit_file` / `todo_write` / `bash` | 有副作用;`edit` 要求 old 唯一;`bash` **不调用** `_resolve` |

几个值得在源码里盯死的细节:

1. **`@tool` 用在嵌套函数上是故意的**  
   每个工具闭包捕获同一个 `root` / `_resolve` / 超时配置。换工作区 = 再调一次工厂,不会串台。

2. **`edit_file` 的失败是 `raise`,不是返回字符串**  
   `n == 0` 或 `n > 1` 时 `raise ValueError(...)`。统一由 `_execute_one` 包成错误消息——工具作者不用记得"要返回 is_error"。

3. **`grep` 用显式状态做早停**  
   命中数到 `max_matches` 就设置 `limit_reached` 并逐层 break。这是"领域截断";外面还有 `Tool.invoke` 的字符截断——两道闸。解码失败单独走 `UnicodeDecodeError` 分支,不与正常早停混在一起。

4. **`bash` 只有 `cwd=root`**  
   注释写得很直白:命令能 `cd /`,jail 锁不住。所以文件工具 = 机制层安全,bash = 必须等第 6 章策略层(再加生产 OS 沙箱)。

5. **`enable_bash=False` 时列表里根本没有 bash**  
   不是"注册了但拒绝",是模型说明书里就看不到这个名字——更干净的只读姿态。

### 分支与失败态(比主路径更值钱)

| 若出现… | 代码落点 | 变成什么 | 读者体感 |
|---|---|---|---|
| `gate` 返回 `str` | `_execute_one` 前半 | `ToolMessage("[已拒绝] …", is_error=True)` | 模型看到拒绝理由,可改主意;工具**未执行** |
| `gate` 返回新的 `ToolCall` | 同上,`call = verdict` | 用改写后的 name/args 继续 | 参数被净化/修正后再执行 |
| `gate` 自己抛异常 | `except` 把异常写成拒绝理由 | 同拒绝 | **安全侧优先**:闸门坏了也不放行 |
| 工具名不存在 | `tools_by_name.get` 得 `None` | `[错误] 不存在名为 …` | 幻觉工具名 → 可自纠 |
| `func` / jail / edit 校验抛错 | `invoke` 上抛 → `_execute_one` except | `[错误] 工具执行失败:` + 2 层 traceback | 循环不崩;模型读错再试 |
| 结果超长 | `Tool.invoke` 截断 | 正文前缀 + `…[已截断 N 字符]` | 仍是成功消息,`is_error=False` |
| 多个调用、完成有快有慢 | `run_tool_calls` 并行分支 | 返回列表顺序 = 请求顺序 | 历史可复现;重放有意义 |
| `parallel=False` 或只 1 个调用 | 串行分支 | 同序,无线程池 | 调试时更好跟栈 |
| 路径 `../` 逃出 root | `_resolve` → `PermissionError` | 同上"工具执行失败" | k02 第一条边界 demo |
| `edit` 的 old 找不到/不唯一 | `edit_file` 内 `ValueError` | 同上 | k02 第二条边界 demo |
| `bash` 超时 | `subprocess.run(..., timeout=)` | `TimeoutExpired` → 错误消息 | 不永久卡住循环 |
| `calls` 为空列表 | 串行分支列表推导 | `[]` | 主循环一般不会发空批,但执行器自身安全 |

记住一条总规则:**`_execute_one` 对外不抛异常**——所有失败都是 `ToolMessage`。  
`run_tool_calls` 因此可以安心并行;`Agent.run` 因此可以安心把结果 append 进历史。

### gate 三态契约(本章埋线,第 6/7 章接线)

```python
# tinycore/tools.py —— 类型即文档
#   gate(call) -> None      放行
#   gate(call) -> str       拒绝(理由给模型)
#   gate(call) -> ToolCall  改写后放行
Gate = Callable[[ToolCall], Union[None, str, ToolCall]]
```

本章可以把 `Agent(..., gate=None)` 跑通全部编码工具。  
第 6 章的 `PermissionPolicy.as_gate()`、第 7 章的 `HookManager.as_gate()`,都会返回一个符合这个契约的函数,再塞进同一个参数槽——**内核一行不改**。

### 与前后章的接缝

- **上游 · 第 1 章的消息与工具定义**——`ToolCall` / `ToolMessage` / `@tool` / `Tool` 四件套在第 1 章就定了形状。本章只补执行器与八件套;说明书怎么生成( `_build_parameters` )不变。
- **上游 · 第 1 章的"模型只请求、框架才执行"**——原则落点就是 `_execute_one` + `run_tool_calls`。读源码时,把这两处标成安全边界的物理位置即可。
- **下游 · 第 3 章上下文**——`Tool.invoke` 的截断、toolkit 里各工具的 `limit`/`max_matches`/`max_output_chars`,都是"别把窗口灌脏"的第一道闸;装不下的长历史由 `ContextManager` 接着做压缩。
- **下游 · 第 4 章事件流**——循环在调用 `run_tool_calls` 前后会 `yield TOOL_START` / `TOOL_RESULT`;执行器本身不发事件,保持"只负责执行"。
- **下游 · 第 6 章权限**——`gate` 接缝在此留好;文件 jail 继续当机制层,bash 走策略层。
- **下游 · 第 8 章子代理**——多个 `task` 工具调用 = 多个 `_execute_one` 并行;保序逻辑原样复用。

### 只要记住的 5 行逻辑

1. **模型只产出 `ToolCall`;真正副作用只发生在 `Tool.invoke` → `func`。**
2. **`_execute_one` 是单次调用的完整生命周期:先 gate,再查表,再执行;任何失败都变成 `is_error` 的 `ToolMessage`。**
3. **`run_tool_calls` 可以并行,但返回顺序永远等于请求顺序——确定性比快更优先。**
4. **文件工具的安全写在 `_resolve` 里(构造即安全);`bash` 锁不住,必须靠以后的 gate/沙箱。**
5. **截断分两层:工具自己的领域上限 + `Tool.invoke` 的字符上限;话术要告诉模型"还有更多"。**

**Q1. `edit_file` 为什么要求 old 串"完全一致且唯一"?这防住了哪两类事故?**

<details><summary>想清楚再展开</summary>

一致性防"文件已变还在改":文件内容和模型记忆不符时,old 对不上,操作失败而不是错改——失败是安全的,错改不是。唯一性防"改错位置":old 出现多处时强制模型给更长的上下文来唯一定位。两者合起来,把编辑的失败模式从"静默出错"变成"显式报错 + 模型自纠"。
</details>

**Q2. 为什么说"文件工具的安全靠构造,bash 的安全靠策略"?**

<details><summary>想清楚再展开</summary>

文件工具的每个路径都经过 `_resolve` 的 jail 检查,越界在机制层就被物理拦截,与模型行为无关。bash 执行任意命令,命令的能力就是整个系统的能力,无法在构造时枚举约束——只能靠策略层判断这条命令危不危险(权限规则、审批),以及生产中用 OS 沙箱把进程整个圈起来。这条分界决定了第 6 章权限系统的重点在哪。
</details>

**Q3. 并行执行为什么必须"按请求顺序收集结果"?乱序会破坏什么?**

<details><summary>想清楚再展开</summary>

乱序 = 完成时间决定历史顺序 = 同样输入产生不同历史。破坏三样:可复现性(调试时跑不出同样轨迹)、可重放性(第 5 章会话日志重放会得到不同状态)、以及缓存(provider 的 prompt cache 对前缀敏感)。保序一行代码,买回全部确定性。
</details>

## 2.10 本章小结

- **工具是写给模型的接口**:description 写"何时用我 + 参数含义";粒度任务导向;约束进说明书。模型用错工具,先改说明书。
- **八件套 = 给模型一台电脑**:read(分页带行号)/write/edit(精确唯一替换)/list/glob/grep/bash(exit code + 超时 + 截断)/todo。每个设计决策都对应真实 harness 的取舍。
- **安全边界的物理位置在执行器**:gate 三态接缝(None/str/改写)是内核唯一策略入口;文件工具靠路径 jail 构造即安全;bash 必须靠策略层把守。
- **错误即消息**:异常包成 `is_error` 的 ToolMessage 喂回,模型是最好的错误恢复器。
- **并行但保序**:线程池提速,按请求顺序收集保确定性——它是深入篇 Reducer 思想的最小特例,也是第 8 章并行子代理的免费地基。
- **截断是上下文的第一道闸**:带元信息的截断让模型知道"还有更多、怎么拿"。
- **源码阅读顺序**:`run_tool_calls` / `_execute_one` 定命运 → `toolkit._resolve` 与八件套定手脚 → `k02` 验证轨迹与边界。
