# 第 4 章 · 事件流与流式

> 目前为止,`agent.invoke()` 只在最后 return 一次——中间十几秒模型在想、工具在跑,外面一无所知,更别提实时打字机、点一下打断、中途补一句话。本章给内核换上正式的输出形态:**事件流**。这不是 UI 优化,而是一个架构决策——事件流是内核对外的**唯一公共 API**,后面每一章(会话存储、审批交互、子代理观测、宿主 CLI)都是这条流的消费者。代码:`tinycore/events.py` 与 `loop.py` 的 `run()`。

## 4.1 为什么是事件流,而不是回调或返回值

"想看中间过程"的朴素解法是塞回调:`on_text(...)`、`on_tool(...)`。能凑合,但很快失控——因为"看过程"的消费者不止一个,且各要各的:

- **终端 UI** 要逐 token 打字机 + 工具执行状态行;
- **会话日志**(第 5 章)要每条消息落盘;
- **可观测**要每步耗时与 token 用量;
- **审批交互**(第 6 章)要在危险调用前拿到控制权;
- **宿主产品**(网页版)要把这一切推过 WebSocket。

每个消费者一套回调,内核很快变成回调森林。正解是反转:**内核只管把发生的事,按发生顺序吐成一条事件流;谁关心谁消费**。就像电台直播:主播(内核)只对着话筒播报正在发生的事,不关心听众是谁;车载收音机、录音机、转播站(各消费者)各自调台各取所需——加一万个听众,主播毫无感知。

```
                       ┌──▶ 终端渲染(打字机/状态行)
   Agent.run()  事件流  ├──▶ 会话日志(第 5 章:透明落盘)
   ────────────────────┼──▶ 可观测(耗时/token/轨迹)
   (唯一输出通道)        ├──▶ 宿主转发(WebSocket/SSE)
                       └──▶ …新消费者随便加,内核零改动
```

这个形态在 2026 年的主流系统里已是标配:Claude Agent SDK 的 `query()` 返回消息/事件流,OpenAI Agents SDK 的 `Runner.run_streamed()` 吐 stream events,LangGraph 的 `stream()` 有一族 stream_mode。**内核与外界之间只隔一条事件流**——第 0 章说的"窄接口",这就是它的实体。

## 4.2 事件协议:类型 + payload,刻意不建类型层级

`tinycore/events.py` 全部家当:一个 `Event` 类 + 一组类型常量。

```python
@dataclass
class Event:
    type: str                       # 见下表
    data: Dict[str, Any]            # payload,内容由 type 决定
    ts: float                       # 发生时刻
```

| type | payload | 谁在乎 |
|---|---|---|
| `run_start` | agent 名、输入 | UI 状态栏、日志 |
| `user_message` | 完整 HumanMessage | 会话日志(重放靠它) |
| `text_delta` | 一段文本增量 | 打字机 |
| `assistant_message` | 完整 AIMessage | 会话日志、工具面板(看 tool_calls) |
| `tool_start` | ToolCall | UI 状态行("正在 grep…") |
| `tool_result` | 完整 ToolMessage | 会话日志、UI |
| `turn_end` | 轮次、本轮 usage | 观测、预算 |
| `compaction` | 压缩前后 token 数 | UI 提示(第 3 章:压缩要可见) |
| `run_end` | stop_reason、总 usage、最终文本 | 所有人 |
| `error` | 错误描述 | 所有人 |

为什么用"字符串类型 + dict payload",而不是每种事件一个类、搞一棵继承树?因为**事件是协议,不是对象模型**。这两个词的区别:对象模型是"我自己程序里怎么组织代码"(类、继承、方法),协议是"跨程序、跨语言之间怎么传数据"(纯数据 + 约定格式)。事件要被序列化成 JSONL(第 5 章)、推过网络给前端、被别的语言消费——它站在边界上,是协议。协议的天然形态是"带 type 标签的数据",类型层级只会让序列化和跨端消费变复杂。同一个理由,`data` 里的消息对象在落盘时走第 1 章的 `to_jsonable`(带 `__type__` 标记),读回来 `from_jsonable` 还原。

另一个纪律:**事件类型一旦发布就是承诺**。L2/L3 全靠它们工作,改名、改 payload 结构都是 breaking change。内核内部随便重构,事件协议保持稳定——"对外协议稳定,对内实现可演进"。

## 4.3 run():生成器形态的主循环

第 1 章末尾见过 `Agent.invoke()`(吞掉事件只要结果),它其实只是对 `run()` 的包装。`run()` 才是本体——一个**边执行边 yield 事件的生成器**:

给没写过生成器的读者先补三十秒课:函数体里出现 `yield`,它就不再是普通函数,而是**生成器函数**——调用它不执行任何代码,只返回一个生成器对象;消费者每 `next()` 一次(`for` 循环帮你做),函数体才推进到下一个 `yield` 处暂停,把 yield 的值交出去。**"执行到一半、停在某处、随时继续"是语言级能力**——这正是我们要的:循环每干一件事就 yield 一个事件、原地暂停,等消费者处理完再继续。`return x` 在生成器里是"结束并附带返回值"(挂在 StopIteration 上,`invoke()` 里我们用属性 `last_messages` 绕开了这个不常用的取法)。

有了这个铺垫,先看 `run()` 的骨架地图——它做的事拿掉细节后只有这么多:

```
run(user_input, prior_messages):
    yield 开工事件;新输入进历史
    每轮循环:
        ① 先看外面有没有话(插话进历史 / 被打断就收工)
        ② 上下文快满了先压缩;把本轮要发的消息装配好
        ③ 请模型决策(流式:边收增量边 yield)
        ④ 模型没要工具 → 得到最终回答,收工
        ⑤ 模型要了工具 → 执行、结果进历史,回到下一轮
    yield 收工事件(带停止原因和总账单)
```

心里有了这张图,完整实现(不是骨架,可直接抄)就好读了——①-⑤ 的注释与上图一一对应:

```python
# tinycore/loop.py —— 完整的 run(),①-⑤ 对应五个关键位置
def __post_init__(self) -> None:            # dataclass 的构造后钩子
    self._inbox: "queue.Queue[str]" = queue.Queue()   # 中途插话队列(线程安全)
    self._interrupted = False
    self.last_messages: Messages = []

def run(self, user_input, prior_messages=None):
    """执行一次 run,yield 事件流;结束后完整历史在 self.last_messages。"""
    self._interrupted = False
    messages: Messages = list(prior_messages or [])            # 恢复会话从这里进
    new_inputs = ([HumanMessage(content=user_input)]
                  if isinstance(user_input, str) else list(user_input))
    yield Event(ev.RUN_START, {"agent": self.name,
                               "input": new_inputs[0].content if new_inputs else ""})
    for m in new_inputs:
        messages.append(m)
        yield Event(ev.USER_MESSAGE, {"message": m})           # 日志靠这类事件重放

    model = self.model.bind_tools(list(self.tools))
    total = Usage()
    stop_reason = "max_turns"          # 若 for 耗尽都没 break,就是这个原因

    for turn in range(1, self.max_turns + 1):
        # ① 消息边界:先处理外部控制(插话 / 打断),再干活
        while not self._inbox.empty():
            m = HumanMessage(content=self._inbox.get())
            messages.append(m)
            yield Event(ev.USER_MESSAGE, {"message": m})
        if self._interrupted:
            stop_reason = "interrupted"
            break

        # ② 上下文预算:超了先压缩;然后装配本轮真正发给模型的列表
        if self.context and self.context.should_compact(messages):
            before = estimate_tokens(messages)
            messages = self.context.compact(messages, self.model)
            yield Event(ev.COMPACTION, {"before_tokens": before,
                                        "after_tokens": estimate_tokens(messages)})
        if self.context:
            working = self.context.assemble(self.system_prompt, messages)
        elif self.system_prompt:
            working = [SystemMessage(content=self.system_prompt)] + messages
        else:
            working = list(messages)

        # ③ 模型决策(流式:先增量后全量;出错先发事件再抛,消费者不至于蒙在鼓里)
        try:
            if self.stream_text:
                ai: Optional[AIMessage] = None
                for item in model.stream(working):
                    if isinstance(item, AIMessage):
                        ai = item
                    elif item:
                        yield Event(ev.TEXT_DELTA, {"text": item})
                assert ai is not None, "stream() 必须以完整 AIMessage 收尾"
            else:
                ai = model.invoke(working)
        except Exception as e:
            yield Event(ev.ERROR, {"error": f"{type(e).__name__}: {e}"})
            raise

        messages.append(ai)
        total += ai.usage
        yield Event(ev.ASSISTANT_MESSAGE, {"message": ai})

        # ④ 终止判据:没有工具调用 = 模型给出最终回答(第 1 章那一个判据)
        if not ai.tool_calls:
            stop_reason = ai.stop_reason or "end_turn"
            break

        # ⑤ 执行工具(gate 把关;并行但结果保序),结果喂回历史
        for call in ai.tool_calls:
            yield Event(ev.TOOL_START, {"call": call})
        results = run_tool_calls(ai.tool_calls,
                                 {t.name: t for t in self.tools},
                                 gate=self.gate, parallel=self.parallel_tools)
        for r in results:
            messages.append(r)
            yield Event(ev.TOOL_RESULT, {"message": r})

        yield Event(ev.TURN_END, {"turn": turn, "usage": asdict(ai.usage)})

    self.last_messages = messages
    yield Event(ev.RUN_END, {"stop_reason": stop_reason,
                             "usage": asdict(total),
                             "final_text": final_text(messages)})
    return messages


def final_text(messages: Messages) -> str:
    """取最后一条 AI 消息的文本(一次 run 的"最终回答")。"""
    for m in reversed(messages):
        if isinstance(m, AIMessage):
            return m.content
    return ""
```

对照第 1 章的教学版逐块看,会发现**结构一模一样**(决策→判据→工具→再决策),多出来的每一块都有名有姓:①是第 4.5 节的控制窗口;②是第 3 章挂进来的;③把 `invoke` 换成了 `stream` 并多了错误事件;⑤把裸 for 换成了第 2 章的执行器。还有三个容易漏看的细节:

- **`stop_reason = "max_turns"` 先写后改**——Python 的 `for...else` 也能表达"没 break",但显式默认值更直白,还统一了三个出口(打断/回答/耗尽)的处理路径:都落到同一个 `RUN_END`。
- **`total += ai.usage` 逐轮累计**,最后随 `RUN_END` 外报——第 6 章的预算控制、第 11 章的成本评测,数据源都是它。
- **出错"先事件后异常"**:消费者(UI/日志)先收到 ERROR 事件,然后异常照常向上抛。吞异常是框架大忌——谁该处理错误是调用方的决策,内核只保证"出事时留下了现场"。

选**生成器**而不是"起线程 + 队列",有两个此处才显形的好处:

- **天然背压。** 背压(backpressure)指"下游处理不过来时,能反向让上游慢下来"。生成器天生自带:它是拉模型——消费者不 `next()`,循环就停在上一个 `yield` 原地等着。渲染卡了、用户在审批框前想了十秒,内核不会闷头跑远。
- **yield 即插入点。** 每个 yield 都是一道"执行的缝隙"——外部在缝隙里可以落盘、可以打断、可以注入。深入篇会看到,图运行时把同样的思想做成了更重的形式("超步之间的空隙是一切能力的插入点",R1 章);生成器是这个思想在循环路线上的轻量形态。

## 4.4 逐 token 流式:把增量从 provider 一路送到屏幕

打字机效果需要 L0 配合。第 1 章 `BaseChatModel.stream` 的契约现在兑现:**先逐段 yield `str` 增量,最后一项 yield 完整 `AIMessage`**。

```python
# 消费端写法永远统一:
for item in model.stream(messages):
    if isinstance(item, AIMessage):
        ai = item                    # 收尾:完整消息(含 tool_calls/usage)
    else:
        print(item, end="")          # 文本增量
```

三个实现,全量代码 + 各自值得记的点:

**Anthropic:最省心。** SDK 的 `messages.stream()` 给现成的 `text_stream` 增量迭代器,结束后 `get_final_message()` 拿全量。第 1 章拆出的 `_params`/`_from_response` 两个小方法在这里回收利用——流式版一行翻译逻辑都不用重写:

```python
# tinycore/models.py —— AnthropicChatModel 补上这个方法即可
def stream(self, messages) -> Iterator[StreamItem]:
    with self.client.messages.stream(**self._params(messages)) as s:
        for delta in s.text_stream:          # 逐段文本增量
            if delta:
                yield delta
        yield self._from_response(s.get_final_message())   # 收尾:完整消息
```

**OpenAI 兼容:要自己当会计。** 文本增量好办,难在两处。其一,**工具调用的参数是分片送达的 JSON 字符串**——线上的 chunk 长这样:

```
chunk1: delta.tool_calls=[{index:0, id:"call_9x", function:{name:"get_weather", arguments:""}}]
chunk2: delta.tool_calls=[{index:0, function:{arguments:"{\"ci"}}]
chunk3: delta.tool_calls=[{index:0, function:{arguments:"ty\": \"北京\"}"}}]
```

任何一片都不是合法 JSON,必须按 `index` 归位拼接、流结束后再整体 `json.loads`。其二,usage 要显式开 `stream_options={"include_usage": True}` 才随最后一个 chunk 给你。完整实现:

```python
# tinycore/models.py —— OpenAIChatModel 的流式版
def stream(self, messages) -> Iterator[StreamItem]:
    params = self._params(messages)          # 与 invoke 共用拼参逻辑
    params["stream"] = True
    params["stream_options"] = {"include_usage": True}
    text, finish, usage = "", "", Usage()
    calls: Dict[int, Dict[str, Any]] = {}    # index → 累积中的调用
    for chunk in self.client.chat.completions.create(**params):
        if chunk.usage:                       # 最后一个 chunk 才有
            usage = Usage(chunk.usage.prompt_tokens, chunk.usage.completion_tokens)
        if not chunk.choices:
            continue
        choice = chunk.choices[0]
        if choice.finish_reason:
            finish = choice.finish_reason
        delta = choice.delta
        if delta and delta.content:
            text += delta.content
            yield delta.content               # ← 增量即时外送
        for tc in (delta.tool_calls or []) if delta else []:
            slot = calls.setdefault(tc.index, {"id": "", "name": "", "args": ""})
            if tc.id:
                slot["id"] = tc.id
            if tc.function and tc.function.name:
                slot["name"] += tc.function.name
            if tc.function and tc.function.arguments:
                slot["args"] += tc.function.arguments     # ← 分片拼接
    tool_calls = [ToolCall(s["name"], json.loads(s["args"] or "{}"),
                           s["id"] or f"call_{i}")
                  for i, s in sorted(calls.items())]      # 按 index 排序,保序
    yield AIMessage(content=text, tool_calls=tool_calls,
                    stop_reason=finish, usage=usage)
```

(注意 `_params` 需要从 invoke 里抽出来共用——把 1.3 节 OpenAI 类的拼参部分挪进 `_params(self, messages)` 即可,invoke 改为一行 `create(**self._params(messages))`。"invoke 与 stream 共用拼参/解析"这个结构,两家实现是对称的。)

**默认实现**(FakeModel 及一切不支持流式的模型):第 1 章已经写了——invoke 后把全文一次 yield、再 yield 消息。**优雅退化**,消费者代码零分支。

于是 `text_delta` 事件从 provider 的 SSE 一路贯通到你的终端,中间每一层都只是转发。

## 4.5 打断与插话:协作式,在消息边界生效

真实使用里两个高频动作:**打断**(它跑偏了,快停)和**插话**(不打断,补个信息让它调整方向——Claude Code 里你随时敲字进队列就是这个)。内核的实现小得惊人:

```python
def interrupt(self):        # 可从别的线程调
    self._interrupted = True

def inject(self, text):     # 可从别的线程调
    self._inbox.put(text)   # queue.Queue,线程安全
```

真正的设计在**生效时机**:两者都不立即生效,而是在 `run()` 每轮开头的"消息边界"(代码位置 ①)统一处理。这叫**协作式**打断——不是强行掐断(像拔电源),而是举个旗子,循环自己在方便的位置看到旗子再停(像跟司机说"前面路口停")。为什么不"立刻停"?因为立刻停会把历史撕裂在非法状态——工具执行了一半、AI 消息带着 tool_calls 却没有结果。**协作式 + 消息边界**保证无论何时打断,`messages` 都是 provider 眼里合法的序列,第 5 章才有资格说"任何时刻崩溃/打断都能恢复"。这是第 3 章 `_safe_cut` 之后,同一个不变量第二次出场:**历史永远合法**。

插话(steering)的语义也因此很清晰:注入的消息在**下一次调模型前**进入历史——模型自然地在下一轮"听到"你的话,不需要任何特殊机制。

## 4.6 诚实的取舍:同步生成器 vs async

必须坦白:生产级 harness 这一层几乎都是 async 的(Claude Code 是 TS 天生异步,Agents SDK 是 asyncio)。原因是真实负载的形状——模型流式、多个工具并发、多会话服务,全是 IO 等待,async 让一个进程同时伺候成百上千条流。

本教程选同步生成器,理由也摆开:

- 教学上,`yield` 把"执行留有缝隙"这个**概念**表达得最裸露,没有 `await`/事件循环的噪音;
- 工具并行我们用线程池已经拿到(第 2 章),单会话 CLI 场景足够;
- **迁移是机械的**:`def run` → `async def run`、`yield` → 事件放入 `asyncio.Queue` 或改用 async generator、线程池 → `asyncio.gather`、`queue.Queue` → `asyncio.Queue`。结构一处不变。

把"async 化 tinycore"列为全书第一顺位的进阶练习(第 11 章的清单里等你)。

## 4.7 跑起来:UI 只是事件流的一个消费者

`examples/k04_events.py` 做三件事。其一,裸看事件流(FakeModel,离线,实际输出):

```
== 裸事件流 ==
  Event(run_start, {agent, input})
  Event(user_message, {message})
  Event(assistant_message, {message})      ← 带两个 tool_calls
  Event(tool_start, {call})                ← 一轮两个调用,先各报一次开工
  Event(tool_start, {call})
  Event(tool_result, {message})            ← 并行执行,结果保序回来
  Event(tool_result, {message})
  Event(turn_end, {turn, usage})
  Event(text_delta, {text})                ← 最终回答的增量(FakeModel 是一整段)
  Event(assistant_message, {message})
  Event(run_end, {stop_reason, usage, final_text})
```

把这串事件背下来是值得的——**它就是一轮完整 agent 循环的"心电图"**,以后调试任何 harness(包括真实产品的日志),你都在读同一种图形。

其二,40 行渲染器把同一条流画成终端 UI(打字机 + 工具状态行)——这就是 `mini_code.py` 里 `render()` 的雏形。做完你会有个体感:**换 UI 不碰内核,换内核不碰 UI**,中间那条事件流就是全部合同。

其三,插话实验(离线可复现):在收到第一轮 `tool_result` 事件时调 `agent.inject("顺便用华氏度再说一遍")`,下一轮的剧本模型回显它看到的最后一条 user 消息——实际输出:

```
== 中途插话:第一轮工具结果回来前注入一句 ==
● get_weather(北京)
  ⎿ 北京 晴 25°C
(第二轮)我看到的最后一条 user 是:「顺便用华氏度再说一遍」
—— end_turn
```

注入的消息在下一次调模型前进了历史,模型"听到了"——没有任何特殊机制,就是 4.5 节那六行代码。真实模型下再跑一次,体验逐 token 打字机,以及 Ctrl+C 触发 `interrupt()` 后循环在边界优雅收尾。

## 4.9 源码解析与代码逻辑

> 动手是"抄得出来";这一节是"讲得清楚"。
> 正文 4.2–4.5 已贴事件清单与 `run()` 大段实现——这里**不重贴全文**,只把**生成器心脏**收成调用地图、yield 缝隙表、流式契约与协作式控制。
> 打开仓库对照:`tinycore/events.py`、`tinycore/loop.py`、`tinycore/models.py` 的 `stream()`、`examples/k04_events.py`。

### 先用一张生活图把关系钉住

把 `Agent.run` 想成**直播间**:

- 主播(循环)边干边喊进度,不一次剪完整片再寄出。
- 观众(UI / 会话日志 / 观测)各自戴耳机收同一路直播。
- 你按暂停(消费者不 `next`)→ 主播卡在句号处——这就是**背压**。
- 导播塞纸条(`inject`)或喊停(`interrupt`)只在**段落之间**生效,不会把半句话撕烂。

```
agent.run(user_input)
    │  yield RUN_START, USER_MESSAGE…
    ▼
for turn in 1..max_turns:
    ① 消息边界: drain inbox / 若 interrupted → break
    ② 可选 compact → assemble working
    ③ model.stream/invoke → TEXT_DELTA* → ASSISTANT_MESSAGE
    ④ 若无 tool_calls → break (end_turn)
    ⑤ TOOL_START* → run_tool_calls → TOOL_RESULT* → TURN_END
    │
    ▼
 yield RUN_END(stop_reason, usage, final_text)
 return messages
```

| 阅读顺序 | 路径 | 体量 | 你要带走的一件事 |
|---|---|---|---|
| 1 | `tinycore/events.py` | ~40 行 | 十个类型常量 + `Event(type, data, ts)`;协议不是类层级 |
| 2 | `tinycore/loop.py` `Agent` 字段与控制 | ~40 行 | `_inbox` / `_interrupted`;`invoke` = 抽干生成器 |
| 3 | `tinycore/loop.py` `run()` | ~95 行 | ①–⑤ 编号步骤 = 内核心电图 |
| 4 | `tinycore/models.py` `stream` | 基类 + 两家实现 | 增量 str…**最后一项 AIMessage** |
| 5 | `examples/k04_events.py` | ~65 行 | 裸流 / 渲染器 / inject 三幕同一条 API |

### 主路径走读:一轮「调两个天气再回答」

对应 k04 第一幕剧本:先发北京+上海两个 `ToolCall`,再给最终文本。

**① 入口重置与用户消息入史**

```python
# tinycore/loop.py —— run 开头
self._interrupted = False
messages = list(prior_messages or [])
# … 把 user_input 变成 HumanMessage 列表 …
yield Event(ev.RUN_START, {...})
for m in new_inputs:
    messages.append(m)
    yield Event(ev.USER_MESSAGE, {"message": m})
model = self.model.bind_tools(list(self.tools))
```

- 每次 `run` 清打断旗,避免上次 interrupt 污染。
- `prior_messages` 支持续聊(第 5 章会话恢复会喂这里)。
- **先 bind_tools 再进轮询**:本轮工具表固定;中途改 tools 不会半轮生效。

**② 每轮开头的消息边界(协作式控制的全部栖息地)**

```python
# tinycore/loop.py —— ① 插话 / 打断
while not self._inbox.empty():
    m = HumanMessage(content=self._inbox.get())
    messages.append(m)
    yield Event(ev.USER_MESSAGE, {"message": m})
if self._interrupted:
    stop_reason = "interrupted"
    break
```

- `inject` 只是 `_inbox.put`;真正入史在下一轮模型调用前。
- `interrupt` 只是置位;这里看见才 break。
- 因此历史里**不会**出现「有 tool_calls 的 AI,却没有配对 ToolMessage」这种半轮——除非你在工具执行**当中**杀进程(第 5 章用日志修剪补)。

**③ 装配 working(为第 3 章留的插座)**

有 `context` 就 `assemble`;否则有 `system_prompt` 就前置 `SystemMessage`;再否则原样 `messages`。  
system **仍然不写进** `messages` 历史——只出现在当轮 `working`。

**④ 模型决策:流式与非流式**

```python
# tinycore/loop.py —— ③ 流式消费契约
if self.stream_text:
    ai = None
    for item in model.stream(working):
        if isinstance(item, AIMessage):
            ai = item
        elif item:
            yield Event(ev.TEXT_DELTA, {"text": item})
    assert ai is not None, "stream() 必须以完整 AIMessage 收尾"
else:
    ai = model.invoke(working)
messages.append(ai)
yield Event(ev.ASSISTANT_MESSAGE, {"message": ai})
```

契约钉死三件事:

1. 中间项是 `str`(或假值跳过)→ 打字机 UI。
2. **最后**必须能拿到完整 `AIMessage`(含 `tool_calls` / `usage`)。
3. 先入史,再发 `ASSISTANT_MESSAGE`——消费者看见事件时,`messages` 里已经有这条。

基类默认 `stream` 退化:

```python
# tinycore/models.py —— 不会流式的模型
ai = self.invoke(messages)
if ai.content:
    yield ai.content
yield ai
```

所以 FakeModel、老接口模型,消费端代码一行不用改。

Anthropic 真流式:文本走 `text_stream`,结束 `get_final_message()` 再译成 `AIMessage`。  
OpenAI 兼容流式:文本 delta 直接 yield;工具参数 JSON **按 index 拼接**,结束再 `json.loads`(正文 4.4 已讲,这里只强调:循环层完全不关心拼接,它只认最终 AIMessage)。

**⑤ 判停 vs 跑工具**

```python
# tinycore/loop.py —— ④⑤
if not ai.tool_calls:
    stop_reason = ai.stop_reason or "end_turn"
    break
for call in ai.tool_calls:
    yield Event(ev.TOOL_START, {"call": call})
results = run_tool_calls(..., gate=self.gate, parallel=self.parallel_tools)
for r in results:
    messages.append(r)
    yield Event(ev.TOOL_RESULT, {"message": r})
yield Event(ev.TURN_END, {"turn": turn, "usage": asdict(ai.usage)})
```

- 判停与第 1 章教学循环相同:`not ai.tool_calls`。
- 工具执行**复用第 2 章** `run_tool_calls`(gate + 并行保序 + 错误即消息)。
- 先批量 `TOOL_START`,再执行,再按保序结果 `TOOL_RESULT`——UI 可以先画「将要跑谁」。
- 只有「模型+工具」都结束后才 `TURN_END`;纯文本收尾的那轮**没有** TURN_END(直接破循环去 RUN_END)。这是读事件序列时的常见坑。

**⑥ 收尾**

```python
self.last_messages = messages
yield Event(ev.RUN_END, {"stop_reason": ..., "usage": asdict(total), "final_text": final_text(messages)})
return messages
```

- `invoke()` 的实现就是 `for _ in self.run(...): pass`,然后读 `last_messages`。
- `final_text` 从后往前找最后一条 `AIMessage.content`。

### yield 缝隙表(背压与副作用该钉在哪)

| 事件 | 何时 yield | 此时 messages 合法性 | 典型消费者动作 |
|---|---|---|---|
| `RUN_START` | 入史前 | 尚可只有 prior | 开文件/画标题 |
| `USER_MESSAGE` | 每条 user 入史后 | 合法 | 落盘、显示气泡 |
| `TEXT_DELTA` | 流式中 | AI 尚未入史 | 打字机;勿当最终答案 |
| `ASSISTANT_MESSAGE` | AI 已 append | 若将调工具,下一拍必须补 Tool | 冻结助手气泡、写日志 |
| `TOOL_START` | 执行前 | AI 已在、结果未到 | 转圈、审批 UI(可与 gate 配合) |
| `TOOL_RESULT` | 每条结果 append 后 | 工具对完整 | 落盘、展示 |
| `TURN_END` | 本轮工具批完成 | 合法完整轮 | 计 turn、刷 usage |
| `COMPACTION` | 压缩后 | 仍合法(第 3 章保证切点) | 提示「已摘要」 |
| `RUN_END` | 一切结束 | 最终历史 | 关会话、亮 stop_reason |
| `ERROR` | 模型调用异常 | 可能停在上一合法点 | 告警;随后 raise |

**背压**:消费者卡在 `for e in agent.run()` 的一次迭代里 → 生成器停在对应 `yield` → 模型/工具都不会往前跑。  
这就是「层间只隔一条事件流」能同时伺候 UI 与第 5 章 `session.record` 的原因。

### 分支与失败态

| 若出现… | 落点 | 变成什么 | 体感 |
|---|---|---|---|
| `stream()` 没给出最终 AIMessage | `assert ai is not None` | AssertionError | 实现方违约;开发期尽早炸 |
| 模型 `invoke/stream` 抛错 | `except` → `yield ERROR` → `raise` | 事件里有错,生成器仍失败 | 日志能看见;调用方需处理 |
| `tool_calls` 为空 | ④ break | `stop_reason=end_turn`(或 provider 原值) | 正常结束 |
| 跑满 `max_turns` | for 自然结束 | `stop_reason` 保持初始 `"max_turns"` | 安全阀 |
| `interrupt()` 于工具执行中 | 旗已立,等下一轮 ① | 当前工具批仍跑完 | 协作式,略延迟 |
| `inject` 于 TOOL_RESULT 时 | 进 inbox,下轮 ① 入史 | 模型下一眼能看见新 user | k04 第三幕 |
| `stream_text=False` | 走 `invoke` | 无 TEXT_DELTA | 省事件、整段返回 |
| `parallel_tools=False` | 传入 `run_tool_calls` | 工具串行 | 调试更简单 |
| 空 `user_input` 列表 | RUN_START input 为 `""` | 仍可跑 | 少见 |
| 只有 prior、无 new_inputs | 不 yield USER_MESSAGE | 续跑场景 | 会话恢复 |

### `interrupt` / `inject` 实现有多「薄」

```python
def interrupt(self) -> None:
    self._interrupted = True

def inject(self, text: str) -> None:
    self._inbox.put(text)
```

薄是优点:可从**另一线程**调用(UI 按钮、超时狗)。  
厚逻辑全在 `run` 的消息边界——保证「历史永远是完整合法前缀」,第 5 章才能放心 append-only 记日志。

### 与前后章的接缝

- **上游 · 第 1 章判停与整卷重发**——原样保留在 ④ 与 `working` 装配;本章只把过程变成事件。
- **上游 · 第 2 章执行器**——⑤ 整段委托 `run_tool_calls`;循环不重新发明并行/gate。
- **上游 · 第 3 章上下文**——② 的 `should_compact` / `assemble`;压缩成功额外 `COMPACTION` 事件。
- **下游 · 第 5 章会话**——`Session.record` 是事件流消费者;只持久化需要的类型;恢复时 `messages()` 重放推导状态。
- **下游 · 第 6–7 章**——`gate` 仍在 `run_tool_calls` 入口;观察型钩子挂在同一条事件流上。
- **下游 · 第 9 章 Harness 门面**——`Harness.run` 基本是「建 Agent + 迭代事件 + 记 session」。

### 只要记住的 5 行逻辑

1. **内核对外的主 API 是事件生成器 `run()`,不是一次性返回值;`invoke` 只是抽干它的糖。**
2. **每个 `yield` 都是缝隙:背压、落盘、UI、插话处理都发生在缝隙,而不是函数返回之后。**
3. **`stream` 契约 = 若干 str + 最后一项完整 AIMessage;循环用 isinstance 分流。**
4. **打断与插话只在轮首消息边界生效,用历史合法性换即时性。**
5. **工具段不新造机制:事件包一层,执行仍走第 2 章 `run_tool_calls`。**

### 对照验收

1. 跑 `python examples/k04_events.py` 第一幕:事件类型序列应含 `run_start → user_message → assistant_message → tool_start×2 → tool_result×2 → turn_end → assistant_message → run_end`(具体以 smoke 为准)。  
2. 渲染器幕:同一 `run()`,只是消费者换了——内核零改动。  
3. 插话幕:在 `TOOL_RESULT` 时 `inject`,下一轮 FakeModel 的 lambda 应读到新 user 文本。  
4. 消费循环里加 `input()`,确认每次回车才进下一事件(背压体感)。

## 4.10 自测

**Q1. 为什么事件流优于回调集合?**

<details><summary>想清楚再展开</summary>

消费者是开放集合(UI/日志/观测/审批/转发…),回调要求内核为每类消费者留接口,耦合且不可序列化;事件流把"发生了什么"统一成一条带类型的数据流,消费者自取所需,可以序列化、跨进程、随意增删,内核零改动。
</details>

**Q2. interrupt() 为什么不立刻生效?"消息边界"保证了什么?**

<details><summary>想清楚再展开</summary>

立刻停可能把历史撕裂在非法状态(tool_calls 没有配对结果、工具执行一半)。协作式打断在每轮开头的边界统一处理,保证任何时刻的 `messages` 都是合法序列——这是会话持久化与恢复(第 5 章)的前提。代价是打断有轻微延迟(最多等当前这一步做完),生产系统同样如此。
</details>

**Q3. OpenAI 流式里工具调用参数为什么不能来一片解析一片?**

<details><summary>想清楚再展开</summary>

参数以 JSON 字符串分片送达,任何一片都不是合法 JSON(`{"ci` 解析必炸)。必须按 `index` 把分片归位拼接,等流结束拿到完整字符串再 `json.loads`。这也是"流式文本好做、流式工具调用难做"的根源。
</details>

## 4.11 本章小结

- **事件流是内核唯一的公共 API**:UI、日志、观测、审批、宿主全是消费者;窄接口让层与层独立演进。
- **事件是协议不是对象模型**:type + payload dict,可序列化、可跨端;类型一旦发布就是承诺。
- **run() 是生成器**:天然背压;每个 yield 都是执行的缝隙——落盘、打断、注入都发生在缝隙里。
- **流式契约**:str 增量……最后一项完整 AIMessage;不支持流式的模型优雅退化;OpenAI 工具参数分片要按 index 累积。
- **打断与插话是协作式的,在消息边界生效**——"历史永远合法"这一不变量,是下一章持久化的入场券。
- 生产用 async,教学用生成器,迁移机械;async 化是第一顺位练习。
- **源码阅读顺序**:`events` 协议 → `run()` ①–⑤ → `models.stream` 契约 → `k04` 三个消费者。

内核篇(L0+L1)到此完工:循环、工具、上下文、事件。下一章开始造壳——第一块砖:让这一切在进程死掉之后还活着。
