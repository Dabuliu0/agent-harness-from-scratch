# 第 7 章 · 钩子与技能

> 到上一章为止,壳里的策略都是**开发者**写死的。但 harness 是要交付给使用者的产品:他们会要求"每次改完 .py 自动跑 ruff"、"提交前必须过测试"、"公司发版流程要按我们的手册来"。本章造两个开放机制:**钩子(hooks)**——把执行时机开放出去,挂用户自己的逻辑;**技能(skills)**——把领域知识打包成可按需加载的手册。两者都是 2026 年 harness 的标配件(Claude Code 的 hooks 与 Agent Skills)。代码:`tinyharness/hooks.py`、`tinyharness/skills.py`。

## 7.1 钩子:确定性的自动化,而不是"让模型记得"

先看清钩子解决的需求形状。用户说:"**每次** Agent 改完 Python 文件,都要跑一遍 lint。"两种实现:

- 写进 system prompt:"改完 .py 请记得跑 ruff"。——这是**许愿**(第 6 章的老话):长上下文里模型会忘,忙起来会跳过,你无法保证"每次"。
- 挂一个钩子:`post_tool_use` 时机、匹配 `edit_file`/`write_file`、执行 `ruff` 并把结果喂回。——这是**保证**:代码路径,次次执行,与模型情绪无关。

一句话立住定位:**凡是"每次 X 就 Y"的需求,都该是钩子,不该是提示词。** 这和第 6 章"硬约束不是提示词"是同一条原则的自动化版本。钩子的气质很像手机里的"自动化"功能(到家自动开灯、插电自动开勿扰):你配置一次,系统在那个时机**必然**执行——而不是靠一个健忘的助理"记得去做"。

钩子与深入篇 R6 的中间件长得像,身份完全不同,对照着记:

| | 中间件(R6,LangChain 式) | 钩子(本章,Claude Code 式) |
|---|---|---|
| 谁在用 | **框架开发者**:写代码扩展 Agent 内核行为 | **产品使用者**:不改框架,配置化挂逻辑 |
| 形态 | 类 + 六个方法,洋葱式包裹 | 时机点 + 回调(真实系统里甚至是 shell 命令) |
| 生效层 | L1(构建 Agent 时编译进去) | L2(harness 在时机点触发) |
| 典型用途 | 压缩、脱敏、换模型 | 自动 lint、提交门禁、通知、审计 |

两者不互斥——真实产品常常两层都有。我们主线选钩子,因为它是"harness 作为产品"的必然形态:用户没有你的源码,只有你的接缝。

## 7.2 五个时机与裁决合并

```python
# tinyharness/hooks.py
SESSION_START      # 会话开始:注入环境说明
USER_PROMPT_SUBMIT # 用户消息提交前:校验/改写/拒绝
PRE_TOOL_USE       # 工具执行前:可拦截、可改参 ★ 控制型
POST_TOOL_USE      # 工具执行后:审计、通知、追加反馈
STOP               # run 结束:收尾、断言"活干完没有"

@dataclass
class HookResult:
    block: bool = False              # 拦截(理由喂回模型)
    reason: str = ""
    replace_args: Optional[dict] = None   # 改写参数(仅 pre_tool_use)
    add_context: str = ""            # 追加给模型的上下文
```

注册带 matcher(对工具名 fnmatch),避免每个钩子自己写一遍 if:

```python
hooks = HookManager()
hooks.register(PRE_TOOL_USE, block_curl, matcher="bash")
hooks.register(POST_TOOL_USE, run_lint, matcher="*_file")   # write_file/edit_file
```

多个钩子命中同一时机时,裁决怎么**合并**?这必须白纸黑字定义清楚——模糊的合并语义是插件系统的万病之源(两个插件都想改同一个参数,听谁的?)。与其写五行注释,不如直接读实现。`fire()` 全文如下,读它只需要盯住两个 ★ 注释:

```python
class HookManager:
    def __init__(self) -> None:
        self._hooks: Dict[str, List[Tuple[str, HookFn]]] = {e: [] for e in HOOK_EVENTS}

    def register(self, event: str, fn: HookFn, matcher: str = "*") -> None:
        if event not in self._hooks:
            raise ValueError(f"未知钩子时机: {event}(可用: {HOOK_EVENTS})")
        self._hooks[event].append((matcher, fn))

    def fire(self, event: str, payload: Dict[str, Any]) -> HookResult:
        """触发一个时机的所有钩子,合并裁决:
        任何一个 block 即 block;replace_args 后写覆盖先写;add_context 累积。"""
        merged = HookResult()
        tool_name = (payload.get("call").name
                     if isinstance(payload.get("call"), ToolCall) else None)
        for matcher, fn in self._hooks.get(event, ()):
            if tool_name is not None and not fnmatch.fnmatch(tool_name, matcher):
                continue                       # matcher 只对工具类事件生效
            r = fn(payload)
            if r is None:
                continue                       # "我没意见"
            if r.block:
                return HookResult(block=True, reason=r.reason or "被钩子拦截")  # ★短路
            if r.replace_args is not None:
                merged.replace_args = r.replace_args
                payload = {**payload, "call": ToolCall(                        # ★接力
                    name=payload["call"].name, args=r.replace_args,
                    id=payload["call"].id)}
            if r.add_context:
                merged.add_context += ("\n" if merged.add_context else "") + r.add_context
        return merged
```

两个 ★ 是语义的关键:**短路**——block 直接 return,后面的钩子连跑都不跑(拦截是终局裁决,不参与合并);**接力**——一旦有钩子改写参数,`payload` 立刻更新,后面的钩子看到的是**改写后的调用**(两个改写钩子串行时,后者在前者的结果上继续改,而不是各改各的原始版)。把这两条写进测试,插件系统的语义就钉死了。

真实系统的规模感:Claude Code 的钩子管线有二十多种事件、支持挂任意 shell 命令、用 JSON 与 harness 对话(exit code 2 即拦截)。我们的五时机版是它的最小同构体。

## 7.3 控制型钩子:pre_tool_use 编译进 gate

`pre_tool_use` 是唯一的"控制型"时机——它能改变将要发生的事。实现上它和第 6 章的权限走同一个接缝:编译成 gate,并与权限 gate **串联**:

```python
# tinyharness/hooks.py
def as_gate(self, inner=None) -> Gate:
    def gate(call):
        r = self.fire(PRE_TOOL_USE, {"call": call})
        if r.block:
            return r.reason                      # 钩子拦截
        if r.replace_args is not None:
            call = ToolCall(call.name, r.replace_args, call.id)
        if inner is not None:                    # 交给下一层(权限)
            verdict = inner(call)
            if verdict is not None:
                return verdict
        return call if r.replace_args is not None else None
    return gate

# harness.py 里的组装:
gate = hooks.as_gate(policy.as_gate())           # 钩子在外,权限在内
```

最后一行 `return call ...` 用的是第 2 章 gate 契约的**第三态**:`None` 放行、`str` 拒绝、`ToolCall` 放行但换成改写后的调用(执行器里 `isinstance(verdict, ToolCall)` 那个分支,当时埋的伏笔在此兑现)。留意一个层次感:改写发生在**gate 里**而不是执行器里——执行器只认裁决结果,永远不知道"曾经有过另一个版本的参数"。

**串联顺序是安全命题,不是实现细节。** 钩子在外、权限在内,意味着权限裁决的是**钩子改写之后**的调用。反过来接会出一个真实漏洞:审批框里用户看到并批准了 `deploy staging`,钩子随后把参数改成 `deploy prod`——"审的是 A,执行的是 B"。规则:**一切会改写调用的逻辑,必须发生在裁决之前;裁决之后的调用不可再变。**(深入篇 R6 的中间件同样有这个顺序命题——洋葱层的排列会改变"人审批的是改写前还是改写后",两条家族线在这里撞见同一堵墙。)

## 7.4 观察型钩子:在事件流上触发

其余四个时机不改变执行,只观察和补充。它们不进内核——**harness 驱动层消费事件流时触发**。又是第 4 章那招:想加能力,不改内核,只在事件流上多站一个消费者:

```python
# tinyharness/harness.py(节选)
r = self.hooks.fire(USER_PROMPT_SUBMIT, {"prompt": prompt})
if r.block:
    yield Event(ev.ERROR, {"error": f"输入被钩子拒绝: {r.reason}"})
    return
if r.add_context:
    prompt += "\n\n[hook 注入]\n" + r.add_context
...
for e in session.record(self.agent.run(prompt, prior)):
    yield e
    if e.type == ev.RUN_END:
        self.hooks.fire(STOP, {"result": e.data})
```

`add_context` 是观察型钩子影响模型的正道:**不篡改历史,只追加信息**。post_tool_use 的 lint 结果、stop 时机的"测试还没跑"提醒,都以附加上下文/注入消息的形式让模型看到,由模型决定怎么办。真实系统同款语义(Claude Code 的 hook 输出会作为 context 提供给模型;Stop 钩子甚至能"不许停,继续干"——把 stop 变成控制型,这是个漂亮的练习:消费 RUN_END 后带理由重新调 `run()`)。

## 7.5 技能:知识的渐进披露

钩子解决"行为"的开放,还剩"知识":公司的发版手册、周报格式、数据库迁移规范——这些**领域知识**放哪?三个坏答案先排除:

- **硬塞 system prompt**:token 全预付(每轮都花),改一次手册要动配置发版,而且 99% 的对话根本用不上发版知识。
- **做成工具**:知识不是能力,`get_release_process()` 这种"返回一段文档的工具"是行为艺术。
- **上 RAG**:检索黑盒,命中不可控、不可 review;对"公司只有几十份手册"的场景是大炮打蚊子。

2026 年的标准答案是**技能(Agent Skills)**:一个目录、一份带元数据的 `SKILL.md`、按需加载。核心机制叫**渐进披露(progressive disclosure)**——白话就是"需要多少给多少,不需要就只给个目录"。想象公司的手册柜:墙上贴一张目录("发版手册在 3 号柜"),手册本体在柜子里,谁需要谁去取;手册里还会写"附件模板见同柜文件夹"。对应到实现就是三级火箭:

```
第一级(常驻,~几十 token/技能)   system prompt 里只有清单:
                                 "- release: 发版流程手册"
第二级(按需,一次性)             模型判断相关 → read_skill("release")
                                 → SKILL.md 全文进上下文
第三级(更按需)                  SKILL.md 里引用同目录脚本/模板
                                 → 模型用文件工具去读去跑
```

代价结构是它赢的原因:**不用时几乎免费,用时全量到位,永远可 review 可版本控制**(技能目录就在 git 里,改手册 = 发 PR)。接入只要三行:

```python
skills = load_skills("./skills")            # 扫 */SKILL.md,解析 frontmatter
context.extra_context = skills_section(skills)   # 第一级:清单进 system(第 3 章的接缝!)
tools.append(make_skill_tool(skills))       # 第二级:read_skill 工具
```

实现也小得可爱,三级火箭各对应一个函数(`tinyharness/skills.py`):

```python
@dataclass
class Skill:
    name: str
    description: str
    path: str                   # SKILL.md 的路径

    def body(self) -> str:      # 正文不驻留内存:每次现读文件
        with open(self.path, "r", encoding="utf-8") as f:
            return f.read()


def load_skills(skills_dir: str) -> List[Skill]:
    """扫描 skills_dir/*/SKILL.md,返回技能清单。目录不存在返回空。"""
    out: List[Skill] = []
    if not os.path.isdir(skills_dir):
        return out
    for entry in sorted(os.listdir(skills_dir)):
        p = os.path.join(skills_dir, entry, "SKILL.md")
        if os.path.isfile(p):
            out.append(_parse_skill(p))     # 解析 frontmatter 的 name/description
    return out
```

以上是"进货":扫目录、建清单。下面两个函数分别是第一级和第二级披露的出口——一个生成贴在墙上的目录,一个造出"去柜子里取手册"的工具:

```python
def skills_section(skills: List[Skill]) -> str:
    """第一级披露:注入 system prompt 的清单,只有名字和一句话描述。"""
    if not skills:
        return ""
    lines = "\n".join(f"- {s.name}: {s.description}" for s in skills)
    return ("# 可用技能\n"
            "以下技能是可按需加载的操作手册。当任务与某技能的描述匹配时,"
            "先调用 read_skill 读取其全文,再按其中的指引行事:\n" + lines)


def make_skill_tool(skills: List[Skill]) -> Tool:
    """第二级披露的入口:read_skill(name) 把技能正文拉进上下文。"""
    by_name = {s.name: s for s in skills}

    def read_skill(name: str) -> str:
        s = by_name.get(name)
        if s is None:
            return f"[错误] 没有名为 {name!r} 的技能,可用: {', '.join(by_name) or '(无)'}"
        return f"<skill name={s.name!r} dir={os.path.dirname(s.path)!r}>\n{s.body()}\n</skill>"

    return Tool(name="read_skill",
                description="加载一个技能的完整操作手册。技能清单见 system prompt 的\"可用技能\"一节。",
                parameters={"type": "object",
                            "properties": {"name": {"type": "string"}},
                            "required": ["name"]},
                func=read_skill)
```

(`_parse_skill` 是十几行 frontmatter 解析——frontmatter 指 markdown 文件开头两条 `---` 之间的元数据块。正则取出这个块,逐行拆 `name:`/`description:`;没写 frontmatter 就拿目录名和正文首行凑合——健壮性优先于格式洁癖。)三个细节各有用意:查无此技能时**报错顺带列出可用项**——第 2 章立过的习惯,报错不只说"不行",还要引导模型自救;返回值包上 `<skill name=… dir=…>` 标签——模型能看出"这是手册",还能从 dir 知道**同目录有配套资源**,第三级披露就靠这个提示接力;`body()` 每次现读文件——手册改了,下一次加载即生效,不用重启会话。

`SKILL.md` 的格式(与真实惯例一致):

```markdown
---
name: release
description: 发版流程手册。当用户要求发版/打 tag/出 release notes 时使用。
---

# 发版流程
1. 完成主线示例的手工检查,确认关键行为没有回退
2. 更新 CHANGELOG.md(格式见同目录 changelog-template.md)
3. ...
```

注意 `description` 的写法——**它是给模型看的触发条件**("当用户要求…时使用"),和第 2 章工具 description 的纪律一模一样:清单级那一行的质量,决定技能会不会在该出场时被想起。

最后把视野扩一格:斜杠命令(`/deploy`)、各家的"插件",剥开看本质都是**受控的上下文注入**——用户或市场提供一段指令/知识,harness 在恰当时机把它放进上下文。技能是其中最有生命力的形态,因为它把"何时注入"也交给了模型判断。

## 7.6 跑起来

`examples/k07_hooks_skills.py`,离线两幕。第一幕挂两个 pre_tool_use 钩子——拦 curl、给 deploy 强制加 `--dry-run`:

```python
hooks = HookManager()
hooks.register(PRE_TOOL_USE,
               lambda p: HookResult(block=True, reason="公司策略禁止 curl 管道执行")
               if "curl" in p["call"].args.get("command", "") else None,
               matcher="bash")
hooks.register(PRE_TOOL_USE,
               lambda p: HookResult(replace_args={"command": p["call"].args["command"] + " --dry-run"})
               if p["call"].args.get("command", "").startswith("deploy") else None,
               matcher="bash")
gate = hooks.as_gate(PermissionPolicy(mode="yolo").as_gate())   # 钩子在外,权限在内
```

第二幕在临时目录造一个 `skills/release/SKILL.md`,把清单接进 `ContextManager(extra_context=...)`,剧本模型先 `read_skill` 再答。实际输出:

```
== 钩子:拦截 curl、给 deploy 强制加 --dry-run ==
  [已拒绝] 公司策略禁止 curl 管道执行
  (exit 0) 已执行: deploy prod --dry-run
  最终: curl 被钩子拦截;deploy 被改写为 dry-run 执行。

== 技能:清单常驻 → read_skill 按需加载 ==
  system prompt 里的第一级披露:
  # 可用技能
  以下技能是可按需加载的操作手册。当任务与某技能的描述匹配时,
  先调用 read_skill 读取其全文,再按其中的指引行事:
  - release: 发版流程手册。当用户要求发版/打 tag 时使用。…
  模型行为: 先 read_skill('release'),再回答 → 按手册:先完成手工检查,再更新
  CHANGELOG,最后打 tag。(我读到的手册共 234 字)
```

第一幕两行输出各踩一个机制:`[已拒绝]` 是钩子 block 的理由走了第 2 章"错误即消息"通道;`deploy prod --dry-run` 证明**执行器拿到的是改写后的调用**——模型请求的明明是 `deploy prod`(翻看 assistant_message 事件可证),落地时多了保险栓。第二幕注意 234 这个数:剧本模型数了数它收到的工具结果长度——手册全文确实只在 `read_skill` 之后才进入上下文,清单级那几十 token 之外,**不用就不付费**。

实验:把 SKILL.md 的 description 改成一句含糊的"一些说明",真实模型下再问"帮我发个版"——大概率它不再想起加载。**description 是触发条件**这句话,靠这个对照组长进记忆。

### 生活类比

钩子像**流水线传感器**:到点响铃,可叫停(block)、可改料单(replace_args)、可贴便签(add_context)。  
技能像**图书馆索书条**:大厅只挂书名+一句话(L1);真要读才借出全书(L2 `read_skill`);附录另架(L3 同目录资源)。

```
控制型: pre_tool_use → HookManager.as_gate(inner=权限gate)
           fire: matcher 过滤 → 合并 HookResult
           block → str 拒绝
           replace_args → 改写后的 ToolCall 再交 inner
观察型: 消费事件流 / Harness 在 USER_PROMPT_SUBMIT、STOP 上 fire
技能:   load_skills → skills_section → ContextManager.extra_context
        make_skill_tool → tools 列表里的 read_skill
```

### 源码地图

| 顺序 | 路径/符号 | 带走一件事 |
|---|---|---|
| 1 | 五时机常量 | 仅 `pre_tool_use` 默认编译进 gate |
| 2 | `HookResult` | block / replace_args / add_context |
| 3 | `fire` | 顺序执行;block 立刻返回;改写后写覆盖并改 payload |
| 4 | `as_gate` | **钩子在外、权限在内**;可返回改写后的 `ToolCall` |
| 5 | `_parse_skill` / `load_skills` | frontmatter 或首行当 description |
| 6 | `skills_section` / `make_skill_tool` | L1 进 system;L2 是普通 Tool |

### `fire` 合并语义(最易写错)

```python
# tinyharness/hooks.py —— 合并规则
if r.block:
    return HookResult(block=True, reason=r.reason or "被钩子拦截")  # 短路
if r.replace_args is not None:
    merged.replace_args = r.replace_args          # 后写覆盖
    payload = {**payload, "call": ToolCall(..., args=r.replace_args, id=...)}
if r.add_context:
    merged.add_context += ...                     # 累积
```

- 工具类事件用 `fnmatch(tool_name, matcher)` 过滤;非工具 payload 则不过滤。  
- 后者改写时,**payload 里的 call 已是前者改过的**,实现「接力」。  
- block 丢弃其后一切(含未合并的 replace)。

### `as_gate` 与权限串联

```python
r = self.fire(PRE_TOOL_USE, {"call": call})
if r.block: return r.reason
if r.replace_args is not None:
    call = ToolCall(name=call.name, args=r.replace_args, id=call.id)
if inner is not None:
    verdict = inner(call)   # 权限看到的是改写后
    if verdict is not None: return verdict
return call if r.replace_args is not None else None
```

这是第 2 章 Gate 三态的完整利用:**改写态返回 `ToolCall`**。  
顺序写死在注释里:审的必须是最终将执行的参数。

### 技能三级

| 级 | 代码 | 何时占 token |
|---|---|---|
| L1 清单 | `skills_section` → `extra_context` | 每轮 system 常驻,极短 |
| L2 正文 | `read_skill` → `s.body()` 整文件 | 模型显式调用后进历史 |
| L3 资源 | SKILL 正文里的相对路径 + 文件工具 | 再按需 read_file |

`_parse_skill`:目录名默认 name;YAML 头可覆盖;无 description 用去 frontmatter 后首行 120 字。  
未知技能返回带可用清单的错误字符串——错误即消息,不抛。

### 教学版实际谁 fire 了?

| 时机 | 内核自动? | 谁触发 |
|---|---|---|
| `pre_tool_use` | 是(经 gate) | 每次工具前 |
| `user_prompt_submit` | 否 | `Harness.run` 开头 |
| `stop` | 否 | `Harness.run` 见 `RUN_END` |
| `session_start` / `post_tool_use` | **未接线** | 留给你/产品在事件流或 run 前后挂 |

读源码时别假设五时机都已在默认路径上——**机制齐了,接线在门面/消费者**。

## 7.9 自测

**Q1. "每次提交前必须跑测试"——钩子还是提示词?为什么?**

<details><summary>想清楚再展开</summary>

钩子(pre_tool_use,matcher 匹配 bash 的 git commit,测试不过就 block)。"每次 X 就 Y"是确定性自动化需求,提示词只能提高概率,钩子给出保证。判据一句话:允许它偶尔不发生吗?不允许,就必须是代码路径。
</details>

**Q2. 为什么钩子 gate 必须串在权限 gate 外面?**

<details><summary>想清楚再展开</summary>

钩子可能改写参数。权限(尤其人工审批)必须裁决"最终会执行的那个调用"。钩子在外,权限看到的是改写后的版本;反过来就会出现"用户批准了 A,实际执行了 B"的安全漏洞。原则:改写在裁决前,裁决后不可变。
</details>

**Q3. 技能相对"塞 system prompt"和"RAG"的核心优势各是什么?**

<details><summary>想清楚再展开</summary>

对比塞 system:token 按需支付(清单常驻仅几十 token,正文用时才加载),更新即生效不动配置。对比 RAG:加载与否由模型显式决策、加载内容是完整手册而非检索碎片,全程可 review、可版本控制、可审计。本质:用文件系统 + 模型判断,替代"预付内存"和"检索黑盒"。
</details>

## 7.10 本章小结

- **钩子 = 把执行时机开放给使用者**:五个时机;"每次 X 就 Y"必须是钩子不是提示词;与中间件的分野在"谁在用、哪一层"。
- **合并语义要白纸黑字**:顺序执行、block 短路、改写后写覆盖、上下文累积。
- **控制型(pre_tool_use)编译进 gate,串在权限外侧**——改写必须发生在裁决前,否则"审 A 执 B"。
- **观察型在事件流上触发**,以 add_context/注入消息影响模型,不篡改历史。
- **技能 = 知识的渐进披露**:清单常驻、正文按需、资源更按需;description 是触发条件;可 review 可版本控制。斜杠命令、插件同为"受控上下文注入"。
- **源码阅读顺序**:`fire` 合并 → `as_gate` 串联 → skills 三级;并核对哪些时机已被 Harness 接线。

行为可挂、知识可载。下一章解决最后一块大拼图:一个 Agent 不够用的时候——子代理与多智能体。
